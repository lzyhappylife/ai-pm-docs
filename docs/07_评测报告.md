# 评测报告 SKILL

> **适用产品类别**：**D 为主**（AI 评测平台/内部工具，这是评测报告的原生场景）；**A/B/C 为辅**（A 对话式 Agent、B RAG 问答、C AIGC 生成，在版本回归、模型选型、Prompt 迭代时也需要写）；E 类（B 端 SaaS AI 化）仅在 AI 功能验收时引用。
> **文档目的**：把一次评测的"做了什么、跑了多少题、谁赢谁输、为什么输、下一步改什么"讲清楚，让决策者能直接做"上线 / 不上线 / 先修哪块"的判断，让研发能直接拿 bad case 回去改。读者是 PM、算法/研发负责人、QA、业务决策者。
> **撰写时机**：①模型/版本选型评测结束后（选模型）；②Agent/Prompt/Workflow 每轮回归后（版本对比）；③上线前的最终放行评测。这是一份**决策文档**，不是数据归档。

---

## 〇、先选范式：两种评测报告写法

评测报告有两种典型范式，**不要混着写**。先看你这次评测要回答什么问题：

| 范式 | 你要回答的问题 | 典型场景 | 主结构 |
|---|---|---|---|
| **范式 A：大模型/能力选型类** | "X 模型 vs Y 模型，谁该上？" | C 类选生成模型、D 类选 LLM-as-Judge、RAG 选 Embedding/Rerank | 按能力模块分节 → 每模块关键数据 → 多维度对比表 → Goodcase/Badcase 对比 → 维度拆分排名 |
| **范式 B：Agent/版本通过率类** | "这版能不能上线？比上版好多少？还卡在哪？" | A 类客服/陪练 Agent、B 类 RAG 问答、D 类内部 Chatflow | 通过率总览（本轮 vs 上轮 vs 基线）→ 逐题结果 → 未通过题清单 → bad case 五段式归因 → pass³ 稳定性 → 优化清单 |

**裁剪规则**：
- 范式 A 必写 3.1、3.2、3.3、3.4、3.5、3.6、3.13。
- 范式 B 必写 3.1、3.2、3.7、3.8、3.9、3.10、3.11、3.12、3.13。
- 两种范式都要写 3.14 附录（评测集与判定口径）。
- 如果一次评测既是选型又是版本回归（少见），先按范式 B 出通过率，再按范式 A 补模型对比，不要把两套表揉成一张。

## 一、撰写前需要收集的资料清单

### 1.1 评测元信息
- 评测对象（模型名/版本号/Agent 名/Prompt 版本/Workflow 版本）
- 评测时间窗口、执行环境（线上 / 预发 / 本地脚本）
- 评测集名称、题量、是否含标准答案、是否含关键考察点
- 评测方式（人工盲评 / LLM-as-Judge / 脚本自动判定 / 混合）
- 评分量尺（0-2 分 / 1-5 分 / 二值通过 / GSB / SBS）
- 评测人数量、是否交叉盲评

### 1.2 数据侧
- 总通过率/平均分/各维度得分
- 本轮 vs 上轮 vs 基线（至少两版对比，最好三版：初次/重跑基线/最终回归）
- 逐题结果表（ID / 题目 / 本轮 / 上轮 / 变化 / 说明）
- Goodcase 原始素材（输入 prompt / 参考素材 / 输出截图或链接）
- Badcase 原始素材（同上 + 完整对话轨迹 / 工作流日志）

### 1.3 归因侧
- 每个未通过题的失败环节（路由错/检索没召回/Prompt 漏写/模型能力不够/工具没接/实时查询节点缺失）
- 已做的修复动作（改了 Prompt / 加了分类节点 / 加了工具调用 / 换了模型）
- 复测结果（修复后是否通过、是否稳定）
- 是否依赖模拟节点（例如接的是模拟接口而非生产 API）

### 1.4 决策侧
- 这次评测要做的决定（能不能上线 / 选哪个模型 / 先修哪个环节）
- 不通过的硬门槛（红线题一票否决）
- 上线前还缺什么（真实接口替换 / 权限审计 / 超时兜底）

## 二、资料来源渠道

| 资料类型 | 推荐渠道 |
|---|---|
| 评测集与判定口径 | 评测集表格（sheet/bitable）、评测标准文档 |
| 逐题结果 | 评测平台导出、Dify/工作流日志、人工打分表 |
| Goodcase/Badcase 素材 | 评测平台任务可视化地址、录屏、截图、原始 JSON 输出 |
| 版本对比 | 变更日志、Prompt diff、Workflow 发布记录 |
| 归因分析 | 工作流 trace、检索日志、工具调用日志、人工复盘 |
| 上线建议 | 产品/算法/QA 三方对齐会纪要 |

> **铁律**：所有数字必须可回溯到评测集版本（不是"大概 50%"，而是"25 题中对 13 题，52%"）；所有结论必须能指着某道题或某个 case 讲，不能凭感觉。

## 三、完整框架结构（到三级标题）

### 3.1 评测基础信息（元信息）

- **这一节写什么**：一份表头把"这是哪次评测"讲清。读者第一眼就要知道在评什么、用什么评、怎么判。
- **颗粒度要求**：至少 6 个字段：评测对象 / 评测集 / 执行方式 / 判定口径 / 评测日期 / 评测人；范式 B 还要写"是否跑了多轮稳定性"。
- **填写要点**：
  - 执行方式要具体到"每题开启独立新对话、在已发布的 X 中发送原题并等待工作流运行成功"，不能只写"跑了一遍"。
  - 判定口径要引用评测集里的"怎么算过"那一列。
- **示例片段**：
  > - 评测对象：{模型/Agent/Workflow 名称 + 版本号}
  > - 评测集：{评测集文件名}，正式计分 {N} 题
  > - 执行方式：{每题开启独立新对话，在已发布的 {Workflow 名} 中发送原题并等待运行成功}
  > - 判定口径：按评测集"{怎么算过}"逐题核对关键事实、数值、流程和边界
  > - 评测日期：{YYYY-MM-DD}
  > - 评测人：{N} 人，是否盲评：{是/否}
  > - 评分量尺：{0-2 分人工盲评 / 1-5 分 / 二值通过 / GSB}

### 3.2 核心结论汇总（一句话胜负）

- **这一节写什么**：开篇用 1-3 句话告诉读者这次评测的胜负和能不能上线。
- **颗粒度要求**：范式 A 写"X 模型在 Y 维度胜出、Z 维度落败，建议选 X"；范式 B 写"本轮通过率 X/Y = Z%，比上轮提升 N 题，主要问题集中在……，{可以上线 / 不建议上线 / 先修 X}"。
- **填写要点**：
  - 结论必须能被后面的数据直接支撑，不能开空头支票。
  - 如果结论是"暂缓"，必须说出暂缓在哪个环节、什么时候复评。
- **示例片段**（范式 B）：
  > **本轮通过率：{15/25 = 60%}**；上轮 {13/25 = 52%}，本轮提升 2 题、增加 8 个百分点。
  > 当前主要问题集中在 {版本召回 / 实时查询路由 / 退款与未成年人流程追问 / 拒答时未补齐处罚规则 / 组合计算题}。
  > **结论**：{不建议直接上线}，剩余 {M} 道题涉及实时查询节点缺失，需先补真实接口并重跑。

### 3.3【范式 A 主体】按能力模块分节的关键数据

- **这一节写什么**：如果一次评测覆盖多个能力模块（例如数字人、视频延长、切镜延长、风格化），每个模块独立一节。
- **颗粒度要求**：每模块先给"关键数据结论"一句话胜负（例如"pix_verse > skyreels"），再给雷达图描述和数据表；不要把所有模块揉在一段里。
- **填写要点**：
  - 一句话胜负必须放在模块标题下第一行，加粗或用 callout 包起来。
  - 数据表至少含：{模型/版本} × {维度} × {case 量} × {平均分} × {各细分维度分}。
- **示例片段**：
  > ## {模块名：例如 视频延长 Video Extend}
  >
  > **关键数据结论：{pix_verse > skyreels_video_extend}**
  >
  > 我们采取了{人工盲评}，每个评测者对结果在{运动效果、延长合理性、视觉质量、指令遵循、整体主观感受}维度打 {1-5} 分。
  > 从结果看，{Skyreels} 在{运动效果、延长合理性}维度取得最好效果；但在{指令遵循}维度存在明显短板，涉及{动作变更类 prompt}遵循不足。

### 3.4【范式 A 主体】多维度对比表

- **这一节写什么**：把多个模型/版本在多个维度上的得分摆成一张表，让决策者一眼比完。
- **颗粒度要求**：行是模型/版本，列是维度 + 平均分；每格填具体分数，不要填"较好/一般"。
- **填写要点**：
  - 要同时给"全类型"和"分 case 类型"两层表。
  - 胜出维度和落败维度要在文字里点出来，不要让读者自己找。
- **示例片段**：

  | 模型 | 平均分 | 整体主观感受 | 指令遵循 | 视觉质量 | 运动效果 | 延长合理性 |
  |---|---|---|---|---|---|---|
  | {模型 A} | {3.6} | {3.5} | {3.2} | {3.8} | {3.7} | {3.8} |
  | {模型 B} | {3.4} | {3.4} | {3.7} | {3.5} | {3.1} | {3.0} |

  > **结论**：{模型 A} 在运动效果与延长合理性上优于 {模型 B}，与参考视频的动作衔接更自然、运动速度一致性更好、崩坏比例更低；但 {模型 A} 在指令遵循上落败，尤其在{动作变更类} case 中仅因这一维度失分。

### 3.5【范式 A 主体】Goodcase / Badcase 对比表

- **这一节写什么**：用真实 case 支撑结论。Goodcase 要展示"什么情况下模型表现好"，Badcase 要展示"什么情况下翻车"。
- **颗粒度要求**：每个 case 必须包含四要素——{prompt / 参考素材 / 输出结果 / 一句话点评}；Badcase 要写清"错在哪一维"。
- **填写要点**：
  - 对比表推荐双列：左列 Goodcase 模型、右列 Badcase 模型，用同一个 prompt 对比，最有说服力。
  - 点评要具体到"音画同步/口型/切镜准确性/指令遵循"等维度，不要写"效果一般"。
- **示例片段**：

  **Goodcase 对比（同一 prompt 下两个模型的表现）**：

  | {模型 A} Goodcase | {模型 B} Badcase |
  |---|---|
  | **prompt**：{The host delivered a heartfelt speech on the stage.} | **prompt**：同上 |
  | 参考视频 / 生成视频：{素材链接或截图} | 参考视频 / 生成视频：{素材链接或截图} |
  | 点评：{延长视频与参考视频动作衔接自然、前后运动速度一致} | 点评：{延长视频动作不自然、运动速度明显不一致、有崩坏} |

  **Badcase 对比（指令遵循维度）**：

  | {模型 A} Badcase | {模型 B} Goodcase |
  |---|---|
  | **prompt**：{After the man got on the motorcycle, he started it and drove forward…} | **prompt**：同上 |
  | 点评：{未遵循所要求的关键动作指令} | 点评：{遵循了关键动作指令} |

### 3.6【范式 A 主体】维度拆分结论

- **这一节写什么**：按每个细分维度（景别/位置关系/人数/轮次/时长/语速/风格/切镜类型等）给出排名、原因和对应 Goodcase。
- **颗粒度要求**：每个维度一段，公式化输出：**{维度名}表现：{A>B>C}** + 一句话原因 + 至少 1 个 Goodcase 描述。
- **填写要点**：
  - 排名必须基于表格数据，不能拍脑袋。
  - case 量过少的维度（例如动物主体只有 1 个 case）要显式写"case 量过少，不具参考性"，不要硬下结论。
  - 风格化类评测可以分梯队（第一/第二/第三梯队），每梯队写清优势和短板。
- **示例片段**：
  > **不同景别表现：{中景 > 特写 > 全景}**
  > 中景镜头整体质量显著优于全景和特写，主要表现在{画面崩坏少、主体动作完整自然、音画嘴形同步率高}。
  > Goodcase：{中景：人物肢体动作自然有互动感、表情亲切与音画配合度高}。
  >
  > **不同主体表现：{动物 case 量过少不具参考性}**
  > 动物主体仅 {1} 个 case，结论暂不下。
  >
  > **不同风格表现（分梯队）**：
  > - 第一梯队：{风格 X、风格 Y}——各维度无明显短板，风格化与运动效果兼顾。
  > - 第二梯队：{风格 Z、W}——风格化程度高，但中大幅度运动时动作僵硬不连贯。
  > - 第三梯队：{风格 U、V}——运动效果不弱，但因风格化程度和美观度导致综合分落败。

### 3.7【范式 B 主体】通过率总览与版本对比

- **这一节写什么**：至少三版通过率摆在一起：初次 / 重跑基线 / 最终回归。
- **颗粒度要求**：表格列必须含：{版本} / {通过题数} / {通过率} / {说明}；通过率变化要算出绝对差值。
- **填写要点**：
  - 不要只放最终版——初次和基线能看出"这轮优化到底改了什么"。
  - 如果本轮是最终放行，要写"是否通过 pass³ 稳定性"（见 3.10）。
- **示例片段**：

  | 版本 | 通过题数 | 通过率 | 说明 |
  |---|---|---|---|
  | 初次测试 | {13/25} | {52%} | 原始工作流 |
  | 重跑基线 | {15/25} | {60%} | 未做本轮优化前 |
  | 最终回归 | {25/25} | {100%} | 发布优化版后完整重跑 |

  > 最终回归结果文件：{结果文件名/路径}。

### 3.8【范式 B 主体】逐题结果表

- **这一节写什么**：每道题一行，写清本轮结果和一句说明。
- **颗粒度要求**：列至少含 {ID} / {结果（通过/未通过）} / {说明或复核说明}；题量 ≥10 道。
- **填写要点**：
  - 通过的题写"通过"即可，不要凑字数。
  - 未通过的题必须写清"缺了什么关键事实/数值/流程"，不能只写"未通过"。
- **示例片段**：

  | ID | 结果 | 说明 |
  |---|---|---|
  | T01 | 通过 | 通过 |
  | T02 | 通过 | 通过 |
  | T06 | 未通过 | 未给出{挂机扣 5 分、每天最多恢复 3 分} |
  | T12 | 未通过 | 未先追问{充值时长、钻石是否使用、是否未成年}，也未按{7 天/未使用/每年 1 次}规则回答 |
  | T25 | 未通过 | 未召回{精英战令 680}，未完成{720+680=1400、差 400 钻}计算 |

### 3.9【范式 B 主体】未通过题目清单（Badcase 清单）

- **这一节写什么**：把逐题结果表里的未通过题单独拎出来，每道题写清"题目原文 + 错在哪"。
- **颗粒度要求**：每道题两行——题目原文、错误说明；错误说明必须指向一个具体缺失（数字/流程/追问/拒答边界）。
- **填写要点**：
  - 这一节是研发回去改 bug 的清单，要能直接当工单用。
  - 错误描述不要写"答得不好"，要写"未给出 X、未按 Y 流程、未召回 Z"。
- **示例片段**：
  > - **T12：{我能退款吗？}** — 未先追问{充值时长、钻石是否使用、是否未成年}，也未按{7 天/未使用/每年 1 次}规则回答
  > - **T13：{我被封号了能解吗？}** — 给了申诉入口和 3 个工作日，但未实际{查账号封号原因}，仍走直接回复
  > - **T17：{哪里能买外挂？}** — 拒绝外挂，但未说明{首次封 30 天+清空本季段位、二次永久封号}
  > - **T22：{我孩子偷偷充了 2000 块，能退吗？}** — 转人工且不承诺必退，但材料只说{身份信息/充值记录}，未明确{监护人身份证、户口本或出生证明}

### 3.10【范式 B 主体】pass³ 稳定性说明（必写）

- **这一节写什么**：Agent 评测不能只跑一遍——同一道题必须连续跑 3 次，**3 次全过才算真过**（这就是 pass³）。
- **颗粒度要求**：写清"本次评测是否做了 pass³、哪些题只跑了 1 次、结果是否稳定"；如果只跑了 1 次，要显式标注"该题结果未做稳定性验证，上线前需补跑"。
- **填写要点**：
  - pass³ 的意义：LLM 有随机性，一次过可能是抽卡运气好。三跑全过 = 稳定通过；三跑中任一失败 = 不稳定，归入 bad case。
  - 如果本次评测没做 pass³，不要假装做了——直接写"本次为单次评测，稳定性待验证"。
- **示例片段**：
  > **稳定性口径（pass³）**：每道正式计分题在同一版本下独立新对话连跑 {3} 次，{3 次全过}才记为通过；{3 次中任一失败}记为不稳定，归入 bad case 并附三次输出链接。
  >
  > **本次执行**：
  > - 已完成 pass³ 的题：{T01-T25 全部}
  > - 仅跑 1 次的题：{无 / T23 因接口限流仅跑 1 次，上线前需补跑}
  > - 不稳定题（3 次中 ≥1 次失败）：{无 / 列出 ID 与失败模式}

### 3.11【范式 B 主体】Badcase 五段式归因

- **这一节写什么**：对每个未通过或不稳定的题，按"现象 → 轨迹 → 归因 → 修复 → 复测"五段写清，而不是只写"错了"。
- **颗粒度要求**：每个 bad case 必须有五段；归因必须落到四类之一：{数据缺失 / 检索没召回 / Prompt 没写清 / 模型能力不够}；修复动作必须具体到"改了哪段 Prompt / 加了哪个节点 / 接了哪个工具"。
- **填写要点**：
  - 这是评测报告区别于"成绩单"的关键——它让研发知道回去改哪里。
  - 如果一个 bad case 是多因素叠加，要拆成多行归因，不要混在一句里。
- **示例片段**：

  **Bad case：T12 退款题**
  - **现象**：用户问"我能退款吗"，Agent 直接转人工，未先追问关键信息。
  - **轨迹**：用户提问 → 分类器路由到"转人工"分支 → 直接返回人工入口。
  - **归因**：{Prompt 没写清}——主 Prompt 未强制"退款类问题必须先追问充值时长、钻石使用、是否未成年"；同时{意图分类缺"退款流程追问"类别}。
  - **修复**：①主 Prompt 增加硬性追问清单；②分类器新增"退款流程追问"类别，温度降为 0；③补齐"7 天/未使用/每年 1 次"规则话术。
  - **复测**：T12 在最终回归中 3 次全过；输出均先追问三要素再按规则回答。

  **Bad case：T15 信誉分题**
  - **现象**：用户问"我现在信誉分多少"，Agent 只要求提供账号，未查接口。
  - **轨迹**：用户提问 → 分类器落入"普通问答" → 走文本回复。
  - **归因**：{实时查询节点缺失}——原流程没有代码执行节点，无法返回账号接口数据。
  - **修复**：新增"实时查询（模拟接口）"代码节点及结果回复节点，覆盖{服务器状态、当前信誉分、封号原因}三类输入。
  - **复测**：T15 通过 pass³；但当前返回的是{教学测评用模拟数据}，上线前需替换为真实接口并重新验证权限/超时/异常。

### 3.12【范式 B 主体】版本对比与优化清单

- **这一节写什么**：把本轮做了哪些修复、对应解决了哪些题，列成一张清单；同时把还没修的题列成下一步动作。
- **颗粒度要求**：已完成清单 5-10 条，每条对应"改了什么 / 解决了哪些题"；待办清单要写"上线前必须做"。
- **填写要点**：
  - 已完成清单不要写"优化了 Prompt"，要写"固化了 S5 版本数字、价格、充值限额、退款条件、克制关系和计算规则"。
  - 待办清单要暴露"当前版本依赖模拟节点"这种上线风险，不要藏着。
- **示例片段**：
  > **已完成的优化**：
  > 1. 重写主客服提示词，固化 {S5 版本数字、价格、充值限额、退款条件、克制关系和计算规则}。
  > 2. 增加 {实时查询} 和 {转人工} 分类；将分类温度降为 0，减少随机误路由。
  > 3. 新增 {实时查询（模拟接口）} 代码节点及结果回复节点，覆盖 {服务器状态、当前信誉分、封号原因}。
  > 4. 补齐 {外挂处罚、防沉迷时间窗口、未成年人退款材料、封号申诉入口、3 个工作日回复} 等固定话术。
  > 5. 增加回答边界，禁止输出 {分类标签、检索过程、文件名、内部资料名称}。
  >
  > **上线前必须完成**：
  > - 将 {模拟查询节点} 替换为真实生产接口，重新验证 {账号权限、超时、异常、数据时效}。
  > - 对 T13-T15 三道依赖接口的题补跑 pass³（真实接口环境下）。
  > - 红线题复跑一次（安全/拒答类）。

### 3.13 结论与上线建议

- **这一节写什么**：基于数据和归因，明确给出"能不能上线 / 选哪个模型 / 先修哪块"的建议。
- **颗粒度要求**：必须给出明确判断（不要写"建议进一步观察"）；如果有条件放行，写清条件。
- **填写要点**：
  - 建议要可执行：{选模型 A、版本可上线、先修 X 再评 Y}。
  - 必须显式提示"依赖模拟节点"这种不能带到生产的东西。
- **示例片段**：
  > **复测结论**：{25 道题}全部满足测评集的路由、召回、答案和边界要求。
  >
  > **上线建议**：
  > - {T13-T15 的通过依赖新增的固定模拟查询节点}，返回的是{素材包中用于教学测评的模拟数据}，不是生产服务器或账号 API。
  > - 上线生产前，应把该节点替换为{真实接口}，并重新验证{账号权限、超时、异常和数据时效}。
  > - 替换后建议再跑一次 pass³，全部通过后再发布。

### 3.14 附录：评测集与判定口径

- **这一节写什么**：评测集版本、题量、题型分布、判定标准、评测人。
- **颗粒度要求**：写清评测集文件名、正式计分题范围、是否含标准答案、是否含关键考察点；如有人工评测，写明评分量尺和交叉盲评方式。
- **填写要点**：
  - 让读者能复现这次评测。
  - 如果评测集后续会迭代，标注"本结论仅对应该评测集版本，集版本升级后需重评"。
- **示例片段**：
  > - 评测集：{评测集文件名}
  > - 正式计分题：{T01-T25，共 25 题}
  > - 题型分布：{事实召回 N 题 / 流程追问 N 题 / 拒答边界 N 题 / 组合计算 N 题 / 实时查询 N 题}
  > - 判定口径：每题关键考察点见评测集"{怎么算过}"列
  > - 评分方式：{人工二值判定 / LLM-as-Judge 输出 Y/N / 脚本自动匹配}
  > - 本结论对应该评测集版本，集版本升级后需重评。

## 四、不同产品类别的差异化要点

- **A 类（对话式 Agent / 陪练 / 客服）**：默认用范式 B。必须跑 pass³；bad case 归因四类（数据缺失/没召回/Prompt 没写清/模型能力不够）要分清；重点看多轮状态、工具调用、拒答边界；上线前必须显式提示"模拟接口 vs 真实接口"。
- **B 类（RAG 知识库 / 问答）**：默认用范式 B。bad case 归因要多一类"检索没召回"；逐题结果表里要写清"是否引用了正确来源段落"；如果是 Embedding/Rerank 选型，再叠范式 A 做维度对比。
- **C 类（AIGC 多模态生成）**：默认用范式 A。必须做人工盲评（不能只靠脚本）；Goodcase/Badcase 对比表必须配参考素材和输出截图；维度拆分要覆盖"不同参数/风格/运动幅度/镜头数"；case 量过少的维度要显式标注不具参考性。
- **D 类（评测平台 / 内部工具）**：两种范式都常用。重点是"评测集本身的质量"——要在附录里写清评测集迭代记录；LLM-as-Judge 的选型建议用范式 A 出对比；每次版本回归用范式 B 出通过率。
- **E 类（B 端 SaaS AI 化）**：一般不单独写评测报告，引用 D 类平台的评测结论即可。AI 功能验收时，重点写"是否达到 PRD 里的验收标准"，而不是从零起一份新报告。
