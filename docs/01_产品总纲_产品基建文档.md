# 【产品总纲 / 产品基建文档】SKILL

> **适用产品类别**：A / B / C / D / E 全类别适用。产品总纲是 0→1 阶段的顶层文档，无论对话式 Agent、RAG 知识库、AIGC 生成、评测平台还是 B 端 SaaS AI 化，都需要一份"为什么做、为谁做、做什么、做到什么程度、投多少、谁负责"的顶层定义；差别只在颗粒度与侧重点。
> **文档目的**：在写任何一份 PRD 之前，先把"问题—用户—方案—指标—边界—资源—风险—待决策"八件事一次性钉死，作为后续所有 PRD、排期、评测、验收的顶层依据。给管理层、业务方、研发、评测、安全/法务共同阅读，是项目对齐和拍板的唯一入口。
> **撰写时机**：MVP 启动前。需求刚收集完、调研已完成或进行中、尚未冻结功能清单时写；写完即作为立项/启动依据，之后每个版本只更新"范围与版本规划"和"指标"两节，不推翻全文。

## 一、撰写前需要收集的资料清单

### 1.1 用户侧
- {目标用户}的角色清单（实际使用者 / 协同审批者 / 管理者 / 受影响但不直接用的人）及其权限边界
- 每个角色的高频任务、当前流程、频率、耗时、排期等待
- 用户原话/书面表达（痛点、抱怨、期望改变什么），区分"规定流程"与"真实行为"
- 现状基线数据：人数、批次、工时、完成率、通过率、等待时长（注明口径与来源）
- 用户对 AI 的接受度、误判容忍度、申诉/转人工意愿

### 1.2 业务侧
- 业务发展要求（扩招、新政策、新考核指标）与组织现状（人岗比、培训/运营人力）
- 现有 SOP、评分标准、红线规则、合规要求，以及它们之间的冲突与缺失（及格线不明、版本不一致）
- 与既有系统的关系（嵌入哪个入口、复用哪些身份/权限/数据、还是独立试点）
- 业务方对"AI 替代到什么程度"的预期边界（辅助 / 影子 / 正式决策）

### 1.3 技术侧
- 可调用的模型、ASR/TTS、Embedding/Rerank、规则引擎、向量库能力与 SLA、单价
- 知识/数据源清单、数据量、清洗难度、脱敏与合规要求
- 关键技术风险（幻觉、延迟、方言/抢话、跨表准确率、越权召回）及兜底手段
- 部署方式约束（私有化 / 公有云 / 混合）与数据分级要求

### 1.4 数据与指标侧
- 可量化的业务指标（工时下降、等待时长、完成率、满意度）及其基线取数方式
- AI 效果指标（人—人基线、人—AI 一致性、证据正确率、红线召回、P95 响应）
- 非功能指标（QPS、并发、留存期、删除 SLA、审计日志覆盖率）
- 已有的历史"相关性信号"（哪些能说明方向、哪些不能证明因果）

## 二、资料来源渠道

| 来源类型 | 具体渠道 | 在总纲里的用途 |
|---------|---------|--------------|
| 用户访谈 / 跟岗观察 | 一线用户深访、影子跟岗、最近一次完整任务复盘 | 还原真实流程、拿到用户原话、发现规定与行为的偏差 |
| 业务书面材料 | 需求提出方书面文档、SOP、考核办法、排班表 | 背景、角色分工、现有规则与冲突 |
| 历史数据与记录 | 工单系统、录音/转写、评分表、认证记录、业务结果报表 | 现状基线、工时测算、相关性信号（须标注口径） |
| 竞品与行业 | 竞品官网、第三方体验报告、行业政策 | 判断时机、技术成熟度、差异化边界 |
| 技术与供应商 | 模型/语音/向量服务文档、报价单、SLA 条款 | 技术可行性、成本、部署方式 |
| 安全/法务/合规 | 数据分级规范、隐私告知模板、审计要求 | 安全合规章节、AI 权限边界 |
| 内部系统 | SSO、组织架构、任务/结果系统、既有业务平台 | 集成方式、权限继承、入口选择 |

> **取证原则**：每一条关键论断后面都要能回答"这是原始材料事实、人工测算、方案建议、还是待确认项"。总纲最忌把测算当结果、把相关当因果。

## 三、完整框架结构（到三级标题）

> **先选粒度模式，再套下面的章节。** 同一份产品总纲存在四种成熟粒度，按场景取用，不要一上来就写最重的立项报告：

| 粒度模式 | 适用场景 | 章节裁剪 | 篇幅参考 |
|---------|---------|---------|---------|
| **模式甲：全景地图（六段式）** | 项目刚启动 / 换人接手 / 需要 30 分钟看懂全局 | 只写 H3 的 0、2、3、5 章的浓缩版，外加"已决定 vs 待验证"和"交接路径" | 1–2 页 |
| **模式乙：问题定义（早期探索）** | 需求刚提出、还没决定做不做、功能清单未冻结 | 只写 H3 的 1、2、3、4、7 章的前半段 + "待调研验证事项" | 3–5 页 |
| **模式丙：立项报告（决策导向）** | 需要管理层拍板、批预算、批人、定 AI 权限 | 完整 H3 全部 0–12 章 + 附录事实口径 | 10–20 页 |
| **模式丁：ToB 一页纸（全要素压缩）** | 对外汇报、客户/甲乙双方对齐、项目启动会 | 把 H3 的 1–11 章压成 10 个小节，每节一张表，外加"双方分工、配合事项、文档索引" | 2–4 页 |

下面 H3 章节以**模式丙（立项报告）**为主框架标注；括号里说明甲/乙/丁模式如何裁剪。

### 3.0 管理层决策摘要
- **这一节写什么**：开头一张"决策问题—本报告结论"表，让决策者不读全文也能拍板。6 行左右：为什么做 / 先为谁做 / 先做什么 / 如何证明有效 / 投入什么 / 主要风险。
- **颗粒度要求**：每行一句话，结论必须可执行（如"条件立项，一个{试点范围}、{周期}、影子模式"），不能写"值得做"这种空话。模式甲可把这节扩成"一眼看懂项目"（一句话 + 一张流程图）。
- **填写要点**：开头放一个 callout 写明立项建议（立项 / 条件立项 / 暂缓）；明确"AI 不拥有哪些决定权"（正式认证、汰换、绩效、真实客户外呼等）；模式丁把这节并到"项目基础信息"里。
- **示例片段**：
  > **立项建议：条件立项。** 批准一个{自然班/试点范围}、{10周}、影子模式试点；首期只验证"{核心假设}"。AI 不拥有正式{认证/审批/绩效}决定权。W5 通过离线评测后再进入{实时语音/正式链路}开发，W10 依据数据做 Go / Continue / Pivot / Stop 决策。

### 3.1 项目基础信息
- **这一节写什么**：一张表把项目"身份证"列清：项目名称、立项状态、产品定位、首期用户、协同用户、核心场景、建议周期、试点范围、项目负责人、业务 Owner、需求联系人。
- **颗粒度要求**：产品定位一句话说清"给谁、用什么方式、解决什么"；首期用户与协同用户分开列；负责人与 Owner 在立项会前可能是"待指定"，不要留空。
- **填写要点**：模式乙把这节扩成"需求基本信息"（需求提出部门、提出人、提出方式、提出时间、涉及岗位）；模式丁加一列"客户/供应商/合同状态/项目周期"；不要在这节堆功能。
- **示例片段**：
  > **产品定位**：面向{目标用户}的{AI 训练/问答/生成}平台，通过{核心能力}，扩大{有效供给/可及性}，减少{重复人工投入}。
  > **首期用户**：{核心角色}；**协同用户**：{审批/管理/运营角色}。
  > **一句话说明**：给{谁}在{什么时间窗}用，解决{什么痛点}，最终让{谁}把时间留给{高价值事项}。

### 3.2 立项背景与动因
- **这一节写什么**：为什么是现在做。按"业务发展要求 / 组织现状 / 用户与业务反馈 / 技术成熟度 / 现有系统问题"五个维度摆证据，每个维度对应一句"立项含义"。
- **颗粒度要求**：每个维度都要有证据 + 推论两列；业务反馈直接引用原文表达（去具体化后保留句式）；技术成熟度要写清"哪些能力可调用、哪些仍需评测"，不能写"技术已经成熟"。
- **填写要点**：模式甲把这节做成"为什么值得做"的证据链流程图（人工投入事实 → 相关性信号 → 结论）；**必须放一个"收益边界"callout**，把历史材料里的收益数字、提升比例标注为"原文测算、未经财务复核、只说明相关性"；模式丁的"背景与动因"要额外写政策/客户驱动（如国产化、AI 落地指标）。
- **示例片段**：
  > | 判断维度 | 现有证据 | 立项含义 |
  > |-|-|-|
  > | 业务发展要求 | {月均约 X 名新人 / 政策指标} | 供给需从"靠少数人排期"变成可扩展能力 |
  > | 组织现状 | {培训师与新人约 1:20} | 人数增加时，个体关注被稀释 |
  > | 技术成熟度 | 大模型、ASR/TTS、RAG 已有可调用能力；{方言/延迟/一致性}仍需评测 | 可做受控原型，不能直接全量上线 |
  >
  > ❗ **收益边界**：历史材料中"{807万收益/效率提升40%}"均为原文测算，不是上线结果；"模拟组 23% vs 未模拟组 14%"只能说明相关性，不能证明因果。

### 3.3 现状与问题分析
- **这一节写什么**：把现有流程画出来（准备 → 主流程 → 评分/审批 → 反馈归档 → 复练），逐环节列"当前怎么做 / 效率损耗在哪 / 证据口径"，最后收敛成 P0/P1 问题清单（问题—根因—业务影响）。
- **颗粒度要求**：流程图 + 环节表缺一不可；每个问题必须标 P0/P1；要写"反例与边界"（哪个场景证据不足、首期不覆盖）。
- **填写要点**：模式乙把这节展开成"当前流程"专章，用 mermaid 画全流程分叉（同步/异步、真人/录制、谁评分、谁复核、通过/补考）；工时数字要注明"下限计算是否有误、是否混用人时与日历历时"；不要把业务方给的痛点直接当根因，要往下追一层。
- **示例片段**：
  > | 环节 | 当前怎么做 | 效率损耗发生在哪里 | 证据/口径 |
  > |-|-|-|-|
  > | 准备与找人 | {用户}找{他人}安排 1V1 | 能否开始取决于他人时间 | 旧记录排队约 40 分钟，需 W1 复核 |
  > | 主流程 | {真人/人工}逐项推进 | 每增加一名{用户}就增加一份{同步投入} | 人工测算约 X 小时/月 |
  >
  > **问题结论**：P0｜{有效供给无法规模化}；P0｜{反馈无法稳定复用}；P1｜{记录与版本分散}。
  > **反例与边界**：{约 80% 对话发生在线下}，{电话录音}只能覆盖少量环节，因此首期选择{证据完整的场景}，不承诺评价{完整能力}。

### 3.4 用户与使用场景
- **这一节写什么**：角色 × 频率 × 权限边界 × 典型任务的四列表；再用"主场景叙事"写一遍（谁、在什么时间窗、走完什么流程、得到什么结果）。
- **颗粒度要求**：每个角色都要写清"能看什么、不能看什么"（权限边界）；典型任务写到动作级，不能只写"用户可以对话"；至少覆盖 4–5 个角色（使用者 / 供给者 / 审批者 / 运营者 / 安全管理员）。
- **填写要点**：模式乙把"用户角色"按"实际使用 / 训练供给 / 认证复核 / 结果影响"四类归组；E 类 B 端 SaaS 要额外列"商户侧/平台侧"双层角色；A 类 Agent 要区分"直接对话者"与"配置 Agent 的运营者"。
- **示例片段**：
  > | 角色 | 频率 | 权限边界 | 典型任务 |
  > |-|-|-|-|
  > | {核心使用者} | {每日/按任务} | 仅看自己的{任务/记录/反馈} | 选择场景，与 AI{角色}完成{核心动作}；查看原话证据；针对薄弱项复练 |
  > | {供给/辅导者} | {每日/每班次} | 查看所负责范围，不能越组织查看 | 下发任务、查看完成与薄弱项、抽查低置信度结果 |
  > | {审批/管理者} | {批次/异常时} | 保留正式决定权 | 处理 AI 无法判断、红线、临界分和申诉 |
  > | {安全管理员} | 按需 | 只做身份、权限、审计 | 权限开通、日志审计、数据删除 |

### 3.5 项目目标与成功指标
- **这一节写什么**：一句话项目目标 + 一张四类指标表（业务 / 产品 / AI 效果 / 运营），每类含核心指标、试点门槛、取数方式。
- **颗粒度要求**：每个指标都要有"基线值—目标门槛—取数方式"三要素；AI 效果指标必须先建立人—人基线，再定人—AI 一致性门槛；明确哪些指标"只做长期观察、不作为试点硬门槛"（如收入、开单率）。
- **填写要点**：开头 callout 写明"W1 建人工基线、W2 冻结验收口径"；模式丁的"项目目标"要写 POC 阶段硬验收数字（准确率、响应时间、并发、日处理量）；不要把"用户满意度"写成唯一产品指标。
- **示例片段**：
  > | 类型 | 核心指标 | 试点门槛 | 取数方式 |
  > |-|-|-|-|
  > | 业务 | {人工工时、等待时间、反馈时长} | 扣除人工复核后工时下降 20%–40%；首次练习中位等待 ≤5 分钟 | 最近班次基线 + 系统事件日志 + 工时抽样 |
  > | 产品 | {激活率、任务完成率、人均次数、满意度} | 激活率≥80%；完成率≥80%；满意度≥4.0/5 | 会话日志 + 课后问卷 + 访谈 |
  > | AI 效果 | {人—AI 一致性、证据正确率、红线召回、P95 响应} | 一致率≥85% 且不低于人—人基线 5pp；证据正确率≥95%；红线召回≥95%；P95≤2s | 双人盲评集、边界样本、对抗集、线上抽检 |

### 3.6 产品方案与核心能力
- **这一节写什么**：三件套——①产品形态与核心能力表（能力 / 用户得到什么 / 首期边界）；②交互流程（6 步左右的用户动作链）；③人机职责边界表（AI 负责 / 确定性规则负责 / 人负责）。
- **颗粒度要求**：能力表每行必须有"首期边界"列，写清不做什么；交互流程写到动作级（收到任务 → 选择场景 → 开始 → 评分 → 复练或转人工 → 沉淀记录）；人机职责边界必须把"权重计算、门槛判断、红线命中"这类确定性决策从大模型手里划给规则引擎。
- **填写要点**：模式甲把这节做成"产品与 AI 如何工作"的端到端流程图（运营配置 → 入口 → 各链路 → 各 Agent → 报告 → 回环）；B 类 RAG 要写离线链路（采集→解析→切分→向量化→入库）+ 在线链路（意图识别→Query 改写→检索→重排→生成）；C 类 AIGC 要写提示词组装与多模型 fallback；A 类 Agent 要写角色扮演与评分/生成是否分离。
- **示例片段**：
  > | 能力 | 用户得到什么 | 首期边界 |
  > |-|-|-|
  > | {实时角色扮演} | AI 扮演{虚拟角色}，根据用户表达动态{追问/抛异议} | 只模拟训练，不连接真实{客户/业务对象} |
  > | {证据化评分} | 按考点给分，引用对应原话，给出判定理由与改进建议 | 总分/门槛/红线由确定性规则计算；低置信度转人工 |
  >
  > **人机职责边界**：AI 负责{角色扮演、转写、初评、证据定位}；确定性规则负责{权重、门槛、红线、版本绑定}；人负责{规则审批、正式决策、申诉、安全合规判断}。

### 3.7 需求范围与版本规划
- **这一节写什么**：三栏对比表——MVP（本期）/ 后续迭代 / 暂不支持；再写用户与场景的接入顺序（试点 → 扩大 → 第二场景 → 其他业务线）。
- **颗粒度要求**：每栏至少 5–8 条具体功能/范围；"暂不支持"必须明确写出被砍的诱惑项（一次接入全业务线、AI 自动正式决策、复杂 BI、未经审批使用真实数据训练）；接入顺序每步都要写"满足什么条件才进入下一步"。
- **填写要点**：模式乙在这节只写"业务方希望改变什么"（从当前状态→希望变成→尚未决定），不冻结功能；任何变更都要说明对里程碑的影响并重新审批。
- **示例片段**：
  > | MVP｜本期 | 后续迭代 | 暂不支持 |
  > |-|-|-|
  > | {一个试点范围}；{核心场景}；{实时+异步}；逐考点评分与原话引用；反馈/复练/人工复核 | {更多班次}；{异步任务}；{多行业剧本}；{深度集成} | {一次接入全业务线}；{AI 自动正式决策}；{复杂 BI}；{未经审批使用真实数据训练} |
  >
  > **接入顺序**：① 试点（影子模式，AI 不改变正式结果）→ ② 过闸后扩大 → ③ 第二场景单独设计评价方式 → ④ 其他业务线待规则/数据/权限/Owner 齐备后逐一接入。

### 3.8 知识、数据与技术方案（立项级）
- **这一节写什么**：两张表——①知识/数据源表（来源 / 首期用途与治理要求 / 责任角色）；②技术环节表（环节 / 系统怎么运行 / 可控性设计）。
- **颗粒度要求**：知识表每类数据必须有"唯一 Owner + 替补人"，无 Owner 不进生产；技术表只写立项级思路（证明可实现即可），不写具体供应商选型；必须覆盖"问题理解 / 核心生成 / 检索上下文 / 评分或校验 / 兜底 / 接口部署 / 日志监控"七个环节。
- **填写要点**：B 类 RAG 直接抄"离线链路 + 在线链路"，并写清 Top-K、重排阈值、意图体系、权限元数据、混合检索、图片处理策略；C 类 AIGC 写多模型 fallback 与成本工程；A 类 Agent 写"生成与评分分离、低置信度转人工"；数据治理要写清洗、切分、更新、权限、责任五条规则。
- **示例片段**：
  > | 环节 | 系统怎么运行 | 可控性设计 |
  > |-|-|-|
  > | {检索与上下文} | 从已批准的{知识源}检索，重排后只组装与当前{考点/意图}相关的上下文 | 只允许使用有版本、有权限的来源 |
  > | {评分与校验} | 独立{评分/审核}对完整{会话/文档}逐{考点/条款}评估，引用原话；规则引擎计算权重、门槛、红线 | {评分}不承担正式{决策}；错放、错杀分别监控 |
  > | {兜底} | 检查引用、格式、事实和置信度；{无答案/红线/临界}进入人工队列 | 任何{P0 幻觉/红线漏报}可一键关闭{辅助能力} |
  >
  > **质量保障规则**：清洗去重/脱敏/冲突检测；按"{业务单元—考点—判定规则—正反例}"切分而非固定长度切片；变更走"提交→审批→回归评测→发布新版本"，历史记录始终绑定当时版本。

### 3.9 系统集成与安全合规
- **这一节写什么**：按领域列 MVP 要求与边界——身份与组织、任务与结果、录音/知识、数据安全、内容安全、留存与删除。
- **颗粒度要求**：每个领域写清"MVP 要求 / 边界与后续"两列；必须写明数据告知用途、可见范围、保留期、删除方式；发生 P0 安全事件的停止条件要写死。
- **填写要点**：E 类 B 端 SaaS 要优先写"嵌入哪个既有入口、SSO、组织权限继承"；A/C/D 类只要涉及真实用户数据/录音/客户合同，就必须写脱敏、分级存储、导出控制、操作审计；部署方式（私有化与否）不在立项阶段预设，由数据分级/安全/成本/延迟共同决定。
- **示例片段**：
  > | 领域 | MVP 要求 | 边界/后续 |
  > |-|-|-|
  > | 身份与组织 | 接入 SSO 和{组织/班次}权限，{多角色}分权 | 跨组织授权后续单独评审 |
  > | 录音与知识 | {员工训练数据}需明确告知用途、可见范围、保留期和删除方式 | 真实{客户/业务对象}数据须另行取得合规批准 |
  > | 数据安全 | 传输/存储加密、最小权限、{原始数据与聚合指标}分级、导出控制、操作审计 | 发生权限泄露或未授权使用即停止试点 |
  > | 留存与删除 | W1 明确保留期限、删除 SLA、申诉与审计留存范围 | 未完成数据生命周期评审，不进入安全验收 |

### 3.10 实施计划、团队与资源投入
- **这一节写什么**：①排期甘特图（相对周次，分阶段闸门）；②阶段表（阶段/关键产出/进入下一阶段条件/主要责任）；③最小团队表（角色/投入/职责）；④外部依赖表；⑤预算口径。
- **颗粒度要求**：排期以"立项当周为 W1"相对表达；每个闸门必须写"进入下一阶段条件"（如"核心规则无冲突、评测样本可用"）；团队最小化（6 人左右核心 + 共享安全/法务/设计）；预算不虚构总金额，采用两段式审批（第一段离线验证、第二段实时/试点）。
- **填写要点**：模式丁把这节压成"里程碑表（计划时间/实际状态）+ 甲乙双方分工表 + 业务方配合事项"；外部依赖要写清"最晚提供时间"；W1 必须冻结单次调用成本、预计会话量、试点总现金上限。
- **示例片段**：
  > | 阶段 | 关键产出 | 进入下一阶段条件 |
  > |-|-|-|
  > | W1 | 范围、指标基线、数据分级、接口清单、Owner、预算上限 | Owner 和预算未确认则不进入开发 |
  > | W2 | 统一{SOP/量表/红线/边界样本/双人盲评集} | 核心规则无冲突，评测样本可用 |
  > | W3–W5 | {异步/离线}MVP 与{评分/审核}闭环，完成离线评测 | {一致性、证据、红线}达到闸门 |
  > | W6–W10 | {实时/正式链路}、试点、决策报告 | 形成 Go / Continue / Pivot / Stop 结论 |

### 3.11 风险与立项决策
- **这一节写什么**：风险表（风险 / 预警信号 / 应对措施 / 停止或降级条件）+ W10 决策标准（Go / Continue / Pivot / Stop 四档触发条件）。
- **颗粒度要求**：每个风险都要有"预警信号"和"停止/降级条件"两列，不能只写应对措施；四档决策标准必须可量化。
- **填写要点**：模式甲把"已决定什么 vs 仍要证明什么"做成两栏清单；常见六类风险——{评分/标准不稳、AI 错判幻觉、用户不使用、权限/数据泄露、体验不达标、集成与范围失控}；P0 安全事件立即停试点，体验不达标则降级链路（实时转异步），不拖延整项目。
- **示例片段**：
  > | 决定 | 触发条件 |
  > |-|-|
  > | Go | 业务、产品、AI、安全硬门槛均达成，无 P0 事件；扩大范围 |
  > | Continue | 用户价值成立，但一项非安全 AI 指标轻微未达；限定 2–4 周修复后复评 |
  > | Pivot | 问题成立、用户愿意用，但{实时链路/自动评分}不可控；转为{异步/人工辅助} |
  > | Stop | 采用率持续低、AI 明显低于人—人基线、核心规则无法统一、出现不可接受安全风险 |

### 3.12 待决策事项、配合事项与交接
- **这一节写什么**：①本次需要管理层决定的事项表（待决策事项 / 本报告建议 / 最晚确认时间）；②业务方/客户配合事项（数据、访谈、验收、变更、环境）；③附录事实口径（原始材料事实 / 人工测算 / 立项建议 / 待确认项 四类标记）；④关键文档索引与交接路径。
- **颗粒度要求**：待决策事项不超过 6 条，每条都有建议值和最晚时间；附录必须把全文数字按四类口径标记，避免"测算当结果"；文档索引按阶段（招投标/售前/立项/设计/技术/数据/测试/项目管理/交付）列出，标注状态（已有/缺失/暂无）。
- **填写要点**：模式甲的"交接路径"用流程图画出"本页 → 问题定义 → 调研 → 决策书 → PRD → 评测 → 上线/停止记录"的推进顺序，并写"接手后的第一步"；模式丁的"业务方配合事项"要写死"所有变更走书面确认、不走口头"。
- **示例片段**：
  > | 待决策事项 | 本报告建议 | 最晚确认时间 |
  > |-|-|-|
  > | 是否立项 | {条件立项}，{周期单范围}试点，不承诺全量上线 | 立项会 |
  > | 谁负责 | 指定 Sponsor、业务 Owner、项目负责人、技术 Owner、知识 Owner、验收负责人 | W1 结束前 |
  > | AI 权限 | 只{训练/辅助}；{正式决策}保留人工 | 立项会 |
  >
  > **事实口径标记**：{原始材料事实}可追溯但不等于全量日志；{人工测算}只判断量级、立项后按统一口径复核；{立项建议}需批准后生效；{待确认项}列出所有 Owner/预算/供应商/部署/保留期/接口未定事项。

## 四、不同产品类别的差异化要点

- **A 类（对话式 / Agent 产品）**：必须写清"角色扮演与评分/规划是否分离为双 Agent"、多轮上下文与长期记忆边界、Tool use 范围、主动触发条件、人设/角色边界（防止 AI 越界生成未经审批的话术）；人机职责边界里尤其要把"高影响结果（认证、汰换、绩效）"划回人工。
- **B 类（RAG 知识库 / 问答）**：3.8 节必须展开"离线链路 + 在线链路"全流程，写清知识库分类体系、Top-K、重排阈值、意图分类（含边界拒答）、权限元数据（access_level / visible_dept / version_id）、混合检索与兜底话术；3.5 节硬指标以"检索准确率、引用溯源正确率、拒答率"为核心。
- **C 类（AIGC 多模态生成）**：3.8 节重点写提示词组装模板、多模型 fallback 链路、结果质量分级、成本工程（单次生成成本 × 并发）；3.5 节硬指标以"一次生成可用率、人工返修率、单张/单条成本"为核心；安全边界写"色情/侵权/虚假宣传"红线拦截。
- **D 类（评测平台 / 内部工具）**：3.4 节要区分"被评测对象的业务用户"与"评测平台自身的用户（标注员、算法、PM）"；3.5 节把 Golden Set 覆盖率、LLM-as-Judge 与人评一致率、bad case 闭环时长作为核心指标；3.7 节"暂不支持"里写死"不直接对业务用户输出正式结论"。
- **E 类（B 端 SaaS / 传统产品 AI 化）**：3.9 节优先写"嵌入既有系统入口、SSO、商户侧与平台侧双层权限"；3.10 节外部依赖表拉长（对接既有订单/工单/支付系统）；3.2 节背景要写清"AI 是既有功能的增量还是重构"，避免把 AI 当独立产品另起炉灶。

## 五、完成度 Checklist

- [ ] 开头有"立项建议 callout"和"决策问题—结论"摘要表，决策者不读全文能拍板
- [ ] 产品定位、首期用户、协同用户、核心场景、试点范围五要素已写死
- [ ] 现状流程画了图，且逐环节标注"当前做法 / 损耗点 / 证据口径"
- [ ] P0/P1 问题清单已收敛，每条有根因和业务影响，并写了"反例与边界"
- [ ] 每个角色都标注了权限边界（能看什么 / 不能看什么）
- [ ] 指标表覆盖业务/产品/AI 效果/运营四类，且每个指标有基线、门槛、取数方式
- [ ] AI 效果指标先建人—人基线，再定人—AI 一致性门槛
- [ ] 产品方案三件套齐备：能力表（含首期边界）、交互流程、人机职责边界；"权重/门槛/红线"等确定性决策明确划给规则引擎而非大模型
- [ ] MVP / 后续迭代 / 暂不支持三栏齐全，"暂不支持"写出了被砍的诱惑项
- [ ] 知识/数据每类有唯一 Owner + 替补人；技术七环节（理解/生成/检索/评分/兜底/部署/日志）无缺
- [ ] 安全合规章节覆盖数据告知、分级存储、导出控制、审计、留存删除、P0 停止条件
- [ ] 排期有阶段闸门（进入下一阶段条件），团队最小化，预算两段式、不虚构总额
- [ ] 风险表每条都有"预警信号"和"停止/降级条件"；Go/Continue/Pivot/Stop 四档可量化
- [ ] 附录把全文数字按"原始事实/人工测算/立项建议/待确认"四类口径标记
- [ ] 已按场景选对粒度模式（甲全景 / 乙问题定义 / 丙立项报告 / 丁 ToB 一页纸），没有过度膨胀

```

【先选粒度模式】
请先判断当前处于哪个场景，并在文档开头标注选用的模式：
- 模式甲（全景地图六段式）：项目刚启动/换人接手，需要 1–2 页让接手人 30 分钟看懂全局
- 模式乙（问题定义）：需求刚提出、还没决定做不做，3–5 页

- 模式丁（ToB 一页纸）：对外/客户/甲乙双方对齐，2–4 页全要素压缩

项目背景：{项目背景，含业务发展要求与组织现状}

核心功能方向：{AI 要做的核心能力，以及首期不做什么}
技术约束：{可调用的模型/语音/知识库能力、延迟与成本约束、部署方式}
数据与知识：{知识源清单、数据量、脱敏与合规要求}
已有数字与相关性信号：{现有工时、通过率、对比数据，标注哪些是测算、哪些是事实}

【撰写要求】
1. 严格按照 SKILL 中"三、完整框架结构"的章节顺序撰写；按所选模式裁剪相应章节。
2. 每个章节写到"颗粒度要求"：角色要写到权限边界、指标要写到基线+门槛+取数方式、产品方案要写到能力表+交互流程+人机职责边界。
3. 必须包含：决策摘要 callout、收益边界 callout、人机职责边界表、MVP/迭代/暂不支持三栏表、阶段闸门表、风险表（含停止条件）、Go/Continue/Pivot/Stop 四档、附录事实口径标记。
4. 所有数字按"原始材料事实 / 人工测算 / 立项建议 / 待确认项"四类口径标注，严禁把测算写成结果、把相关写成因果。
5. 去具体化：不要使用任何真实产品名、公司名、行业名、人名，全部用 {占位符}（如 {产品名}、{目标行业}、{客户名称}、{核心指标}）替换。
6. 在文末列出"待确认事项"清单（Owner、预算、供应商、部署、数据保留期、接口、最终验收口径）。
```
