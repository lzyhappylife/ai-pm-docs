# 【验收表】SKILL

> **适用产品类别**：**E 为主**（B 端 SaaS / 传统产品 AI 化，验收表是 B 端项目交付的标配——客户拿着这张表逐项打勾才算验收通过）；**A/B/C/D 为辅**（A 对话式 Agent、B RAG 问答、C AIGC 生成、D 评测平台，在版本上线、模型发布、功能交付时也需要验收表，但 AI 能力验收占比更大）。
> **文档目的**：把 PRD 里散落在各功能描述里的验收标准，变成"一张可打勾的表"——QA、业务方、客户拿着这张表就能逐项验收，不用回去翻 PRD。验收表的灵魂是"**每一项都能被打勾或打叉，没有'基本通过''差不多'这种模糊词**"。读者是 QA、PM、业务 Owner、客户验收人、研发负责人。
> **撰写时机**：PRD 已评审通过、功能开发完成进入测试阶段时写；正式上线前完成签字。**验收表不是事后补的——它要和 PRD 同时起草**，否则 PRD 里写的"体验良好"到验收时根本没法打勾。

---

## 一、撰写前需要收集的资料清单

### 1.1 上游文档
- 评审通过的 PRD（每个 P0 功能的验收标准）
- 设计稿（Figma/Sketch 链接，含标注版）
- 接口文档（OpenAPI/Swagger）
- 排期表与版本号（这次验收的是哪个版本）

### 1.2 技术侧
- 部署环境（生产/预发/测试环境的地址）
- 测试账号清单（不同角色的账号：管理员/普通用户/复核者/越权用户）
- 测试数据（已准备的测试样本、Golden Set、红线题集）
- 监控与日志平台地址（用来查接口调用、AI trace）

### 1.3 业务侧
- 业务方指定的验收人（具名，不要写"业务部"）
- 验收通过的硬门槛（哪些项不过就不能上线）
- 客户侧验收流程（E 类 B 端：客户要不要派人来验）
- 红线清单（安全/合规/P0 题，一票否决）

### 1.4 AI 产品特有
- 模型/Prompt/知识版本号（这次验收的是哪个版本）
- 离线评测报告（对应《评测报告 SKILL》）
- Golden Set / 评测集版本
- 性能与成本预算（P95 时延、单次成本上限）

## 二、资料来源渠道

| 来源 | 拿什么 |
|---|---|
| PRD | 每个 P0 功能的验收标准、异常流程、边界条件 |
| 设计稿 | UI 走查的对照基准（页面布局/字体/颜色/间距） |
| 接口文档 | 请求/响应字段、错误码、超时阈值 |
| 离线评测报告 | AI 能力指标（一致率/幻觉率/红线召回率）的达标线 |
| 测试用例库 | 已写好的功能用例、异常用例、越权用例 |
| 监控/日志平台 | 验收时实时查接口调用、AI trace、错误率 |
| 业务 Owner | 验收人、硬门槛、红线清单、客户侧验收流程 |
| 上一版本验收表 | 回归项对照（这次要验"上次的 bug 修了没"） |

> **铁律**：验收表每一项都必须能追溯到 PRD 的某一条或某条设计标注；写不出来源的"验收项"都是 PM 拍脑袋，必须删掉或补依据。

## 三、完整框架结构（到三级标题）

> 以下 8 章骨架融合自 6 份真实验收表。E 类 B 端以"传统功能验收"为主（UI/功能/接口/链路），AI 能力验收只占一小块；A/B/C/D 类反过来，AI 能力验收占最大比重。但 **第 0、1、2、3、7、8 章是任何 AI 产品验收都不能省的**。

### 3.0 验收基础信息

- **这一节写什么**：一页纸钉死"这次验的是哪版、在什么环境、谁来验、前置条件是什么"。读者第一眼就要知道这次验收的范围和边界。
- **颗粒度要求**：至少 10 个字段——版本号、验收日期、验收人（PM/QA/业务方/客户）、验收环境、部署地址、测试账号清单、前置条件、本次验收范围、本次不验范围、整体通过硬门槛。
- **填写要点**：
  - **前置条件要写清**——"预发环境部署完成、测试数据已准备、Golden Set 已跑过离线评测"这些必须列，否则验到一半发现环境没准备好。
  - **本次不验范围**要显式写——这是防止范围蔓延的第一道闸门（"本期不验支付、不验移动端、不验性能压测"）。
  - **整体通过硬门槛**要写清——例如"所有 P0 功能 100% 通过、P1 功能 ≥95% 通过、AI 红线题 0 漏报、无 S1 阻断 bug"。
- **示例片段**：
  ```
  | 字段 | 内容 |
  |---|---|
  | 验收版本 | v1.2.0（build {N}） |
  | 验收日期 | {YYYY-MM-DD} 至 {YYYY-MM-DD}，共 {N} 天 |
  | 验收人 | PM：{姓名}；QA：{姓名}；业务 Owner：{姓名}；客户验收：{客户方姓名}（E 类） |
  | 验收环境 | 预发环境 {https://staging.xxx.com}；AI 走{影子模式/真实链路} |
  | 测试账号 | 管理员 {admin@xx.com}；普通用户 {user@xx.com}；复核者 {reviewer@xx.com}；
  越权测试账号 {other@xx.com} |
  | 前置条件 | ①预发环境部署完成；②Golden Set（{N} 题）离线评测已通过；
  ③测试数据已准备（{N} 条）；④红线题集（{N} 题）已跑过 |
  | 本次验收范围 | ①P0 功能 F01-F06；②AI 能力（{核心场景}）；③接口 8 个；
  ④权限链路；⑤端到端主流程 |
  | 本次不验范围 | ①支付链路（下版验）；②移动端适配（下版验）；
  ③性能压测（专项验）；④灰度放量 |
  | 整体通过硬门槛 | ①P0 功能 100% 通过；②P1 功能 ≥95% 通过；
  ③AI 红线题 0 漏报；④无 S1 阻断 bug；⑤越权测试 0 通过 |
  ```

### 3.1 UI 设计验收（视觉走查）

- **这一节写什么**：把设计稿和实际页面摆在一起逐项比对。这是验收表最"机械"但最不能省的一章——UI 走查不过，功能再对也不能上线。
- **颗粒度要求**：至少 5 类走查项——①页面布局与设计稿一致性；②字体/颜色/间距规范；③响应式适配；④空状态/加载状态/错误状态；⑤图标/图片清晰度。每类给具体检查点。
- **填写要点**：
  - **走查要逐页面做**——每个页面一行（首页/列表页/详情页/对话框/设置页），不要只写"UI 符合设计稿"。
  - **三种状态必须验**：空状态（没数据时显示什么）、加载状态（转圈/骨架屏）、错误状态（报错文案/重试按钮）——这三种状态最容易被开发漏掉。
  - 响应式至少验 3 个分辨率（桌面 1920 / 笔记本 1366 / 平板 768）；C 端再加手机 375。
  - 验收结果列三选一：✅ 通过 / ⚠️ 有条件通过（写清遗留）/ ❌ 不通过（写清 bug）。
- **示例片段**：
  ```
  | 页面/模块 | 检查项 | 设计稿对照 | 结果 | 备注 |
  |---|---|---|---|---|
  | 首页-布局 | 与设计稿一致（左导航+主内容区） | Figma 第 {N} 页 | ✅ | |
  | 首页-字体 | 标题 {20px/粗体}、正文 {14px/常规} | 设计规范 | ✅ | |
  | 首页-颜色 | 主色 {#xxx}、背景 {#xxx} | 设计规范 | ⚠️ | 按钮色偏 {#yyy}，待修 |
  | 首页-间距 | 卡片间距 {16px} | 设计规范 | ✅ | |
  | 响应式-1920 | 桌面端无溢出 | — | ✅ | |
  | 响应式-1366 | 笔记本端导航折叠 | — | ✅ | |
  | 响应式-375 | 手机端布局（C 端必验） | — | ❌ | 主按钮被截断，P1 |
  | 空状态 | 无任务时显示插画+"暂无任务" | 设计稿 | ⚠️ | 插画缺失，先用占位图 |
  | 加载状态 | 列表加载时骨架屏 | 设计稿 | ✅ | |
  | 错误状态 | 网络失败时显示"网络异常，点击重试" | 设计稿 | ❌ | 现在只显示"Error"，P1 |
  | 图标清晰度 | 图标在高分屏无锯齿 | — | ✅ | |
  ```

### 3.2 功能验收（逐项打勾）

- **这一节写什么**：这是验收表的主体。每个 P0/P1 功能一行，写清"功能 ID / 功能描述 / 验收标准 / 测试结果 / 备注"。正常流程、异常流程、边界条件都要验。
- **颗粒度要求**：每个功能至少验 3 类场景——①正常流程（Happy Path）；②异常流程（网络失败/权限不足/数据为空/超时）；③边界条件（最大输入/最小输入/极端值）。每类给具体测试用例。
- **填写要点**：
  - **功能 ID 要和 PRD 对应**（F01/F02...）——这样能追溯到 PRD 哪一条。
  - **验收标准要可测**——不要写"用户可以对话"，要写"用户发送消息后 2 秒内收到回复，回复内容与输入相关"。
  - **异常流程不能省**——80% 的线上 bug 来自异常流程没验。每个功能至少验"网络失败"和"权限不足"两类。
  - **边界条件**要写清：最大输入（1000 字？10000 字？）、最小输入（空输入？空格？）、极端值（负数？超长？特殊字符？）。
- **示例片段**：
  ```
  | 功能 ID | 功能描述 | 场景 | 验收标准 | 结果 | 备注 |
  |---|---|---|---|---|---|
  | F01 | 用户登录 | 正常：正确账号密码 | 登录成功，跳转首页 | ✅ | |
  | F01 | 用户登录 | 异常：密码错误 | 提示"账号或密码错误"，不暴露具体哪错 | ✅ | |
  | F01 | 用户登录 | 异常：网络失败 | 提示"网络异常，请重试" | ❌ | 现在白屏，P1 |
  | F01 | 用户登录 | 边界：连续 5 次错密 | 锁定 15 分钟 | ✅ | |
  | F03 | 创建{任务} | 正常：填写必填项提交 | 创建成功，列表可见 | ✅ | |
  | F03 | 创建{任务} | 异常：必填项为空 | 前端拦截，提示"请填写 XX" | ✅ | |
  | F03 | 创建{任务} | 边界：输入 1000 字 | 正常提交，超长截断或提示 | ⚠️ | 现在 800 字就截断，P2 |
  | F03 | 创建{任务} | 边界：特殊字符 <script> | 不执行脚本，正常存储 | ✅ | XSS 已拦 |
  | F06 | 查看{报告} | 正常：有权限用户查看 | 报告完整展示 | ✅ | |
  | F06 | 查看{报告} | 异常：无权限用户访问 | 提示"无权限"，不返回数据 | ✅ | |
  | F06 | 查看{报告} | 异常：报告数据为空 | 显示"暂无数据" | ✅ | |
  ```

### 3.3 链路验收（端到端）

- **这一节写什么**：单个功能验完不够——要把"从入口到产出"的完整链路跑一遍，看数据在各系统间流转对不对、状态机流转对不对、权限链路通不通。
- **颗粒度要求**：至少 4 类链路验收——①端到端主流程跑通；②数据在系统间流转正确；③状态机流转（草稿→审核→发布→下线）；④权限链路（越权测试）。
- **填写要点**：
  - **端到端主流程**要写清"从哪开始、经过哪些系统、到哪结束"——例如"用户提交任务→AI 处理→生成报告→用户查看→导出"。
  - **状态机流转**要逐状态验：草稿能提交吗？审核中能撤回吗？发布后能下线吗？每个状态跳转都要试。
  - **越权测试是 B 端生死线**——普通用户能不能看到别人的数据？复核者能不能改数据？管理员能不能删？每个角色都要试"越权访问"。
  - 数据流转要验"写入后查询正确"——提交任务后，数据库里有吗？列表里能看到吗？导出的内容和数据库一致吗？
- **示例片段**：
  ```
  | 链路 | 验收项 | 验收标准 | 结果 | 备注 |
  |---|---|---|---|---|
  | 端到端主流程 | 用户提交{任务}→AI 处理→生成{报告}→用户查看→导出 | 全流程跑通，每步数据正确 | ✅ | 总耗时 {N} 秒 |
  | 端到端主流程 | 异常分支：AI 处理失败→转人工队列 | 失败后自动入人工队列，用户看到"处理中" | ⚠️ | 转人工队列延迟 {N} 分钟，P2 |
  | 数据流转 | 任务提交后数据库写入正确 | 字段完整、无丢失 | ✅ | |
  | 数据流转 | 导出的报告与数据库一致 | 内容、格式、时间戳一致 | ✅ | |
  | 状态机 | 草稿→提交审核 | 状态变为"审核中"，不可编辑 | ✅ | |
  | 状态机 | 审核中→撤回 | 可撤回为草稿 | ✅ | |
  | 状态机 | 审核通过→发布 | 状态变为"已发布"，用户可见 | ✅ | |
  | 状态机 | 已发布→下线 | 状态变为"已下线"，用户不可见 | ❌ | 下线后用户仍能访问链接，P0 |
  | 权限链路 | 普通用户访问他人任务 | 拦截，提示无权限 | ✅ | |
  | 权限链路 | 复核者修改正式数据 | 拦截，只能批注不能改 | ✅ | |
  | 权限链路 | 未登录用户访问接口 | 拦截，返回 401 | ✅ | |
  ```

### 3.4 接口验收

- **这一节写什么**：后端接口的验收。前端页面点完不够——要直接调接口，看请求/响应字段、错误码、超时、限流、数据一致性。
- **颗粒度要求**：至少 5 类接口验收——①请求/响应字段与文档一致；②错误码处理；③超时/限流/重试；④数据一致性（写入后查询正确）；⑤AI 接口专项（模型调用、Prompt 版本、trace 可查）。
- **填写要点**：
  - **字段一致性**要对着 OpenAPI 文档逐字段核——多一个字段、少一个字段、字段类型错（数字传成字符串）都算不通过。
  - **错误码**要验：参数错返回 400、未授权返回 401、未找到返回 404、服务器错返回 500——每个错误码都要触发一次。
  - **超时/限流**要验：慢接口（模拟 10 秒响应）前端怎么处理？限流（QPS 超限）返回什么？
  - **AI 接口专项**：模型调用是否带版本号？Prompt 版本是否可追溯？trace id 是否能查到完整调用链？
- **示例片段**：
  ```
  | 接口 | 验收项 | 验收标准 | 结果 | 备注 |
  |---|---|---|---|---|
  | POST /api/task | 请求字段 | 与 OpenAPI 一致：task_name/type/params | ✅ | |
  | POST /api/task | 响应字段 | 返回 task_id/status/created_at | ✅ | |
  | POST /api/task | 错误码：参数缺失 | 返回 400，error_code=MISSING_PARAM | ✅ | |
  | POST /api/task | 错误码：未登录 | 返回 401 | ✅ | |
  | GET /api/task/{id} | 数据一致性 | 写入后查询返回一致 | ✅ | |
  | GET /api/task/{id} | 错误码：不存在 | 返回 404 | ✅ | |
  | POST /api/ai/chat | 模型调用 | 请求带 model_id/prompt_version | ✅ | |
  | POST /api/ai/chat | trace 可查 | 响应带 trace_id，可在日志平台查 | ✅ | |
  | POST /api/ai/chat | 超时处理 | 模型超时 30 秒返回 504，前端提示 | ⚠️ | 现在超时 60 秒才返回，P2 |
  | POST /api/ai/chat | 限流 | QPS 超限返回 429 | ✅ | |
  ```

### 3.5 AI 能力专项验收（AI 产品特有）

> 这一章是 AI 产品验收表区别于传统验收表的核心。A/B/C/D 类必须写全；E 类如果 AI 只是嵌入小功能，可裁剪但不能完全省。

#### 3.5.1 准确率与幻觉率门槛

- **这一节写什么**：AI 输出的准确性是否达到 PRD 里定的门槛。这是 AI 能力验收的第一道硬门槛。
- **颗粒度要求**：每个指标给"门槛 + 实测值 + 是否达标"——AI-人工一致率、幻觉率、红线召回率、引用正确率。每个指标写清评测集规模和判定口径。
- **填写要点**：
  - **严重幻觉/违规指导/权限泄露 = 0 容忍**——任一发生即不通过，没有"基本通过"。
  - 实测值要基于 Golden Set 跑出来的数字，不要拍脑袋。
  - 判定口径要和《评测报告 SKILL》一致——不能验收时换一套口径。
- **示例片段**：
  ```
  | 指标 | 门槛 | 实测值 | 评测集 | 是否达标 |
  |---|---|---|---|---|
  | AI-人工一致率（分项） | ≥85% | {88%} | Golden Set {200} 题 | ✅ |
  | 幻觉率（编造事实） | ≤5% | {3%} | Golden Set {200} 题 | ✅ |
  | 红线召回率（P0 漏报） | 0 漏报 | {0} | 红线题集 {30} 题 | ✅ |
  | 引用正确率（B 类） | ≥95% | {97%} | RAG 评测集 {150} 题 | ✅ |
  | 拒答正确率（B 类） | ≥90% | {85%} | 拒答题集 {50} 题 | ❌ |
  | 角色遵循率（A 类） | ≥90% | {92%} | 多轮对话集 {100} 轮 | ✅ |
  ```

#### 3.5.2 拒答边界与红线题

- **这一节写什么**：AI 在什么情况下该拒答、什么情况下该回答，这个边界对不对。红线题（安全/合规/P0）必须全部通过。
- **颗粒度要求**：至少验 3 类——①该拒答的是否拒答（红线题、违规题、超范围题）；②不该拒答的是否误拒（合法请求被拒）；③拒答话术是否合规。
- **填写要点**：
  - **红线题必须 100% 过**——任一漏报即不通过，没有商量。
  - **误拒率也要测**——AI 太保守也不行，合法问题被拒用户体验很差。
  - 拒答话术不能只写"我无法回答"——要告诉用户"为什么不能答、可以问什么"。
- **示例片段**：
  ```
  | 类别 | 验收标准 | 实测 | 结果 |
  |---|---|---|---|
  | 该拒答-红线题（{违规/敏感/越权}） | 100% 拒答，不输出违规内容 | {30/30} | ✅ |
  | 该拒答-超范围题（问{非业务领域}） | 拒答并引导到正确范围 | {15/15} | ✅ |
  | 不该拒答-合法请求被误拒 | 误拒率 ≤5% | {3/50 = 6%} | ⚠️ |
  | 拒答话术 | 包含"为什么不能答"+"可以问什么" | 抽样 {10} 条，{8} 条合规 | ⚠️ |
  ```

#### 3.5.3 引用溯源与知识准确性（B 类重点）

- **这一节写什么**：B 类 RAG 产品必须验——AI 回答引用的来源是不是真的、能不能点开、位置对不对。
- **颗粒度要求**：至少 3 项——①引用来源可点击；②引用位置准确（原文位置对得上）；③引用内容支持结论（不是硬凑）。
- **填写要点**：
  - **引用不能假**——AI 编造一个不存在的文档名或链接是 B 类最严重的 bad case。
  - **位置要准确**——引用的段落要真的在原文里，不能"大概在那个位置"。
  - **权限过滤要验**——用户 A 能不能引用用户 B 权限外的文档？这是 B 类权限生死线。
- **示例片段**：
  ```
  | 验收项 | 验收标准 | 实测 | 结果 |
  |---|---|---|---|
  | 引用来源可点击 | 每条引用可跳转到原文 | {150/150} | ✅ |
  | 引用位置准确 | 引用段落与原文一致 | {142/150 = 95%} | ✅ |
  | 引用内容支持结论 | 引用真的能支撑回答 | {145/150 = 97%} | ✅ |
  | 权限过滤 | 用户 A 不能引用用户 B 权限外文档 | 抽样 {20} 条越权 | ✅ |
  | 无编造引用 | 不存在的文档/链接 0 个 | {0} | ✅ |
  ```

#### 3.5.4 响应时延与性能

- **这一节写什么**：AI 响应速度是否达标。用户对 AI 等待的容忍度比传统功能低得多。
- **颗粒度要求**：至少 3 个时延指标——首字时延（TTFT）P95、端到端 P95、异步任务完成时间。每个给门槛和实测值。
- **填写要点**：
  - **首字时延 P95** 是用户感知最强的指标——超过 3 秒用户就会以为卡了。
  - **P95 不是平均值**——要分位数，平均值会掩盖长尾。
  - 异步任务（生成报告/处理长文档）要给"平均完成时间"和"90% 完成时间"。
- **示例片段**：
  ```
  | 指标 | 门槛 | 实测 P50 | 实测 P95 | 结果 |
  |---|---|---|---|---|
  | 首字时延（TTFT） | P95 ≤2 秒 | {1.2} 秒 | {2.3} 秒 | ⚠️ |
  | 端到端响应 | P95 ≤5 秒 | {3.5} 秒 | {5.8} 秒 | ❌ |
  | 异步任务完成（生成{报告}） | 90% ≤5 分钟 | {3} 分钟 | {6} 分钟 | ⚠️ |
  ```

#### 3.5.5 成本与预算

- **这一节写什么**：单次 AI 调用成本是否在预算内。AI 产品的成本是隐形的——不验成本，上线后账单会爆炸。
- **颗粒度要求**：至少 3 项——①单次调用平均成本；②按当前 DAU 估算月成本；③是否在预算内。
- **填写要点**：
  - **单次成本要算全**——Embedding + Rerank + LLM 生成 + Judge，不是只算 LLM。
  - **按当前 DAU 估算月成本**——单次成本 × 日均调用次数 × 30 天，和预算对比。
  - 如果超预算，要写"降级方案"（换便宜模型/降 Rerank Top-k/降上下文长度）。
- **示例片段**：
  ```
  | 指标 | 预算 | 实测 | 结果 |
  |---|---|---|---|
  | 单次对话平均成本 | ≤{0.05} 元 | {0.038} 元 | ✅ |
  | 单次{报告}生成成本 | ≤{0.5} 元 | {0.62} 元 | ❌ |
  | 按当前 DAU {N} 估算月成本 | ≤{预算}元 | {实测}元 | ⚠️ |
  | 降级方案 | — | {换更小模型/降 Top-k} | 待评估 |
  ```

### 3.6 非功能验收

- **这一节写什么**：性能、稳定性、安全、兼容性。这些不是"功能"，但不过就不能上线。
- **颗粒度要求**：至少 4 类——①性能（页面加载/首字时延）；②稳定性（连续运行 N 小时无异常）；③安全（渗透测试/越权/PII 脱敏）；④兼容性（浏览器/设备）。
- **填写要点**：
  - **稳定性**要做长时间运行（至少 24 小时），看内存泄漏、接口错误率、AI 调用失败率。
  - **安全**必验：渗透测试（OWASP Top 10）、越权访问、PII 脱敏（日志里不能有手机号/身份证）。
  - **兼容性**至少验 3 个浏览器（Chrome/Safari/Edge）；C 端再加手机系统（iOS/Android）。
- **示例片段**：
  ```
  | 类别 | 验收项 | 验收标准 | 结果 | 备注 |
  |---|---|---|---|---|
  | 性能 | 页面加载 | P95 ≤3 秒 | {4.2} 秒 | ❌ P1 |
  | 稳定性 | 连续运行 24 小时 | 无内存泄漏、错误率 ≤1% | {0.3%} | ✅ |
  | 稳定性 | AI 调用失败率 | ≤2% | {1.5%} | ✅ |
  | 安全 | 渗透测试（OWASP Top 10） | 无高危漏洞 | 已测 | ✅ |
  | 安全 | 越权访问 | 所有越权测试被拦截 | ✅ | |
  | 安全 | PII 脱敏 | 日志/导出中无明文手机号/身份证 | 抽样 {50} 条 | ⚠️ | 导出含手机号，P1 |
  | 兼容性 | Chrome 最新版 | 正常 | ✅ | |
  | 兼容性 | Safari 最新版 | 正常 | ✅ | |
  | 兼容性 | iOS {17} / Android {14} | 正常 | ❌ | iOS 上按钮错位，P1 |
  ```

### 3.7 验收结论

- **这一节写什么**：验完了，给结论——通过 / 有条件通过 / 不通过。这是验收表的最后一章，也是最有决策价值的一章。
- **颗粒度要求**：至少 3 部分——①验收结论（三选一）；②遗留问题清单（按严重度排序）；③上线建议。
- **填写要点**：
  - **结论必须三选一**，不能写"基本通过"。三档定义：
    - **通过**：所有硬门槛达标，无 S1/S2 bug，可以上线。
    - **有条件通过**：硬门槛达标，但有少量 S2/S3 bug 不阻塞上线，限期修复后上线。
    - **不通过**：有 S1 阻断或硬门槛未达，不能上线，修复后重新验收。
  - **遗留问题清单**按严重度排序（S1>S2>S3>P2），每个写清"问题/负责人/修复期限"。
  - **上线建议**要具体——"可以全量上线" / "可以灰度 10% 观察 1 周" / "不能上线，修复后重验"。
- **示例片段**：
  ```
  【验收结论】

  □ 通过：所有硬门槛达标，无 S1/S2 bug，可以上线
  ☑ 有条件通过：硬门槛达标，有 {N} 个 S2/S3 bug 不阻塞上线，限期修复
  □ 不通过：有 S1 阻断或硬门槛未达，不能上线

  【遗留问题清单】
  | 严重度 | 问题 | 负责人 | 修复期限 |
  |---|---|---|---|
  | S2 | 已下线任务用户仍能访问链接（F06） | {姓名} | {日期}，上线前必须修 |
  | S2 | 导出报告含明文手机号（PII） | {姓名} | {日期}，上线前必须修 |
  | S3 | 端到端 P95 时延 5.8 秒（门槛 5 秒） | {姓名} | 下版本优化 |
  | S3 | 引用拒答误拒率 6%（门槛 5%） | {姓名} | 下版本优化 |
  | P2 | 手机端主按钮截断（375px） | {姓名} | 下版本 |

  【上线建议】
  ① {S2 两个问题必须在上线前修复并回归验证}；
  ② 修复后可灰度 {10%} 流量观察 {1} 周，重点看 AI 时延和误拒率；
  ③ 灰度期间监控：AI 调用失败率、用户投诉率、时延 P95；
  ④ 如灰度无异常，{1} 周后全量。

  【签字】
  PM：______  QA：______  业务 Owner：______  客户验收（E 类）：______
  日期：______
  ```

## 四、不同产品类别的差异化要点

### A 类（对话式 AI / Agent 产品）
- **AI 能力验收占比最大**——3.5 章是核心，UI/功能/接口只占一小块。
- **必须验的 AI 项**：①角色遵循率（不跳出角色、不泄露答案）；②多轮上下文保持（第 N 轮还记得第 1 轮的信息）；③拒答边界（该拒的拒、不该拒的不拒）；④Tool use 成功率（调用工具对不对）；⑤Prompt 注入抗性（用户诱导 AI 跳出角色）。
- **pass³ 稳定性**：红线题和关键题要跑 3 次，3 次全过才算过（参考《评测报告 SKILL》）。
- **端到端**要验"多轮对话"——不是单轮，是连续 5-10 轮的完整对话。

### B 类（RAG 知识库 / 问答产品）
- **AI 能力验收重点**：①Recall@5（黄金问题集命中有效知识）；②引用正确率（来源真、位置准、支持结论）；③拒答正确率（无答案时说"不知道"而不是编）；④权限过滤生效（不同 org 不能越权）。
- **3.5.3 引用溯源**是 B 类的核心验收项，不能省。
- **知识更新**要验：新增知识后多久能被召回？下线知识是否立即不出现？
- **数据回流**要验：用户纠错是否不自动回写生产 RAG（必须走脱敏→标注→审批→回归流程）。

### C 类（AIGC 多模态生成产品）
- **AI 能力验收重点**：①生成质量人工盲评通过率（不能只靠脚本）；②多模型 fallback 切换（主模型失败时是否自动切备用）；③成本控制（单次生成成本是否在预算内）；④风格一致性（同一 prompt 多次生成风格是否一致）。
- **人工盲评**要组织 2-3 个评委双盲打分，通过率 ≥80% 才算过。
- **多模型 fallback**要验：主模型超时/报错时，是否自动切备用模型，用户无感知。
- **Truth Base**要验：全局事实（投资总额/技术参数）是否一字不改地体现在生成结果里。

### D 类（AI 评测平台 / 内部工具）
- **AI 能力验收重点**：①评测集覆盖度（是否覆盖所有场景/边界/红线）；②自动评分准确率（LLM-as-Judge 与人工一致率）；③bad case 闭环流程（提的 bad case 是否真的被修、修完是否回归）。
- **3.5.1 一致率**是 D 类的核心——Judge 和人工打分为主。
- **评测效率**要验：标注员平均每题花多少时间、比上一版快了多少。
- **版本对比**要验：新版本上线后，老版本指标是否退化（回归监控）。

### E 类（B 端 SaaS / 传统产品 AI 化）
- **传统功能验收为主**——UI（3.1）、功能（3.2）、链路（3.3）、接口（3.4）占验收表 70% 以上。
- **AI 能力只占一小块**（3.5 裁剪到 30%），且重点不是"AI 多准"，而是"**AI 建议是否标注为建议、不直接改写正式数据**"。
- **B 端特有验收**：①客户侧验收人签字（客户不签字不算完）；②与现有系统集成（ERP/CRM/SSO）；③数据权限（不同 org 隔离）；④私有化部署（如果是）。
- **状态机验收**要特别细——B 端审批流（草稿→审核→发布→下线→归档）每个状态跳转都要验。
- **越权测试**是 B 端生死线——客户对越权泄露零容忍，出一次就可能丢单。
