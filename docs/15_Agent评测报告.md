# 【Agent 评测报告】SKILL

> **适用产品类别**：**A 为主**（对话式 AI / Agent 产品——这是 Agent 评测报告的原生场景：多轮对话、Tool use、长期记忆、人设遵循、主动触发，每一项都需要专门的评测维度）；**B 为辅**（RAG 知识库 / 问答产品——在 A 类基础上叠加引用溯源、检索召回、无答案拒答等 RAG 专项维度）；**D 为辅**（AI 评测平台 / 内部工具——这份报告本身就是平台的核心产出物，重点在评测集迭代记录与 Judge 准确性校验）。C 类 AIGC 生成产品若涉及 Agent 编排（多步生成、工具调用、fallback）也适用；E 类 B 端 SaaS AI 化一般不单独写 Agent 评测报告，引用 D 类平台结论即可。
> **文档目的**：把"这版 Agent 能不能上线、比上版好多少、卡在哪、回去改什么"一次性讲清楚，让决策者能直接做 Go/No-Go 判断，让研发/算法能直接拿 bad case 回去定位到 Workflow 节点、Prompt 段落或工具接口。读者是 PM、算法/研发负责人、QA、业务决策者、Agent 平台 Owner。
> **撰写时机**：①Agent / Workflow / Prompt 每轮回归后（版本对比）；②上线前最终放行评测；③新 Agent 从 0→1 首次离线评测；④线上出现大面积 bad case 后做专项归因。这是一份**决策文档 + 归因文档**，不是数据归档——每一条结论都必须能指着某道题、某个 Workflow 节点讲。

## 一、撰写前需要收集的资料清单

### 1.1 评测元信息（必须先钉死，否则后面所有数字都没意义）
- **Agent 标识**：Agent 名称、Agent 版本号、Workflow 版本号、节点拓扑（几个 LLM 节点、几个工具节点、几个条件分支）
- **Prompt 版本**：System Prompt 版本号、每个节点的 User Prompt 模板版本、Few-shot 示例版本
- **模型版本**：每个 LLM 节点用的模型名 + 版本号（如 `{模型名}-{日期}`）、温度、top_p、max_tokens
- **工具版本**：每个 Tool 节点调用的工具名、接口版本、是否为模拟接口 / 真实接口
- **知识库版本**：RAG 类 Agent 必须写清知识库名称、版本号、切片策略、索引构建时间
- **评测集信息**：评测集名称、版本号、题量、是否含金标、是否含关键考察点、是否含多轮对话历史
- **执行环境**：线上 / 预发 / 本地脚本 / Workflow 编辑器；每题是否独立新会话；是否关闭随机缓存
- **评测方式**：人工盲评 / LLM-as-Judge / 脚本自动判定 / 三者混合
- **评分量尺**：二值通过 / 0-2 分 / 1-5 分 / GSB（Good-Same-Bad）
- **评测人**：人数、是否交叉盲评、是否双标 + 仲裁
- **执行时间窗口**：起止日期，是否跨了模型供应商的静默升级

### 1.2 评测执行数据
- 总通过率、平均分、各维度得分
- **pass³ 执行情况**：哪些题跑了 3 次、哪些题只跑了 1 次、哪些题因为限流 / 超时没跑完
- 本轮 vs 上轮 vs 基线（至少三版：初次 / 重跑基线 / 最终回归）
- 逐题结果表：ID / 题目 / 本轮结果 / 上轮结果 / 变化 / 一句话说明
- Workflow trace 日志：每个 LLM 节点的输入 / 输出 / tool call 入参 / tool 返回值 / 耗时 / token 消耗
- Goodcase 原始素材：输入 prompt / 多轮历史 / 完整输出 / 截图或链接
- Badcase 原始素材：同上 + 完整对话轨迹 + Workflow 节点流转图 + 工具调用日志

### 1.3 归因侧（这是 Agent 评测区别于传统测试的核心）
- 每个未通过题的失败环节：路由错 / 分类错 / 检索没召回 / Prompt 漏写 / 模型能力不够 / Tool 入参错 / Tool 返回错 / 多轮状态丢失 / 角色跳出 / 拒答边界错
- 四类归因标签：**数据缺失 / 检索没召回 / Prompt 没写清 / 模型能力不够**（多因素叠加要拆多行）
- 已做的修复动作：改了哪段 Prompt 的哪个段落、加了哪个 Workflow 节点、接了哪个工具、降了温度、换了模型
- 复测结果：修复后是否通过 pass³、是否在真实接口环境下重跑
- 是否依赖模拟节点：哪些题的通过是靠 mock 数据撑的，上线前必须替换

### 1.4 决策侧
- 这次评测要回答的核心问题：能不能上线 / 哪个版本好 / 哪个环节有问题 / 该换模型还是该改 Prompt
- 硬门槛：红线题一票否决（安全 / 合规 / 越权 / 严重幻觉 = 0 容忍）
- 上线前还缺什么：真实接口替换 / 权限审计 / 超时兜底 / 评测集补题 / pass³ 补跑
- 不通过时的退路：降级为异步 / 转人工 / 不进入下一阶段

## 二、资料来源渠道

| 资料类型 | 推荐渠道 |
|---|---|
| 评测集与金标 | 评测集表格（飞书多维表格 / sheet）、评测标准文档、金标标注手册 |
| 逐题结果与 trace | Agent 评测平台导出、Workflow 运行日志、LangSmith / Langfuse / 自研 trace 后台 |
| Goodcase / Badcase 素材 | 评测平台任务可视化地址、会话 ID 反查、录屏、截图、原始 JSON 输出 |
| 版本对比 | 变更日志、Prompt diff（git）、Workflow 发布记录、模型供应商版本公告 |
| 归因分析 | Workflow trace 逐节点对比、检索日志（召回了哪些 chunk）、工具调用日志、人工复盘会 |
| pass³ 数据 | 评测平台"多次运行"功能、同一题三次独立会话的结果对比表 |
| 上线建议 | PM / 算法 / QA / 业务 Owner 四方对齐会纪要 |
| 线上 bad case 回流 | 客服工单、用户点踩日志、线上告警、VOC 系统 |

> **铁律**：所有数字必须可回溯到评测集版本和 Workflow 版本——不是"大概 50%"，而是"50 题中 30 题通过 pass³，60%"；所有结论必须能指着某道题的某个 Workflow 节点讲，不能凭感觉。如果一次评测的结果无法被另一个人用同一套评测集 + 同一版本 Workflow 复现，这份报告就是废纸。

## 三、完整框架结构（到三级标题）

> 以下 11 章骨架融合自真实 Agent 项目的离线评测报告、上线放行报告、专项 bad case 复盘报告。**第 1、2、3、4、5、6、7、10、11 章是任何 Agent 评测都不能省的**；第 8 章（四类归因法详解）和第 9 章（版本对比与优化清单）是 Agent 报告区别于通用评测报告的灵魂。

### 3.1 评测基础信息（元信息页）

- **这一节写什么**：一页表头把"这是哪次评测、在评什么、用什么评、怎么判、谁判的"讲清。读者第一眼就要能判断这份报告的可信度。
- **颗粒度要求**：至少 12 个字段——Agent 名 / Agent 版本 / Workflow 版本 / Prompt 版本 / 模型版本 / 工具版本 / 知识库版本 / 评测集 / 执行方式 / 判定口径 / 评测日期 / 评测人。**必须显式写清"哪些题做了 pass³、哪些没做"**。
- **填写要点**：
  - 执行方式要具体到"每题开启独立新对话、清空多轮历史、在已发布的 {Workflow 名} 中发送原题并等待运行成功"，不能只写"跑了一遍"。
  - 判定口径要引用评测集里的"怎么算过"那一列，不要在报告里另立标准。
  - 如果跨了模型供应商的静默升级窗口，必须标注"本次评测期间 {模型} 于 {日期} 发生版本更新，前后结果可能不可比"。
- **示例片段**：
  ```
  | 字段 | 值 |
  |---|---|
  | 评测对象 | {客服 Agent} v{X.Y} / Workflow {W-编号} v{Z} |
  | Prompt 版本 | System Prompt v{P}；节点 {分类器} Prompt v{P1}；节点 {回答生成} Prompt v{P2} |
  | 模型版本 | 分类器：{模型 A}-{日期}，temperature=0；回答生成：{模型 B}-{日期}，temperature=0.3 |
  | 工具版本 | {实时查询}：{模拟接口 v1}；{转人工}：{固定话术库 vK} |
  | 知识库版本 | {产品知识库} v{KB-编号}，索引构建于 {YYYY-MM-DD} |
  | 评测集 | {Agent 评测集 vN}，正式计分 {50} 题 |
  | 执行方式 | 每题独立新会话，关闭历史缓存，等待 Workflow 运行成功后人工判定 |
  | 判定口径 | 按评测集"{怎么算过}"列逐题核对关键事实、流程、追问、拒答边界 |
  | 评分量尺 | 二值通过（pass / fail）；红线题一票否决 |
  | 评测日期 | {YYYY-MM-DD} 至 {YYYY-MM-DD} |
  | 评测人 | {N} 人，交叉盲评 {是/否}，争议题 {M} 道由 {第三方} 仲裁 |
  | pass³ 执行 | {50} 题全部跑了 3 次；{0} 题仅跑 1 次 |
  ```

### 3.2 核心结论（一句话胜负）

- **这一节写什么**：开篇用 1-3 句话告诉读者"这版能不能上线、通过率多少、主要问题在哪、建议是什么"。这是决策者唯一会仔细读的段落。
- **颗粒度要求**：必须包含四个要素——本轮通过率（X/Y=Z%）、比上轮变化（+/- N 题 / +/- M 个百分点）、主要问题集中在哪个环节、明确判断（可以上线 / 不建议上线 / 先修 X 再评 Y）。
- **填写要点**：
  - 结论必须能被后面的数据直接支撑，不能开空头支票。
  - 如果结论是"暂缓"，必须说出暂缓在哪个环节、什么时候复评、复评看什么指标。
  - **禁止写"建议进一步观察"这种和稀泥的话**——要么能上、要么不能上、要么附条件能上。
- **示例片段**：
  > **本轮通过率：{38/50 = 76%}**（pass³ 口径，3 次全过才算过）；上轮基线 {30/50 = 60%}，本轮提升 8 题、16 个百分点。
  >
  > 当前主要问题集中在三个环节：①**多轮追问类**（{退款流程、未成年充值、封号申诉}），Agent 拿到问题后未按 SOP 追问关键信息直接转人工；②**实时查询类**（{查信誉分、查服务器状态}），路由到了查询分支但工具入参缺失，返回空结果；③**拒答边界类**（{外挂、代练、赌博引导}），拒了但没给处罚规则。
  >
  > **结论**：{有条件上线}。{38} 题 pass³ 通过；剩余 {12} 题中 {8} 题已定位到 Prompt 段落可在本周修复，{4} 题依赖 {真实接口替换}。建议：①本周修复 8 道 Prompt 类问题并重跑 pass³；②{真实接口}上线后对 {4} 道接口类题补跑 pass³；③全部通过后再发布全量。

### 3.3 五步评测框架（这是 Agent 评测的灵魂）

- **这一节写什么**：把一次 Agent 评测从"拍脑袋跑一遍"升级到"可复现、可对比、可归因"的标准流程。五步走：**定目标 → 定标准 → 建评测集 → 打分 → 找原因**。
- **颗粒度要求**：每一步写清"这步要产出什么、谁负责、什么时候完成"；不能只写方法论口号。
- **填写要点**：
  - **第一步定目标**最容易被跳过——很多团队一上来就跑题，跑完才发现"这题根本不是这次要测的"。目标必须是一个可回答的问题："这版能不能上线？" / "A 模型 vs B 模型哪个好？" / "第 3 节点为什么老出错？"
  - **第二步定标准**要先于跑题——"怎么算过"必须写进评测集，不能跑完再回头定。
  - **第四步打分**：人工盲评、LLM-as-Judge、脚本判定各有适用场景，不能全靠一种。
- **示例片段**：

  | 步骤 | 要回答的问题 | 产出物 | Owner | 何时完成 |
  |---|---|---|---|---|
  | 第一步：定目标 | 这次评测要回答什么？ | 一句话评测目标 + 上线门槛数字 | PM | 跑题前 1 周 |
  | 第二步：定标准 | 怎么算过、怎么算不过？ | 评测集"怎么算过"列 + 红线清单 | PM + 业务专家 | 跑题前 1 周 |
  | 第三步：建评测集 | 用什么题测？ | 评测集 vN，含金标、考察点、难度分层 | PM + 标注员 | 跑题前 3 天 |
  | 第四步：打分 | 每题结果是什么？ | 逐题结果表 + pass³ 三次结果 | 评测执行 + Judge | 跑题当周 |
  | 第五步：找原因 | 为什么错？怎么修？ | Bad case 五段式归因表 + 修复清单 | PM + 算法 + 研发 | 跑题后 3 天 |

  > **第一步：定目标**示例——
  > 本次评测目标：判断 {客服 Agent v2.3} 是否达到上线门槛。上线门槛：①pass³ 通过率 ≥ {90%}；②红线题（{安全/越权/违规指导}）通过率 {100%}；③多轮状态保持正确率 ≥ {85%}；④Tool use 成功率 ≥ {95%}。任一不达标即不能上线。
  >
  > **第二步：定标准**示例——
  > 每道题必须列出"关键考察点"（3-5 个），例如退款题的考察点：①是否先追问充值时长；②是否追问钻石是否使用；③是否追问是否未成年；④是否按 {7 天/未使用/每年 1 次}规则回答；⑤是否给出申诉入口。**5 个考察点全满足才算过**，缺任意一个即 fail。

### 3.4 通过率总览（本轮 vs 上轮 vs 基线三版对比）

- **这一节写什么**：把至少三版通过率摆在一起——初次 / 重跑基线 / 最终回归——让读者一眼看出"这轮优化到底改了什么"。
- **颗粒度要求**：表格列必须含：版本 / 通过题数 / 通过率 / pass³ 通过率 / 主要问题 / 说明；通过率变化要算出绝对差值（+/- 题数、+/- 百分点）。
- **填写要点**：
  - 不要只放最终版——初次和基线能看出"优化前后的差距"。
  - **pass³ 通过率和单次通过率要分开列**——单次过了但 pass³ 没过的题，本质上还是不稳定。
  - 如果本轮是最终放行，必须写"是否通过全部硬门槛"。
- **示例片段**：

  | 版本 | 通过题数（单次） | 单次通过率 | pass³ 通过题数 | pass³ 通过率 | 主要问题 | 说明 |
  |---|---|---|---|---|---|---|
  | 初次测试 v2.0 | {20/50} | {40%} | {15/50} | {30%} | 分类器路由错、无追问、无实时查询 | 原始 Workflow |
  | 重跑基线 v2.2 | {30/50} | {60%} | {25/50} | {50%} | 追问缺失、拒答话术不全 | 未做本轮优化前 |
  | 最终回归 v2.3 | {45/50} | {90%} | {38/50} | {76%} | 4 题依赖真实接口未接 | 发布优化版后完整重跑 |

  > **关键发现**：单次通过率 90% 看着漂亮，但 pass³ 通过率只有 76%——{7} 道题存在"3 次中过 1-2 次"的不稳定现象，这些题在生产环境里就是定时炸弹。**上线决策必须基于 pass³ 通过率，不是单次通过率**。

### 3.5 pass³ 稳定性专节（Agent 评测必须跑 3 次）

- **这一节写什么**：Agent 评测不能只跑一遍——LLM 有随机性，一次过可能是抽卡运气好。**同一道题在同一版本下独立新会话连跑 3 次，3 次全过才算真过（pass³）；3 次中任一失败 = 不稳定，归入 bad case**。
- **颗粒度要求**：必须列清三件事——①哪些题做了 pass³；②哪些题只跑了 1 次（标注"上线前需补跑"）；③不稳定题清单（3 次中 ≥1 次失败的题，列出 ID + 失败模式）。
- **填写要点**：
  - pass³ 是 Agent 评测和传统测试最大的区别——传统 Bug 是确定性的，Agent 的输出是概率性的。
  - 温度越高的节点越要跑 pass³；temperature=0 的节点稳定性会显著好于 temperature=0.7 的节点。
  - **如果本次评测没做 pass³，不要假装做了**——直接写"本次为单次评测，稳定性待验证，上线前必须补跑"。
- **示例片段**：
  > **稳定性口径（pass³）**：每道正式计分题在同一 Workflow 版本、同一 Prompt 版本、同一模型版本下，开启独立新会话、清空多轮历史，连跑 {3} 次。{3 次全过}记为通过；{3 次中任一失败}记为不稳定，归入 bad case 并附三次输出链接。
  >
  > **本次执行情况**：
  > - 已完成 pass³ 的题：{T01-T50 全部 50 题}
  > - 仅跑 1 次的题：{T41-T45 因模型接口限流仅跑 1 次，上线前需补跑}
  > - 不稳定题（3 次中 ≥1 次失败）：
  >
  > | 题 ID | 3 次结果 | 失败模式 |
  > |---|---|---|
  > | T12 | 过 / 过 / fail | 第 3 次未追问"是否未成年" |
  > | T23 | 过 / fail / 过 | 第 2 次 Tool 入参传错（把"查信誉分"传成了"查余额"） |
  > | T31 | fail / 过 / fail | 拒答时话术随机，有时给了处罚规则有时没给 |
  >
  > **结论**：{T12、T23、T31} 三道题虽然单次能过，但稳定性不达标。其中 {T12、T31} 可通过降低节点温度 + 在 Prompt 里加硬性检查清单解决；{T23} 需要在 Tool 入参层加 Schema 校验。

### 3.6 逐题结果表

- **这一节写什么**：每道题一行，写清本轮结果（pass³ 口径）和一句说明。这是研发回去找问题的索引页。
- **颗粒度要求**：列至少含 {ID} / {题型} / {本轮单次结果} / {pass³ 结果} / {上轮结果} / {变化} / {说明}；题量 ≥50 道（A 类 Agent）。
- **填写要点**：
  - 通过的题写"通过"即可，不要凑字数。
  - 未通过的题必须写清"缺了什么关键考察点"，不能只写"未通过"。
  - pass³ 不稳定的题要单独标注"△"符号，让读者一眼看到。
- **示例片段**：

  | ID | 题型 | 单次结果 | pass³ 结果 | 上轮 | 变化 | 说明 |
  |---|---|---|---|---|---|---|
  | T01 | 事实型 | 通过 | 通过 | 通过 | — | 通过 |
  | T02 | 流程型 | 通过 | 通过 | fail | ↑ | 已补追问话术 |
  | T12 | 流程型（退款） | 通过 | **△ 不稳定** | fail | ↑ | 3 次中第 3 次未追问未成年 |
  | T23 | Tool use | 通过 | **△ 不稳定** | fail | ↑ | Tool 入参偶发传错 |
  | T31 | 拒答边界 | 通过 | **△ 不稳定** | fail | ↑ | 拒答话术随机 |
  | T41 | 实时查询 | fail | fail | fail | — | 依赖模拟接口，未接真实接口 |
  | T50 | 红线题 | 通过 | 通过 | fail | ↑ | 已加安全护栏 |

### 3.7 Bad case 五段式归因（每个 bad case 必须五段）

- **这一节写什么**：对每个未通过或不稳定的题，按"**现象 → 轨迹 → 归因 → 修复 → 复测**"五段写清，而不是只写"错了"。这是评测报告区别于"成绩单"的关键——它让研发知道回去改哪里。
- **颗粒度要求**：每个 bad case 必须有完整五段；归因必须落到四类之一（数据缺失 / 检索没召回 / Prompt 没写清 / 模型能力不够）；多因素叠加要拆多行；修复动作必须具体到"改了哪段 Prompt 的哪个段落 / 加了哪个 Workflow 节点 / 接了哪个工具的哪个接口"。
- **填写要点**：
  - **现象**：用户问了什么、Agent 怎么回的、错在哪（具体到缺了哪个考察点）。
  - **轨迹**：完整 Workflow 节点流转——用户提问 → 分类器路由到哪个分支 → 检索了什么 → Tool 调了什么 → 哪个节点生成的回答。要能指着 trace 日志讲。
  - **归因**：四类之一，多因素拆多行。
  - **修复**：动作要可执行——"在 System Prompt 第 3 条加硬性追问清单"而不是"优化了 Prompt"。
  - **复测**：修复后是否通过 pass³，附复测结果链接。
- **示例片段**：

  **Bad case：T12 退款题**
  - **现象**：用户问"我能退款吗"，Agent 直接转人工，未先追问"充值时长、钻石是否使用、是否未成年"三个关键信息。
  - **轨迹**：用户提问 → 分类器路由到"转人工"分支（概率 0.85）→ 直接返回人工入口话术。**未进入"退款流程追问"分支**。
  - **归因**：
    - {Prompt 没写清}——主 Prompt 未强制"退款类问题必须先追问三要素"，只写了"复杂问题转人工"。
    - {Prompt 没写清}——分类器 Prompt 缺"退款流程追问"这个类别，把"退款"直接归到"转人工"。
  - **修复**：①主 Prompt 第 3 条加硬性追问清单："收到退款类问题，必须先追问：充值时长、钻石使用情况、是否未成年，再按规则回答"；②分类器新增"退款流程追问"类别，temperature 从 0.3 降为 0；③补齐"7 天/未使用/每年 1 次"规则话术。
  - **复测**：修复后 T12 跑 pass³ 三次全过；三次输出均先追问三要素再按规则回答。复测结果链接：{链接}。

  **Bad case：T23 查信誉分题**
  - **现象**：用户问"我现在信誉分多少"，Agent 调了 Tool 但入参传错（把"credit_score"传成了"balance"），返回了余额而不是信誉分。
  - **轨迹**：用户提问 → 分类器路由到"实时查询"分支 → LLM 节点生成 Tool call 入参 → 入参 schema 未校验 → Tool 返回错误数据 → 直接拼进回答。
  - **归因**：
    - {Prompt 没写清}——Tool 描述里没写清入参的枚举值，LLM 自由发挥。
    - {其他类：代码 bug}——Tool 调用层未加 Schema 校验，错误入参直接放行。
  - **修复**：①Tool 描述中入参枚举值写死：`query_type ∈ {credit_score, server_status, ban_reason}`；②Tool 调用层加 JSON Schema 校验，非法入参直接重试；③LLM 节点 temperature 降为 0。
  - **复测**：修复后 T23 pass³ 三次全过。但当前返回的是{教学测评用模拟数据}，上线前需替换为真实接口并重新验证权限/超时/异常。

### 3.8 四类归因法详解（Agent 评测的核心方法论）

- **这一节写什么**：把所有 bad case 按四类归因法分类统计，给出每类的典型案例模式、识别方法、修复路径。这是让"找原因"从玄学变成方法论的关键。
- **颗粒度要求**：每类给 3-5 个典型案例模式 + 识别方法 + 修复路径；最后给一张归因占比统计表。
- **填写要点**：
  - **数据缺失类**：知识库 / 规则 / 参数没配全——这类问题最好修，补数据就行。
  - **检索没召回类**：RAG 没召回到正确文档——要区分"完全没召回"和"召回了但没排上来"。
  - **Prompt 没写清类**：System Prompt / 节点 Prompt 有歧义、缺约束、缺硬性检查清单——Agent 问题的头号原因。
  - **模型能力不够类**：模型本身理解 / 生成 / 推理 / Tool 调用能力不足——这类问题改 Prompt 没用，要换模型或加规则引擎兜底。
- **示例片段**：

  | 归因类别 | 典型案例模式 | 识别方法 | 修复路径 |
  |---|---|---|---|
  | **数据缺失** | ①知识库没收录最新版本规则；②话术库缺某个场景的固定回答；③参数表缺某类商户的费率 | 把"应该召回的正确文档/规则"手动塞给 Agent，Agent 答对了 → 说明是数据没配，不是模型不行 | 补录知识库、补话术、补参数；走审批流程发布 |
  | **检索没召回** | ①完全没召回到相关文档（top-5 全不相关）；②召回了但排在第 6 名以后（被 Rerank 漏掉）；③召回到了但 chunk 切分把关键句子切碎了 | 把同一道题用 BM25 / 向量 / Rerank 分别跑一遍，看是哪一层丢的 | 调切片策略、加 query 改写、换 Rerank 模型、加元数据过滤 |
  | **Prompt 没写清** | ①System Prompt 只写了"你是一个专业助手"，没写边界；②节点 Prompt 缺硬性检查清单；③Few-shot 示例太少导致 LLM 自由发挥；④Prompt 里有歧义表述 | 把 Prompt 逐句读一遍，问自己"如果我是 LLM，这句话会不会有多种理解" | 加硬性约束、加检查清单、加 Few-shot、降温度 |
  | **模型能力不够** | ①多步推理算错数（如 720+680=1400 算成 1300）；②Tool call 格式错（JSON 非法）；③多轮对话第 5 轮后忘记用户开头说的信息；④复杂指令只遵循了前 2 条 | 把同一个问题喂给多个模型，如果都错 → 是任务本身超出能力；如果只有 A 错 B 对 → 换模型 | 换更强模型、加规则引擎做确定性计算、加摘要节点压缩多轮历史 |

  > **本次评测归因占比**：
  >
  > | 归因类别 | bad case 数 | 占比 | 已修复 | 未修复 |
  > |---|---|---|---|---|
  > | 数据缺失 | {3} | {25%} | {2} | {1}（等待业务方补录） |
  > | 检索没召回 | {1} | {8%} | {0} | {1}（需调 Rerank） |
  > | Prompt 没写清 | {6} | {50%} | {6} | {0} |
  > | 模型能力不够 | {2} | {17%} | {1}（加规则引擎） | {1}（待换模型评估） |
  >
  > **关键洞察**：{50%} 的 bad case 都是 Prompt 没写清——这意味着 Agent 问题的头号解法不是换模型，而是把 Prompt 写清楚。这也是为什么第 3.3 节"五步评测框架"里"定标准"和"打分"之间必须有一个 Prompt 评审环节。

### 3.9 版本对比与优化清单（已完成的优化 / 上线前必须做的）

- **这一节写什么**：把本轮做了哪些修复、对应解决了哪些题列成一张清单；同时把还没修的题列成下一步动作。这是给研发和算法的 to-do list。
- **颗粒度要求**：已完成清单 5-10 条，每条对应"改了什么 / 解决了哪些题 / 复测结果"；待办清单要写"上线前必须做"，每条给 Owner 和截止时间。
- **填写要点**：
  - 已完成清单不要写"优化了 Prompt"，要写"固化了 {版本数字、价格、充值限额、退款条件} 等 {N} 条事实"。
  - 待办清单要暴露"当前版本依赖模拟节点"这种上线风险，不要藏着。
  - 每条待办必须有 Owner 和截止时间，否则就是空头支票。
- **示例片段**：
  > **本轮已完成的优化**：
  > 1. 重写主客服 Prompt，固化 {版本数字、价格、充值限额、退款条件、计算规则} 共 {N} 条事实。（解决 T02、T05、T18、T22）
  > 2. 分类器新增 {退款流程追问、实时查询、转人工} 三个类别，temperature 从 0.3 降为 0。（解决 T12、T15、T23）
  > 3. 新增 {实时查询（模拟接口）} 代码节点及结果回复节点，覆盖 {服务器状态、当前信誉分、封号原因}。（解决 T15、T23）
  > 4. 补齐 {外挂处罚、防沉迷时间窗口、未成年退款材料、封号申诉入口、3 个工作日回复} 等固定话术。（解决 T17、T31、T35）
  > 5. 增加回答边界，禁止输出 {分类标签、检索过程、文件名、内部资料名称}。（解决 T40）
  >
  > **上线前必须完成**：
  >
  > | 待办 | Owner | 截止时间 |
  > |---|---|---|
  > | 将 {模拟查询节点} 替换为真实生产接口 | {研发 A} | {YYYY-MM-DD} |
  > | 对 T13-T15、T41-T45 五道依赖接口的题补跑 pass³（真实接口环境） | {QA B} | 接口替换后 2 天内 |
  > | 红线题复跑一次（安全/拒答类） | {安全 C} | 上线前 1 天 |
  > | 知识库补录 {最新版本规则} | {业务 D} | {YYYY-MM-DD} |

### 3.10 结论与上线建议（明确判断，不和稀泥）

- **这一节写什么**：基于数据和归因，明确给出"能不能上线 / 先修哪块 / 什么时候复评"的建议。
- **颗粒度要求**：必须给出明确判断（Go / No-Go / Conditional Go）；如果有条件放行，写清条件、Owner、复评时间；必须显式提示"依赖模拟节点 / 待接真实接口 / 待补 pass³"等上线风险。
- **填写要点**：
  - 三种判断：**Go**（全部硬门槛达标，可直接上线）；**Conditional Go**（核心指标达标，但有 N 项上线前必须完成的待办）；**No-Go**（硬门槛未达，退回修复，给复评时间）。
  - 禁止写"建议进一步观察"——这不是判断，是逃避。
  - 如果是 No-Go，必须说出"卡在哪个指标、差多少、预计什么时候能补上"。
- **示例片段**：
  > **复测结论**：{50} 道题中 {38} 道通过 pass³，pass³ 通过率 {76%}；{7} 道题单次通过但 pass³ 不稳定；{5} 道题仍 fail（其中 {4} 道依赖真实接口、{1} 道知识库待补）。
  >
  > **上线建议：Conditional Go（有条件上线）**
  >
  > 满足以下条件后可发布全量：
  > 1. {T13-T15、T41-T45} 五道题在真实接口环境下补跑 pass³ 全过；
  > 2. {T12、T23、T31} 三道不稳定题的 Prompt 修复后 pass³ 全过；
  > 3. 红线题（{安全/越权/违规指导}）复跑 100% 通过；
  > 4. 知识库补录 {最新版本规则} 并重新索引。
  >
  > **预计复评时间**：{YYYY-MM-DD}（接口替换后 3 天）。
  >
  > **风险提示**：当前 {T13-T15} 的通过依赖{模拟查询节点}，返回的是{教学测评用模拟数据}，不是生产接口。**在真实接口替换并补跑 pass³ 之前，这 5 道题的"通过"不计入上线依据**。

## 四、不同产品类别的差异化要点

### A 类（对话式 AI / Agent 产品）
- **这是本 SKILL 的主适用类别**，11 章全部写全。
- **重点加厚的评测维度**：
  - **多轮状态保持**：第 5 轮以后是否还记得第 1 轮的关键信息（用户姓名、场景、约束）。
  - **角色遵循率**：是否跳出角色、是否泄露答案 / 评分标准 / 内部规则。
  - **Tool use 成功率**：工具调用是否成功、入参是否正确、返回是否被正确使用。
  - **拒答边界**：红线问题是否识别、拒答话术是否合规。
  - **Prompt 注入抗性**：用户试图绕过角色 / 泄露系统提示时是否守住。
- **pass³ 必须做**：A 类 Agent 的输出随机性最大，不跑 3 次等于没测。
- **归因重点**：{Prompt 没写清}通常占 50% 以上——先把 Prompt 写清楚再谈换模型。

### B 类（RAG 知识库 / 问答产品 Agent）
- 在 A 类基础上叠加以下专项维度：
  - **引用溯源正确率**：回答引用的 source_id 是否真实存在、是否能支持结论。
  - **检索召回率（Recall@k）**：golden chunk 是否在 top-k 内被召回。
  - **无答案拒答率**：知识库没有答案时是否说"不知道"，还是硬编。
  - **权限过滤正确率**：不同 org / 不同角色的知识是否被正确隔离。
- **归因重点**：{检索没召回}类 bad case 占比会显著高于 A 类；要区分"完全没召回"和"召回了但 Rerank 没排上来"。
- **第 3.8 节四类归因法**要展开"检索没召回"的子分类：BM25 没召 / 向量没召 / Rerank 漏排 / chunk 切分错误 / 元数据过滤过严。

### C 类（AIGC 多模态生成产品 Agent）
- 如果 C 类产品只是"单轮生成图片/视频"，不建议用本 SKILL——用 07 评测报告的范式 A（模型选型）更合适。
- 如果 C 类产品涉及 **Agent 编排**（多步生成、提示词组装、多模型 fallback、质量门禁），则适用本 SKILL，但重点维度改为：
  - **提示词组装正确性**：Role + Global Context + Current Task + Constraints 是否拼对。
  - **多模型 fallback 切换**：主模型失败时是否正确切到备用模型。
  - **生成结果质量**：用人工盲评（1-5 分）而不是二值通过。
  - **成本与延迟**：单次生成的 token 消耗、API 成本、端到端延迟。
- **pass³ 对生成类产品意义有限**——因为每次生成本来就是随机的，跑 3 次看的是"质量稳定性"而不是"是否通过"。

### D 类（AI 评测平台 / 内部工具）
- 这份报告本身就是平台的核心产出物——重点不是"评某个 Agent"，而是"评测平台本身的质量"：
  - **评测集迭代记录**：v1.0 → v1.1 → v2.0 新增/删除/修改了哪些题。
  - **Judge 准确性**：LLM-as-Judge 和人工打分的一致性（Cohen's Kappa）。
  - **bad case 闭环率**：从发现到修复到复测的平均时长。
- **第 3.11 节附录**要加厚：评测集版本管理记录、标注规范、双标一致性数据。
- **归因重点**：如果 Judge 本身打错了，所有结论都不可信——必须先校验 Judge 准确性。

### E 类（B 端 SaaS / 传统产品 AI 化）
- **一般不单独写 Agent 评测报告**——引用 D 类平台的评测结论即可。
- 如果一定要写，重点不是"Agent 能力"，而是"AI 功能是否达到 PRD 里的验收标准"：
  - 对比 PRD 第 3.7.4 节的 AI 评测门槛表，逐项核对是否达标。
  - bad case 以工单系统来源为主，AI 专项 bad case 占比小。
  - 重点标注"AI 建议错误但用户没采纳"这种隐性问题——用户绕过了 AI，说明 AI 不可信。
