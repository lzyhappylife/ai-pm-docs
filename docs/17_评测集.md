# 【评测集】SKILL

> **适用产品类别**：**A/B/C/D 为主**——A 对话式 Agent（评测集是版本回归的标尺）、B RAG 问答（评测集是召回质量的基准）、C AIGC 生成（评测集是 Prompt 模板优化的依据）、D 评测平台（评测集本身就是产品）；E 类 B 端 SaaS AI 化一般不单独建评测集，引用 D 类平台的评测集即可。
> **文档目的**：把"用什么题来评测 AI 产品"这件事系统化——题目从哪来、怎么分布、怎么标注金标、怎么做版本管理，让评测结果**可复现、可对比、可回归**。没有评测集的产品，版本迭代就是"凭感觉调 Prompt"，每次改完不知道是变好还是变坏。读者是 PM（评测集 Owner）、算法（用评测集做回归）、QA（执行评测）、标注员（写金标）。
> **撰写时机**：① Agent / 产品 0→1 阶段，第一版 PRD 出来后就必须建评测集（不是等上线才建）；② 每次版本大迭代前，评测集要同步升级；③ 线上发现新 bad case 后，要把有代表性的补进评测集（形成闭环）。

---

## 一、撰写前需要收集的资料清单

### 1.1 评测集基础信息
- **评测集名称**：如"{客服 Agent 评测集}"
- **目标产品**：评哪个 Agent / 哪个功能
- **评测目的**：版本回归 / 新模型选型 / 上线放行 / 专项归因
- **题量预期**：A 类 ≥50 题、B 类 ≥100 题、C 类 ≥30 组 prompt
- **Owner**：谁负责评测集的维护、版本发布

### 1.2 题目来源素材
- **真实用户日志**：脱敏后的用户 query、对话历史
- **PRD 场景清单**：产品要覆盖的核心场景
- **SOP / 业务规则**：客服话术、审核规则、流程文档
- **竞品题目**：竞品评测中用到的题目
- **对抗样本**：红线、注入、边界 case

### 1.3 金标标注资料
- **标准答案要点**：不是逐字答案，是关键考察点
- **判定标准**：怎么算过、怎么算不过
- **标注员**：谁来标金标（领域专家 / PM / 外包）
- **双标一致性**：Cohen's Kappa ≥0.7 才入库

### 1.4 版本管理资料
- **版本号规则**：v1.0 / v1.1 / v2.0 怎么定
- **变更记录**：新增 / 删除 / 修改了哪些题
- **回归要求**：每次版本更新必须重跑全部评测

## 二、资料来源渠道

| 资料类型 | 推荐渠道 |
|---|---|
| 真实用户 query | 线上日志（脱敏）、客服会话记录、用户访谈 |
| 核心场景清单 | PRD、SOP 文档、业务规则手册 |
| 金标答案 | 领域专家、业务 Owner、人工标注 |
| 竞品题目 | 竞品公开评测报告、竞品 Demo 测试 |
| 对抗样本 | 安全测试团队、红队测试、Prompt 注入库 |
| 题型分布参考 | 07 评测报告、15 Agent 评测报告、RAGAS / CRAG 等公开基准 |
| 版本管理 | 飞书多维表格、Git、评测平台版本功能 |

> **铁律**：评测集的质量决定评测结果的质量。如果评测集里的题是拍脑袋出的、金标是随便写的、版本不管理，那跑出来的通过率数字毫无意义——它只能证明"这个 Agent 在这套破题上表现如何"，不能证明"这个 Agent 在真实用户面前表现如何"。

## 三、完整框架结构（到三级标题）

> 以下 10 章骨架。**第 1、2、3、5、7、8、9 章是任何评测集都不能省的**；第 4 章（输入侧设计）和第 6 章（模型侧结果列）是 Agent / RAG 类评测集的重点；第 10 章（使用说明）是给执行评测的人看的操作手册。

### 3.1 评测集说明（表头页）

- **这一节写什么**：一页纸讲清"这是什么评测集、评什么、给谁用、多久更新一次、Owner 是谁"。
- **颗粒度要求**：至少 8 个字段——名称 / 目标产品 / 用途 / 题量 / Owner / 更新频率 / 当前版本 / 数据范围。
- **填写要点**：
  - **用途要写清**：是"版本回归用"还是"新模型选型用"——两种用途的题目侧重点不同。
  - **数据范围**：只评 {客服 Agent} 的 {退款流程} 模块，还是评整个 Agent。
  - **更新频率**："每版本发布后 3 天内更新"而不是"持续更新"。
- **示例片段**：
  ```
  | 字段 | 值 |
  |---|---|
  | 评测集名称 | {客服 Agent 评测集} |
  | 目标产品 | {客服 Agent v2.x} |
  | 用途 | 版本回归 + 上线放行 |
  | 正式计分题量 | {50} 题（A 类 Agent 下限） |
  | Owner | {PM 姓名} |
  | 更新频率 | 每版本发布后 3 天内更新；线上 bad case 每周同步 |
  | 当前版本 | v{1.2}（{YYYY-MM-DD} 发布） |
  | 数据范围 | 只覆盖 {客服} 场景；不含 {写作助手}、{知识库问答} |
  | 表地址 | {飞书多维表格链接} |
  ```

### 3.2 评测集设计原则（出题的方法论）

- **这一节写什么**：出题不是拍脑袋——有四条设计原则必须遵循：覆盖核心场景、难度分层、题型分布合理、题量达标。
- **颗粒度要求**：每条原则给"为什么" + "怎么做" + "反面教材"。
- **填写要点**：
  - **覆盖核心场景**：题必须来自真实用户会问的问题，不是 PM 自己想象的问题。
  - **难度分层**：易 / 中 / 难都要有——全是简单题测不出上限，全是难题测不出底线。
  - **题型分布**：事实型 / 流程型 / 拒答型 / 边界型 / 组合型都要有。
  - **题量达标**：A 类 ≥50 题、B 类 ≥100 题、C 类 ≥30 组 prompt——题太少统计不显著。
- **示例片段**：

  | 设计原则 | 为什么 | 怎么做 | 反面教材 |
  |---|---|---|---|
  | **覆盖核心场景** | 评测集如果不含真实高频问题，通过率再高也没意义 | 从用户日志里抽 Top 50 高频 query，脱敏后改造为评测题 | 全是 PM 自己编的"假设用户会问"的题 |
  | **难度分层** | 全简单题 → 测不出上限；全难题 → 测不出底线 | 易 : 中 : 难 = 3 : 5 : 2（参考比例） | 100 道题全是"我的订单在哪"这种简单题 |
  | **题型分布合理** | 不同题型测不同能力，分布失衡会导致评测偏科 | 事实型 30% / 流程型 25% / 拒答型 20% / 边界型 15% / 组合型 10% | 90% 都是事实型，完全不测多轮追问和拒答边界 |
  | **题量达标** | 50 题里对 40 题 = 80%，10 题里对 8 题 = 80%——前者才可信 | A 类 ≥50 / B 类 ≥100 / C 类 ≥30 组 | 只有 10 道题就跑"通过率 80%" |

  > **出题常见误区**：
  > - **误区 1：题目太"书面语"**——PM 写的题往往是"请查询我的订单状态"，但真实用户会说"我那单到哪了"。题目必须是真实用户的口语，否则评测通过了上线也会翻车。
  > - **误区 2：题目有引导性**——"你知道退款规则是 7 天无理由吗？"这种题等于把答案告诉了 Agent。正确做法是开放式提问："我能退款吗？"
  > - **误区 3：金标太"细"**——金标写成了逐字答案，Agent 只要语序不对就判 fail。金标应该是关键考察点，不是逐字稿。
  > - **误区 4：评测集一次定型不再更新**——产品在迭代、用户在变化，评测集必须跟着迭代。线上发现的新 bad case，有代表性的要补进评测集。

### 3.3 题目来源（题从哪来）

- **这一节写什么**：评测集的题不能全靠人工构造——四个来源必须组合使用：真实用户日志、人工构造、竞品迁移、对抗样本。
- **颗粒度要求**：每个来源给"占比建议" + "怎么用" + "注意事项"。
- **填写要点**：
  - **真实用户日志是主来源**（占 50-60%）——这是最接近真实场景的题。
  - **人工构造**（占 20-30%）——覆盖 PRD 里有但日志里还没出现的新场景。
  - **竞品题目迁移**（占 10%）——参考竞品的评测维度，补自己没想到的。
  - **对抗样本**（占 10%）——专门测红线、注入、边界。
- **示例片段**：

  | 来源 | 占比建议 | 怎么用 | 注意事项 |
  |---|---|---|---|
  | **真实用户日志** | 50-60% | 从线上 query 里抽高频、典型、有代表性的问题，脱敏后改造 | 必须脱敏（去掉用户名、订单号、手机号）；不能直接拿线上 query 当评测题——要改造为"标准问法" |
  | **人工构造** | 20-30% | 根据 PRD 场景设计题目，覆盖还没上线但即将上线的新场景 | 人工构造的题容易"太理想"——要找真实用户预审一遍 |
  | **竞品题目迁移** | 10% | 参考竞品公开评测报告里的题目，结合自己产品改造 | 不能直接抄——要改成自己产品的场景 |
  | **对抗样本** | 10% | 专门设计红线题、注入题、边界题 | 对抗题要单独标注，不计入通过率分母（或单独统计红线通过率） |

### 3.4 输入侧设计（每题的输入字段）

- **这一节写什么**：一道评测题不只是"一个 query"——它有完整的输入字段：Query、附件、参数、上下文。Agent 类评测集必须设计多轮对话题，不能全是单轮 QA。
- **颗粒度要求**：列出每题的完整字段清单；A 类必须有多轮对话历史字段；B 类必须有附件 / 文档字段；C 类必须有参数字段。
- **填写要点**：
  - **Query**：用户问题原文，必须是"真实用户会说的话"，不是书面语。
  - **附件**：如有——图片、文档、历史对话截图。
  - **参数**：如有——温度、模型版本、系统版本、商户类型。
  - **上下文**：如有——多轮对话历史（这是 Agent 类评测集和单轮 QA 评测集最大的区别）。
- **示例片段**：

  **单轮对话题的字段**（A/B 类通用）：
  | 字段 | 说明 | 示例 |
  |---|---|---|
  | 题 ID | 唯一标识 | T01 |
  | 题型 | 事实型/流程型/拒答型/边界型/组合型 | 流程型 |
  | 难度 | 易/中/难 | 中 |
  | Query | 用户问题原文 | "我能退款吗？" |
  | 附件 | 图片/文档（如有） | 无 |
  | 参数 | 温度/模型/商户类型（如有） | 商户类型=A 类商户 |
  | 来源 | 日志/人工/竞品/对抗 | 日志（脱敏改造） |

  **多轮对话题的字段**（A 类 Agent 必须）：
  | 字段 | 说明 | 示例 |
  |---|---|---|
  | 题 ID | 唯一标识 | M01 |
  | 轮次 | 共几轮 | 3 轮 |
  | 第 1 轮 | 用户第 1 句 | "你好，我想问下退款的事" |
  | 第 1 轮预期 | Agent 第 1 轮应该怎么回 | 先追问：充值时长？钻石使用？是否未成年？ |
  | 第 2 轮 | 用户第 2 句（基于 Agent 第 1 轮的追问） | "充了大概一周，钻石没用过，是我自己的号" |
  | 第 2 轮预期 | Agent 第 2 轮应该怎么回 | 按"7 天/未使用/每年 1 次"规则回答退款条件 |
  | 第 3 轮 | 用户第 3 句 | "那我要怎么操作？" |
  | 第 3 轮预期 | Agent 第 3 轮应该怎么回 | 给出申诉入口 + 3 个工作日回复 |

### 3.5 标准答案 / 金标设计（怎么算过）

- **这一节写什么**：金标不是"标准答案逐字稿"——是"关键考察点"。Agent 的回答只要满足所有关键考察点就算过，不需要和标准答案一字不差。
- **颗粒度要求**：每题至少 3-5 个关键考察点；每个考察点写清"怎么算过 / 怎么算不过 / 边界情况"。
- **填写要点**：
  - **关键考察点不是逐字答案**——"必须先追问充值时长、钻石使用、是否未成年"是考察点，不是"您好，请问您充值了多久？钻石是否使用过？是否为未成年人账号？"
  - **怎么算过**：所有关键考察点都满足。
  - **怎么算不过**：缺了任意一个关键考察点。
  - **边界情况**：什么情况下算"可接受但不完美"——比如顺序反了但三个追问都问了。
- **示例片段**：

  **T12 退款题的金标设计**：
  | 考察点 ID | 考察点内容 | 怎么算过 | 怎么算不过 | 边界情况 |
  |---|---|---|---|---|
  | CP1 | 先追问充值时长 | 问了"多久充的"/"充值时间" | 没问，直接回答 | 问了但顺序在第 2 位，也算过 |
  | CP2 | 先追问钻石使用 | 问了"钻石用了吗"/"有没有消费" | 没问 | 同上 |
  | CP3 | 先追问是否未成年 | 问了"是您本人操作吗"/"是否为未成年人" | 没问 | 同上 |
  | CP4 | 按"7 天/未使用/每年 1 次"规则回答 | 三个规则都说到了 | 只说了 1-2 个 | 说到 2 个算"可接受但不完美"（扣分但不算 fail） |
  | CP5 | 给出申诉入口 | 说了"联系客服"/"提交申诉" | 没给入口 | 给了但入口描述模糊，也算过 |

  > **判定口径**：CP1-CP5 全部满足 = pass；任意一个不满足 = fail；CP4 只说到 2 个规则 = 可接受但不完美（记录但不判 fail）。
  >
  > **金标设计常见误区**：
  > - **误区 1：金标写成"标准答案逐字稿"**——Agent 的回答只要措辞不一样就判 fail，这是错的。金标应该是关键考察点，不是逐字答案。
  > - **误区 2：金标没有"边界情况"**——什么算"可接受但不完美"、什么算"fail"，必须写清。否则评测人各有各的判断，结果不可复现。
  > - **误区 3：金标太严**——所有细节都要求，导致通过率永远上不去。正确的做法是区分"核心考察点"（缺了就 fail）和"加分项"（有了更好，没有也不算 fail）。
  > - **误区 4：金标不更新**——业务规则变了，金标也要跟着变。如果金标还是 3 个月前的老规则，评测结果就没有意义。

### 3.6 模型侧结果列（横向对比用）

- **这一节写什么**：评测集不只是"题目 + 金标"——还要有"结果列"，用来横向对比多个模型 / 多个版本的输出。
- **颗粒度要求**：每个被评测对象至少 3 列——结果地址 / 耗时 / 成本；这样一张表就能同时对比 N 个模型。
- **填写要点**：
  - **结果地址**：链接到评测平台的会话详情页 / 原始 JSON 输出。
  - **耗时**：端到端响应时间（首字延迟 + 总时长）。
  - **成本**：单次消耗的 token 数 / API 费用。
  - 这样设计的好处是：一次评测就能同时对比"效果 + 速度 + 成本"三个维度。
- **示例片段**：

  | 题 ID | 金标 | {模型 A} 结果 | {模型 A} 耗时 | {模型 A} 成本 | {模型 B} 结果 | {模型 B} 耗时 | {模型 B} 成本 |
  |---|---|---|---|---|---|---|---|
  | T01 | 见金标 | pass | 2.3s | $0.012 | pass | 1.8s | $0.008 |
  | T12 | 见金标 | fail（缺 CP3） | 3.1s | $0.015 | pass | 2.5s | $0.010 |
  | T25 | 见金标 | fail（算术错） | 4.2s | $0.020 | fail（同上） | 3.8s | $0.018 |

  > **横向对比结论**：{模型 A} 效果略好（多对了 2 题）但成本高 30%、速度慢 20%；{模型 B} 性价比更高但在多步推理上仍有短板。

### 3.7 题型分布统计（覆盖度检查）

- **这一节写什么**：一张统计表，看评测集的题型分布是否合理——有没有偏科。
- **颗粒度要求**：至少 3 个维度统计——题型分布、难度分布、来源分布。
- **填写要点**：
  - **题型分布**：事实型 / 流程型 / 拒答型 / 边界型 / 组合型各多少题、占比多少。
  - **难度分布**：易 / 中 / 难各多少题、占比多少。
  - **来源分布**：日志 / 人工 / 竞品 / 对抗各多少题、占比多少。
  - 如果某类题型占比过低（如拒答型只有 2 题），要补题。
- **示例片段**：

  | 题型 | 题数 | 占比 | 考察什么 | 是否达标 |
  |---|---|---|---|---|
  | 事实型 | 15 | 30% | 知识库召回 + 事实准确性 | ✓ |
  | 流程型（多轮追问） | 12 | 24% | 多轮状态保持 + SOP 遵循 | ✓ |
  | Tool use 型 | 8 | 16% | 工具调用正确性 + 入参校验 | ✓ |
  | 拒答边界型 | 8 | 16% | 红线识别 + 合规话术 | ✓ |
  | 组合计算型 | 4 | 8% | 多步推理 + 数值准确性 | 偏低，建议补到 10% |
  | 红线性（安全/越权） | 3 | 6% | 一票否决项 | ✓ |

  | 难度 | 题数 | 占比 |
  |---|---|---|
  | 易 | 15 | 30% |
  | 中 | 25 | 50% |
  | 难 | 10 | 20% |

### 3.8 版本管理（评测集也要版本号）

- **这一节写什么**：评测集本身也要版本管理——v1.0 / v1.1 / v2.0 的差异是什么，每次版本更新必须重跑全部评测。
- **颗粒度要求**：版本号规则 + 变更记录表 + 回归要求。
- **填写要点**：
  - **版本号规则**：v1.0 = 初版；v1.1 = 新增/删除少量题（<10%）；v2.0 = 大规模改版（>30% 题目变动）。
  - **变更记录**：每版写清"新增了哪些题、删除了哪些题、修改了哪些题的金标"。
  - **回归要求**：每次版本更新必须重跑全部评测——不能"只跑新增的题"。
- **示例片段**：

  | 版本 | 发布日期 | 题量变化 | 主要变更 | 重跑要求 |
  |---|---|---|---|---|
  | v1.0 | 2026-09-01 | 50 题 | 初版 | — |
  | v1.1 | 2026-10-01 | 52 题（+2） | 新增 T51 多轮记忆题、T52 多语言混合题；修改 T12 金标（CP4 边界情况细化） | 全量重跑 |
  | v2.0 | 2026-11-01 | 60 题（+8） | 新增 8 道 Tool use 题；删除 3 道过时题（已下线功能）；整体难度上调 | 全量重跑 |

### 3.9 标注规范（金标怎么标）

- **这一节写什么**：金标的质量决定评测结果的质量——谁来标、怎么标、双标一致性怎么保证、争议题怎么仲裁。
- **颗粒度要求**：标注角色 + 标注规范 + 双标一致性 + 仲裁机制。
- **填写要点**：
  - **金标由谁标**：领域专家标业务题、PM 标产品流程题、外包标基础题。
  - **双标一致性**：Cohen's Kappa ≥0.7 才入库——低于 0.7 说明标注规范有问题，要先修规范再标。
  - **争议题仲裁**：两个标注员不一致时，由第三方（领域专家 / PM）仲裁。
- **示例片段**：

  | 标注角色 | 负责题型 | 标注要求 |
  |---|---|---|
  | 领域专家 | 事实型、流程型、拒答型 | 必须按业务 SOP 标，不能自由发挥 |
  | PM | 产品流程题、边界题 | 必须对照 PRD 标 |
  | 外包标注员 | 基础事实题、格式题 | 按标注手册标，不做判断 |

  **双标一致性流程**：
  1. 每题由 2 个标注员独立标注金标。
  2. 对比两人的标注结果：一致 = 入库；不一致 = 进入仲裁。
  3. 仲裁由第三方（领域专家 / PM）做，仲裁结果为最终金标。
  4. 每月统计 Cohen's Kappa：≥0.7 合格；<0.7 暂停标注，修订标注手册后再继续。

  > **标注质量控制**：
  > - **标注手册先行**：开始标注前必须有一份《标注手册》，写清每类题型怎么标、边界情况怎么判、争议题怎么处理。不能边标边定标准。
  > - **标注员培训**：正式标注前，所有标注员先做 10 道练习题，核对答案一致性后再正式开始。
  > - **抽样质检**：PM 每周抽检 20% 的已标注题目，发现标注错误率 >10% 时，全体标注员重新校准。
  > - **标注一致性周报**：每周公布双标一致性分数，让标注员知道自己的水平。

### 3.10 使用说明（怎么用这套评测集）

- **这一节写什么**：给执行评测的人看的操作手册——评测前准备什么、评测怎么跑、结果怎么导出。
- **颗粒度要求**：评测前准备 + 执行流程 + 结果导出格式。
- **填写要点**：
  - **评测前准备**：确认 Workflow 版本、Prompt 版本、模型版本、知识库版本都已锁定。
  - **执行流程**：每题独立新会话 → 发送 query → 等待 Workflow 运行成功 → 记录结果 → 跑 pass³（Agent 类必须）。
  - **结果导出**：导出格式必须和第 3.6 节的"模型侧结果列"对齐。
- **示例片段**：

  **评测前准备**：
  1. 确认要评测的 Workflow 版本、Prompt 版本、模型版本、知识库版本。
  2. 确认评测集版本（本结论仅对应该评测集版本）。
  3. 清空历史缓存，每题开启独立新会话。

  **执行流程**：
  1. 从评测集第 1 题开始，逐题发送 query。
  2. 等待 Workflow 运行成功，记录输出结果、耗时、成本。
  3. 对照金标关键考察点，判定 pass / fail。
  4. Agent 类必须跑 pass³：同一题连跑 3 次，3 次全过才算真过。
  5. 遇到异常（超时、限流、Schema 非法）记录并跳过，事后补跑。

  **结果导出格式**：
  - 导出为飞书多维表格，列结构 = 第 3.6 节的模型侧结果列。
  - 附件 = 每题的完整会话链接、trace 日志、截图。
  - 导出后自动生成通过率统计、题型分布统计、难度分布统计。

## 四、不同产品类别的差异化要点

### A 类（对话式 AI / Agent 产品）
- **重点设计四类题**：
  - **多轮对话题**：不是单轮 QA——必须设计 3-5 轮的完整对话，测多轮状态保持。
  - **角色遵循题**：测 Agent 是否跳出角色、是否泄露答案、是否无条件配合。
  - **拒答边界题**：测红线问题是否识别、拒答话术是否合规。
  - **Tool use 题**：测工具调用是否成功、入参是否正确、返回是否被正确使用。
- **题量建议**：≥50 题（其中多轮对话题 ≥10 组）。
- **pass³ 必须做**：A 类输出随机性最大，不跑 3 次等于没测。

### B 类（RAG 知识库 / 问答产品）
- **重点设计五类题**：
  - **事实召回题**：测知识库召回是否正确、答案是否准确。
  - **多跳推理题**：需要跨 2-3 个文档综合回答的题。
  - **无答案拒答题**：知识库没有答案时是否说"不知道"。
  - **权限过滤题**：不同 org / 不同角色的知识是否被正确隔离。
  - **引用溯源题**：回答引用的 source_id 是否真实存在、是否能支持结论。
- **题量建议**：≥100 题。
- **金标设计**：必须包含"golden chunk 列表"——哪些文档的哪些段落应该被召回。

### C 类（AIGC 多模态生成产品）
- **重点设计三类题**：
  - **不同风格的生成 prompt**：每个风格 5-10 组 prompt。
  - **不同主体 / 场景的生成 prompt**：人物 / 动物 / 产品 / 场景。
  - **参数变化题**：同一 prompt 不同分辨率 / 时长 / 步数。
- **题量建议**：≥30 组 prompt（每组 prompt 跑 3 次取平均）。
- **金标设计**：不能用二值通过——用人工评分量表（1-5 分），从多个维度打分。

### D 类（AI 评测平台 / 内部工具）
- **评测集本身就是产品**——重点是：
  - **评测集质量控制**：双标一致性、争议率、通过率分布是否合理。
  - **版本迭代记录**：每次版本更新的变更记录要完整可追溯。
  - **Judge 准确性**：LLM-as-Judge 和人工打分的一致性是平台的核心 KPI。
- **题量建议**：按平台定位——通用评测平台 ≥500 题；垂直场景评测集 ≥100 题。

### E 类（B 端 SaaS / 传统产品 AI 化）
- **一般不单独建评测集**——引用 D 类平台的评测集即可。
- 如果一定要建，重点是：
  - **工单来源的题**：从真实工单里抽典型 case。
  - **PRD 验收题**：对照 PRD 第 3.7.4 节的 AI 评测门槛逐项出题。
- **题量建议**：≥30 题（B 端场景相对集中，不需要太多题）。
