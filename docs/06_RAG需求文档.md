# 【RAG 需求文档】SKILL

> **适用产品类别**：B 类（RAG 知识库 / 问答产品）为主，A 类（对话式 Agent）、E 类（B 端 SaaS AI 化）为辅。
> **为什么**：只要产品里存在"让大模型基于公司内部资料回答问题、做事实核验、生成带引用的文案"的能力，就必须把 RAG 作为一个独立模块写清楚；A 类 Agent 的"工具调用知识库"那一段、E 类 SaaS 的"AI 问答 / AI 助手"模块也适用。
> **文档目的**：给算法、研发、测试、业务知识 Owner 一份"知识从哪里来、怎么切、怎么检、谁在用、出问题怎么回滚"的完整契约，避免模型靠记忆编公司事实。
> **撰写时机**：MVP 范围内已经确认要接知识库、且第一批业务资料已经在业务侧对齐口径时；在 Embedding / Rerank 选型和首次 Golden Set 评测之前完成。

---

## 一、撰写前需要收集的资料清单

### 1.1 用户侧 / 业务侧
- **上层调用方是谁**：哪些 Agent / 哪些功能会调 RAG（例如：角色扮演 Agent、评分 Agent、文案生成 Agent、客服问答）。
- **业务事实清单**：哪些公司事实、产品权益、SOP、话术、FAQ 必须由 RAG 提供，而不是让模型自由发挥。
- **业务红线**：哪些内容绝对不能被检索出来（跨业务线、未发布、已下线、敏感权限）。
- **知识 Owner 名单**：每类资料的业务 Owner、审核人、培训负责人是谁。

### 1.2 数据侧
- **知识源清单**：现有资料文件（PDF / Word / Excel / HTML / 数据库表 / 历史对话），以及每类资料的量（条数、字数）。
- **元数据字段**：每条资料需要打哪些标签（业务线、产品、行业、场景、销售阶段、有效期、Owner）。
- **Golden Set 初稿**：业务专家标注的"问题 → 应该命中哪条知识 / 应该返回什么状态"的样本。

### 1.3 技术侧
- **检索架构**：单库还是多库、是否混合检索（关键词 + 向量）、是否需要 Rerank、是否需要元数据预过滤。
- **关键参数候选值**：Top-K、Rerank 数量、重排阈值、Chunk 长度、Overlap、Embedding 模型、Rerank 模型。
- **调用契约**：上层 Agent 用什么字段发起请求、RAG 返回什么状态枚举。
- **运维能力**：是否有知识快照、版本发布、回滚、全链路日志。

## 三、完整框架结构（到三级标题）

> 标准骨架：**基础信息 → 模块背景 → 功能规划 → 功能需求（7 个功能点）→ 非功能需求 → 评测需求（Golden Set）→ 兜底策略**。
> 功能需求的 7 个功能点是本文档的核心，缺一不可。

### 3.1 基础信息（版本 / 变更 / 名词解释）

- **这一节写什么**：文档元信息（名称、版本、状态、关联主 PRD、负责人）、变更记录表、关键名词的本项目定义。
- **颗粒度要求**：名词解释至少覆盖 Chunk、知识快照、精确读取、Golden Set 四个核心概念；每个名词给出"本项目内的定义"，不是教科书定义。
- **填写要点**：
  - 关联主 PRD 必须写清楚，避免 RAG 文档和主 PRD 口径打架。
  - 变更记录每一条都要说明"为什么把 RAG 从主 PRD 拆出来"。
- **示例片段**：
  | 名词 | 本项目定义 |
  |---|---|
  | Chunk | 可独立检索、能保留完整业务含义的最小知识单元 |
  | 知识快照 | 一次正式发布时全部可用知识及索引的版本集合，同一场{会话/任务}固定使用同一快照 |
  | 精确读取 | 按 ID 和版本直接取得{配置/规则}，不通过相似度检索 |
  | Golden Set | 由业务专家标注预期命中、禁止命中和异常状态的固定评测集 |

### 3.2 模块背景（为什么要单独建 RAG / 模块目标 / 系统边界 / MVP 范围）

- **这一节写什么**：讲清楚"不用 RAG 会出什么事"、"RAG 要达成什么目标"、"RAG 系统和谁对接"、"本期做什么 / 不做什么"。
- **颗粒度要求**：痛点至少列 4 条，每条要写"发生位置 + 业务影响"；系统边界用 Mermaid 图画出 RAG 和上下游的关系；MVP 范围用两栏表（本期包含 / 本期不包含）。
- **填写要点**：
  - 核心产品决定要先写一句加粗 callout："**不是所有资料都进入向量库**"——场景/人设/评分规则这类强配置按 ID 精确读取，只有业务知识和标准样例走检索。
  - "本期不包含"里必须显式排除：自动爬网入库、独立问答入口、自动算总分这类容易越界的需求。
- **示例片段**：
  ```
  核心产品决定：不是所有资料都进入向量库。{场景、人设、评分规则}必须按 ID 与版本精确读取；
  只有{业务知识和经审核的标准样例}需要检索。MVP 先采用一个逻辑索引，通过元数据分类与过滤；
  只有权限、更新频率或检索方式明显不同，后续才拆成多个物理库。

  系统边界（Mermaid flowchart LR）：
    {任务/配置} --按 ID 与版本精确读取--> {上层 Agent A}
    {RAG 知识服务} --业务事实--> {上层 Agent A}
    {RAG 知识服务} --事实核验与样例--> {上层 Agent B}
    {规则/Rubric} --按 ID 与版本精确读取--> {上层 Agent B}
  ```

### 3.3 功能规划（知识域规划 / MVP 功能清单）

- **这一节写什么**：把所有知识分成几个域，每个域写清楚"包含什么、怎么获取、谁在用、有什么限制"；再用一张表列出本期交付的模块、优先级、完成标志。
- **颗粒度要求**：知识域至少 4 类（配置类精确读取 / 业务知识检索 / 规则类精确读取 / 样例类检索）；功能清单至少 7 行对应后面 7 个功能点，每行要有 P0/P1 和"完成标志"。
- **填写要点**：
  - 明确区分"走 RAG 检索"和"按 ID 精确读取"两类，不要混在一起。
  - 样例类知识要写明"只能用于解释和建议，不能直接决定正式分数"。
- **示例片段**：
  | 知识域 | 包含内容 | 获取方式 | 使用方与限制 |
  |---|---|---|---|
  | {场景与角色配置} | {商户资料、人设、剧本、触发规则} | 按 `{task_id + role_version}` 精确读取 | {上层 Agent A}；不属于 RAG 正式索引 |
  | {业务知识} | {平台事实、产品权益、方法、行业资料、常见异议} | 元数据过滤后，关键词与语义混合召回并重排 | {两类 Agent} 共用 |
  | {评分规则} | {维度、阈值、权重、红线、计分公式} | 按 `{rubric_id + version}` 精确读取 | {评分 Agent}；规则服务负责确定性计分 |
  | {标准样例} | {经业务确认的优秀话术、常见错误、改进示例} | 按{行业、阶段、评分项}检索 | 只用于解释，不能直接决定正式分数 |

### 3.4 功能点 1：知识源准入与发布

- **这一节写什么**：哪些来源的资料可以进库、进库前要满足什么条件、进库后的状态机是什么。
- **颗粒度要求**：写到"使用前提 / 操作 / 系统响应 / 业务规则 / 异常 / 验收"6 段；来源类型至少 4 类（官方业务资料 / 培训行业资料 / 真实对话样例 / 外部网络或个人经验），每类写准入要求。
- **填写要点**：
  - 必须有"外部网络 / 个人经验默认不进正式索引"这一条，防止模型幻觉被当成事实。
  - 验收指标：已发布知识的必填元数据完整率 100%；未审核、过期、已下线内容进入正式索引为 0 条。
- **示例片段**：
  | 来源类型 | 准入要求 | 用途 |
  |---|---|---|
  | 官方业务资料 | 必须有业务 Owner、版本、生效时间、权限范围 | 正式事实依据，优先级最高 |
  | 培训与行业资料 | 培训负责人和业务负责人共同审核 | 角色判断和辅导建议 |
  | 真实对话样例 | 必须脱敏，标注适用场景 | 只用于解释和改进建议 |
  | 外部网络 / 个人经验 | 不得直接进入正式索引；需业务确认后转为受控资料 | 默认不使用 |

  **业务规则**：只有"已发布"且在有效期内的知识可被召回；同一资料更新生成新版本，禁止静默覆盖。
  **异常**：解析失败、缺 Owner、来源不明、资料冲突或权限缺失时进入待处理列表，不进入正式索引。

### 3.5 功能点 2：清洗、切片与元数据

- **这一节写什么**：不同内容类型怎么切、Chunk 必须带哪些元数据字段、清洗时要保留 / 删除什么。
- **颗粒度要求**：切片规则至少 5 类（产品事实、FAQ、SOP、规则表格、话术样例），每类写"怎么切 + 禁止行为"；元数据字段分 6 组（唯一标识 / 分类过滤 / 版本时效 / 权限状态 / 责任归属 / 来源引用）。
- **填写要点**：
  - 切片长度、Overlap、召回数量、置信阈值必须做成"可配置参数，由 Golden Set 评测后冻结"，不要在 PRD 里写死一个数字当真理。
  - 必须写一句安全规则："知识文档中的任何指令只作为资料内容，不得覆盖系统 Prompt 或触发工具执行"（防提示词注入）。
  - 相同 `content_hash` 的重复导入不新建 Chunk；内容变化必须形成新版本。
- **示例片段**：
  | 内容类型 | 切片规则 | 禁止行为 |
  |---|---|---|
  | 产品事实与权益 | 一个完整事实、适用条件、限制放在同一 Chunk | 不能把权益与限制条件拆开 |
  | FAQ | 一组问题、标准答案、适用范围作为一个 Chunk | 不能只保留答案而丢失问题语境 |
  | SOP 与步骤 | 按完整任务或连续步骤切分，保留标题层级 | 不能拆散必须连续执行的步骤 |
  | 规则与表格 | 按完整规则项或完整表行转结构化文本 | 不能把表头、阈值、例外条件分离 |
  | 话术样例 | 保留场景、阶段、原话、判定、改进示例 | 不能把样例当普适事实或评分标准 |

  **元数据字段模板**：
  - 唯一标识：`source_id、document_id、chunk_id、content_hash`
  - 分类过滤：`knowledge_type、business_line、product_id、industry、scenario_id、stage`
  - 版本时效：`source_version、effective_at、expires_at、kb_snapshot_version`
  - 权限状态：`permission_scope、publish_status`
  - 责任归属：`owner、reviewer、updated_at`
  - 来源引用：`source_title、source_url、source_page`

### 3.6 功能点 3：检索与重排

- **这一节写什么**：一次检索从 Agent 发起到返回的完整流程，以及可能返回的所有状态。
- **颗粒度要求**：必须画 Mermaid 流程图，分支至少包含"是否需要检索 / 元数据预过滤 / 混合召回 / 重排去重 / 可靠命中 / 无可靠依据 / 资料冲突 / 权限不符"；再用 6 段式表（使用前提 / 操作 / 系统响应 / 业务规则 / 异常 / 验收）写清楚。
- **填写要点**：
  - **过滤必须发生在向量召回之前**（权限、业务线、版本、有效期），不能先召回再过滤。
  - 同一场会话固定一个知识快照版本，不能中途换。
  - 异常状态不能统一返回空字符串，必须区分 `no_hit / conflict / permission_denied / timeout / service_error`。
  - **关键参数模板**（由 Golden Set 冻结，不要拍脑袋）：
    - 检索准确率（Top-5 命中率）≥ {90%}（P0 核心问题）/ ≥ {85%}（全量）
    - Top-K（向量召回）= {12}
    - Rerank 后保留 = {3}
    - 重排阈值（confidence threshold）= {0.6}，低于此值按 no_hit 处理
    - 在线检索 P95 延迟 ≤ {1}s；异步检索 P95 ≤ {3}s
- **示例片段（Mermaid）**：
  ```
  flowchart TD
    A["Agent 发起知识请求"] --> B{"当前是否需要检索"}
    B -->|否：寒暄或纯角色| C["继续正常对话"]
    B -->|是| D["构造 Query：当前原话 + 最近对话 + 任务信息"]
    D --> E["先过滤权限、业务线、版本、有效期、发布状态"]
    E --> F["关键词与语义混合召回 Top-K={12}"]
    F --> G["Rerank、去重、置信判断（阈值={0.6}）"]
    G -->|可靠命中| H["hit：正文 + 来源 + 版本"]
    G -->|无可靠依据| I["no_hit"]
    G -->|资料冲突| J["conflict"]
    E -->|权限不符| K["permission_denied"]
  ```

### 3.7 功能点 4：上层 Agent 的使用规则

- **这一节写什么**：每个调用 RAG 的 Agent 分别"什么时候调、怎么用、不能做什么、没结果怎么办"。
- **颗粒度要求**：用一张对比表，行是每个调用方，列是"固定加载 / 何时调用 RAG / 如何使用 / 禁止行为 / 无可靠结果时 / 追溯要求"。
- **填写要点**：
  - 必须写清"普通寒暄不检索"，否则 RAG 成本和延迟会爆炸。
  - 必须写清"样例不能替代规则打分"——这是最常见的滥用。
  - 如果业务规则本身还在冲突中，要加 callout 说明："口径冻结前 RAG 只支持证据定位和定性建议，不能产出正式总分 / 认证结论"。
- **示例片段**：
  | 项目 | {角色扮演 Agent} | {评分 Agent} |
  |---|---|---|
  | 固定加载 | {任务、场景、人设、剧本、触发规则} | {完整对话、转写、本次评分表及版本} |
  | 何时调用 RAG | 用户提到{产品、权益、业务事实}时 | 核验用户原话事实或生成改进建议时 |
  | 如何使用 | 判断用户表达是否合理，保持真实反应 | 先定位原话，再用知识核验；样例只辅助解释 |
  | 禁止行为 | 不能主动讲出标准答案，不能暴露内部资料 | 不能用相似样例直接打分，不能自行补写规则 |
  | 无可靠结果 | 保持角色中性回应，不编造公司事实 | 标记"依据不足/暂无法判断"，保留待复核项 |
  | 追溯要求 | 记录本轮使用的 Chunk、来源、知识快照 | 保存原话、评分项、知识依据、版本 |

### 3.8 功能点 5：调用契约（请求 / 返回字段 + 状态枚举 + 逻辑接口）

- **这一节写什么**：产品层逻辑契约（不是最终接口协议），规定请求字段、返回字段、状态枚举、逻辑接口名。
- **颗粒度要求**：请求字段至少 4 组（调用方身份 / 检索范围 / Query / 版本权限）；返回字段至少 3 组（状态追踪 / 命中正文 / 相关度）；状态枚举列出全部；逻辑接口至少 4 个（检索 / 建快照 / 发布 / 回滚）。
- **填写要点**：
  - 强调"这是产品层逻辑契约，研发评审后再定接口路径和协议"。
  - 调用方必须逐一处理所有状态，不能把异常状态当正常命中。
- **示例片段**：
  | 方向 | 字段 | 说明 |
  |---|---|---|
  | 请求 | `agent_type、session_id、task_id、scene_id` | 谁在什么会话、任务、场景中调用 |
  | 请求 | `industry、stage、knowledge_scope` | 限定行业、阶段、知识类型 |
  | 请求 | `query、recent_turns` | 当前待核验内容及必要最近对话 |
  | 请求 | `kb_snapshot_version、permission_scope` | 固定知识版本并执行权限过滤 |
  | 返回 | `status、retrieval_id、latency_ms` | 状态、链路追踪号、耗时 |
  | 返回 | `chunk_id、content、source_id、source_title、source_version` | 命中正文与来源 |
  | 返回 | `relevance_score、conflict_group` | 相关度和冲突分组（仅供系统判断，不展示给终端用户） |

  **状态枚举**：`hit、no_hit、conflict、permission_denied、timeout、service_error`。

  **逻辑接口**：
  - `retrieveKnowledge`：上层 Agent 调用，返回命中证据或异常状态。
  - `buildKnowledgeSnapshot`：离线入库任务，生成可评测的候选快照。
  - `publishKnowledgeSnapshot`：受控发布流程，新会话开始使用新快照。
  - `rollbackKnowledgeSnapshot`：授权运维恢复指定稳定快照并留审计记录。

### 3.9 功能点 6：更新、下线与回滚

- **这一节写什么**：知识从草稿到下线的完整状态机、发布前要过哪些关卡、进行中的会话用哪个版本、严重问题怎么回滚。
- **颗粒度要求**：先给状态机（草稿 → 清洗中 → 待审核 → 已发布 → 已下线），再写 5 条运维规则，最后列一张"角色责任表"（业务 Owner / 培训负责人 / 产品 / 研发 / 测试）。
- **填写要点**：
  - **新会话读新快照，进行中的会话继续用启动时的快照**——这是保证同一场不口径漂移的关键。
  - 发布前必须完成：元数据校验 + 业务审核 + Golden Set 回归。
  - 严重错误可以下线单条知识并重建索引；影响面不明时回滚整个快照。
  - 所有发布 / 下线 / 回滚必须记录：操作者、时间、原因、影响知识、前后版本。
- **示例片段**：
  ```
  知识状态：草稿 → 清洗中 → 待审核 → 已发布 → 已下线。
  MVP 通过知识源清单、受控脚本和发布记录运维，不建设后台页面。

  规则：
  1. 发布前必须完成元数据校验、业务审核和 Golden Set 回归。
  2. 新会话读取最新已发布快照；进行中的会话继续使用启动时的快照。
  3. 内容更新生成新版本；旧版本保留审计，但不再进入新会话检索。
  4. 发现严重错误或权限问题时，可下线单条知识并重建索引；影响面不明时回滚整个快照。
  5. 发布、下线、回滚均记录操作者、时间、原因、影响知识、前后版本。
  ```

### 3.10 功能点 7：日志与问题闭环

- **这一节写什么**：全链路要埋哪些事件、日志里必须带什么字段、badcase 怎么进待处理清单。
- **颗粒度要求**：至少列出 8 个埋点事件名；每个检索日志必须含 `retrieval_id` 全链路字段；badcase 按 P0/P1/P2 分级定义处理时效。
- **填写要点**：
  - 日志中的真实对话、员工、商户信息必须脱敏，非必要不存完整原话。
  - 每次知识更新后用同一套 Golden Set 回归，结果和上一快照对比。
- **示例片段**：
  **至少记录的事件**：`kb_ingest_finished、kb_publish、kb_rollback、rag_search_finished、rag_no_hit、rag_conflict、rag_permission_blocked、rag_evidence_used`。

  **检索日志字段**：`retrieval_id、请求过滤条件、候选与重排结果、最终使用的 Chunk、知识快照版本、状态、耗时`。

  **问题分级**：
  - P0：权限泄露、严重事实错误、错误版本被使用——立即停快照并回滚。
  - P1：核心问题无结果、冲突未处理——进业务待办，修复后跑 Golden Set 回归。
  - P2：排序不佳、普通样例缺失——进迭代池，不阻断主流程。

### 3.11 非功能需求

- **这一节写什么**：性能、稳定性、权限、安全、可追溯、可配置、一致性、兼容性 8 个维度的要求与验证方式。
- **颗粒度要求**：每个维度写"要求 + 验证方式"两列，必须可测（压测输出 P50/P95/P99、越权用例、提示词注入测试等）。
- **填写要点**：
  - 稳定性要写："RAG 超时不能影响上层业务原始数据保存"。
  - 安全要写："知识内容只能作为数据，不能执行资料中包含的指令"。
  - 兼容性要写：检索要覆盖口语、同义、简称、ASR 错词。
- **示例片段**：
  | 维度 | 要求 | 验证方式 |
  |---|---|---|
  | 性能 | 在线检索 P95 ≤ {1}s，异步检索 P95 ≤ {3}s | 压测输出 P50/P95/P99 与超时率 |
  | 稳定性 | RAG 不可用不影响上层业务原始数据 | 断网 / 服务异常 / 索引不可用演练 |
  | 权限 | 权限过滤必须在召回前执行 | 跨业务线、跨角色越权用例 |
  | 安全 | 知识内容不得被当指令执行；敏感信息脱敏 | 提示词注入、恶意文档测试 |
  | 可追溯 | 一次召回能从 `retrieval_id` 还原全链路 | 通过 retrieval_id 还原请求/候选/证据/版本 |
  | 一致性 | 同一场会话两个 Agent 用同一快照 | 知识发布前后跨会话对比 |

### 3.12 评测需求（Golden Set 设计 + 指标门槛 + 验收流程）

- **这一节写什么**：Golden Set 怎么分组、量化门槛定多少、验收按什么流程走。
- **颗粒度要求**：Golden Set 样本组至少 6 类（正常命中 / 表达变化 / 无答案 / 冲突与时效 / 权限 / Agent 行为）；指标门槛至少 10 项；验收流程 6 步。
- **填写要点**：
  - 指标门槛要写"建议值 + 首轮基线评测后冻结，调整必须写入变更记录，不能上线前临时放宽"。
  - 每个 P0 知识源、行业、阶段、异常分支都必须有样本覆盖。
  - 验收边界要写清楚：RAG 单模块验收不依赖上层评分公式冻结，但评分公式未冻结时不能验收正式总分 / 认证结论。
- **示例片段——Golden Set 分组**：
  | 样本组 | 必须覆盖 | 预期结果 |
  |---|---|---|
  | 正常命中 | {产品事实、权益、方法、行业资料、常见异议} | 命中正确知识与来源 |
  | 表达变化 | 同义问法、简称、口语、省略、ASR 错词 | 核心语义仍可召回 |
  | 无答案 | 库中不存在、信息不全、超出业务范围 | 返回 `no_hit`，不拼接相似但错误的知识 |
  | 冲突与时效 | 新旧版本冲突、两份正式资料冲突、过期下线 | 识别冲突或只用当前有效版本 |
  | 权限 | 跨业务线、跨角色、敏感资料 | 越权内容 0 召回、0 使用 |
  | Agent 行为 | 角色 Agent 泄露答案、评分 Agent 用样例替代规则 | 两类禁止行为均不发生 |

- **示例片段——指标门槛模板**：
  | 指标 | 建议门槛 | 验收范围 |
  |---|---|---|
  | P0 核心问题 Top-5 命中率 | ≥ {90%} | 首批核心产品与权益问题 |
  | 全量 Golden Set Top-5 命中率 | ≥ {85%} | 全部正常命中样本 |
  | 来源引用正确率 | ≥ {95%} | 返回来源能支持实际正文 |
  | 必填元数据完整率 | {100%} | 全部已发布 Chunk |
  | 未审核 / 过期 / 已下线 / 越权资料被使用 | {0} 次 | 权限与时效测试 |
  | 无答案与资料冲突正确退出率 | {100%} | `no_hit` 与 `conflict` 样本 |
  | 严重公司事实编造 | {0} 次 | 双 Agent 联合测试 |
  | 在线检索 P95 延迟 | ≤ {1}s | 在线链路，不含语音模型耗时 |
  | 异步检索 P95 延迟 | ≤ {3}s | 会后异步 |
  | 更新 / 下线 / 回滚演练 | 全部通过 | 每个发布候选快照 |

- **示例片段——验收流程**：
  1. 业务确认首批知识源、正确答案、权限、冲突处理口径。
  2. 研发生成候选知识快照并跑离线 Golden Set。
  3. 针对 badcase 调整切片、标签、召回、重排或阈值，重新回归。
  4. 测试执行权限、过期、异常、回滚、提示词注入测试。
  5. 与上层 Agent 联调，确认不泄露答案、不滥用样例。
  6. 所有硬门槛通过后发布；每个新快照重复同一流程。

### 3.13 兜底策略

- **这一节写什么**：8 类异常情况下（无召回 / 低置信 / 冲突 / 越权 / 超时 / 过期下线 / 转写低置信 / 规则未冻结），RAG 怎么处理、每个上层 Agent 怎么配合。
- **颗粒度要求**：一张三列表（异常 / 系统处理 / 上层 Agent A 行为 / 上层 Agent B 行为），每类异常都要写。
- **填写要点**：
  - 核心原则：RAG 不可靠时，**宁可返回"依据不足"，也不要让模型编造**。
  - 低置信结果不注入正文，按无结果处理。
- **示例片段**：
  | 异常 | 系统处理 | {上层 Agent A} | {上层 Agent B} |
  |---|---|---|---|
  | 无召回 | 返回 `no_hit`，记录 Query 与条件 | 保持角色中性，不输出公司事实 | 显示"依据不足"，不作事实判定 |
  | 低置信 | 不注入正文，按无结果处理 | 不因相似内容改变结论 | 保留待复核，不引用低置信资料 |
  | 资料冲突 | 返回 `conflict` 和冲突组，提交业务确认 | 不强行选一份回答 | 暂不判断，不给确定性建议 |
  | 权限不足 | 返回 `permission_denied`，不返回候选 | 继续对话但不用受限知识 | 不在理由中泄露受限内容 |
  | 超时 / 服务异常 | 返回独立状态；在线快失败，异步按策略重试 | 继续角色对话，不补写事实 | 进重试或"暂无法完成"，原始记录正常保存 |

## 四、不同产品类别的差异化要点

### 4.1 B 类（RAG 知识库 / 问答产品，主用）
- **必须写全**：7 个功能点一个不能少；Golden Set 6 类样本组必须齐；指标门槛至少 10 项。
- **常见坑**：只写"接一个知识库"，不写知识源准入、不写元数据、不写回滚、不写 badcase 闭环——结果上线后知识乱、口径飘、回不去。

### 4.2 A 类（对话式 Agent，辅用）
- **写法**：A 类产品的 RAG 部分通常只占《05_Agent 需求文档》的 Sys Prompt 表格一行；但只要 RAG 本身有 2 个以上调用方、知识量 > 100 条，就必须单独拆出本文档。
- **重点**：在 3.7（Agent 使用规则）里把"什么时候不检索"写死，控制成本和延迟。

### 4.3 C 类（AIGC 多模态生成，辅用）
- **常见用法**：生图 Agent 用 RAG 检索"商品历史素材 / 风格参考库"。
- **重点**：知识源准入要加"图片素材版权 / 授权范围"字段；切片规则要覆盖"图像 alt 文本 / 多模态描述"。

### 4.4 D 类（AI 评测平台，辅用）
- **写法**：D 类产品本身不建知识库，但要消费 RAG 的 Golden Set 作为评测输入；本文档的 3.12 节直接作为评测平台的评测集来源。

### 4.5 E 类（B 端 SaaS AI 化，主用）
- **重点**：B 端客户数据权限隔离是红线——`permission_scope` 必须按租户 / 部门过滤，跨租户越权是 P0 事故。
- **运维**：B 端客户的知识更新频率高，发布 / 回滚流程必须产品化，不能靠脚本。
