# 【数据埋点表】SKILL

> **适用产品类别**：**A / B / C / D / E 全类别**——只要产品上线就要埋点，区别只在"埋哪些事件"。A 类对话式 Agent 要埋对话轮次、采纳率、拒答率；B 类 RAG 要埋检索召回、no_hit、conflict；C 类 AIGC 要埋生成成本、失败率、fallback 次数；D 类评测平台要埋评测任务、Judge 一致性；E 类 B 端 SaaS 要埋商户使用频次、功能渗透率。没有埋点表的产品，上线后等于"盲人骑瞎马"——不知道用户在哪一步流失、不知道模型成本多少、不知道 bad case 为什么发生。
> **文档目的**：把"哪些事件要埋、每个事件带什么属性、谁来看这些数据"系统化——事件名规范、公共字段、AI 产品专项事件、多语言文案、数据质量校验、和 BI 看板怎么衔接。读者是 PM（埋点 Owner）、客户端 / 服务端研发（实现埋点）、数据分析师（用数据做看板）、算法（用日志做 bad case 归因）。
> **撰写时机**：① PRD 评审通过后、研发排期前——埋点表必须和功能开发同步排期，不能等上线后再补；② 每次功能迭代新增事件时同步更新版本；③ 发现数据缺失或口径打架时，回头修订埋点表。**埋点表是 PRD 的配套文档，不是上线后的补丁**。

---

## 一、撰写前需要收集的资料清单

### 1.1 埋点基础信息
- **埋点目的**：这份埋点表主要服务哪些决策（功能渗透率 / 用户留存 / 模型成本 / bad case 归因）
- **上报端**：客户端（iOS / Android / Web）/ 服务端 / 小程序——不同端的埋点实现不同
- **数据仓库**：上报到哪个数仓 / 分析平台（自有数仓 / 第三方埋点 SDK）
- **Owner**：PM 为埋点 Owner，数据分析师为口径 Owner
- **版本号**：埋点表也要版本管理

### 1.2 业务事件清单
- **PRD 里的用户流程**：每个关键节点（进入页面 / 点击按钮 / 提交 / 成功 / 失败）
- **功能清单**：每个 P0/P1 功能要埋"使用次数、使用人数、成功率、失败率"
- **转化漏斗**：从进入产品到完成核心动作的每一步

### 1.3 AI 产品专项事件（重点）
- **对话 / 生成事件**：conversation_start / turn_end / message_send / message_receive / generation_finished
- **采纳率事件**：answer_adopted / answer_rejected / answer_copy / answer_thumb_up / answer_thumb_down
- **报错事件**：llm_timeout / llm_error / rag_retrieve_fail / tool_call_fail / asr_error / tts_error
- **成本事件**：token_usage_report / cost_per_session / model_fallback_triggered
- **模型版本事件**：model_version_changed / prompt_version_changed / kb_snapshot_changed
- **拒答与转人工**：agent_refused / escalated_to_human / human_takeover_finished

### 1.4 属性字段资料
- **公共字段**：user_id / session_id / device / os / app_version / region / tenant_id / event_time
- **业务字段**：每个事件专属的属性（如对话轮次、chunk_id、模型名、错误码）
- **多语言文案**：用户可见文案的 i18n key

## 二、资料来源渠道

| 资料类型 | 推荐渠道 |
|---|---|
| 用户流程与关键节点 | PRD、交互原型、用户流程图 |
| 业务事件清单 | 功能清单、PRD 功能需求章节 |
| AI 专项事件 | Agent / RAG / AIGC 需求文档（《05_Agent 需求》《06_RAG 需求》）、模型调用日志 |
| 公共字段 | 现有埋点 SDK 文档、数据团队规范 |
| 多语言文案 | i18n 文案管理平台、翻译团队 |
| 看板指标 | BI 看板需求、数据分析师需求清单 |
| 历史埋点 | 已上线版本的埋点表、数仓已有表结构 |

> **铁律**：埋点表不是"想到什么埋什么"——每个事件都必须能回答一个业务问题。如果埋了一个事件但没人看、不驱动任何决策，就不要埋。**埋点 = 决策的弹药**，不是越多越好。

## 三、完整框架结构（到三级标题）

> 以下 10 章骨架。**第 1、2、3、5、8、9、10 章是任何埋点表都不能省的**；第 5 章（AI 产品专项事件）是 AI 产品埋点表区别于传统互联网埋点表的核心章节。

### 3.1 埋点表说明（表头页）

- **这一节写什么**：一页纸讲清"这份埋点表服务什么决策、上报到哪个数仓、Owner 是谁、版本号"。
- **颗粒度要求**：至少 8 个字段——埋点目的 / 上报端 / 数据仓库 / Owner / 版本号 / 更新频率 / 适用产品 / 公共字段版本。
- **填写要点**：
  - **埋点目的要写清**：是"功能渗透率分析"还是"模型成本核算"还是"bad case 归因"——不同目的决定要埋哪些事件。
  - **上报端要列全**：iOS / Android / Web / 服务端 / 小程序，缺一个端就会漏数据。
  - **公共字段版本**：和数据团队的《公共字段规范》对齐，不要自己造字段名。
- **示例片段**：
  ```
  | 字段 | 值 |
  |---|---|
  | 埋点目的 | ① 核心功能渗透率 ② AI 对话轮次与采纳率 ③ 模型成本核算 ④ bad case 归因 |
  | 上报端 | iOS / Android / Web / 服务端 |
  | 数据仓库 | {自有数仓}（{表前缀 = product_a_}） |
  | Owner | {PM 姓名} |
  | 口径 Owner | {数据分析师姓名} |
  | 版本 | v{1.3}（{YYYY-MM-DD} 发布） |
  | 更新频率 | 每版本发布前 3 天冻结；新增功能随 PRD 同步 |
  | 适用产品 | {产品名 v2.x} |
  | 公共字段版本 | 数据团队《公共字段规范 v2.1》 |
  ```

### 3.2 埋点命名规范（事件名怎么取）

- **这一节写什么**：事件名必须有统一规范——否则 3 个月后没人知道 `btn_click_123` 是什么按钮。
- **颗粒度要求**：命名规则 + 反例 + 示例表。
- **填写要点**：
  - **统一用 snake_case**——不要驼峰、不要中文、不要数字编号。
  - **格式：模块_动作_对象**——如 `practice_start_click`、`rag_search_finished`、`answer_adopted`。
  - **版本后缀**：重大改版时加 `_v2`，如 `chat_send_v2`，避免旧事件口径混淆。
  - **禁止**：用用户可见文案当事件名（如"点击开始对练按钮"）、用序号（event_001）、用测试名（test_click）。
- **示例片段**：

  | 规则 | 正确示例 | 错误示例 |
  |---|---|---|
  | 模块_动作_对象 | `practice_start_click` | `click123` / `按钮点击` |
  | 动作统一 | `view / click / submit / success / fail` | `view_page / show_page / open_page`（同一个动作三种叫法） |
  | 对象统一 | `answer_adopted / answer_rejected` | `like_answer / answer_good / thumb_up_on_answer` |
  | 版本后缀 | `chat_send_v2` | `chat_send_new / chat_send_old` |
  | 全小写 snake_case | `rag_no_hit` | `RagNoHit` / `rag-no-hit` |

  > **动作词表（统一口径）**：
  > - 页面：`page_view`
  > - 曝光：`expose`
  > - 点击：`click`
  > - 提交：`submit`
  > - 成功：`success / finished`
  > - 失败：`fail / error`
  > - 开始：`start`
  > - 结束：`end`
  > - 采纳 / 拒绝：`adopted / rejected`
  > - 上传 / 下载：`upload / download`

### 3.3 六列字段详解（事件名 / 触发时机 / 属性字段 / 数据类型 / 多语言文案 / 埋点目的）

- **这一节写什么**：埋点表的最小行结构是六列——{事件名} / {触发时机} / {属性字段} / {数据类型} / {多语言文案} / {埋点目的}。本节给填写规范和完整示例表。
- **颗粒度要求**：每列给"写什么 / 怎么写 / 反例"；示例表至少 10 行覆盖不同类型事件。
- **填写要点**：
  - **触发时机要精确到"用户做了什么动作的哪一刻"**——不是"用户使用了功能"，而是"用户点击开始对练按钮、客户端发起采音请求前"。
  - **属性字段要列全**：每个事件的私有属性 + 公共字段。
  - **数据类型要明确**：string / int / float / bool / enum / timestamp——不写清楚研发就会乱传。
  - **多语言文案**：用户可见文案的 i18n key（不是中文原文），事件名本身固定英文。
  - **埋点目的必须能回答一个业务问题**——"这个数据拿来看什么"。
- **示例片段**：

  | 事件名 | 触发时机 | 属性字段 | 数据类型 | 多语言文案（i18n key） | 埋点目的 |
  |---|---|---|---|---|---|
  | `task_list_view` | 用户进入任务列表页时 | `task_type` / `task_count` / `entry_source` | string / int / enum | —（页面内文案走 i18n） | 统计任务列表日活、入口分布 |
  | `practice_start_click` | 用户点击"开始对练"按钮时 | `mic_auth_result` / `scene_id` | enum / string | `practice.button.start` | 统计开始对练点击量、麦克风授权失败率 |
  | `practice_started` | 成功创建会话并开始采音时 | `scene_version` / `session_id` / `user_id` | string / string / string | — | 统计实际开始对练会话数 |
  | `practice_ended` | 主动结束或异常中断时 | `duration` / `turn_count` / `end_type` | int / int / enum | — | 统计对练时长分布、轮次分布、中断率 |
  | `record_saved` | 对练记录保存完成时 | `audio_status` / `transcript_status` | enum / enum | — | 统计录音转写成功率 |
  | `score_finished` | 评分成功或失败时 | `score_status` / `rubric_version` / `score_total` | enum / string / int | — | 统计评分成功率、分数分布 |
  | `practice_error` | 语音 / 模型 / 保存 / 评分异常时 | `error_stage` / `error_code` / `retry_result` | enum / string / enum | `practice.toast.error.{code}` | 统计各环节错误率、错误码分布 |
  | `record_detail_view` | 查看对话记录或评分详情时 | `view_tab` / `record_id` | enum / string | — | 统计记录页渗透率、tab 分布 |
  | `share_click` | 用户点击分享按钮时 | `share_channel` / `record_id` | enum / string | — | 统计分享率、渠道分布 |
  | `favorite_click` | 用户点击收藏时 | `record_id` / `favorite_action` | string / enum | — | 统计收藏率 |

  > **六列填写常见错误**：
  > - **错误 1：触发时机太模糊**——"用户使用对练功能时"。正确："用户点击开始对练按钮、客户端发起采音请求前"。
  > - **错误 2：属性字段只写"其他参数"**——必须列全每个字段名和类型。
  > - **错误 3：多语言文案写成中文**——必须是 i18n key，如 `practice.button.start`，不是"开始对练"。
  > - **错误 4：埋点目的写"监控"**——必须具体到"看哪个决策"。

### 3.4 通用事件清单（页面 / 按钮 / 曝光 / 分享 / 收藏）

- **这一节写什么**：所有产品都要埋的通用事件——不管是 AI 产品还是传统产品，这 8-10 个事件是看板的基础。
- **颗粒度要求**：至少 10 个通用事件，每个给触发时机和目的。
- **填写要点**：
  - **通用事件不要每个产品重造**——直接复用本表的事件名，保证跨产品口径一致。
  - **曝光事件要带"位置"和"素材 id"**——不然不知道用户看到的是哪个版本。
- **示例片段**：

  | 事件名 | 触发时机 | 核心属性 | 埋点目的 |
  |---|---|---|---|
  | `app_launch` | App 冷启动 / 热启动 | `launch_source`（push / icon / deep_link） | 启动量、来源分布 |
  | `page_view` | 页面曝光 | `page_name` / `page_url` / `referrer` | 页面 PV/UV |
  | `expose` | 组件 / 卡片 / 按钮曝光 | `element_id` / `position` / `material_id` | 曝光率、素材效果 |
  | `click` | 任意可点击元素 | `element_id` / `position` | 点击率 |
  | `submit_success` | 表单 / 提交成功 | `form_id` / `duration_ms` | 转化率、耗时 |
  | `submit_fail` | 表单 / 提交失败 | `form_id` / `error_code` | 失败率、错误码 |
  | `share_click` | 点击分享 | `share_channel` / `content_id` | 分享率 |
  | `share_success` | 分享成功 | `share_channel` / `content_id` | 分享成功率 |
  | `favorite_click` | 收藏 / 取消收藏 | `content_id` / `action`（add / remove） | 收藏率 |
  | `search_submit` | 搜索提交 | `keyword` / `result_count` | 搜索量、零结果率 |

### 3.5 AI 产品专项事件清单（重点）

- **这一节写什么**：AI 产品和传统互联网产品最大的区别——必须埋"对话轮次、采纳率、报错率、成本、模型版本、拒答与转人工"这 6 类事件。没有这些事件，AI 产品的效果和成本根本无法衡量。
- **颗粒度要求**：6 大类每类至少 2-4 个事件，每个事件给触发时机、属性字段、埋点目的。
- **填写要点**：
  - **对话轮次类**：必须能算"平均会话轮次、首轮到结束的流失率"。
  - **采纳率类**：必须能算"答案采纳率、复制率、点赞 / 点踩率"——这是 AI 产品效果最直接的用户信号。
  - **报错率类**：必须按错误环节拆分（LLM / RAG / Tool / ASR / TTS），不能只埋一个"error"。
  - **成本类**：必须按 session 聚合 token 消耗，能算"单次会话成本、月活成本"。
  - **模型版本类**：必须记录"这一次响应用的是哪个模型版本、哪个 Prompt 版本、哪个知识快照"——bad case 归因的基础。
  - **拒答与转人工类**：必须能算"Agent 拒答率、转人工率、转人工解决率"——这是 AI 产品兜底能力的核心指标。
- **示例片段**：

  **① 对话 / 生成类**：
  | 事件名 | 触发时机 | 属性字段 | 埋点目的 |
  |---|---|---|---|
  | `conversation_start` | 用户开启新会话时 | `scene_id` / `entry_source` / `session_id` | 会话量、入口分布 |
  | `message_send` | 用户发送一条消息时 | `turn_index` / `message_length` / `channel` | 消息量、轮次分布 |
  | `message_receive` | 模型返回一条消息时（流式首字） | `turn_index` / `ttft_ms` / `model_version` | 首字延迟 |
  | `turn_end` | 一轮对话完整结束时 | `turn_index` / `duration_ms` / `token_input` / `token_output` | 单轮耗时、token 消耗 |
  | `conversation_end` | 会话结束（主动关闭 / 超时 / 转人工） | `total_turns` / `total_duration` / `total_token` / `end_reason` | 会话完整度、总成本 |

  **② 采纳率类**：
  | 事件名 | 触发时机 | 属性字段 | 埋点目的 |
  |---|---|---|---|
  | `answer_adopted` | 用户点击"采纳 / 使用此答案" | `session_id` / `turn_index` / `answer_id` | 答案采纳率 |
  | `answer_rejected` | 用户点击"不采纳 / 重新生成" | `session_id` / `turn_index` / `reject_reason`（enum） | 答案拒绝率、拒绝原因分布 |
  | `answer_copy` | 用户复制答案 | `session_id` / `turn_index` / `copy_length` | 复制率（隐含价值信号） |
  | `answer_thumb_up` | 用户点赞答案 | `session_id` / `turn_index` | 好评率 |
  | `answer_thumb_down` | 用户点踩答案 | `session_id` / `turn_index` / `down_reason`（enum） | 差评率、差评原因分布 |
  | `regenerate_click` | 用户点击"重新生成" | `session_id` / `turn_index` / `regenerate_count` | 重新生成率 |

  **③ 报错率类（按环节拆）**：
  | 事件名 | 触发时机 | 属性字段 | 埋点目的 |
  |---|---|---|---|
  | `llm_timeout` | LLM 调用超时 | `model_version` / `timeout_ms` / `session_id` | LLM 超时率 |
  | `llm_error` | LLM 返回错误（非超时） | `model_version` / `error_code` / `error_message` | LLM 错误率、错误码分布 |
  | `rag_retrieve_fail` | RAG 检索失败（timeout / service_error） | `kb_snapshot` / `error_code` / `query` | RAG 失败率 |
  | `rag_no_hit` | RAG 检索返回 no_hit | `query` / `kb_snapshot` / `filter_conditions` | 零结果率（优化知识库的输入） |
  | `rag_conflict` | RAG 返回资料冲突 | `query` / `conflict_group` | 冲突率（业务口径问题） |
  | `rag_permission_blocked` | RAG 因权限拦截 | `query` / `tenant_id` / `attempted_scope` | 越权尝试次数（安全监控） |
  | `tool_call_fail` | 工具调用失败 | `tool_name` / `error_code` / `retry_count` | 工具失败率 |
  | `asr_error` | 语音识别失败 | `audio_duration` / `error_code` | ASR 错误率 |
  | `tts_error` | 语音合成失败 | `text_length` / `error_code` | TTS 错误率 |

  **④ 成本类**：
  | 事件名 | 触发时机 | 属性字段 | 埋点目的 |
  |---|---|---|---|
  | `token_usage_report` | 每轮对话结束时（聚合） | `model_version` / `token_input` / `token_output` / `token_cache_hit` / `cost_estimate` | 单轮 token 消耗、成本 |
  | `cost_per_session` | 会话结束时（聚合） | `total_cost` / `total_token` / `model_composition` | 单次会话成本 |
  | `model_fallback_triggered` | 主模型失败 / 降级到备用模型 | `primary_model` / `fallback_model` / `trigger_reason` | fallback 率（模型稳定性） |

  **⑤ 模型版本类**：
  | 事件名 | 触发时机 | 属性字段 | 埋点目的 |
  |---|---|---|---|
  | `model_version_changed` | 线上模型版本发布 | `old_version` / `new_version` / `release_time` | 版本变更记录（bad case 归因） |
  | `prompt_version_changed` | Prompt 模板版本发布 | `old_version` / `new_version` / `change_summary` | Prompt 变更记录 |
  | `kb_snapshot_changed` | 知识快照发布 | `old_snapshot` / `new_snapshot` / `doc_count_delta` | 知识库变更记录 |
  | `experiment_bucket` | 用户进入实验分组时 | `experiment_id` / `bucket` / `model_version` / `prompt_version` | A/B 实验分组（和指标对齐） |

  **⑥ 拒答与转人工类**：
  | 事件名 | 触发时机 | 属性字段 | 埋点目的 |
  |---|---|---|---|
  | `agent_refused` | Agent 主动拒答（命中红线 / 越权 / 无答案） | `refuse_reason`（enum：red_line / no_hit / permission / out_of_scope） / `query` | 拒答率、拒答原因分布 |
  | `escalated_to_human` | Agent 转人工 | `escalate_reason` / `query` / `wait_time_ms` | 转人工率、原因分布 |
  | `human_takeover_finished` | 人工客服接管并结束 | `agent_id` / `duration` / `resolution_status` | 转人工解决率、人工处理时长 |
  | `user_request_human` | 用户主动要求转人工 | `query` / `wait_time_ms` | 用户主动转人工率 |

## 3.6 多语言文案设计

- **这一节写什么**：事件名固定英文 snake_case，但用户可见的 toast / 按钮 / 错误提示文案要 i18n。本节写清怎么设计 i18n key。
- **颗粒度要求**：i18n key 命名规范 + 多语言覆盖表 + 错误码到文案的映射规则。
- **填写要点**：
  - **i18n key 命名**：`模块.组件.动作`，如 `practice.button.start`、`practice.toast.error.timeout`。
  - **错误码到文案**：`practice_error` 事件的 `error_code` 直接映射到 `practice.toast.error.{code}`，不要在埋点里传中文文案。
  - **多语言覆盖**：至少覆盖中文 / 英文；按产品市场扩展。
- **示例片段**：

  | i18n key | 中文 | 英文 |
  |---|---|---|
  | `practice.button.start` | 开始对练 | Start Practice |
  | `practice.button.regenerate` | 重新生成 | Regenerate |
  | `practice.toast.error.timeout` | 响应超时，请重试 | Response timeout, please retry |
  | `practice.toast.error.permission` | 暂无权限 | No permission |
  | `practice.toast.error.kb_no_hit` | 暂时没有相关信息 | No related information found |

  > **铁律**：埋点里只传 i18n key 和错误码，**不传用户可见文案**——否则换语言、改文案都要改埋点代码。

### 3.7 属性字段字典（公共字段 + 业务字段）

- **这一节写什么**：所有事件都要带的公共字段、以及每个事件的业务字段。本节给字段字典。
- **颗粒度要求**：公共字段 ≥ 10 个，每个写类型、是否必填、取值范围；业务字段按事件归类。
- **填写要点**：
  - **公共字段一次定义、所有事件复用**——不要每个事件都重新定义 user_id。
  - **业务字段**：在 3.3 / 3.5 的示例表中已经列出，本节做汇总索引。
- **示例片段**：

  **公共字段字典（所有事件必带）**：
  | 字段 | 类型 | 必填 | 说明 / 取值 |
  |---|---|---|---|
  | `user_id` | string | 是 | 脱敏后的用户唯一标识 |
  | `session_id` | string | 是 | 会话唯一标识（AI 产品必带，用于聚合对话） |
  | `event_time` | timestamp | 是 | 事件发生时间（毫秒） |
  | `app_version` | string | 是 | App 版本号 |
  | `platform` | enum | 是 | ios / android / web / miniprogram / server |
  | `os_version` | string | 是 | 操作系统版本 |
  | `device_model` | string | 否 | 设备型号 |
  | `region` | string | 否 | 地区（国家 / 省份） |
  | `tenant_id` | string | B 端必填 | 租户标识（B 端 SaaS 必带） |
  | `network_type` | enum | 否 | wifi / 4g / 5g |
  | `experiment_id` | string | 实验时必填 | A/B 实验标识 |
  | `bucket` | enum | 实验时必填 | 实验组别 |

  **业务字段索引**：见 3.3 通用事件表和 3.5 AI 专项事件表的"属性字段"列。

### 3.8 数据质量校验

- **这一节写什么**：埋点上线后必须校验数据质量——上报率、去重、采样率、异常值。没有质量校验的埋点表 = 一堆垃圾数据。
- **颗粒度要求**：4 类质量校验，每类给阈值和校验方式。
- **填写要点**：
  - **上报率**：关键事件的客户端上报成功率 ≥ 99%；服务端接收成功率 ≥ 99.9%。
  - **去重**：同一事件同一 `event_time` 不重复上报；用 `event_id` 做幂等。
  - **采样率**：全量上报关键事件（对话、采纳、错误）；高频事件（如 message_receive 的流式 chunk）按 1-10% 采样。
  - **异常值监控**：单轮 duration > 300s、token 单轮 > 10 万、cost 单次 > ￥1，触发异常告警。
- **示例片段**：

  | 校验项 | 阈值 | 校验方式 | 不达标处置 |
  |---|---|---|---|
  | 关键事件上报率 | ≥ 99% | 客户端 SDK 心跳 vs 服务端接收量 | 排查 SDK 集成、网络拦截 |
  | 事件重复率 | < 0.1% | 按 event_id 去重统计 | 修复幂等逻辑 |
  | 必填字段缺失率 | < 0.5% | 抽样 1000 条检查 user_id / session_id | 补埋点 |
  | 枚举字段合法率 | ≥ 99.5% | 检查 platform / error_code 是否在字典内 | 修正枚举值 |
  | 单轮 duration 异常占比 | < 0.5% | 统计 > 300s 的轮次 | 排查超时、卡死 |
  | 单次成本异常占比 | < 0.1% | 统计 > ￥1 的 session | 排查 prompt 膨胀、死循环 |

### 3.9 与 BI 看板的衔接（埋点怎么变成看板指标）

- **这一节写什么**：埋点表的最终目的是驱动决策——本节写清每个埋点对应哪个看板指标。
- **颗粒度要求**：看板指标清单 + 指标计算公式 + 告警阈值。
- **填写要点**：
  - **每个埋点都要能落到一个看板指标**——如果落不上去，说明这个埋点没必要。
  - **AI 产品看板必看的 6 个核心指标**：会话量、平均轮次、采纳率、报错率、单次成本、拒答 / 转人工率。
- **示例片段**：

  | 看板指标 | 计算公式 | 数据来源事件 | 告警阈值 |
  |---|---|---|---|
  | 日活会话数 | COUNT(DISTINCT session_id) WHERE event = `conversation_start` | `conversation_start` | — |
  | 平均会话轮次 | AVG(total_turns) WHERE event = `conversation_end` | `conversation_end` | < 3 触发（用户聊不下去） |
  | 答案采纳率 | COUNT(adopted) / COUNT(message_receive) | `answer_adopted` / `message_receive` | < 30% 触发 |
  | 报错率 | COUNT(error events) / COUNT(message_receive) | `llm_error` / `rag_retrieve_fail` / `tool_call_fail` | > 5% 触发 |
  | 单次会话成本 | AVG(total_cost) WHERE event = `cost_per_session` | `cost_per_session` | > ￥0.05 触发 |
  | 拒答率 | COUNT(agent_refused) / COUNT(message_receive) | `agent_refused` | > 20% 触发（模型太保守） |
  | 转人工率 | COUNT(escalated_to_human) / COUNT(conversation_start) | `escalated_to_human` | > 10% 触发（AI 解决不了） |
  | RAG 零结果率 | COUNT(rag_no_hit) / COUNT(rag 检索总次数) | `rag_no_hit` | > 15% 触发（知识库要补） |

### 3.10 版本管理与上线前 Checklist

- **这一节写什么**：埋点表也要版本管理——每个版本新增 / 修改 / 删除了哪些事件，上线前要过哪些检查。
- **颗粒度要求**：版本号规则 + 变更记录表 + 上线前 Checklist（10 项）。
- **填写要点**：
  - **版本号规则**：v1.0 = 初版；v1.1 = 新增 < 10 个事件；v2.0 = 重大改版（口径变更、事件重命名）。
  - **上线前 Checklist**：埋点表必须在研发提测前冻结，测试环境先验数，再上生产。
- **示例片段**：

  | 版本 | 发布日期 | 事件数变化 | 主要变更 | 重跑要求 |
  |---|---|---|---|---|
  | v1.0 | 2026-09-01 | 25 个事件 | 初版 | — |

  **上线前 Checklist**：
  - [ ] 所有事件已和数据团队对齐口径
  - [ ] 公共字段已按《公共字段规范 v2.1》接入
  - [ ] 枚举字段取值范围已写死，研发不允许自由传
  - [ ] 多语言文案 i18n key 已接入翻译平台
  - [ ] 测试环境已跑通：客户端上报 → 服务端接收 → 数仓落表
  - [ ] 抽样 100 条验证：user_id / session_id / event_time 不缺失
  - [ ] 关键事件（conversation_start / answer_adopted / llm_error）上报率 ≥ 99%
  - [ ] BI 看板已配置好对应指标，告警阈值已设
  - [ ] 版本变更记录已更新
  - [ ] 已同步给 QA、数据分析师、算法团队

## 四、不同产品类别的差异化要点

### 4.1 A 类（对话式 AI / Agent 产品）
- **必埋重点**：对话轮次（`conversation_start` / `turn_end` / `message_send` / `message_receive`）、采纳率（`answer_adopted` / `answer_rejected` / `regenerate_click`）、拒答与转人工（`agent_refused` / `escalated_to_human`）。
- **重点关注指标**：平均会话轮次、采纳率、转人工率、首字延迟 TTFT。
- **特殊字段**：`agent_version` / `persona_id` / `tool_call_count`。

### 4.2 B 类（RAG 知识库 / 问答产品）
- **必埋重点**：RAG 全链路事件（`rag_search_finished` / `rag_no_hit` / `rag_conflict` / `rag_permission_blocked` / `rag_evidence_used`）、检索耗时、Top-k 数量、命中 chunk_id 列表。
- **重点关注指标**：RAG 零结果率、权限拦截率、引用正确率、检索 P95 延迟。
- **特殊字段**：`kb_snapshot` / `retrieval_id` / `top_k_chunks` / `rerank_score`。

### 4.3 C 类（AIGC 多模态生成产品）
- **必埋重点**：生成事件（`generation_start` / `generation_finished` / `generation_fail`）、模型 fallback（`model_fallback_triggered`）、生成成本、用户对生成结果的采纳 / 重新生成。
- **重点关注指标**：生成成功率、平均生成时长、单次生成成本、fallback 率。
- **特殊字段**：`prompt_template_version` / `model_version` / `resolution` / `duration` / `seed`。

### 4.4 D 类（AI 评测平台 / 内部工具）
- **必埋重点**：评测任务事件（`eval_task_start` / `eval_task_finished` / `eval_task_fail`）、Judge 一致性、bad case 闭环。
- **重点关注指标**：评测任务完成率、Judge 与人工一致性、bad case 修复率。
- **特殊字段**：`eval_set_version` / `model_under_test` / `judge_model` / `kappa_score`。

### 4.5 E 类（B 端 SaaS / 传统产品 AI 化）
- **必埋重点**：商户维度的使用频次、功能渗透率、AI 功能 vs 传统功能的使用率对比。
- **重点关注指标**：DAU / MAU、功能渗透率、AI 功能留存、商户成本（按租户聚合）。
- **特殊字段**：`tenant_id` / `merchant_id` / `plan_type`（free / pro / enterprise）。
