# 【功能排期表】SKILL

> **适用产品类别**：E 类（B 端 SaaS / 传统产品 AI 化）为主，A/B/C/D 类为辅。功能排期表是 E 类项目管理的中枢——把销售/售前/业务方抛回来的成百上千条需求收敛成一张 200 行左右的可控清单，让"本期做什么、谁在做、做到哪、哪些不做"一目了然。A/B/C/D 类产品在多功能并行迭代（如 Agent 平台同时做问答/生成/审核/评测）时也用它，但行数一般在 50-100 行；纯 MVP 单功能项目可以只用它替代完整版 Roadmap。
> **文档目的**：解决"需求满天飞、谁也说不清本期到底做什么、超纲需求没法回绝、已交付功能找不到验收记录"这四个问题。读者是产品经理、研发负责人、业务 Owner、项目经理、验收人。
> **撰写时机**：立项通过后、PRD 撰写前（先有功能清单再写 PRD）；每个迭代启动前更新一次；需求新增/变更/下线时实时更新。

---

## 一、撰写前需要收集的资料清单

### 需求侧
- 业务方/销售/售前带回来的所有原始需求清单（微信、邮件、工单、会议纪要）
- 每个需求的提出人、提出时间、原始话术（不要只记结论）
- 需求背后的真实场景（谁、在什么情况下、要解决什么问题）

### 业务侧
- 本期业务目标（要上线哪个客户/哪个部门/哪个场景）
- 已承诺客户的合同范围（SOW）
- 业务方指定的 P0/P1 优先级意见

### 技术侧
- 技术预研结论（哪些功能技术上已验证、哪些未验证、哪些做不了）
- 现有可复用能力（已预交付的接口、已上线的模块）
- 排期约束（研发人数、并行迭代数、外部依赖）

### 数据/合规侧
- 涉及数据合规的需求（录音、合同、PII、私有化部署）是否已过法务
- 涉及第三方授权的需求（爬取外部数据、商用字体、外部 API）是否已拿到授权

## 二、资料来源渠道

| 来源 | 拿什么 |
|---|---|
| 销售/售前/客户经理 | 客户原话、合同承诺、商务侧必须交付的范围 |
| 业务 Owner / 业务专家 | 优先级意见、SOP 依赖、验收标准 |
| 工单/客服/投诉系统 | 真实用户抱怨、高频问题、超纲需求的原始出处 |
| 竞品/行业方案 | 哪些功能是标配、哪些是差异化 |
| 技术预研文档 / Spikes | 可行性结论、单价、延迟、风险 |
| 项目周会/复盘会 | 已延期项、阻塞项、历史决策 |
| 飞书多维表格 / Sheet | 已有的功能清单（直接在其上迭代，不要重造） |

## 三、完整框架结构（到三级标题）

### 3.1 表结构：六列是最小完备集

- **这一节写什么**：功能排期表的最小列结构是六列——**需求 ID、模块、一级功能、二级功能、需求描述、备注（状态）**。
- **颗粒度要求**：一行 = 一个可独立交付、可独立验收、可独立排期的最小功能单元。不要一行塞三件事，也不要把一个按钮拆成三行。
- **填写要点**：
  - **需求 ID**：统一编号 R001、R002...，跨文档引用时用 ID 不用名字。ID 一旦分配不复用（即使需求被砍掉）。
  - **模块**：业务域/产品域大类（如"标准规范智能问答"、"可研报告生成"、"人力资源应用助手"），用于分组和筛选。
  - **一级功能**：模块下的功能域（如"问答智能体搭建"、"文档爬取"、"智能审查"）。
  - **二级功能**：一级功能下的具体能力点（如"切片定位"、"段落翻译"），可空。
  - **需求描述**：一句话说清"做什么、给谁、达到什么效果"，不写实现方案。
  - **备注/状态**：本期状态标签（见 3.2）。
- **示例片段**（真实结构提炼）：
  ```
  | 需求ID | 模块 | 一级功能 | 二级功能 | 需求描述 | 备注 |
  |---|---|---|---|---|---|
  | R001 | 标准规范智能问答 | 问答智能体搭建 | 问答智能体搭建 | 搭建可自定义的标准规范问答智能体 | 本期核心 |
  | R002 | 标准规范智能问答 | 答案溯源 | 切片定位 | 回答支持点击查看引用文档切片及召回分值 | 已预交付 |
  | R003 | 标准规范智能问答 | 文档爬取 | — | 爬取外部网站{行业}标准数据并入库 | 需合规授权，暂不确定 |
  | R004 | 标准规范智能问答 | 标准有效性检查 | — | 系统自动识别标准是否被废止/更新 | 客户自完成，超出范围 |
  | R005 | 标准规范智能问答 | 测试集 | — | 提供 95% 准确率测试集（50 问答对） | 验收条件 |
  | R008 | 可研报告生成 | 智能生成 | 市场分析报告模板 | 先训练市场分析模板，后续再扩展 | 本期优先 |
  | R011 | 可研报告生成 | PPT 生成 | 文生 PPT | 按目录自动生成可下载 PPT 成品 | 直接超纲，本期不做 |
  ```

### 3.2 状态标签体系（六类状态 + 备注写法）

- **这一节写什么**：备注列不是随便写，而是一套状态标签体系。每个需求在任意时刻只处于一个主状态。
- **颗粒度要求**：状态标签必须能一眼看出"做不做、谁做、什么时候交付"。
- **填写要点**：
  - 主状态六类：**待设计 / 待开发 / 待测试 / 已交付 / 超纲不做 / 暂不可交付**。
  - 附加修饰词：本期核心 / 本期优先 / 已预交付 / 接口已预交付 / 可预交付 / 验收条件 / 客户自完成。
  - "超纲不做"必须写清为什么超纲（直接超纲 / 需独立 BI / 依赖其他未建模块 / 需合规授权）。
  - "暂不可交付"必须写清阻塞原因（OCR 版式未知 / 资源库未建 / 依赖 R0xx / 合规授权未到位）。
- **状态流转图**：
  ```
  待设计 ──设计评审通过──> 待开发 ──开发完成──> 待测试 ──测试通过──> 已交付
    │                        │                       │
    │                        └──阻塞──> 暂不可交付（写明原因，解除后回待开发）
    │
    └──评审不通过/范围外──> 超纲不做（写明理由，不再回到待设计）
  ```
- **示例片段**（真实状态分布）：
  ```
  | 状态标签 | 含义 | 典型备注写法 |
  |---|---|---|
  | 本期核心 | 本期必须交付的 P0，验收硬指标 | "本期核心" |
  | 本期优先 | 本期要做但非硬验收 | "本期优先" |
  | 待设计 | 已立项但 PRD/原型未写完 | "待设计，预计 W3 出 PRD" |
  | 待开发 | PRD 已评审，排期已锁 | "待开发，@研发，W4 提测" |
  | 待测试 | 研发已提测，QA 验收中 | "待测试，W5 验收" |
  | 已交付 | 已上线/已预交付/接口已预交付 | "已预交付" / "接口已预交付" / "可预交付" |
  | 验收条件 | 不直接交付，但作为本模块验收门槛 | "验收条件：95% 准确率测试集（50 问答对）" |
  | 超纲不做 | 本期明确不做，写入范围外清单 | "直接超纲，本期不做" / "超纲，需独立 BI" |
  | 暂不可交付 | 想做但被外部依赖阻塞 | "OCR 版式未知，暂不可交付" / "依赖 R022，暂不可交付" / "需合规授权，暂不确定" |
  | 客户自完成 | 客户自己做，不纳入我方范围 | "客户自完成，超出范围" |
  ```

### 3.3 模块分组与优先级排序

- **这一节写什么**：整张表按模块分组，每个模块内按"本期核心 → 本期优先 → 可预交付 → 暂不可交付 → 超纲不做"排序。
- **颗粒度要求**：200 行规模的表，模块数一般 3-8 个；每个模块内本期核心不超过 5-8 项。
- **填写要点**：
  - 同一模块的需求排在一起，不要按提出时间散排。
  - 本期核心项用颜色/加粗/星号标注，让评审会上一眼能看到。
  - 超纲项不要删，保留在表尾并写明原因——这是回绝业务方的证据，也是下次排期的历史资产。
- **示例片段**：
  ```
  模块分组示意：
  ▎模块 A：{标准规范智能问答}（8 项）
    R001 问答智能体搭建        [本期核心]
    R002 答案溯源-切片定位     [已预交付]
    R005 测试集 50 问答对      [验收条件]
    R003 外部标准爬取          [需合规授权，暂不确定]
    R004 标准有效性检查        [客户自完成，超出范围]

  ▎模块 B：{可研报告生成}（10 项）
    R008 市场分析报告模板      [本期优先]
    R006 相似报告推荐          [接口已预交付]
    R007 一致性审查            [接口已预交付]
    R009 段落翻译              [已预交付]
    R010 重点提炼              [已预交付]
    R011 文生 PPT              [直接超纲，本期不做]
    R012 周报月报自动生成      [超纲，本期不做]
    R013 智能问数（NL2SQL）    [超纲，需独立 BI]
  ```

### 3.4 排期与责任映射（可选增强列）

- **这一节写什么**：如果表超过 50 行，建议在六列基础上加"优先级 / 里程碑 / 计划完成日期 / 负责人"四列。
- **颗粒度要求**：每个 P0 功能必须能看到排期里程碑（M1/M2/M3）和负责人；超纲项不需要排期。
- **填写要点**：
  - 里程碑用 M1/M2/M3 或 W1-WN，不要写"尽快"。
  - 负责人写到具体人（@某人），不写"前端组"。
  - 这是可研 PRD V2.0 功能清单表的标准增强列。
- **示例片段**：
  ```
  | 需求ID | 模块 | 一级功能 | 二级功能 | 需求描述 | 优先级 | 里程碑 | 完成日期 | 负责人 | 状态备注 |
  |---|---|---|---|---|---|---|---|---|---|
  | R001 | {模块A} | {一级} | {二级} | {一句话描述} | P0 | M1 | 8-10 | @算法 | 本期核心 |
  | R006 | {模块B} | 智能推送 | 相似报告推荐 | 根据当前报告推送历史相似报告 | P1 | M1 | 8-10 | @后端 | 接口已预交付 |
  ```

### 3.5 变更管理与版本记录

- **这一节写什么**：表尾或独立 sheet 记录变更日志——什么时候、谁、把哪个需求从什么状态改成什么状态、为什么。
- **颗粒度要求**：每次需求新增/状态变更/优先级调整都要留痕。
- **填写要点**：
  - 超纲项从"本期核心"改成"超纲不做"必须有业务/产品双签。
  - 已交付项不得回退到"待开发"；如要改，新增一行新版本需求。
- **示例片段**：
  ```
  | 日期 | 需求ID | 变更前 | 变更后 | 变更人 | 原因 |
  |---|---|---|---|---|---|
  | 2026-08-15 | R011 | 待设计 | 超纲不做 | @产品 | 评估后 PPT 生成质量不可控，本期不做 |
  | 2026-08-20 | R003 | 本期优先 | 暂不可交付 | @产品 | 外部数据爬取未拿到合规授权 |
  | 2026-09-01 | R008 | 待开发 | 待测试 | @研发 | 开发完成，提测 |
  ```

## 四、不同产品类别的差异化要点

### A 类（对话式 Agent 产品）
- 功能行数一般 30-60 行；模块按"角色 Agent / 评分 Agent / RAG / 语音链路 / 管理后台"分。
- 状态标签里建议加"已离线评测过闸 / 未过闸"——AI 能力项不能只按开发状态管，还要按评测状态管。
- "超纲不做"特别要写"不做自动认证/不做正式绩效判断"这类边界。

### B 类（RAG 知识库产品）
- 模块按"知识源准入 / 清洗切片 / 检索重排 / Agent 使用 / 调用契约 / 更新回滚 / 日志闭环 / Golden Set 评测"分。
- "验收条件"项特别多（Recall@5、引用正确率、无答案识别率），这些不是交付物本身，但是上线门槛。
- "暂不可交付"常见原因：知识源未授权、切片策略未调优、Embedding 模型未选型。

### C 类（AIGC 多模态生成产品）
- 模块按"素材上传 / 大纲生成 / 分章生成 / 全局优化 / 导出 / 对话助手"分。
- 每个生成能力项都要在备注里写清"采纳率目标"和"事实性错误率目标"。
- "超纲不做"常见：文生 PPT、自动排版、多风格模板库这些容易被业务方要求但质量不可控的项。

### D 类（评测平台 / 内部工具）
- 模块按"评测集管理 / 评分任务 / LLM-as-Judge / bad case 闭环 / 版本对比 / 报表"分。
- 状态标签建议加"金标已标注 / 未标注"——评测集没标完就不能进打分。
- "验收条件"项极多（每个模型、每个维度都有通过率门槛）。

### E 类（B 端 SaaS / 传统产品 AI 化）
- **这是本 SKILL 的主用类别**，行数 100-300 行。
- 模块按客户业务域分（如"标准规范问答"、"可研报告生成"、"HR 助手"），一个客户可能有 3-8 个模块。
- 状态标签必须区分"已预交付 / 接口已预交付 / 可预交付"三个层级——B 端项目大量复用已有接口，这三个状态直接影响排期。
- "客户自完成，超出范围"是 B 端特有的高频状态——客户内部系统自己做的事，不要揽过来。
- "直接超纲，本期不做"必须有书面记录，否则合同审计时会被追责。

## 五、完成度 Checklist

- [ ] 表结构是六列最小集（需求 ID / 模块 / 一级功能 / 二级功能 / 需求描述 / 状态备注），ID 连续不复用
- [ ] 每个需求是一个可独立交付、可独立验收、可独立排期的最小单元
- [ ] 状态标签落在六类主状态之一（待设计/待开发/待测试/已交付/超纲不做/暂不可交付）
- [ ] 本期核心项已用视觉方式标出（加粗/颜色/星号），数量控制在模块内 5-8 项
- [ ] 超纲项没有删除，保留在表尾并写明超纲原因
- [ ] 暂不可交付项写明阻塞原因（依赖 R0xx / 合规未授权 / 版式未知 / 资源库未建）
- [ ] 已预交付 / 接口已预交付 / 可预交付三个层级区分清楚
- [ ] 模块按业务域分组，模块数 3-8 个，整表规模 50-200 行
- [ ] 超过 50 行时已加优先级/里程碑/完成日期/负责人四列增强
- [ ] 表尾有变更日志（日期/需求 ID/变更前/变更后/变更人/原因）
- [ ] 超纲项从"本期核心"改出时，有产品/业务双签记录
- [ ] 每个 P0 需求都能在 PRD 中找到对应章节（ID 对得上）
- [ ] 没有"尽快"、"待定"、"以后再说"这种无效备注
- [ ] 本期范围、超纲范围、客户自完成范围三块边界清晰可对业务方复述

```
你是一名资深 AI 产品经理。请根据以下项目信息，产出一份功能排期表（Markdown 表格）。

【本期目标】{本期要上线哪个客户/哪个部门/哪个场景、要达成什么业务结果}
【原始需求清单】
{逐条粘贴业务方/销售/售前抛回来的原始需求，每条一行}
{需求1：...}
{需求2：...}
{需求3：...}
...

【技术预研结论】
{哪些已验证可做、哪些未验证、哪些做不了、哪些已有可复用接口}

【业务方优先级意见】
{业务方指定必须做的 P0 项、可做可不做的 P1 项}

【产品类别】{A/B/C/D/E}
【预计规模】{50 行以内 / 100-200 行}

要求：
1. 严格按六列结构输出：需求 ID（R001 起连续编号）、模块、一级功能、二级功能、需求描述（一句话）、状态备注
2. 模块按业务域分组，整表按模块聚类，不按提出时间散排
3. 每个需求只给一个主状态：待设计 / 待开发 / 待测试 / 已交付 / 超纲不做 / 暂不可交付
4. 状态备注用以下标签组合：本期核心 / 本期优先 / 已预交付 / 接口已预交付 / 可预交付 / 验收条件 / 客户自完成 / 需合规授权 / 依赖 R0xx
5. 超纲项必须写明超纲原因（直接超纲 / 需独立 BI / 依赖未建模块），不要删除
6. 暂不可交付项必须写明阻塞原因
7. 本期核心项每个模块不超过 5-8 个
8. 表尾附 5-10 行变更日志示例
9. 去具体化：不要使用真实公司名、产品名、行业名，全部用 {占位符}
10. 最后输出一份完成度 Checklist 供自查
```
