# 【测试反馈表】SKILL

> **适用产品类别**：**A/B/C/D/E 全类别**——A 对话式 Agent（幻觉/多轮上下文丢失是高频反馈类型）、B RAG 问答（检索召回/引用错误/误拒是高频类型）、C AIGC 生成（生成质量/风格偏离/参数失效是高频类型）、D 评测平台（评测任务本身的 Bug）、E B 端 SaaS（商户场景问题）。只要产品在测试，就需要反馈表；AI 产品的反馈表比传统软件多一整套"模型输出专项字段"。
> **文档目的**：把众测/内测/预发/发版各阶段收到的问题、体验、建议**结构化地收集起来**，让每一条反馈都能被分级、被认领、被修复、被复测、被关闭。没有结构化反馈表的团队，反馈只会散落在群聊、邮件、客服工单里——谁提了什么、谁在处理、修没修好，全靠记忆。读者是 PM（Owner）、QA（分级与验收）、研发（修复）、测试用户（提交人）。
> **撰写时机**：① 产品 0→1 阶段，第一版功能可测时就要建反馈表（不是等上线才建）；② 每个测试阶段开始前，根据阶段目标调整反馈表字段（众测简化、内测完整、预发加回归对照）；③ 发版后转为线上事故/监控反馈模板。

## 一、撰写前需要收集的资料清单

### 1.1 反馈单基础信息
- 反馈 ID 编号规则（如 FB-{日期}-{序号}）
- 提交人身份（测试用户/内部 QA/PM/客服转办）
- 反馈渠道（众测平台/内测群/应用内入口/工单/客服）
- 提交时间（含时区）

### 1.2 环境与版本信息
- 产品名、客户端版本号/构建号
- 测试阶段（众测/封闭内测/公开 Beta/预发 RC/正式发版）
- 部署环境（Prod/Staging/Dev）
- 操作系统与设备（iOS/Android/Web/桌面端 + 型号）、浏览器版本
- 网络环境（Wi-Fi/5G/弱网）
- **AI 特有**：模型名称与版本、功能模块、用户会话 ID（脱敏）

### 1.3 问题描述素材
- 问题标题（一句话，行动导向）
- 问题类型分类（Bug/体验/功能建议/内容质量/性能/隐私安全）
- 预期行为 vs 实际行为
- 复现步骤（编号列表）
- 截图/录屏/日志/错误信息附件

### 1.4 AI 模型输出专项素材（AI 产品必收）
- 问题子类（幻觉/伪造来源/答非所问/格式错误/误拒/延迟/偏见/上下文丢失/角色混淆/时间数字错误）
- 触发问题的完整用户输入原文（不能改写）
- 模型实际输出原文
- 对话历史（问题发生前的完整多轮上下文——AI Bug 报告最常缺的字段）
- 系统 Prompt / Prompt 版本号
- 采样参数（temperature/top_p/max_tokens）
- RAG/工具调用：是否检索、检索了什么、工具返回什么
- 复现性（每次都出现 / 偶尔几成 / 仅一次）
- 影响范围（只影响我 / 可能影响很多 / 不确定）

### 1.5 分级与流转信息（PM/QA 填）
- 严重度 Severity（S1-S4，测试定）
- 优先级 Priority（P0-P3，产品定）
- 是否系统性问题（查日志后判定）
- 处理人、状态流转、关联单号

## 三、完整框架结构（到三级标题）

> 以下 10 章骨架。**第 1、2、3、5、6、8、9 章是任何反馈表都不能省的**；第 4 章（AI 专项字段）是 AI 产品的核心差异；第 7 章（反馈 taxonomy）决定了后续统计分析的质量；第 10 章（使用说明）是给提交人和处理人看的操作手册。

### 3.1 反馈表说明（表头页）

- **这一节写什么**：一页纸讲清"这是什么反馈表、谁该填、怎么填、多久处理一次、Owner 是谁"。
- **颗粒度要求**：至少 8 个字段——反馈表名称 / 适用阶段 / 填写人 / 处理 Owner / SLA 时效 / 更新频率 / 当前版本 / 表地址。
- **填写要点**：
  - **适用阶段要写清**：是"众测简化版"还是"内测完整版"——不同阶段字段不一样。
  - **SLA 要具体到小时**："P0 2 小时响应、24 小时解决"而不是"尽快处理"。
  - **填写人要写清**：哪些字段是测试用户填、哪些字段是 PM/QA 填，不要让用户填严重度和优先级。
- **示例片段**：
  ```
  | 字段 | 值 |
  |---|---|
  | 反馈表名称 | {产品名}测试反馈表（AI 版） |
  | 适用阶段 | {封闭内测 / 公开 Beta / 预发 RC} |
  | 填写人 | 测试用户 + 内部 QA + PM |
  | 处理 Owner | {PM 姓名}（总负责）、{研发 Lead}（技术分级） |
  | SLA | P0 2h 响应 / 24h 解决；P1 8h / 3 天；P2 24h / 2 周；P3 2 天 / 季度 |
  | 更新频率 | 每日 10:00 分诊新反馈；每周四跨职能评审会 |
  | 当前版本 | v{1.2}（{YYYY-MM-DD} 发布） |
  | 表地址 | {飞书多维表格链接} |
  ```

### 3.2 反馈流程总览（7 步闭环）

- **这一节写什么**：一张流程图/一张表，讲清一条反馈从提交到关闭的完整生命周期。
- **颗粒度要求**：至少 7 个节点——提交 → 分诊 → 分级 → 认领 → 修复 → 复测 → 关闭；每个节点写清"谁做、多久、输出什么"。
- **填写要点**：
  - **分诊节点最关键**：每天有人专门看新反馈、打标签、派给处理人，不能让反馈石沉大海。
  - **复测节点不能省**：研发说修好了不算数，QA 要按原反馈复现步骤复测一遍。
  - **关闭前要回访**：P0/P1 反馈必须回复提交人，告诉人家"你提的问题修好了"。
- **示例片段**：

  | 节点 | 谁做 | 时效 | 输出 |
  |---|---|---|---|
  | 1. 提交 | 测试用户 | — | 一条反馈记录 |
  | 2. 分诊 | 值班 PM | 每日 10:00 前 | 打标签、初分类 |
  | 3. 分级 | QA + PM | 24h 内 | 严重度 S1-S4、优先级 P0-P3 |
  | 4. 认领 | 处理人 | 48h 内 | 状态变为"处理中" |
  | 5. 修复 | 研发/算法 | 按 SLA | 代码/Prompt/配置变更 |
  | 6. 复测 | QA | 修复后 24h | 通过/不通过（不通过退回修复） |
  | 7. 关闭 | PM | 复测通过后 | 回复提交人、状态关闭 |

### 3.3 第一部分：基本信息（表头字段）

- **这一节写什么**：反馈单的"身份证"——谁、什么时候、从哪个渠道、提的哪条反馈。
- **颗粒度要求**：至少 6 个字段——反馈 ID / 提交时间 / 提交人 / 联系方式 / 反馈渠道 / 所属版本。
- **填写要点**：
  - **反馈 ID 自动生成**：格式统一为 FB-{YYYYMMDD}-{序号}，不要让用户自己编。
  - **提交人要留联系方式**：众测用户留昵称 + 微信群，内部用户留飞书名——后续复测需要找得到人。
  - **反馈渠道单选**：众测平台 / 封闭内测群 / 应用内入口 / 客服转办 / 工单——不同渠道的反馈权重不同。
- **示例片段**：

  | 字段 | 类型 | 必填 | 示例/选项 |
  |---|---|---|---|
  | 反馈单号 | 自动编号 | 是 | FB-20261102-0001 |
  | 提交时间 | 日期时间 | 是 | 2026-11-02 18:00 GMT+8 |
  | 提交人 | 文本 | 是 | {张三 / 内测群昵称} |
  | 联系方式 | 文本 | 是 | {飞书/微信/邮箱} |
  | 反馈渠道 | 单选 | 是 | {众测平台 / 封闭内测群 / 应用内 / 客服转办 / 工单} |
  | 所属版本 | 单选 | 是 | {v2.3.1 build 4521} |

### 3.4 第二部分：环境与版本（必填）

- **这一节写什么**：反馈发生在什么环境下——不同设备、不同版本、不同网络下的问题，修复优先级完全不同。
- **颗粒度要求**：至少 8 个字段——测试阶段 / 产品版本号 / 部署环境 / 设备系统 / 网络 / 模型名称版本 / 功能模块 / 会话 ID。
- **填写要点**：
  - **测试阶段必须单选**：众测(开放) / 封闭内测 / 公开 Beta / 预发 RC / 正式发版——不同阶段的反馈表复杂度不同（见 3.7 节）。
  - **模型版本是 AI 产品的核心字段**：同一个 Prompt 在不同模型上表现可能完全不同，不知道模型版本就没法归因。
  - **会话 ID 要脱敏**：保留 sess_xxx 这种格式，让研发能反查日志，但不暴露用户隐私。
- **示例片段**：

  | 字段 | 类型 | 必填 | 示例/选项 |
  |---|---|---|---|
  | 测试阶段 | 单选 | 是 | {众测(开放) / 封闭内测 / 公开 Beta / 预发 RC / 正式发版} |
  | 产品版本号 | 文本 | 是 | {v2.3.1 build 4521} |
  | 部署环境 | 单选 | 是 | {生产 / 预发 / 测试} |
  | 设备与系统 | 文本 | 是 | {iPhone15 / iOS18.1 / Chrome130 / Win11} |
  | 网络 | 单选 | 否 | {Wi-Fi / 蜂窝 / 弱网} |
  | 模型名称版本 | 文本 | 是 | {claude-sonnet-4-6 / gpt-x / 自建 v3.2} |
  | 功能模块 | 单选 | 是 | {对话页 / 写作助手 / 编程助手 / 设置 / 登录…} |
  | 用户会话 ID | 文本 | 否 | {sess_xxx（脱敏）} |

### 3.5 第三部分：问题描述（必填）

- **这一节写什么**：反馈的主体——是什么问题、期望怎样、实际怎样、怎么复现。
- **颗粒度要求**：至少 6 个字段——问题标题 / 问题类型 / 预期行为 / 实际行为 / 复现步骤 / 附件。
- **填写要点**：
  - **问题标题要行动导向**："多轮对话第 5 轮后忘记用户姓名"而不是"对话有 bug"。
  - **预期 vs 实际分两栏写**：不要混在一段里，混在一起 QA 就分不清"是没达到预期"还是"和预期完全相反"。
  - **复现步骤要编号**：1) 新建对话 2) 告知姓名 3) 聊 4 轮别的 4) 问"我叫什么"——能按步骤复现的问题才是真问题。
  - **附件优先**：截图/录屏/日志比文字描述效率高 10 倍。
- **示例片段**：

  | 字段 | 类型 | 必填 | 示例/选项 |
  |---|---|---|---|
  | 问题标题 | 文本 | 是 | {多轮对话第 5 轮后忘记用户姓名} |
  | 问题类型 | 单选 | 是 | {功能 Bug / 体验问题 / 模型输出质量 / 性能 / 功能建议 / 隐私安全} |
  | 预期行为 | 多行文本 | 是 | {应记住用户姓名并在后续对话中继续使用} |
  | 实际行为 | 多行文本 | 是 | {第 5 轮后改称"这位用户"，完全忘记之前说过的名字} |
  | 复现步骤 | 多行文本 | 是 | {1) 新建对话 2) 告知"我叫张三" 3) 聊 4 轮无关话题 4) 问"我叫什么"} |
  | 附件 | 附件 | 否 | {录屏.mp4 / 截图.png / 日志.txt} |

### 3.6 第四部分：AI 模型输出专项（AI 产品核心差异，重点）

- **这一节写什么**：传统软件的 Bug 到上一节就结束了，但 AI 产品的"问题"往往不是代码错，而是模型输出不对——需要一整套字段来定位是 Prompt 问题、检索问题还是模型能力问题。
- **颗粒度要求**：至少 9 个字段——问题子类 / 用户输入原文 / 模型输出原文 / 对话历史 / 系统 Prompt 版本 / 采样参数 / RAG/工具调用 / 复现性 / 影响范围。
- **填写要点**：
  - **问题子类要多选**：一个反馈可能同时是"幻觉 + 上下文丢失"，不要只选一个。
  - **用户输入必须原文粘贴**：不要让用户"概括一下问题"——原话里的措辞、语气、语序都可能影响模型输出，概括了就没法复现。
  - **对话历史是最常缺的字段**：AI 产品的问题 80% 出在多轮上下文，但用户往往只贴最后一句。必须强制要求"问题发生前的完整多轮上下文"。
  - **RAG 产品必须附召回内容**：如果是 RAG 问答，要写清"检索了哪些 chunk、source_id 是什么、为什么召回了这些、有没有召回错误文档"。
- **示例片段**：

  | 字段 | 类型 | 条件必填 | 示例/选项 |
  |---|---|---|---|
  | AI 问题子类 | 多选 | 条件必填 | {幻觉/事实错误 / 伪造来源或引用 / 答非所问 / 格式错误 / 误拒合法请求 / 响应延迟或超时 / 偏见或不当内容 / 多轮上下文丢失或混淆 / 角色身份混淆 / 时间或数字错误} |
  | 用户输入原文 | 多行文本 | 条件必填 | {粘贴原话，不要改写："我叫张三，帮我写个周报…"} |
  | 模型输出原文 | 多行文本 | 条件必填 | {粘贴实际回复："好的，这位用户，我来帮你写…"} |
  | 对话历史 | 多行文本 | 条件必填 | {前 4 轮完整内容（用户说什么、Agent 回什么）} |
  | 系统 Prompt 版本 | 文本 | 否 | {sys_prompt_v12} |
  | 采样参数 | 文本 | 否 | {temp=0.7, top_p=0.9, max_tokens=2048} |
  | RAG/工具调用情况 | 文本 | 条件必填 | {是否检索知识库、召回了哪些 chunk、工具返回了什么} |
  | 复现性 | 单选 | 是 | {每次都出现 / 偶尔（3 成）/ 仅一次} |
  | 影响范围 | 单选 | 否 | {只影响我 / 可能影响较多 / 不确定} |

  > **AI 问题子类 10 类详细定义**（搭表单时直接用）：
  > - **幻觉/事实错误**：编造了不存在的事实、数据、人物、事件
  > - **伪造来源或引用**：引用了不存在的文档、错误的页码、编造的链接
  > - **答非所问**：回答和用户问题完全不相关
  > - **格式错误**：JSON/Markdown/Schema 结构错乱、输出格式不符合要求
  > - **误拒合法请求**：该回答的问题不回答、错误地走了拒答分支
  > - **响应延迟或超时**：首字延迟 >5s、总时长 >30s、直接超时
  > - **偏见或不当内容**：输出含有歧视、偏见、不适当内容
  > - **多轮上下文丢失或混淆**：忘记前文、混淆不同用户、上下文串台
  > - **角色身份混淆**：跳出人设、暴露内部 Prompt、忘记自己是 AI
  > - **时间或数字错误**：日期算错、数字算错、单位换算错

### 3.7 第五部分：严重度分级与 SLA（PM/QA 填）

- **这一节写什么**：不是所有问题都一样急——要分严重度（技术影响多大）和优先级（业务上多急），并定好 SLA 时效。
- **颗粒度要求**：严重度 4 级 + 优先级 4 级 + SLA 表 + 是否系统性问题判定。
- **填写要点**：
  - **严重度 vs 优先级是两回事**：严重度是"技术影响多大"（测试定），优先级是"业务上多急"（产品定）。一个边缘场景的幻觉严重度是 S3，但如果是付费客户投诉的，优先级可以是 P1。
  - **AI 产品的严重度要特殊考虑**："输出含有违法内容"即使只出现一次也是 S1；"偶尔格式错乱"影响不大是 S3。
  - **是否系统性问题要查日志后判定**：不能用户说"我遇到了"就当真，要查"受影响的会话有多少"。
- **示例片段**：

  **严重度（Severity，测试定）**：

  | 等级 | 定义 | AI 产品示例 |
  |---|---|---|
  | S1 阻断 | 崩溃/核心功能完全不可用/安全问题 | 输出违法内容、直接宕机、所有请求都超时 |
  | S2 严重 | 主要功能出错，无 workaround | 幻觉率 >30%、多轮上下文全丢、RAG 完全不召回 |
  | S3 一般 | 功能可用但体验受损，有 workaround | 偶尔格式错、首字延迟 >5s、部分场景误拒 |
  | S4 轻微 | UI/文案/不影响使用 | 错别字、按钮位置奇怪、提示文案不友好 |

  **优先级（Priority，产品定）**：

  | 等级 | 定义 | 时效 |
  |---|---|---|
  | P0 立即 | 安全/合规/资损 | 数小时内 |
  | P1 本迭代 | 核心路径高频问题 | 本版本内 |
  | P2 下迭代 | 边缘场景/体验问题 | 下版本 |
  | P3 Backlog | 偶发/极低价值 | 需求池 |

  **SLA 对照表**：

  | 优先级 | 响应时限 | 解决时限 | 升级路径 |
  |---|---|---|---|
  | P0 | 2h | 24h | 直接抄送产品负责人 |
  | P1 | 8h | 3 天 | 周会评审 |
  | P2 | 24h | 2 周 | 排期评审 |
  | P3 | 2 天 | 季度 | 需求池投票 |

### 3.8 第六部分：4 阶段流程差异（众测/内测/预发/发版）

- **这一节写什么**：反馈表不是一套字段走天下——不同测试阶段的目标、参与者、反馈重点、表复杂度都不一样。
- **颗粒度要求**：一张大表，列 4 个阶段（众测/封闭内测/预发 RC/正式发版），行是维度（参与者/环境/目标/反馈重点/表复杂度/退出标准/AI 特殊关注）。
- **填写要点**：
  - **众测/开放 Beta：表要简化**——用户量大、表单太长没人填，只留核心字段（标题/描述/截图/联系方式），复杂的 AI 专项字段由 PM 后续补。
  - **封闭内测：表要完整**——受邀的都是核心用户/员工，愿意认真填，AI 专项字段全上。
  - **预发 RC：加回归对照**——这阶段主要是验证"之前的 bug 修没修好"，要加"关联原反馈 ID"字段。
  - **正式发版：转事故模板**——线上问题不是"反馈"，是"事故"，要用事故复盘模板，而不是测试反馈表。
- **示例片段**：

  | 维度 | 众测/开放 Beta | 封闭内测 | 预发 RC | 正式发版后 |
  |---|---|---|---|---|
  | 参与者 | 公开大量早期用户 | 受邀核心用户/员工+忠实客户 | 内部+小比例灰度 | 全量+客服工单 |
  | 环境 | 类生产真实环境 | 受控测试环境 | 预发（接近生产） | 生产 |
  | 主要目标 | 真实场景、兼容性、体验广度 | 功能正确性、早期 Bug | 回归、稳定性、Go/No-Go | 监控、线上事故、长尾 |
  | 反馈重点 | 体验问题、功能建议、易用性 | 功能 Bug、模型输出质量、阻塞 | 回归验证、性能、安全 | P0/P1 事故、监控告警 |
  | 反馈表复杂度 | 可简化（轻量表单 6-8 字段） | 完整字段（含 AI 专项 20+ 字段） | 完整+回归用例对照 | 事故复盘模板为主 |
  | 退出/准入标准 | — | S1/S2 Bug 清零才能进 Beta | 零严重度 Bug、自动化全过、安全评审完成才放 GA | P1 事故 ≤ 阈值 |
  | AI 特殊关注 | 用户对生成质量的主观感受 | 幻觉/误拒/格式错误是否可控 | 多轮上下文、RAG、延迟回归 | 模型版本变更退化监控 |

### 3.9 第七部分：反馈分类 Taxonomy（打标用）

- **这一节写什么**：反馈收上来要打标签——不然后续统计的时候，没法回答"这个版本哪类问题最多"。
- **颗粒度要求**：一级分类 6-8 类 + 二级细分 + AI 专属标签单列。
- **填写要点**：
  - **一级分类建议**：功能 Bug / AI 输出质量 / 体验问题 / 性能问题 / 内容安全 / 功能建议 / 商务计费 / 其他。
  - **AI 专属标签必须单列**：幻觉/上下文丢失/误拒/误答/格式错误/工具调用失败——这些不是传统软件的"功能 Bug"，是 AI 特有的。
  - **taxonomy 要持续迭代**：每季度评审一次，新聚类连续 2 周占比 >3% 就新增类别。
- **示例片段**：

  | 一级分类 | 二级分类 | 说明 |
  |---|---|---|
  | **功能 Bug** | 无法使用 / 结果错误 / 崩溃 / 数据错误 | 传统软件的代码问题 |
  | **AI 输出质量** | 幻觉 / 上下文丢失 / 误拒 / 误答 / 格式错误 / 工具调用失败 | AI 产品专属 |
  | **体验问题** | UX 困惑 / 文案不清 / 入口难找 / 学习成本高 | 非 Bug 但影响使用 |
  | **性能问题** | 首字延迟 / 总时长 / 并发失败 / 超时 | 速度类 |
  | **内容安全** | 不当内容 / 偏见歧视 / 隐私泄露 | 合规类 |
  | **功能建议** | 新功能 / 功能增强 / 流程优化 | 用户主动提的需求 |
  | **商务计费** | 价格 / 扣费 / 套餐 / 退款 | 商业类 |
  | **其他** | 其他 | 兜底 |

### 3.10 第八部分：处理闭环与回灌评测集

- **这一节写什么**：反馈不是收上来就完了——要走完"提交→认领→修复→复测→关闭"的闭环；有代表性的 badcase 还要回灌到评测集，形成"线上发现问题→补进评测集→下次回归必测"的飞轮。
- **颗粒度要求**：闭环流程 + 回灌规则 + 闭环考核指标。
- **填写要点**：
  - **闭环是反馈表的灵魂**：没有 Owner、没有 SLA、没有关闭确认的反馈表，只是"反馈垃圾桶"。
  - **badcase 回灌评测集**：P0/P1 且有代表性的 badcase，修复后必须补进评测集——否则下次改 Prompt 又会在同一个地方翻车。
  - **闭环考核指标**：首次响应时长、平均解决时长、超期率、复测通过率、badcase 回灌率。
- **示例片段**：

  **闭环流程**：
  1. 新反馈 → 值班 PM 分诊打标（每日 10:00 前）
  2. QA + PM 分级定 S1-S4 / P0-P3（24h 内）
  3. 处理人认领（48h 内）
  4. 研发/算法修复（按 SLA 时效）
  5. QA 按原复现步骤复测（修复后 24h 内）
  6. 复测通过 → PM 回复提交人 → 关闭
  7. 复测不通过 → 退回修复，记录原因

  **badcase 回灌规则**：
  - P0/P1 且有代表性的 badcase，修复后 3 天内补进评测集
  - 补题时标注来源（"来自 FB-20261102-0015"），方便追溯
  - 每月统计 badcase 回灌率 = 已回灌的 P0/P1 数 / 总 P0/P1 数（目标 ≥80%）

  **闭环考核指标**：
  - 首次响应时长（目标 <4h）
  - 平均解决时长（目标 <7 天）
  - 超期率（目标 <10%）
  - 复测通过率（目标 >90%）
  - badcase 回灌率（目标 ≥80%）

## 四、不同产品类别的差异化要点

### A 类（对话式 AI / Agent 产品）
- **AI 专项字段是重中之重**：幻觉、多轮上下文丢失、角色混淆、工具调用失败是高频反馈类型。
- **对话历史必须强制填写**：A 类产品 80% 的问题出在多轮上下文，但用户往往只贴最后一句。
- **pass³ 复测**：修复后不能只测一次，要连跑 3 次都过才算真修好（LLM 有随机性）。
- **复现性字段很重要**：A 类输出随机性大，"偶尔出现"和"每次都出现"的归因方向完全不同。

### B 类（RAG 知识库 / 问答产品）
- **RAG 专项字段必收**：召回了哪些 chunk、source_id、为什么召回错误文档。
- **误拒是高频问题**：知识库有答案但 Agent 说"不知道"——这类问题要单独打标。
- **引用溯源错误**：引用了不存在的文档、错误的页码——这是 RAG 产品的特有 Bug。
- **权限过滤问题**：不同 org/角色的知识是否被正确隔离——B 端 RAG 必测。

### C 类（AIGC 多模态生成产品）
- **问题子类偏"质量类"**：风格偏离、动作不自然、崩坏、指令遵循失败——不是传统软件的"功能 Bug"。
- **必须附生成素材**：prompt + 参考图 + 生成图——没有素材没法判断是 prompt 写得不好还是模型能力不行。
- **参数敏感问题**：同一 prompt 不同 seed/步数/分辨率下表现不同——要记录参数。
- **人工评分维度**：C 类问题不能二值通过/不通过，要按 1-5 分从多个维度打分。

### D 类（AI 评测平台 / 内部工具）
- **反馈的是评测任务本身**：评测题出错、Judge 判定不准、平台 bug、导出格式错误。
- **评测集质量反馈**：如果评测题本身有问题（金标错了、题目有歧义），也算一类反馈。
- **LLM-as-Judge 一致性**：Judge 和人工打分不一致的 case 要单独收集，用于优化 Judge Prompt。

### E 类（B 端 SaaS / 传统产品 AI 化）
- **反馈来源偏工单**：商户/客服转办的多，不是用户主动在应用内提。
- **商户场景特殊性**：不同商户类型（A 类商户/B 类商户）下的问题要分开记录。
- **AI 功能相对少**：可能只有一个"AI 助手"入口，反馈类型集中在回答不准/答非所问。
- **数据看板问题**：AI 功能的数据看板是否正确显示——这也是一类反馈。
