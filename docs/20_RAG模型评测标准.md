# RAG 模型评测标准 SKILL

> **适用产品类别**：**B 类（RAG 知识库 / 问答产品）为主**——RAG 评测标准是 RAG 0→1 选型和版本回归的判定基准；**D 类（AI 评测平台）为辅**——评测平台要支持 RAG 类产品的评测标准模板；**A 类（对话式 Agent）为辅**——Agent 带知识库检索时，引用 B 类的评测标准；C 类和 E 类一般不单独编写 RAG 评测标准，引用 B 类或 D 类的即可。
> **文档目的**：把"RAG 系统好不好"这件事拆成可量化、可对比、可回归的指标体系——不是凭感觉说"答得还行"，而是有 Faithfulness、Context Recall、Negative Rejection 这些具体指标，每个指标有公式、有阈值、有 badcase 归因。RAG 评测标准是评测集和评测报告之间的**判定契约**：评测集定义"用什么题"，本标准定义"怎么算对"，评测报告定义"结果怎么呈现"。读者是 PM（标准 Owner）、算法（用标准做自动判定）、QA（执行人工评测）、标注员（按标准标注 golden chunk）。
> **撰写时机**：① RAG 项目 0→1 阶段，Golden Set 第一版出来之前——标准必须先于题目确定；② 每次 Embedding / Rerank / LLM / Prompt 版本更新前——确定回归门槛；③ 线上 bad case 归因时——用指标定位是哪一层的问题。

## 〇、RAG 评测的五大目标维度

RAG 不是单一指标能衡量的——它要同时回答五个问题：

```
用户问了一个问题
    │
    ▼
┌─────────────────────────────────────────────┐
│  1. 检索得准吗？（Retrieval Quality）          │
│     - 该召回的知识召回来了吗？                 │
│     - 不该召回的有没有混进来？                 │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│  2. 生成得对吗？（Generation Quality）         │
│     - 答案是基于检索到的知识生成的吗？          │
│     - 有没有幻觉？有没有答非所问？              │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│  3. 该拒答时拒了吗？（Negative Rejection）      │
│     - 知识库里没有的问题，会不会硬编答案？       │
│     - 不该拒的问题，有没有乱拒？               │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│  4. 快不快？（Latency）                        │
│     - 用户等多久才能拿到答案？                  │
│     - 首字延迟、总时长分别是多少？              │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│  5. 贵不贵？（Cost）                           │
│     - 单次调用成本是多少？                     │
│     - QPS 上来之后扛得住吗？                   │
└─────────────────────────────────────────────┘
```

**这五个维度的优先级**：
- **安全底线**：Negative Rejection（拒答正确率）必须 ≥95%，这是红线——知识库没有的问题硬编答案，是 RAG 最大的信任杀手。
- **核心效果**：Faithfulness（忠实度）≥0.9、Context Recall@5 ≥0.85，这是及格线。
- **体验指标**：TTFT ≤2s、单次成本 ≤￥0.05，这是体验线。

### 1.1 业务侧
- **业务场景一句话**：客服问答 / 内部知识库 / 搜索增强 / 法律问答 / 金融投研

- **用户对答案准确性的容忍度**：错一个数字行不行？（医疗/金融 = 不行；客服 = 小错可以）
- **红线场景**：哪些问题绝对不能硬编答案

### 1.2 检索侧
- **Embedding 模型候选**：3-5 个，各有公开榜单分数
- **Rerank 模型候选**：2-3 个
- **切片策略**：chunk_size、overlap、切片函数
- **Top-K 当前值**：现在取多少，要不要调

### 1.3 生成侧
- **LLM 候选**：3-5 个
- **Prompt 版本**：System Prompt、User Prompt 全文
- **输出格式要求**：要不要引用、要不要结构化模板

### 1.4 评测集侧
- **业务 QA 集**：100-500 条 query + 参考答案 + golden chunk 标注

- **双标一致性要求**：Cohen's Kappa ≥0.7

## 三、完整框架结构（到三级标题）

> 以下 10 章骨架。**第 1、2、3、4、5、7、10 章是任何 RAG 评测标准都不能省的**；第 6 章（引用溯源）和第 8 章（评测集设计）根据产品需要裁剪；第 9 章（Judge 配置）在自动评测时必写。

### 3.1 RAGAS 四指标详解：Faithfulness（忠实度）

- **这一节写什么**：Faithfulness 是 RAG 生成层最核心的指标——答案里的每一句话，是不是都能在检索到的 context 里找到依据。
- **颗粒度要求**：定义 + 计算公式 + 达标阈值 + 典型 badcase + 常见误区。
- **填写要点**：
  - **Faithfulness 不评答案对不对**——它评的是"答案是不是基于 context 生成的"。答案和 context 一致 = 忠实；答案自己编了 = 不忠实。
  - **和 Factual Correctness 的区别**：Factual Correctness 是"答案和标准答案对不对得上"；Faithfulness 是"答案和检索到的 context 对不对得上"。RAG 场景先评 Faithfulness——如果连检索到的内容都不忠实，就不用谈和标准答案对不对了。
- **示例片段**：

  **Faithfulness 定义**：
  > 答案中所有可被 context 支持的陈述数，除以答案中总陈述数。
  > 计算公式：Faithfulness = 被支持的陈述数 / 总陈述数

  **怎么算（RAGAS 实现方式）**：
  1. LLM 把答案拆成 N 个原子陈述（Atomic Statements）
  2. 对每个陈述，LLM 判断：这个陈述能不能从 context 里推导出来？
  3. 能推导出来的陈述数 ÷ 总陈述数 = Faithfulness 分数

  **达标阈值**：
  | 分数 | 等级 | 说明 |
  |---|---|---|
  | ≥0.9 | 优秀 | 几乎没有幻觉，可上线 |
  | 0.7-0.9 | 及格 | 有少量幻觉，核心结论正确 |
  | <0.7 | 不及格 | 幻觉严重，不能上线 |

  **典型 badcase**：
  - **badcase 1（事实幻觉）**：context 写"退款 7 天无理由"，答案写"退款 3 天无理由"——数字错了，Faithfulness 扣分。
  - **badcase 2（编造来源）**：答案引用了"根据《XXX 规定》第 3 条"，但 context 里根本没有这个规定——Faithfulness = 0。
  - **badcase 3（过度推断）**：context 写"钻石充值后 7 天内可退款"，答案写"钻石充值后 7 天内可退款，每年最多退 2 次"——"每年最多 2 次"是编造的，Faithfulness 扣分。

  **常见误区**：
  - **误区 1：Faithfulness = 答案正确性**——错。答案可能完全错误，但 Faithfulness 是 1.0（因为答案完全照搬了错误的 context）。
  - **误区 2：Faithfulness 只看有没有引用**——错。引用了不代表忠实，引用了但内容和 context 对不上，还是不忠实。
  - **误区 3：人工拆陈述**——成本太高。用 LLM 自动拆陈述 + 自动判定，再抽样人工校验。

### 3.2 RAGAS 四指标详解：Answer Relevance（答案相关性）

- **这一节写什么**：Answer Relevance 评的是——答案有没有切题，有没有答非所问。
- **颗粒度要求**：定义 + 计算方法 + 达标阈值 + 典型 badcase。
- **填写要点**：
  - **Answer Relevance 和 Faithfulness 是两个维度**：Faithfulness 评"有没有基于 context"，Answer Relevance 评"有没有回答用户的问题"。
  - 常见的 badcase：context 是 A 文档，答案答的是 B 文档的内容——Faithfulness 可能很高（因为答案是基于 context 的），但 Answer Relevance 很低（因为答非所问）。
- **示例片段**：

  **Answer Relevance 定义**：
  > 答案是否切题，是否回答了用户的原始问题。
  > 计算方法（RAGAS）：让 LLM 根据答案反推一个 question，然后算反推的 question 和原 question 的 embedding 相似度。

  **达标阈值**：
  | 分数 | 等级 | 说明 |
  |---|---|---|
  | ≥0.8 | 优秀 | 答案切题，没有答非所问 |
  | 0.6-0.8 | 及格 | 答案沾边，但有冗余信息 |
  | <0.6 | 不及格 | 答非所问，答的不是用户问的 |

  **典型 badcase**：
  - **badcase 1（答非所问）**：用户问"退款流程是什么"，答案写"退款规则是 7 天无理由"——只答了规则，没答流程，Answer Relevance 扣分。
  - **badcase 2（冗余太多）**：用户问"怎么退款"，答案写了一大段公司介绍、产品历史，最后才提了一句退款——冗余信息太多，Answer Relevance 扣分。
  - **badcase 3（跳题）**：用户问 A，context 里有 A 和 B，答案把 A 和 B 都答了——跳题，Answer Relevance 扣分。

### 3.3 RAGAS 四指标详解：Context Precision（上下文精度）

- **这一节写什么**：Context Precision 评的是——检索到的 top-k 里，有多少是真正相关的。
- **颗粒度要求**：定义 + 计算公式 + 达标阈值 + 典型 badcase。
- **填写要点**：
  - **Context Precision 是检索层的指标**，不是生成层的。
  - Precision 高 = top-k 里大部分是相关的；Precision 低 = top-k 里混了很多不相关的噪声。
  - Precision 低的后果：LLM 被噪声带偏，Faithfulness 下降。
- **示例片段**：

  **Context Precision@k 定义**：
  > top-k 个检索结果中，相关 chunk 的占比。
  > 计算公式：Context Precision@k = 相关 chunk 数 / k

  **达标阈值**：
  | 分数 | 等级 | 说明 |
  |---|---|---|
  | ≥0.8 | 优秀 | top-k 里大部分是相关的，噪声少 |
  | 0.5-0.8 | 及格 | 有一些噪声，但核心信息在 |
  | <0.5 | 不及格 | top-k 里一半以上是噪声，LLM 容易被带偏 |

  **典型 badcase**：
  - **badcase 1（噪声太多）**：top-5 里只有 1 个相关的，其他 4 个都是同领域但不相关的——Precision = 0.2，不及格。
  - **badcase 2（排序不对）**：top-5 里有 3 个相关的，但最相关的那个排在第 5 位——Precision = 0.6，及格但不优秀。
  - **badcase 3（完全不相关）**：用户问退款，召回的都是产品介绍——Precision = 0，完全跑偏。

### 3.4 RAGAS 四指标详解：Context Recall（上下文召回率）

- **这一节写什么**：Context Recall 评的是——golden chunks（标准答案应该用到的段落）有多少被召回了。
- **颗粒度要求**：定义 + 计算公式 + 达标阈值 + 典型 badcase。
- **填写要点**：
  - **Context Recall 是检索层最重要的指标**——如果 golden chunk 没被召回，LLM 再强也答不对。
  - **Recall 低的后果**：答案凭空编造（因为没有正确的 context），Faithfulness 下降。
  - **Recall 和 Precision 的权衡**：k 越大，Recall 越高，但 Precision 越低——要找甜点。
- **示例片段**：

  **Context Recall@k 定义**：
  > golden chunks 中，被 top-k 召回的比例。
  > 计算公式：Context Recall@k = |golden ∩ top-k| / |golden|

  **达标阈值**：
  | 分数 | 等级 | 说明 |
  |---|---|---|
  | ≥0.85 | 优秀 | 几乎所有该召回的都召回了 |
  | 0.7-0.85 | 及格 | 核心信息召回了，但有遗漏 |
  | <0.7 | 不及格 | 关键信息没召回，答案一定错 |

  **典型 badcase**：
  - **badcase 1（关键 chunk 没召回）**：golden chunk 有 3 个，top-5 只召回了 1 个——Recall = 0.33，不及格。
  - **badcase 2（多跳题漏召回）**：用户问"A 和 B 的区别"，需要同时召回 A 的段落和 B 的段落——只召回了 A，没召回 B——Recall = 0.5，及格但不优秀。
  - **badcase 3（权限过滤过度）**：golden chunk 存在，但因为元数据过滤把它滤掉了——Recall = 0，这是配置问题，不是 Embedding 问题。

  **Recall vs Precision 权衡**：
  | k 值 | Recall@k | Precision@k | 说明 |
  |---|---|---|---|
  | k=3 | 0.70 | 0.80 | 召回太少，漏得多 |
  | k=5 | 0.85 | 0.60 | 甜点：召回够了，精度也还行 |
  | k=10 | 0.92 | 0.35 | 召回全了，但噪声太多 |

  > **推荐 k=5**：Recall 0.85 够用，Precision 0.6 也还行。如果 k=5 Recall 不够，先换更好的 Embedding，而不是盲目调大 k。

### 3.5 Negative Rejection（无答案拒答）

- **这一节写什么**：Negative Rejection 是 RAG 场景的红线指标——知识库里没有答案的问题，系统应该说"不知道"，而不是硬编一个答案。
- **颗粒度要求**：什么样的 query 算"库中无答案" + 拒答话术规范 + 误拒率 / 漏拒率两个指标。
- **填写要点**：
  - **两个方向都要测**：漏拒（该拒的没拒，硬编了）和误拒（不该拒的拒了，答不了）。
  - **漏拒是红线**：漏拒率高 = 幻觉多，信任崩塌。
  - **误拒是体验问题**：误拒率高 = 不好用，用户问什么都说不知道。
- **示例片段**：

  **什么样的 query 算"库中无答案"**：
  | 类型 | 示例 | 算不算无答案 |
  |---|---|---|
  | 知识库完全没有的主题 | 用户问"怎么申请补贴"，知识库全是退款相关 | 算，应该拒答 |
  | 知识库没有的时效信息 | 用户问"今天天气怎么样"，知识库没有天气 | 算，应该拒答 |
  | 知识库有但不完整 | 用户问"退款需要什么材料"，知识库只说了 7 天规则，没说材料 | 半算——应该说"目前了解到的规则是……，具体材料请咨询客服" |
  | 知识库有但权限不够 | 用户问其他部门的内部资料 | 算，应该拒答（权限不足） |

  **拒答话术规范**：
  - ❌ 不好的拒答："我不知道。"（太生硬）
  - ❌ 不好的拒答："这个问题我回答不了，请你问别人。"（太敷衍）
  - ✅ 好的拒答："关于这个问题，目前我了解到的信息有限。我可以帮你联系客服同事，或者你也可以查阅《XXX 手册》。"
  - **核心原则**：拒答不等于不服务——要告诉用户"我能做什么"，而不是只说"我不能做什么"。

  **两个指标**：
  | 指标 | 定义 | 达标阈值 |
  |---|---|---|
  | **漏拒率**（False Rejection Negative） | 该拒的问题里，没拒、硬编了答案的比例 | ≤5%（红线） |
  | **误拒率**（False Rejection Positive） | 不该拒的问题里，错误地拒了的比例 | ≤10%（体验线） |

  **典型 badcase**：
  - **badcase 1（漏拒——硬编答案）**：知识库没有"活动退款"的规则，用户问"活动期间能退款吗"，系统编了一个"活动期间不支持退款"——这是幻觉，红线。
  - **badcase 2（误拒——该答不答）**：知识库有"退款流程"的完整答案，用户问"我想退款怎么办"，系统说"这个问题我不太清楚，建议联系客服"——这是误拒，体验差。
  - **badcase 3（拒答话术太生硬）**：系统说"我不知道"就结束了——用户体验不好，要加兜底指引。

### 3.6 检索指标：Top-K 命中率 / MRR@K / NDCG@K / Golden Chunk 命中率

- **这一节写什么**：除了 RAGAS 的 Context Precision / Recall，检索层还有几个传统信息检索指标，用来更细粒度地评估排序质量。
- **颗粒度要求**：4 个检索指标的定义 + 计算公式 + 各自适用场景。
- **填写要点**：
  - **RAGAS 的 Context Precision / Recall 是"有没有召回"**，传统指标是"排得好不好"。
  - **MRR@K**：第一个正确结果排在第几位——衡量"最相关的排得够不够靠前"。
  - **NDCG@K**：考虑位置的排序质量——越相关的排越前面，分数越高。
  - **Hit Rate@K**：top-k 里有没有至少一个正确的——最简单的召回率。
- **示例片段**：

  **检索层 4 大指标对比**：

  | 指标 | 定义 | 公式 | 适用场景 | 达标阈值 |
  |---|---|---|---|---|
  | **Hit Rate@k** | top-k 里至少有一个正确结果的比例 | \|存在正确 chunk 的 query 数\| / 总 query 数 | 粗看召回率 | ≥0.9 |
  | **MRR@k** | 第一个正确结果排名的倒数的平均值 | (1/rank₁ + 1/rank₂ + ...) / N | 看最相关的排得够不够靠前 | ≥0.7 |
  | **NDCG@k** | 考虑位置的归一化折损增益 | 见 NDCG 公式 | 精细评估排序质量 | ≥0.75 |
  | **Golden Chunk 命中率** | golden chunks 被召回的比例（= Context Recall@k） | \|golden ∩ top-k\| / \|golden\| | 业务集的精细召回评估 | ≥0.85 |

  **怎么选指标**：
  - **快速评估**：Hit Rate@5 + MRR@5 就够了——简单直观。
  - **精细选型**：NDCG@10 + Context Recall@5 + Context Precision@5 三件套——能看出排序的好坏。
  - **上线监控**：Hit Rate@5 + Golden Chunk 命中率——最容易自动化，适合线上埋点。

### 3.7 Top-K 参数与重排阈值

- **这一节写什么**：Top-K 取多少、Rerank 后取多少、Rerank 阈值怎么定——这些参数直接影响效果和成本。
- **颗粒度要求**：Top-K 参数怎么选 + Rerank 阈值怎么定 + 什么时候触发重排。
- **填写要点**：
  - **Top-K 不是越大越好**：k 越大，Recall 越高，但 Precision 越低，成本也越高。
  - **Rerank 不是必须加的**：如果 k=5 时 Recall 已经够了，就不需要 Rerank——加了反而增加延迟和成本。
  - **Rerank 阈值**：相似度分数低于阈值的直接过滤掉，不要送入 LLM——减少噪声。
- **示例片段**：

  **Top-K 参数选择指南**：

  | 场景 | 推荐 k | 理由 |
  |---|---|---|
  | 事实型问答（简单） | k=3-5 | 单跳问题，一个 chunk 就够了 |
  | 多跳推理（中等） | k=8-10 | 需要 2-3 个 chunk 综合回答 |
  | 法律 / 医疗（复杂） | k=15-20 | 需要多个条款 / 多个段落综合 |

  **Rerank 后 Top-N**：
  - Rerank 一般把 top-20 重排成 top-5 或 top-8
  - **N=5 是常用值**：送入 LLM 的 context 不要太多，否则 prompt 太长、成本太高、LLM 容易丢信息

  **Rerank 阈值**：
  - Cross-Encoder 输出的是 0-1 之间的相关性分数
  - **阈值设为 0.3**：分数低于 0.3 的 chunk 直接过滤，不送入 LLM
  - 阈值不是拍脑袋定的——要用业务集测：阈值从 0.1 调到 0.5，看 Faithfulness 和 Recall 的变化，找甜点

  **什么时候触发 Rerank**：
  - **不是所有 query 都要 Rerank**——简单的事实型问题，Embedding 召回就够了，不需要 Rerank
  - **触发条件**：query 长度 > 20 字 或 置信度分数 < 阈值 → 触发 Rerank
  - 这样可以省成本——不是每次都走最重的 Rerank 路径

### 3.8 引用溯源质量（Source 引用规范）

- **这一节写什么**：RAG 产品的答案应该带引用——让用户知道答案来自哪里、可追溯。引用质量也是评测的一部分。
- **颗粒度要求**：source_id 真实存在率 + 引用与结论支持率 + 引用格式规范。
- **填写要点**：
  - **引用不是可有可无的装饰**——RAG 的核心价值之一就是可追溯、可验证。
  - **常见 badcase**：引用了不存在的 source_id、引用了但内容和结论对不上、引用格式混乱。
- **示例片段**：

  **引用质量 2 大指标**：

  | 指标 | 定义 | 达标阈值 |
  |---|---|---|
  | **source_id 真实存在率** | 答案中引用的 source_id，在知识库中真实存在的比例 | 100%（红线——不能引用不存在的文档） |
  | **引用与结论支持率** | 答案中的结论，能被引用的 source 内容支持的比例 | ≥0.9 |

  **引用格式规范**：
  - ✅ 好的格式："根据《退款政策》第 2 条（source_id: DOC_001），7 天内可无理由退款。"
  - ❌ 不好的格式："退款可以 7 天无理由。"（没有引用，不知道来自哪里）
  - ❌ 不好的格式："根据相关规定，7 天内可退款。"（引用模糊，不知道是哪个规定）
  - ❌ 不好的格式："根据《XXX 规定》第 3 条。"（但 source_id 根本不存在——幻觉）

  **典型 badcase**：
  - **badcase 1（编造来源）**：答案写"根据《用户手册》第 5 章"，但知识库中根本没有《用户手册》——source_id 真实存在率 = 0，红线。
  - **badcase 2（引用和结论对不上）**：结论是"退款需要身份证"，引用的 source 是"退款 7 天无理由"——引用和结论不支持，支持率扣分。
  - **badcase 3（引用太多）**：答案一句话引了 5 个 source——引用过载，用户看不过来。

### 3.9 LLM-as-Judge 在 RAG 场景的特殊配置

- **这一节写什么**：RAG 场景的 LLM-as-Judge 和通用场景不同——Judge 要同时看答案、context、query 三方，而不是只看答案。
- **颗粒度要求**：Judge Prompt 模板（RAG 专用）+ 温度参数 + 人工校验 Kappa 要求。
- **填写要点**：
  - **RAG Judge 必须输入三方**：query + context + answer——不能只给 answer 让 Judge 打分。
  - **RAG Judge 要分维度打**：Faithfulness、Answer Relevance、Context Precision 分开打，不要一个总分。
  - **Judge 模型要够强**：至少 GPT-4o / Claude 3.5 Sonnet 级别——弱模型自己都拆不好陈述。
- **示例片段**：

  **RAG 专用 Judge Prompt 模板**：
  ```
  你是一名专业的 RAG 系统质量评测员。请根据以下信息，对答案进行多维度评分。

  【用户问题】{query}
  【检索到的 Context】{retrieved_context}
  【AI 生成的答案】{model_answer}

  请按以下维度分别打分（每个维度 0-1 分）：

  1. Faithfulness（忠实度）：答案中的每一句话，是否都能在 context 中找到依据？
     - 1.0 = 所有陈述都能从 context 推导出来
     - 0.5 = 有一半陈述有依据，一半是自己编的
     - 0.0 = 答案完全和 context 无关，自己编的
     - 扣分原因：……

  2. Answer Relevance（答案相关性）：答案有没有切题，有没有回答用户的问题？
     - 1.0 = 完全回答了用户的问题，没有冗余
     - 0.5 = 沾边，但有冗余信息或答了一半
     - 0.0 = 答非所问
     - 扣分原因：……

  3. Context Precision（上下文精度）：检索到的 context 里，有多少是真正相关的？
     - 1.0 = 所有 context 都和问题相关
     - 0.5 = 一半相关，一半噪声
     - 0.0 = 全是噪声
     - 扣分原因：……

  请输出 JSON 格式：
  {
    "faithfulness": 0.xx,
    "answer_relevance": 0.xx,
    "context_precision": 0.xx,
    "reasons": "……"
  }
  ```

  **配置要求**：
  | 参数 | 推荐值 | 理由 |
  |---|---|---|
  | Judge 模型 | {GPT-4o / Claude 3.5 Sonnet} | 能力够强，能拆陈述、能判断 |
  | 温度 | 0 | 减少随机性，同一输入多次打分一致 |
  | 抽样人工校验 | 每批抽 20% | 校验 Judge 和人工的一致性 |
  | Kappa 目标 | ≥0.7 | 低于 0.7 = Judge 不可信，要调 Prompt |

### 3.10 RAG 版本回归门槛（每次更新后必须重跑哪些指标）

- **这一节写什么**：RAG 系统的任何一层改动（换 Embedding / 换 Rerank / 换 LLM / 改 Prompt / 加新知识），都必须重跑评测——不能"改完就上线"。
- **颗粒度要求**：不同层改动对应的必跑指标 + 回归门槛 + 全量重跑 vs 增量重跑。
- **填写要点**：
  - **任何改动都要回归**：哪怕只是改了一句 Prompt，也要重跑——因为 Prompt 变了，生成质量可能变。
  - **分层改动对应分层指标**：改 Embedding 重点看检索指标，改 LLM 重点看生成指标。
  - **红线指标永远要重跑**：Negative Rejection 不管改哪层，都必须重跑。
- **示例片段**：

  **不同改动对应的回归指标**：

  | 改动类型 | 必跑指标 | 门槛要求 | 重跑范围 |
  |---|---|---|---|
  | **换 Embedding 模型** | Context Recall@5、Context Precision@5、MRR@5、Hit Rate@5 | Recall 下降 >5% = 不通过 | 全量重跑 |
  | **换 Rerank 模型** | NDCG@10、Hit@1、Faithfulness（因为 context 变了） | NDCG 下降 >5% = 不通过 | 全量重跑 |
  | **换 LLM 模型** | Faithfulness、Answer Relevance、Negative Rejection、TTFT、成本 | Faithfulness 下降 >3% = 不通过 | 全量重跑 |
  | **改 Prompt** | Faithfulness、Answer Relevance、Negative Rejection | 任意指标下降 = 不通过 | 全量重跑 |
  | **加新知识** | 新增题目的召回率、整体 Recall@5 | 新增题目 Recall <0.8 = 不通过 | 增量重跑（新增题目）+ 全量红线题 |
  | **改 Top-K 参数** | Recall@k、Precision@k、Faithfulness、成本 | Recall 下降 >5% = 不通过 | 全量重跑 |

  **回归门槛（通用）**：
  - **红线指标**：Negative Rejection 漏拒率 ≤5%——任何改动后必须满足
  - **核心指标**：Faithfulness ≥0.85、Context Recall@5 ≥0.80——任何改动后不能比上一版下降超过 3%
  - **体验指标**：TTFT P95 ≤2s、单次成本 ≤￥0.05——任何改动后不能超预算

  **什么时候全量重跑，什么时候增量重跑**：
  - **全量重跑**：换模型、换 Prompt、改参数——影响面大，必须全量
  - **增量重跑**：加新知识、改了个别 chunk——只跑新增的题目 + 全部红线题
  - **全量重跑频率**：每季度至少一次，哪怕没有改动——因为新模型在发布，要看看有没有更好的选择

## 四、不同产品类别的差异化要点

### A 类（对话式 AI / Agent 产品）
- **RAG 评测标准是辅助**——Agent 的核心是多轮对话和工具调用，RAG 只是其中一个能力。
- **重点指标**：多轮状态下的 Faithfulness（多轮对话中是否保持事实一致）、工具调用结果的 Groundedness。
- **不需要单独建 RAG 评测集**——引用 B 类的指标，在 Agent 评测集里加几道 RAG 相关题即可。

### B 类（RAG 知识库 / 问答产品）
- **本标准的原生场景**——RAG 评测标准是 RAG 产品的核心度量体系。
- **必须全量**：RAGAS 四指标 + Negative Rejection + 检索指标 + 引用质量——一个都不能少。
- **必须分层归因**：bad case 要落到是 Embedding 没召回、Rerank 没排上、还是 LLM 没读对。

### C 类（AIGC 多模态生成产品）
- **一般不适用**——C 类是生成产品，不是检索增强产品。
- 如果有素材检索（如婚纱馆的样片检索），可以引用 B 类的检索指标，但生成质量用 C 类自己的标准。

### D 类（AI 评测平台 / 内部工具）
- **本标准是平台的模板之一**——评测平台要内置 RAG 类评测标准模板。
- **重点**：Judge 模型本身的质量也要评测——LLM-as-Judge 在 RAG 场景的准确性是平台的核心 KPI。

### E 类（B 端 SaaS / 传统产品 AI 化）
- **引用 B 类的评测标准即可**——不需要从零起一套。
- **重点调整**：成本门槛（B 端对成本更敏感）、拒答话术（B 端场景更正式）。
