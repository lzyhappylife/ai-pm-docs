# 【功能分析报告】SKILL

> **适用产品类别**：A / B / C / D / E 全类别。功能分析报告是产品中后期的核心文档——不是从零定义产品，而是"我们想加一个功能，先看看别人都怎么做"。A 类对话式产品加"语音通话"功能时，对比 Character.AI / Replika / 小手机怎么做；B 类 RAG 产品加"多知识库切换"功能时，对比 Dify / FastGPT / 店智参谋怎么做；C 类 AIGC 产品加"批量生成"功能时，对比 Midjourney / 即梦 / 可灵怎么做。
> **文档目的**：针对一个具体的功能需求，横向拆解 3-5 个竞品在该功能上的实现方式，输出"别人怎么做、好在哪、差在哪、我们该怎么做"的决策依据。读者是产品 Owner、研发负责人、业务方。
> **撰写时机**：产品已上线、进入迭代期；当你想新增一个功能、或对现有功能做重大调整时，先写这份报告再开 PRD。

---

## 一、撰写前需要收集的资料清单

### 功能定义侧
- 你要分析的功能到底是什么？一句话定义（不要只写"语音通话"，要写"用户和 AI 角色实时语音对话，AI 能听懂并即时回应"）
- 功能要解决的核心问题（用户为什么需要这个功能？现在怎么解决的？痛点是什么？）
- 我们的目标用户是谁？他们在什么场景下用这个功能？
- 功能的优先级和预期指标（上线后要达到什么效果？使用率/满意度/留存提升多少？）

### 竞品侧
- 哪些竞品有这个功能？选 3-5 个（不能太少，至少 3 个才有横向对比意义）
- 竞品选择标准：直接竞品 2 个 + 跨界参考 1-2 个（比如做语音功能，参考微信/抖音的语音设计也是跨界参考）
- 每个竞品的产品阶段（成熟产品 vs 早期产品，设计思路不同）
- 每个竞品的目标用户和定位（不同定位的产品，功能设计思路完全不同）

### 技术实现侧
- 这个功能涉及的技术栈（比如语音通话涉及 ASR/TTS/实时传输/回声消除）
- 我们团队的技术能力边界（哪些能做、哪些要外包、哪些做不了）
- 成本预估（按次/按时长，竞品的收费模式是什么？）

### 用户反馈侧
- 我们自己的用户有没有提过这个功能？提了多少？怎么说的？
- 竞品的用户评论里，这个功能的好评/差评是什么？
- App Store / 应用宝 / 小红书上的相关评价截图

## 三、完整框架结构（到三级标题）

### 3.0 文档概述

- **这一节写什么**：一页纸说清"这份报告要分析什么功能、为什么现在要分析、选了哪些竞品、预期输出什么结论"。
- **颗粒度要求**：功能定义必须一句话能讲清楚；竞品清单至少 3 个、最多 5 个；预期结论要具体（比如"决定做/不做/怎么做"）。
- **填写要点**：
  - 先明确"为什么现在要做这个功能"——是用户提的？是竞品都有？还是老板要求的？动机不同，分析的侧重点不同。
  - 竞品选择要"宁精勿滥"——3 个深度体验过的竞品，比 5 个只看了官网的强。
- **示例片段**：
  ```
  | 功能名称 | {功能名，一句话定义} |
  | 背景动机 | {用户诉求/竞品压力/业务目标} |
  | 分析竞品 | 1. {竞品A}（直接竞品） 2. {竞品B}（直接竞品） 3. {竞品C}（跨界参考） |
  | 预期输出 | 功能是否要做、如果做的话怎么做、差异化点在哪 |
  | 撰写人 / 日期 | {姓名} / {日期} |
  ```

### 3.1 功能需求拆解

- **这一节写什么**：把"我们想加个功能"这个模糊想法，拆成具体的需求点和衡量标准。
- **颗粒度要求**：至少拆成 3 个核心需求点；每个需求点要有"用户场景"和"成功标准"。
- **填写要点**：
  - 不要只写"我们要有语音通话功能"，要拆成：1）用户发起通话的方式 2）AI 实时回应的能力 3）通话结束后的沉淀（录音/摘要/待办）
  - 每个需求点要问"用户为什么需要这个"——不要为了做功能而做功能。
- **示例片段**：
  ```
  功能一句话定义：{用户在聊天界面一键发起语音通话，AI 角色实时语音回应，对话结束后自动生成摘要和待办}

  核心需求拆解：
  | # | 需求点 | 用户场景 | 成功标准 |
  |---|--------|---------|---------|
  | 1 | 一键发起通话 | 用户打字打累了，想直接说话 | 发起通话点击率 ≥ 30% |
  | 2 | AI 实时语音回应 | 用户想听到角色的声音、有真实感 | 通话满意度 ≥ 4.0/5.0 |
  | 3 | 通话沉淀 | 重要的事不想在通话里说完就忘 | 通话后摘要查看率 ≥ 50% |
  ```

### 3.2 竞品功能横向对比表

- **这一节写什么**：一张大表，把每个竞品在该功能上的做法逐维度列出来，禁止"较好/一般"这种模糊描述，必须具体到"怎么做的"。
- **颗粒度要求**：至少 5 个对比维度；每个单元格写具体做法，不写评价词；表格宽度超过一页时，分横向对比表和详细拆解表两张。
- **填写要点**：
  - 对比维度要从"用户体验全链路"出发：入口位置 → 触发方式 → 交互流程 → 输出形式 → 异常处理 → 增值功能
  - 每个单元格写"它是怎么做的"，而不是"它做得好不好"——评价放在后面的结论章节。
- **示例片段**：
  ```
  | 对比维度 | 竞品A | 竞品B | 竞品C |
  |---------|-------|-------|-------|
  | 入口位置 | 聊天页右上角电话图标 | 长按语音条弹"语音通话" | 首页底部Tab"通话" |
  | 触发方式 | 点击图标直接发起 | 长按语音条→选择"语音通话" | 进入专属通话页 |
  | 交互流程 | 3-2-1倒数接通，实时对话 | 打字+语音混合，可切换 | 纯语音模式，无文字 |
  | 输出形式 | 实时语音+字幕 | 语音+文字双输出 | 纯语音，结束后生成文字摘要 |
  | 异常处理 | 网络差自动降为文字 | 网络差提示重连 | 网络差直接挂断 |
  | 增值功能 | 通话中可发图片 | 通话中可暂停/回放 | 通话结束生成摘要+待办 |
  | 收费模式 | 免费 | 免费，高级角色收费 | 按时长收费 |
  ```

### 3.3 每个竞品的功能详细拆解

- **这一节写什么**：横向对比表看的是"点"，详细拆解看的是"面"——每个竞品的这个功能完整的用户旅程是什么样的，设计思路是什么。
- **颗粒度要求**：每个竞品至少拆到 5 个步骤；每个步骤描述用户操作和系统反馈；要写"为什么这么设计"（设计意图，不是只写现象）。
- **填写要点**：
  - 按用户旅程拆：进入 → 操作 → 结果 → 离开 → 后续
  - 不仅写"它做了什么"，还要写"它没做什么"——没做的地方往往就是差异化机会。
  - 特别注意异常状态（网络差/权限不足/内容违规）的处理，这是最容易看出产品功力的地方。
- **示例片段**：
  ```
  【竞品A 语音通话功能拆解】

  用户旅程：
  1. 入口发现：聊天页右上角电话图标，旁边有"新"红点提示 → 设计意图：引导用户尝试
  2. 发起通话：点击图标 → 3-2-1倒数动画 → 模拟拨号等待音 → 接通
  3. 通话中：实时语音对话，底部有字幕条，可点"静音"/"挂断"
  4. 异常处理：网络差时自动降为文字模式，提示"网络不佳，已切换为文字"
  5. 结束通话：挂断按钮 → 弹出"通话时长 XX 分钟，要保存录音吗？"
  6. 后续沉淀：保存的录音在"回忆"页可以回放，自动生成对话摘要

  设计亮点：
  - 倒数动画让用户有"真实打电话"的仪式感
  - 网络降级处理很丝滑，不是硬切断

  设计不足：
  - 没有通话中发图片/表情的功能
  - 摘要质量一般，经常漏关键信息
  ```

### 3.4 优劣势分析与用户评价

- **这一节写什么**：结合竞品拆解 + 用户评论，总结每个竞品在这个功能上的优势和劣势，以及真实用户怎么评价。
- **颗粒度要求**：每个竞品至少列 3 个优势、3 个劣势；用户评价至少引用 2-3 条真实评论（截图或原话）。
- **填写要点**：
  - 优势/劣势要从"用户价值"角度写，不要从"技术角度"写——"响应速度快"不如"网络差的时候也能聊"
  - 用户评价要找极端的（最好的和最差的），不要找中庸的——极端评价最能暴露问题
- **示例片段**：
  ```
  【竞品A 语音通话 优劣势】

  优势：
  1. 仪式感强，用户接通率高
  2. 网络降级处理丝滑，不打断对话
  3. 有字幕，嘈杂环境也能用

  劣势：
  1. 没有通话中发图片的功能
  2. 摘要质量一般
  3. 免费额度少，很快就要收费

  用户评价：
  - "第一次接通话的时候真的有心跳加速的感觉，太真实了"（App Store 5星）
  - "网络稍微差一点就变文字了，体验打折"（小红书吐槽帖）
  ```

### 3.5 功能设计方向建议

- **这一节写什么**：看完所有竞品后，我们应该怎么做？给出明确的设计方向建议。
- **颗粒度要求**：至少给 2 个方案选项（推荐方案 + 备选方案）；每个方案说明"借鉴了谁、差异化在哪、成本预估、预期效果"。
- **填写要点**：
  - 不要只写"我们要做一个更好的"——要具体到"借鉴 A 的仪式感 + 借鉴 C 的摘要 + 加一个我们独有的 X"
  - 一定要写"我们不做什么"——这是防止范围蔓延的关键
  - 成本预估要粗算（开发量 + 运营成本 + 边际成本），不要拍脑袋
- **示例片段**：
  ```
  【推荐方案】

  设计思路：
  - 借鉴竞品A的通话仪式感（倒数动画+拨号音）
  - 借鉴竞品C的通话摘要+待办沉淀
  - 差异化：我们加"通话中可发图片/表情"，竞品都没有

  核心功能清单：
  1. 一键发起通话 + 倒数接通动画
  2. 实时语音对话 + 实时字幕
  3. 通话中可发图片/表情
  4. 网络差自动降级为文字
  5. 通话结束自动生成摘要 + 待办提取

  成本预估：
  - 开发量：前端 2 周 + 后端 3 周 + AI 1 周
  - 边际成本：ASR+TTS 约 0.05 元/分钟

  我们明确不做：
  - 不做多人通话
  - 不做通话录音回放（先做摘要，回放下版本）
  - 不做按时长收费（MVP 阶段免费）

  【备选方案（更轻量）】
  如果开发资源紧张，先做"语音消息"而不是"实时通话"——降低技术难度，先验证用户喜不喜欢语音互动。
  ```

### 3.6 风险与待验证事项

- **这一节写什么**：做这个功能有什么风险？哪些假设需要验证？
- **颗粒度要求**：至少列 3 个风险、3 个待验证假设；每个风险有应对措施，每个假设有验证方法。
- **填写要点**：
  - 风险要具体：不是"技术风险"，而是"ASR 准确率在噪音环境下只有 70%，用户体验差"
  - 待验证假设要可证伪：不是"用户会喜欢"，而是"发起通话的用户中，70% 会在一周内发起第二次"
- **示例片段**：
  ```
  【风险】
  1. 实时语音延迟高（>500ms），对话不自然 → 应对：先做语音消息，验证需求再上实时通话
  2. AI 语音声音太机械，用户不满意 → 应对：先用第三方 TTS，接 3 个声音让用户选
  3. 通话成本太高（按 0.05 元/分钟，1000 用户×10 分钟 = 500 元/天）→ 应对：免费额度每人每天 10 分钟

  【待验证假设】
  1. 用户愿意在 AI 产品里用语音通话 → 验证：发问卷，看 30%+ 的用户表示愿意尝试
  2. 通话摘要能提升留存 → 验证：MVP 上线后对比有/没有摘要的用户 7 日留存
  3. 通话功能能提升付费意愿 → 验证：付费用户 vs 免费用户的通话使用率对比
  ```

## 四、不同产品类别的差异化要点

### A 类（对话式 AI / Agent 产品）
- 功能拆解重点：人设一致性、记忆连贯性、主动触发能力
- 竞品参考：Character.AI、Replika、小手机、星野
- 特别注意：AI 角色的"主动性"设计——竞品都是用户发起，但你可以做"角色主动打过来"，这是差异化机会

### B 类（RAG 知识库 / 问答产品）
- 功能拆解重点：检索准确率、引用溯源、多知识库切换
- 竞品参考：Dify、FastGPT、Coze、店智参谋
- 特别注意：知识库的"权限管理"和"数据隔离"——ToB 场景是刚需，竞品里很多没做好

### C 类（AIGC 多模态生成产品）
- 功能拆解重点：提示词模板、批量生成、风格一致性
- 竞品参考：Midjourney、即梦、可灵、Stable Diffusion
- 特别注意：成本控制和 fallback 策略——生成类功能失败率高，竞品怎么处理失败的？

### D 类（AI 评测平台 / 内部工具）
- 功能拆解重点：评测维度、bad case 管理、版本对比
- 竞品参考：PromptLayer、LangSmith、Weights & Biases
- 特别注意：数据可视化和报告导出——评测结果能不能一键导出给老板看？

### E 类（B 端 SaaS / 传统产品 AI 化）
- 功能拆解重点：权限体系、审计日志、与现有系统的集成
- 竞品参考：钉钉 AI、企业微信智能助手、飞书智能伙伴
- 特别注意：商户的"数据安全"顾虑——竞品怎么做数据隔离和权限控制的？

## 五、完成度 Checklist

- [ ] 功能定义清晰，一句话能讲明白

- [ ] 每个竞品都做了完整的用户旅程拆解（至少 5 步）
- [ ] 每个竞品至少列了 3 个优势、3 个劣势
- [ ] 引用了至少 3 条真实用户评论（好评/差评都有）
- [ ] 给出了至少 2 个方案选项（推荐 + 备选）
- [ ] 推荐方案明确说了"我们做什么"和"我们不做什么"
- [ ] 成本预估粗算了（开发量 + 边际成本）
- [ ] 至少列了 3 个风险，每个有应对措施
