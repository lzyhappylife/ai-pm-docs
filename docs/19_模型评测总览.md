# 模型评测三件套总览（LLM / Embedding / Rerank）SKILL

> **适用产品类别**：**B/D 为主**——B 类 RAG 知识库（三类模型选型是 RAG 0→1 的必经步骤）、D 类评测平台（模型评测是核心业务）；**A 类为辅**——A 类对话式 Agent 在选底座 LLM 时用 LLM 评测部分；**C 类为辅**——C 类 AIGC 生成在选生成模型时用 LLM 评测部分；E 类 B 端 SaaS AI 化一般不单独做模型选型，引用 D 类或 B 类的结论即可。
> **文档目的**：这不是某一份具体的评测报告，而是"RAG 模型选型"这件事的**总览方法论地图**——讲清 LLM / Embedding / Rerank 三类模型分别在 RAG Pipeline 的哪个位置、各自评什么、用什么指标、用什么数据集、怎么从 N 个候选压到 1 套最优组合。避免"拿一个 LLM 评测集就想选完所有模型"的误区。读者是 PM（选型 Owner）、算法工程师（执行评测）、技术决策者（做最终决策）。
> **撰写时机**：① RAG 项目 0→1 阶段，PRD 已出、知识库已建、第一版 Golden Set 就绪时；② 每季度模型复评（新模型发布后重新选型）；③ 线上指标掉点时（怀疑是某层模型的问题）。

## 〇、为什么 RAG 要分三类模型分别评测

很多人做 RAG 选型时犯的第一个错：**拿一个端到端 QA 评测集，跑几个 LLM，就选了一个效果最好的**。这是错的——RAG 是三层 Pipeline，每一层的错是不同性质的：

```
用户 Query
    │
    ▼
┌─────────────┐
│  Embedding   │  ← 把 query 变成向量，去向量库召回 top-k
│  （召回层）   │
└──────┬──────┘
       │
       ▼
┌─────────────┐
│   Rerank    │  ← 把 top-k 重新排序，挑出最相关的 top-n
│  （重排层）   │
└──────┬──────┘
       │
       ▼
┌─────────────┐
│    LLM      │  ← 拿着 top-n context，生成最终答案
│  （生成层）   │
└─────────────┘
       │
       ▼
   最终答案
```

**三层各自的失败模式完全不同**：

| 层级 | 失败模式 | 典型现象 | 选错的后果 |
|---|---|---|---|
| **Embedding** | 该召回的没召回（Recall 低） | 用户问 A，知识库有答案，但向量库根本没召回出来 | 答案凭空编造，幻觉率高 |
| **Rerank** | 召回了但排不上来（Precision 低） | top-20 里有正确段落，但排在第 15 位，top-5 里没有 | LLM 没看到正确信息，答非所问 |
| **LLM** | 看到了但没读对（Groundedness 低） | context 里有正确答案，但 LLM 没按 context 回答，自己编了 | 有引用但引用的内容和结论对不上 |

**所以评测必须分层**：
- 端到端评测只能告诉你"这套组合效果好不好"，但不能告诉你"是哪一层的问题"。
- 分层评测才能定位：是 Embedding 不行？还是 Rerank 不行？还是 LLM 不行？
- 只有分层评测 + 组合矩阵，才能选出**最优性价比组合**，而不是最贵的组合。

## 三、完整框架结构（到三级标题）

> 以下 8 章骨架。**第 1、2、3、4、5、6、7 章是选型必做的**；第 8 章是和下游文档（评测标准 / 评测集 / 评测报告）的衔接说明。

### 3.1 LLM 选型评测：评什么、怎么评

- **这一节写什么**：LLM 是生成层，评测的核心是"拿到 context 后，能不能正确、完整、相关地生成答案"。
- **颗粒度要求**：列出 LLM 的 5 个核心评测维度 + 每个维度的指标 + 达标阈值 + 典型 badcase。
- **填写要点**：
  - **LLM 不评召回质量**——召回是 Embedding 和 Rerank 的事。
  - **LLM 重点评生成质量**：事实性、相关性、拒答能力、多轮能力、成本与延迟。
- **示例片段**：

  **LLM 评测 5 大维度**：

  | 维度 | 指标 | 怎么算 | 达标阈值 | 典型 badcase |
  |---|---|---|---|---|
  | **事实性（Faithfulness）** | 答案中可被 context 支持的陈述数 / 总陈述数 | LLM-as-Judge 拆分陈述 → 逐条核对 context | ≥0.9 优秀，<0.7 不可用 | context 里写"退款 7 天"，答案写"退款 3 天" |
  | **答案相关性（Answer Relevance）** | 让 judge 根据答案反推 question，与原 question 算 embedding 相似度 | RAGAS 实现 | ≥0.8 优秀 | context 是 A 文档，答案答的是 B 文档的内容 |
  | **无答案拒答（Negative Rejection）** | context 里没有答案时，是否说"不知道"而不是硬编 | 二值判定 | 拒答正确率 ≥0.95 | 知识库没有的问题，硬编一个答案 |
  | **多轮一致性** | 多轮对话中是否保持一致的人设、事实、流程 | 人工评或 LLM-as-Judge | ≥0.8 | 第一轮说"7 天退款"，第三轮说"30 天退款" |
  | **成本与延迟** | 单次调用 token 数、API 费用、首字延迟 TTFT | 脚本统计 | TTFT P50 ≤ 2s，单次成本 ≤ ￥0.05 | 效果好但太贵，QPS 一上来就扛不住 |

  **LLM 候选对比表模板**：
  | LLM | Faithfulness | Answer Relevance | Negative Rej Acc | TTFT(P50) | E2E P95 | 单次成本 | 是否达标 |
  |---|---|---|---|---|---|---|---|
  | {模型 A} | {0.92} | {0.85} | {0.97} | {1.8s} | {3.5s} | {￥0.04} | √ |
  | {模型 B} | {0.88} | {0.82} | {0.93} | {0.9s} | {1.8s} | {￥0.015} | ×（拒答不达标） |
  | {模型 C} | {0.95} | {0.90} | {0.98} | {2.5s} | {5.0s} | {￥0.12} | √（但成本超预算） |

### 3.2 Embedding 选型评测：评什么、怎么评

- **这一节写什么**：Embedding 是召回层，评测的核心是"用户 query 能不能从向量库里把正确的段落召回来"。
- **颗粒度要求**：列出 Embedding 的 4 个核心评测指标 + 正负样本构造方法 + 双语适配注意事项。
- **填写要点**：
  - **Embedding 不评生成质量**——生成是 LLM 的事。
  - **Embedding 重点评检索质量**：命中率、排序质量、召回率。
  - **必须用业务集评，不能只看公开榜单**——公开榜单分数高，不代表在你的领域好用（OOD 掉点）。
- **示例片段**：

  **Embedding 评测 4 大指标**：

  | 指标 | 定义 | 怎么算 | 达标阈值 |
  |---|---|---|---|
  | **Recall@k** | golden chunks 被召回的比例 = \|gold ∩ top-k\| / \|gold\| | 业务 QA 集 + golden chunk 标注 | Recall@5 ≥ 0.85 优秀 |
  | **MRR@k** | 第一个正确结果排在第几位的倒数 | 同上 | MRR@5 ≥ 0.7 |
  | **NDCG@k** | 考虑位置的排序质量指标 | 同上 | NDCG@5 ≥ 0.75 |
  | **Context Precision@k** | top-k 里相关 chunk 占比 | 同上 | Precision@5 ≥ 0.6 |

  **正负样本构造**：
  - **正样本**：query + 对应的 golden chunk（从业务专家标注的 QA 集来）
  - **负样本**：query + 不相关的 chunk（从同库其他文档随机抽，或 hard negative：语义相似但不相关的）
  - **hard negative 很重要**：如果负样本都是完全不相关的，Embedding 模型闭着眼睛都能区分，评测就没意义

  **双语 / 多语言适配**：
  - 如果业务是中文场景，必须看 C-MTEB 榜单，不能只看 MTEB 英文榜
  - 如果是中英混合场景，必须测中英跨语言检索（中文 query 召回英文文档）

  **Embedding 候选对比表模板**：
  | Embedding | 业务集 Recall@5 | 业务集 Precision@5 | C-MTEB Retrieval | 编码延迟 | 成本 |
  |---|---|---|---|---|---|
  | {模型 A} | {0.88} | {0.62} | {65} | {5ms} | {￥0.0001/千token} |
  | {模型 B} | {0.82} | {0.55} | {72}（榜单高但业务集掉点） | {3ms} | {免费（开源）} |

  > **关键提醒**：{模型 B} 公开榜单分数更高（72 vs 65），但在你的业务集上掉点 6 个百分点——这就是 OOD（Out-of-Distribution）问题。**永远以业务集为准，公开榜单只作参考**。

### 3.3 Rerank 选型评测：评什么、怎么评

- **这一节写什么**：Rerank 是重排层，评测的核心是"召回的 top-k 里，能不能把最相关的排到最前面"。
- **颗粒度要求**：列出 Rerank 的 3 个核心指标 + 长文档截断策略 + 加了 Rerank 后的提升幅度。
- **填写要点**：
  - **Rerank 不评召回率**——召回是 Embedding 的事。
  - **Rerank 重点排序质量**：NDCG@k、首条命中率、比纯 Embedding 的提升幅度。
  - **要算"Rerank 值不值"**：加了 Rerank 延迟增加多少、成本增加多少、效果提升多少——如果提升 <5%，不如不加。
- **示例片段**：

  **Rerank 评测 3 大指标**：

  | 指标 | 定义 | 怎么算 | 达标阈值 |
  |---|---|---|---|
  | **NDCG@10** | 重排后 top-10 的排序质量 | 业务 QA 集 + golden chunk | NDCG@10 ≥ 0.8 |
  | **首条命中率（Hit@1）** | 最相关的 chunk 排在第 1 位的比例 | 同上 | Hit@1 ≥ 0.5 |
  | **提升幅度** | 加 Rerank 后 vs 不加的指标提升 | 对比纯 Embedding 的结果 | 提升 ≥10% 才值得加 |

  **长文档截断策略**：
  - Cross-Encoder 一般有最大长度限制（如 512 token），超过要截断
  - 截断策略：取开头 + 结尾，还是取中间？——要在评测里测哪种策略效果好
  - 如果文档普遍很长，要考虑"父子分块"（召回大块，送入 LLM 前取小块）

  **Rerank 候选对比表模板**：
  | Rerank | NDCG@10 业务集 | 加 Rerank 后 Recall 提升 | Faithfulness 提升 | 延迟增加 | 额外成本 | 值不值 |
  |---|---|---|---|---|---|---|
  | {模型 A} | {0.82} | {+8%} | {+5%} | {+200ms} | {￥0.002/次} | √（提升明显） |
  | {模型 B} | {0.78} | {+3%} | {+1%} | {+150ms} | {免费（开源）} | ×（提升太小） |

### 3.4 三类模型的组合矩阵（怎么压测最优组合）

- **这一节写什么**：单独评完 LLM / Embedding / Rerank 后，还要做**组合矩阵**——因为三类模型不是独立的，不同组合的端到端效果不是简单相加。
- **颗粒度要求**：从每类 Top-2 里挑组合，做 2×2×2 = 8 组端到端全跑；输出组合对比表 + 热力图 + 性价比甜点。
- **填写要点**：
  - **不要全组合**：3×3×3 = 27 组，评测成本太高。每类取 Top-2，做 8 组就够了。
  - **组合矩阵看端到端指标**：Faithfulness / Recall / 延迟 / 成本，而不是单看某一层。
  - **性价比甜点**：在所有达标的组合里，选成本最低的那个——不是效果最好的那个。
- **示例片段**：

  **组合矩阵设计**：
  - LLM Top-2：{模型 A}、{模型 C}
  - Embedding Top-2：{模型 A}、{模型 B}（注意：可能一个召回好、一个精度好）
  - Rerank Top-2：{模型 A}、{不加 Rerank}（对比有没有 Rerank 的差别）

  **8 组组合端到端对比表**：
  | 组合 ID | LLM | Embedding | Rerank | Faithfulness | Recall@5 | P95 延迟 | 单次成本 | 是否达标 |
  |---|---|---|---|---|---|---|---|---|
  | G1 | A | A | A | 0.92 | 0.85 | 4.2s | ￥0.042 | √ |
  | G2 | A | A | 无 | 0.88 | 0.82 | 3.8s | ￥0.040 | √ |
  | G3 | A | B | A | 0.86 | 0.78 | 4.0s | ￥0.038 | ×（Recall 不达标） |
  | G4 | C | A | A | 0.95 | 0.88 | 6.0s | ￥0.122 | √（但成本超预算） |
  | … | … | … | … | … | … | … | … | … |

  **结论读法**：
  - **效果最好**：G4（模型 C + Embedding A + Rerank A），但成本是预算的 3 倍
  - **性价比最高**：G2（模型 A + Embedding A + 无 Rerank），Faithfulness 0.88 刚过线，成本最低
  - **推荐组合**：G1（模型 A + Embedding A + Rerank A），Faithfulness 0.92，成本在预算内，延迟可接受

### 3.5 成本与延迟工程（怎么平衡质量与成本）

- **这一节写什么**：模型选型不是只看效果——还要算钱、算时间。成本和延迟不是附属指标，是和效果同等重要的决策维度。
- **颗粒度要求**：成本曲线散点图 + 延迟预算分配 + 敏感性分析 + 性价比甜点。
- **填写要点**：
  - **成本 = Embedding 编码 + 向量检索 + Rerank + LLM 生成 + Judge**，每一层都要算。
  - **延迟 = 首字延迟 TTFT + 总时长 E2E**，用户对 TTFT 更敏感（等 2 秒才出第一个字就觉得慢）。
  - **敏感性分析**：Top-k 从 5 调到 20、chunk size 从 256 调到 1024，指标变化多少——找到参数甜点。
- **示例片段**：

  **单次 RAG 调用成本拆解**：
  | 环节 | 调用量 | 单价 | 成本 |
  |---|---|---|---|
  | Embedding 编码（query） | 1 次 | ￥0.0001/千token | ￥0.00001 |
  | 向量检索（top-20） | 1 次 | 基础设施成本 | ~￥0.001 |
  | Rerank（top-20 → top-5） | 20 条 | ￥0.0001/条 | ￥0.002 |
  | LLM 生成（输入 ~1000 token + 输出 ~300 token） | 1 次 | 输入￥0.001/千token，输出￥0.003/千token | ￥0.001 + ￥0.0009 = ￥0.0019 |
  | **合计** | | | **~￥0.005/次** |

  **延迟预算分配**（P95 ≤ 3s 目标）：
  | 环节 | 预算 | 说明 |
  |---|---|---|
  | Embedding 编码 | ≤ 50ms | |
  | 向量检索 | ≤ 100ms | |
  | Rerank | ≤ 300ms | |
  | LLM 首字延迟 TTFT | ≤ 1500ms | 用户最敏感的部分 |
  | LLM 生成完 | ≤ 1000ms | |
  | **合计** | ≤ 2950ms | |

  **敏感性分析（Top-k 变化的影响）**：
  | Top-k | Recall@5 | Precision@5 | 延迟增加 | 成本增加 |
  |---|---|---|---|---|
  | k=5 | 0.75 | 0.65 | 基准 | 基准 |
  | k=10 | 0.85 | 0.50 | +50ms | +20% |
  | k=20 | 0.88 | 0.35 | +100ms | +40% |

  > **甜点**：k=10 时 Recall 提升 10%，成本只增加 20%——性价比最高。k=20 再多召回的收益递减。

### 3.6 决策门（什么指标达标才算可上线）

- **这一节写什么**：选型不能"哪个效果好选哪个"——必须有明确的**决策门**：所有指标都达标，才算通过；任何一个不达标，就不能选。
- **颗粒度要求**：效果门槛 + 延迟门槛 + 成本门槛 + 安全红线，四类门槛列成一张表。
- **填写要点**：
  - **门槛要在评测前定，不是评测后调**——否则就是"先看结果再定门槛"，自欺欺人。
  - **红线一票否决**：例如拒答正确率必须 ≥0.95，哪怕效果再好，拒答不行也不能选。
  - **门槛要分档**：及格线（能上线）、优秀线（推荐）、挑战线（未来目标）。
- **示例片段**：

  **决策门门槛表**（示例值，根据业务调整）：

  | 类别 | 指标 | 及格线（能上线） | 优秀线（推荐） | 挑战线 |
  |---|---|---|---|---|
  | **效果** | Faithfulness | ≥0.85 | ≥0.90 | ≥0.95 |
  | **效果** | Context Recall@5 | ≥0.80 | ≥0.85 | ≥0.90 |
  | **效果** | Negative Rejection Acc | ≥0.90（红线：必须 ≥0.90） | ≥0.95 | ≥0.98 |
  | **延迟** | TTFT P50 | ≤2s | ≤1.5s | ≤1s |
  | **延迟** | E2E P95 | ≤5s | ≤3s | ≤2s |
  | **成本** | 单次请求成本 | ≤￥0.10 | ≤￥0.05 | ≤￥0.02 |
  | **安全** | 幻觉率（红线） | ≤5% | ≤2% | ≤1% |

  > **使用方法**：每个候选组合对着这张表打分——
  > - 所有指标都 ≥ 及格线 = 可以上线
  > - 有指标 < 及格线 = 不能选（哪怕其他指标再好）
  > - 所有指标都 ≥ 优秀线 = 推荐组合
  > - 有指标 < 红线 = 直接淘汰

### 3.7 与下游文档的衔接关系

- **这一节写什么**：本总览是"方法论地图"，不是具体的评测执行文档。它和下游三份文档（RAG 评测标准 / RAG 评测集 / RAG 评测报告）的关系是什么。
- **颗粒度要求**：三份下游文档的职责分工 + 从总览到具体执行的流程。
- **填写要点**：
  - **本总览（19 号）**：讲"为什么这么评、评什么、整体框架"——是方法论
  - **RAG 评测标准（20 号）**：讲"具体每个指标怎么算、阈值多少、badcase 怎么归因"——是判定规则
  - **RAG 评测集（21 号）**：讲"用什么题、golden chunk 怎么标、意图怎么分类"——是题目集
  - **RAG 评测报告（22 号）**：讲"跑出来的结果是什么、选哪套组合、为什么"——是结论文档
- **示例片段**：

  | 文档 | 定位 | 解决什么问题 | 读者 |
  |---|---|---|---|
  | **19_模型评测总览**（本文） | 方法论地图 | 三类模型分别评什么、怎么组合、决策门怎么定 | PM、技术决策者 |
  | **20_RAG 模型评测标准** | 判定规则 | RAGAS 四指标怎么算、Negative Rejection 怎么判、阈值多少 | 算法、QA、标注员 |
  | **21_RAG 模型评测集** | 题目集 | 用什么题、5 类意图怎么分、golden chunk 怎么标 | 标注员、评测执行 |
  | **22_RAG 模型评测报告** | 结论文档 | 跑出来的结果对比、推荐哪套组合、为什么 | 决策者、PM |

  **选型完整流程**：
  ```
  1. 用 19 号总览 → 定评测框架（三类模型分别评什么、决策门门槛）
  2. 用 20 号标准 → 定每个指标怎么算、怎么判定
  3. 用 21 号评测集 → 建题目集（100-500 条 QA + golden chunk）
  4. 跑评测 → 得到各类模型的单评结果 + 组合矩阵结果
  5. 用 22 号报告 → 写选型结论、推荐组合、风险与建议
  ```

## 四、不同产品类别的差异化要点

### A 类（对话式 AI / Agent 产品）
- **只用 LLM 评测部分**——Agent 不一定有 RAG，但一定有底座 LLM。
- **重点评**：指令遵循、多轮一致性、工具调用正确性、角色遵循。
- **Embedding / Rerank 部分**：只有 Agent 带知识库检索时才需要。

### B 类（RAG 知识库 / 问答产品）
- **三类模型全用**——这是 RAG 选型的原生场景。
- **重点**：分层归因（是 Embedding 没召回？还是 Rerank 没排上？还是 LLM 没读对？）。
- **必须做组合矩阵**——不能只单评某一层。

### C 类（AIGC 多模态生成产品）
- **只用 LLM 评测部分**——选生成模型。
- **重点评**：指令遵循、风格一致性、生成质量、成本与延迟。
- **Embedding / Rerank 部分**：一般用不到（除非有素材检索）。

### D 类（AI 评测平台 / 内部工具）
- **三类模型全用**——平台要支持各种模型的评测。
- **重点**：Judge 模型本身的质量也要评测——LLM-as-Judge 和人工的一致性是平台的核心 KPI。

### E 类（B 端 SaaS / 传统产品 AI 化）
- **一般不单独做模型选型**——引用 B 类或 D 类平台的评测结论即可。
- 如果一定要做，重点是**成本门槛**——B 端对成本更敏感，要在满足基本效果的前提下选最便宜的组合。
