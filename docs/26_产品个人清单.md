# 【产品经理个人清单 To Do List】SKILL

> **适用产品类别**：**A/B/C/D/E 全类别**——这是 PM 个人的工作管理工具，不绑定具体产品类型。只要是 AI 产品经理，都需要一套个人待办管理方法；AI 产品的 PM 比传统 PM 多一整套"评测/Prompt/badcase/模型更新"类的专项任务。
> **文档目的**：帮产品经理把脑子里散着的事（这个版本要做什么、那个 badcase 要跟进、模型下周要更新）变成一张可追踪的清单，每天/每周/每月照着清单推进，不遗漏、不临时抱佛脚。没有个人清单的 PM，工作全靠"记在脑子里 + 群聊里被 @ 才想起来"——容易漏事、容易被紧急的事拖着走、重要不紧急的事永远排不上。读者是 PM 自己（自用）、直属 Leader（了解你在做什么）。
> **撰写时机**：① 入职/接手新产品的第一周就要建个人清单；② 每周一规划本周任务、周五复盘；③ 每月底对齐 OKR、调整下月优先级。

---

## 一、撰写前需要收集的资料清单

### 1.1 项目侧
- 当前负责的所有项目/产品清单（可能不止一个）
- 每个项目的当前阶段（0→1 / 迭代中 / 维护期）
- 每个项目的近期里程碑（发版日、评审日、上线日）

### 1.2 任务侧
- 已承诺但未完成的事（跟研发说的"下周三给你 PRD"、跟业务说的"下周给你数据"）
- 待评审的文档（PRD、评测报告、方案）
- 待跟进的 badcase / 反馈 / 工单
- 待参加的会议（评审会、周会、对齐会）

### 1.3 AI 产品专项（区别于传统 PM）
- 当前 Prompt 版本号、下一版要改什么
- 评测集当前版本、下轮评测时间、本轮通过率
- 待闭环的 badcase（待修复/已修复待回归）
- 模型更新窗口（新版本发布时间、灰度计划、回滚预案）
- 知识库/数据源更新计划（切片变更、重排阈值调整）

### 1.4 个人成长侧
- 最近在学什么（论文/工具/方法论）
- 想做但一直没做的事（竞品分析、用户访谈、复盘文档）

## 二、资料来源渠道

| 资料类型 | 推荐渠道 |
|---|---|
| 项目里程碑 | 项目排期表、飞书日历、发版计划 |
| 待办任务 | 大脑 + 群聊消息 + 邮件 + 会议纪要 |
| badcase/反馈 | 反馈表、VOC 表、评测平台 |
| 评测进度 | 评测集、评测报告 |
| Prompt 版本 | Prompt 管理平台、Dify/工作流版本记录 |
| 模型更新 | 模型厂商 changelog、内部技术同步 |
| 个人任务工具 | 飞书任务 / 滴答清单 / Notion / Things / 飞书多维表格 |

> **铁律**：个人清单不是越多越好——要"少而精"，每天看一眼就知道今天该干什么。清单太长 = 清单没用。核心是"每件事有明确的下一步动作和截止日"，不是"把所有事都列上去"。

## 三、完整框架结构（到三级标题）

> 以下 8 章骨架。**第 1、2、3、5、6、7 章是必须有的**；第 4 章（周度/月度节奏）是让清单"活起来"的关键；第 8 章（复盘）是让 PM 持续进步的闭环。

### 3.1 个人清单说明（表头页）

- **这一节写什么**：一页纸讲清"这是谁的清单、用什么工具管、多久更新一次、按什么规则排优先级"。
- **颗粒度要求**：至少 6 个字段——清单 Owner / 工具 / 更新频率 / 优先级规则 / 视图偏好 / 与团队看板的关系。
- **填写要点**：
  - **工具不重要，习惯重要**：飞书任务、滴答清单、Notion、Excel 都行——关键是每天打开看、每周整理。
  - **优先级规则要提前定好**：不能每天凭感觉排——提前定好"P0=今天必须做、P1=本周必须做、P2=本月要做、P3=有空再做"。
  - **要和团队看板区分开**：个人清单是"我自己要推进的事"，项目排期表是"团队要做的事"——不要混在一起。
- **示例片段**：
  ```
  | 字段 | 值 |
  |---|---|
  | 清单 Owner | {PM 姓名} |
  | 工具 | {飞书任务 / 飞书多维表格 / 滴答清单} |
  | 更新频率 | 每日早 10 分钟整理；每周五下午 30 分钟周复盘；每月底 1 小时月度对齐 |
  | 优先级规则 | P0=今天必须做完 / P1=本周必须做完 / P2=本月要推进 / P3=有空再做 |
  | 视图偏好 | 按优先级分组 → P0 今天、P1 本周、P2 本月、P3 Backlog |
  | 与团队看板关系 | 项目排期表里的"我负责的任务"同步到个人清单；个人清单里的"非项目任务"不进团队看板 |
  ```

### 3.2 字段结构（每条任务记什么）

- **这一节写什么**：一张任务卡片要有哪些字段——不是只写"写 PRD"，还要写"什么时候要、给谁的、下一步是什么、卡在哪"。
- **颗粒度要求**：至少 8 个字段——任务 ID / 任务名 / 所属项目 / 优先级 / 截止日 / 状态 / 下一步动作 / 依赖。
- **填写要点**：
  - **下一步动作最重要**：不要写"跟进退款流程"——要写"给研发发退款流程的 SOP 文档"。模糊的任务 = 不会做。
  - **截止日要具体到日**：不要写"下周"——要写"11 月 5 日（下周三）"。没有截止日的事永远排不上。
  - **依赖要写清**："等算法给我评测结果"——这种事不能一直挂着，要设个跟进时间（"11 月 4 日问算法要结果"）。
- **示例片段**：

  | 字段 | 类型 | 必填 | 说明 | 示例 |
  |---|---|---|---|---|
  | 任务 ID | 自增 | 是 | 唯一标识 | T-001 |
  | 任务名 | 文本 | 是 | 简短描述 | {写退款流程 PRD v2} |
  | 所属项目 | 单选 | 是 | 属于哪个产品/项目 | {客服 Agent} |
  | 任务分类 | 单选 | 是 | 产品类/评测类/数据类/沟通类/学习类 | {产品类} |
  | 优先级 | 单选 | 是 | P0/P1/P2/P3 | {P1} |
  | 截止日 | 日期 | 是 | 具体到日 | {2026-11-05} |
  | 状态 | 单选 | 是 | 待做/进行中/等依赖/已完成 | {进行中} |
  | 下一步动作 | 文本 | 是 | 具体的下一步 | {给研发发 SOP 文档并约 15 分钟对齐} |
  | 依赖 | 文本 | 否 | 等什么/等谁 | {等算法给我评测结果（11 月 4 日跟进）} |
  | 备注 | 长文本 | 否 | 其他信息 | {之前 v1 的反馈是追问不够} |

### 3.3 任务分类 Taxonomy（5 大类）

- **这一节写什么**：任务不能只按优先级分——还要按类型分，方便月底复盘"这个月我主要在做什么"。
- **颗粒度要求**：5 大类——产品类 / 评测类 / 数据类 / 沟通类 / 学习类；每类给典型任务示例。
- **填写要点**：
  - **产品类**：写 PRD、写方案、做竞品分析、画原型——核心产出类。
  - **评测类**（AI 产品特有）：跑评测、分析 badcase、优化 Prompt、调整 RAG 参数——AI 产品 PM 的日常占比很高。
  - **数据类**：看数据看板、出周报月报、做用户分析——用数据驱动决策。
  - **沟通类**：开会、对齐、评审、跨部门协调——PM 大量时间花在这上面。
  - **学习类**：读论文、学工具、复盘——长期能力建设。
- **示例片段**：

  | 分类 | 占比建议 | 典型任务 |
  |---|---|---|
  | **产品类** | 30-40% | 写 PRD、写方案、做竞品分析、画原型、定需求 |
  | **评测类（AI 特有）** | 20-30% | 跑评测、分析 badcase、优化 Prompt、调 RAG 参数、跟模型更新 |
  | **数据类** | 10-15% | 看数据看板、出周报月报、做用户分析、算转化漏斗 |
  | **沟通类** | 20-30% | 开周会、评审会、跨部门对齐、跟研发/算法/设计对齐 |
  | **学习类** | 5-10% | 读论文、学新工具、写复盘、参加分享 |

  > **AI 产品 PM 的特点**：评测类任务占比远高于传统 PM——传统 PM 可能 5% 时间在测试，AI 产品 PM 可能 30% 时间在跑评测、改 Prompt、跟 badcase。个人清单里必须给评测类任务留足够的位置，不能让"写 PRD"把评测类任务全挤掉。

### 3.4 周度/月度节奏（清单怎么用起来）

- **这一节写什么**：清单不是列在那就完了——要有节奏地用它，每天/每周/每月做什么，写清楚。
- **颗粒度要求**：每日节奏 + 每周节奏 + 每月节奏，每个节奏给具体动作和耗时。
- **填写要点**：
  - **每日早 10 分钟**：看 P0 今天要做什么，列 3 件今天必须做完的事。
  - **每周五下午 30 分钟**：本周复盘 + 下周规划——完成了什么、没完成什么、为什么、下周重点是什么。
  - **每月底 1 小时**：OKR 对齐——这个月 OKR 进展如何、哪些任务要调整优先级、哪些事可以砍掉。
- **示例片段**：

  | 节奏 | 时间 | 做什么 | 耗时 |
  |---|---|---|---|
  | **每日** | 早到公司后 | 1. 看 P0 任务 2. 列今天 3 件最重要的事 3. 回复重要消息 | 10 分钟 |
  | **每日** | 下班前 | 1. 标记今天完成的任务 2. 把没做完的 P0 移到明天 3. 看一眼明天的日程 | 10 分钟 |
  | **每周** | 周五下午 | 1. 本周完成/未完成复盘 2. 未完成的原因分析 3. 下周 P0/P1 任务规划 4. 清理 Backlog | 30 分钟 |
  | **每月** | 月底最后一天 | 1. OKR 进展对齐 2. 任务分类占比分析（产品/评测/数据/沟通/学习） 3. 砍掉低价值任务 4. 下月重点目标 | 1 小时 |

### 3.5 AI 产品专项任务清单（重点）

- **这一节写什么**：AI 产品 PM 比传统 PM 多一整套专项任务——这些事如果不专门列出来，很容易被紧急的事挤掉，导致"版本改了但没评测、模型更新了但没回归"。
- **颗粒度要求**：5 类专项——Prompt 版本跟踪 / 评测进度 / Badcase 闭环 / 模型更新窗口 / 知识库更新。
- **填写要点**：
  - **Prompt 版本跟踪**：当前版本号、下一版要改什么、待验证的假设是什么——不能"感觉 Prompt 还行"就不改，要带着假设去改。
  - **评测进度**：评测集版本、本轮通过率、下轮评测时间——每次改完 Prompt 都要跑评测，不能"我觉得改好了"就上线。
  - **Badcase 闭环**：待修复的 badcase、已修复待回归的 badcase——每个 badcase 都要有 Owner、有截止日。
  - **模型更新窗口**：厂商新版本什么时候发、灰度计划是什么、回滚预案是什么——模型更新是高风险操作，必须提前规划。
  - **知识库更新**：文档版本、切片变更、重排阈值调整——RAG 产品的知识库不是一成不变的。
- **示例片段**：

  **AI 专项任务清单模板**：

  | 类别 | 当前状态 | 下一步动作 | 截止日 | 优先级 |
  |---|---|---|---|---|
  | **Prompt 版本** | 当前 v12 | v13 要改：退款类问题加追问清单（假设：追问后退款题通过率从 60% 升到 80%） | 11 月 8 日 | P1 |
  | **评测进度** | v1.1 评测集，本轮通过率 60%（15/25） | 下轮评测：v13 Prompt 改完后全量回归 + pass³ | 11 月 10 日 | P1 |
  | **Badcase 闭环** | 待修复 3 个（T12 退款追问、T15 实时查询、T22 未成年人材料） | T12 已改 Prompt，待回归；T15 等算法接真实接口；T22 等业务给材料清单 | T12: 11/5<br>T15: 11/12<br>T22: 11/8 | P1 |
  | **模型更新** | 厂商说 11 月中旬出新模型 | 提前准备：新模型评测 prompt、灰度计划（10%→50%→100%）、回滚预案 | 11 月 15 日 | P2 |
  | **知识库更新** | 当前知识库 v3（50 篇文档） | 业务要加 3 篇新文档（活动规则更新），切片后重跑召回评测 | 11 月 7 日 | P2 |

### 3.6 优先级判定（怎么排优先级）

- **这一节写什么**：不是所有事都一样重要——要一套简单的判定规则，避免每天纠结"先做什么"。
- **颗粒度要求**：优先级矩阵（影响面 × 紧急度）+ 判定原则。
- **填写要点**：
  - **影响面 × 紧急度 2×2**：重要且紧急（P0）、重要不紧急（P1）、紧急不重要（P2）、不重要不紧急（P3）。
  - **AI 产品特殊原则**：评测类任务经常被归为"重要不紧急"——但如果跳过评测直接上线，线上出问题就是"重要且紧急"。所以评测类任务要主动提到 P1，不能一直往后排。
  - **学会说"不"**：P3 的事能推就推、能砍就砍——PM 的时间是最稀缺的资源。
- **示例片段**：

  **优先级判定矩阵**：

  | | 紧急 | 不紧急 |
  |---|---|---|
  | **重要** | **P0（今天必须做）**：线上事故、P0 badcase、今天要评审的 PRD | **P1（本周必须做）**：写 PRD、跑评测、跟进 badcase、模型更新准备 |
  | **不重要** | **P2（有空就做）**：临时开会、别人临时找你帮忙、回复非紧急消息 | **P3（Backlog）**：想做的竞品分析、想学的工具、可以推迟的事 |

  **判定原则**：
  1. P0 不超过 3 件——超过 3 件说明你在救火，不是在推进产品
  2. P1 每周固定时间做——比如"周二周四下午专门写 PRD"，不要被临时事打断
  3. P3 每月清理一次——超过 3 个月没做的 P3，直接砍掉
  4. 别人临时找你的事，先问"这个 P 几？截止日什么时候？"——不要来者不拒

### 3.7 与团队看板的衔接

- **这一节写什么**：个人清单不是孤立的——要和项目排期表、工单系统、团队看板对齐，避免"个人清单里有、团队看板里没有"或者反过来。
- **颗粒度要求**：个人清单 vs 项目排期表 vs 工单系统的边界 + 同步规则。
- **填写要点**：
  - **项目排期表里的事**：同步到个人清单——知道自己在团队里负责哪些任务、什么时候要交。
  - **个人清单里的事**：如果涉及到协作（要研发做、要设计出图），要同步到项目排期表——不能只自己知道。
  - **工单/反馈系统里的事**：P0/P1 的要同步到个人清单——不能忘了处理。
- **示例片段**：

  | 工具 | 管什么 | 怎么和个人清单衔接 |
  |---|---|---|
  | **项目排期表**（飞书项目/Jira） | 团队级的任务、里程碑、排期 | 排期表里"我负责的任务"自动同步到个人清单的 P1/P2 |
  | **工单系统**（客服/反馈） | 用户提的问题、badcase | P0/P1 工单每天分诊，同步到个人清单 |
  | **个人清单**（飞书任务/滴答） | 我自己要推进的事、非项目任务 | 是个人工作台，所有事的"中转站" |

  > **衔接原则**：个人清单是"我的工作台"——所有要我做的事，不管来自项目排期、工单、还是我自己想做的，都汇总到这里。但不重复——项目排期表里已经有的事，个人清单里只放"下一步动作"，不放完整任务描述。

### 3.8 复盘模板（每周/每月怎么复盘）

- **这一节写什么**：清单不是列完就完了——要定期复盘，看看"这个月我到底干了什么、哪些事没做好、下个月怎么改进"。
- **颗粒度要求**：周复盘模板 + 月复盘模板，每个模板给固定问题。
- **填写要点**：
  - **周复盘要快**：30 分钟搞定——完成了什么、没完成什么、为什么、下周重点是什么。
  - **月复盘要深**：1 小时——OKR 进展、任务分类占比、时间花在哪了、哪些事可以砍掉、下月重点。
  - **复盘要写下来**：脑子里复盘 = 没复盘。
- **示例片段**：

  **周复盘模板**（每周五下午，30 分钟）：

  | 问题 | 我的回答 |
  |---|---|
  | 本周完成了哪些事？（列 P0/P1 的完成情况） | 1. … 2. … 3. … |
  | 哪些事没完成？为什么？ | 1. …（原因：等依赖/被打断/估时不准） |
  | 本周最大的阻塞是什么？怎么解决？ | … |
  | 下周 3 件最重要的事是什么？ | 1. … 2. … 3. … |

  **月复盘模板**（每月底，1 小时）：

  | 问题 | 我的回答 |
  |---|---|
  | OKR 进展如何？（红/黄/绿） | O1：… O2：… |
  | 本月任务分类占比？（产品/评测/数据/沟通/学习） | 产品 35%、评测 25%、数据 10%、沟通 25%、学习 5% |
  | 时间都花在哪了？有什么浪费？ | … |
  | 哪些事可以砍掉/授权出去？ | … |
  | 下月 3 个重点目标是什么？ | 1. … 2. … 3. … |
  | 本月学到了什么？ | … |

## 四、不同产品类别的差异化要点

### A 类（对话式 AI / Agent 产品）
- **评测类任务占比最高**：多轮对话题的评测、pass³ 稳定性测试、badcase 归因——A 类产品 PM 可能 30%+ 时间在评测上。
- **Prompt 版本管理是专项**：每次改 Prompt 都要跑评测，个人清单里要把"改 Prompt → 跑评测 → 写报告"串成一条任务链。
- **人设/角色相关任务多**：调整人设话术、测试角色遵循、拒答边界——这些是 A 类特有的。

### B 类（RAG 知识库 / 问答产品）
- **知识库更新是专项**：新文档切片、召回评测、重排阈值调整——RAG 产品的知识库不是一成不变的。
- **检索准确率跟踪**：每周看召回准确率、误拒率、幻觉率——这些指标的趋势要定期看。
- **来源质量任务**：哪些文档质量差、要更新、要下架——这也是 RAG PM 的日常。

### C 类（AIGC 多模态生成产品）
- **生成质量评测是专项**：人工盲评、风格一致性、参数调优——C 类产品的评测更主观。
- **模型 fallback 策略**：主模型挂了切哪个备用模型——要跟踪模型可用性。
- **成本优化任务**：生成一次多少钱、能不能降本——C 类产品的成本工程很重要。

### D 类（AI 评测平台 / 内部工具）
- **评测集维护是专项**：新增题目、调整金标、双标一致性校准——D 类产品的核心资产就是评测集。
- **Judge Prompt 优化**：LLM-as-Judge 的 Prompt 要持续调——Judge 不准，评测结果就不准。
- **badcase 闭环是核心**：平台的使命就是帮用户闭环 badcase，PM 自己的清单里 badcase 闭环占比很高。

### E 类（B 端 SaaS / 传统产品 AI 化）
- **商户场景任务多**：不同商户类型的 AI 功能验证、商户反馈跟进——E 类的任务偏"项目制"。
- **工单驱动**：很多任务来自商户工单、客服转办——个人清单里要给工单处理留位置。
- **数据看板任务**：AI 功能的数据看板要定期看、定期出报告——E 类 PM 的数据类任务占比高。
