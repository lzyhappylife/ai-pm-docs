# 【VOC 用户声音表】SKILL

> **适用产品类别**：**A/B/E 为主**——A 对话式 Agent（用户对人设/对话体验的反馈最直接）、B RAG 问答（用户对回答准确性/幻觉的反馈是核心 VOC）、E B 端 SaaS（商户反馈/投诉是 B 端产品迭代的主要输入）；**C 类为辅**（AIGC 生成产品也有 VOC 但偏主观评价）；**D 类一般不用**（评测平台是内部工具，没有 C 端用户声音）。
> **文档目的**：把分散在客服工单、应用商店、社媒、用户访谈、退款投诉里的"用户声音"**汇聚成一张表**，打标签、分优先级、派 Owner、走完闭环，最终驱动产品迭代。没有 VOC 表的团队，产品迭代靠"老板拍脑袋 + PM 自己感觉"——用户到底在抱怨什么、表扬什么、想要什么，没人说得清。读者是 PM（Owner）、客服（一线输入）、产品团队（迭代输入）、管理层（NPS/满意度汇报）。
> **撰写时机**：① 产品上线后 1-2 周内就要建 VOC 表（不是等做了半年才回头整理）；② NPS/CSAT 调研发布后，开放题原文要进 VOC 表；③ 重大版本上线后，要专门跟踪新版本的 VOC。

## 一、撰写前需要收集的资料清单

### 1.1 定量满意度指标（结构化）
- NPS：推荐意愿 0-10 分、推荐理由开放题、不推荐理由；按用户分层（新/活跃/付费/流失）
- CSAT：每次关键交互后满意度 1-5 分（注册、首次对话、解决问题、支付、续费）
- CES：任务完成省力程度 1-7 分
-  churn / 留存 / 续费 / 转化等与体验相关的业务指标

### 1.2 定性反馈（非结构化文本）
- 应用商店评论（App Store / Google Play / 华为 / 小米 / OPPO / vivo / 应用宝）
- 客服工单（会话记录、邮件、电话录音转写）
- 应用内反馈入口（摇一摇、意见反馈按钮）
- NPS 开放题原文、CSAT 追评
- 社媒声量：微博、小红书、知乎、抖音、B 站、X/Twitter
- 销售/客户成功访谈记录（B 端）
- 竞品评论区（间接用户声音）

### 1.3 用户属性标签
- 用户 ID、注册时间、用户分层（新/活跃/沉默/流失）
- 订阅套餐、付费金额、生命周期阶段
- 渠道来源（自然量/投放/邀请）
- 设备、OS、App 版本
- B 端：行业、规模、使用部门

### 1.4 反馈内容标签（打标后生成）
- 反馈类型：Bug / 功能建议 / 体验抱怨 / 表扬 / 咨询 / 商务 / 其他
- 情感极性：正面/中性/负面；情感强度 1-5
- 主题分类（三级 taxonomy）
- 严重度：P0 阻断 / P1 严重 / P2 一般 / P3 建议
- 影响用户数、是否付费用户、是否头部客户

### 1.5 闭环工单字段
- 处理 Owner（具体到人，不写"客服部"）
- 处理状态：待认领/处理中/待验证/已关闭/已拒绝
- SLA：P0 24h、P1 3 天、P2 2 周
- 处理动作：修复/排期/拒绝/转 FAQ
- 是否回复用户、用户是否满意闭环结果
- 关联需求单/Bug 单号

## 三、完整框架结构（到三级标题）

> 以下 10 章骨架。**第 1、3、4、5、7、8、9 章是任何 VOC 表都不能省的**；第 2 章（接入渠道）和第 6 章（BI 看板）决定了 VOC 表的覆盖面和可视化能力；第 10 章（数据隐私）是合规底线。

### 3.1 VOC 表说明（表头页）

- **这一节写什么**：一页纸讲清"这是什么 VOC 表、收哪些渠道的声音、谁负责、多久更新一次、怎么用"。
- **颗粒度要求**：至少 8 个字段——表名称 / 目的 / 数据源 / Owner / 更新频率 / 当前版本 / SLA 标准 / 表地址。
- **填写要点**：
  - **目的要写清**：是"每周同步产品评审"还是"月度管理层汇报"——两种用途的字段侧重点不同。
  - **更新频率要具体**："每周一上午 PM 汇总，周四跨职能评审会"而不是"持续更新"。
  - **Owner 要具体到人**：不能写"产品部"，要写"{PM 姓名}"。
- **示例片段**：
  ```
  | 字段 | 值 |
  |---|---|
  | VOC 表名称 | {产品名}用户声音跟踪表 |
  | 版本 | v{1.2}（{YYYY-MM-DD} 发布） |
  | 目的 | 把分散在客服/商店/社媒/问卷中的声音汇聚成可行动的产品输入 |
  | 数据源 | {客服工单 / App Store 评论 / 应用内反馈 / NPS 开放题 / 社媒} |
  | Owner | {PM 姓名} |
  | 更新频率 | 每日：值班 PM 分诊；每周四：跨职能评审会；每月：发布《VOC 月度报告》 |
  | SLA 标准 | P0 2h 响应 / 24h 解决；P1 8h / 3 天；P2 24h / 2 周；P3 2 天 / 季度 |
  | 表地址 | {飞书多维表格链接} |
  ```

### 3.2 接入渠道清单（声音从哪来）

- **这一节写什么**：列出所有接入 VOC 表的渠道，每个渠道写清"怎么接、字段映射、更新频率"。
- **颗粒度要求**：至少 6 个渠道——APP 内反馈 / 客服工单 / 应用商店评论 / 社交媒体 / 用户访谈 / 退款投诉；每个渠道给"字段映射表"。
- **填写要点**：
  - **不要只接一个渠道**：只接客服工单 = 只听到"已经生气到要找客服的人"的声音，听不到"默默流失的人"的声音。
  - **每个渠道的字段映射要写清**：客服工单的"问题类型"对应 VOC 的"二级分类"，商店评论的"评分"对应 VOC 的"情感极性"。
  - **更新频率不一样**：客服工单实时同步，社媒聆听每日抓一次，用户访谈手动录入。
- **示例片段**：

  | 渠道 | 怎么接 | 字段映射 | 更新频率 |
  |---|---|---|---|
  | **APP 内反馈** | 自研 SDK / 兔小巢 | 用户 ID / 原文 / 截图 / 设备版本 | 实时 |
  | **客服工单** | Zendesk / 七鱼 / 美洽 API | 工单 ID / 用户 ID / 会话原文 / 工单标签 → VOC 二级分类 / CSAT 评分 | 实时 |
  | **应用商店评论** | App Store Connect / 七麦爬取 | 评分 → 情感极性 / 评论原文 / 版本号 / 用户昵称 | 每日 |
  | **社交媒体** | 舆情工具 / 手动 | 平台 / 原文 / 发布时间 / 情感 / KOL 粉丝数 | 每日 |
  | **用户访谈** | 手动录入 | 访谈记录 / 用户分层 / 关键原话 / 标签 | 访谈后 3 天内 |
  | **退款/投诉** | 财务/客服系统 | 退款原因 / 投诉内容 / 付费金额 / 是否头部客户 | 每日 |
  | **NPS/CSAT 开放题** | 问卷系统导出 | 评分 / 推荐理由 / 不推荐理由 / 用户分层 | 调研结束后 |

### 3.3 三级分类 Taxonomy（打标的核心）

- **这一节写什么**：VOC 表的灵魂——一套三级分类体系（一级主题 → 二级分类 → 三级子标签），让每条反馈都能被打上标签，后续才能统计分析。
- **颗粒度要求**：一级 6-8 类 + 二级每类 3-6 个 + 三级每二级 3-5 个；**AI 专属标签必须单列**。
- **填写要点**：
  - **一级主题建议**：核心功能效果 / 性能与稳定性 / 易用性与交互 / 价格与计费 / 内容与安全 / 客服与支持 / 商务与合作 / 其他。
  - **AI 专属标签必须单列**：幻觉（编造事实）/ 上下文丢失（多轮忘记前文）/ 误拒（该答不答）/ 误答（不该答乱答）/ 成本过高（用户嫌贵）/ 人设偏离 / 工具调用失败——这些不是传统软件的"功能 Bug"。
  - **taxonomy 要持续迭代**：每季度评审一次，新聚类连续 2 周占比 >3% 就新增类别，重复类别合并。
- **示例片段**：

  | 一级主题 | 二级分类 | 三级子标签（示例） |
  |---|---|---|
  | **A. 核心功能效果** | A1 回答不准确 | 事实错误 / 数字算错 / 时间错误 / 单位换算错 |
  | | A2 幻觉编造 | 编造不存在的事实 / 伪造引用来源 / 编造不存在的功能 |
  | | A3 答非所问 | 完全跑题 / 部分跑题 / 理解错问题 |
  | | A4 多轮上下文丢失 | 忘记前文 / 混淆不同用户 / 上下文串台 |
  | | A5 角色/人设偏离 | 跳出人设 / 暴露内部 Prompt / 语气不对 |
  | | A6 工具调用失败 | 工具调用错 / 入参错 / 返回没被正确使用 |
  | **B. 性能与稳定性** | B1 首字延迟慢 | >3s / >5s / >10s |
  | | B2 长输出中断 | 输出到一半断了 / JSON 截断 |
  | | B3 并发失败 | 高峰期超时 / 502 / 限流 |
  | | B4 登录失效 | Token 过期 / 频繁掉线 |
  | **C. 易用性与交互** | C1 新手引导缺失 | 不知道怎么用 / 不知道能干什么 |
  | | C2 设置项难找 | 找不到入口 / 找不到设置 |
  | | C3 提示词难写 | 不知道怎么写 prompt / 模板不够 |
  | **D. 价格与计费** | D1 免费额度不足 | 送的次数太少 / 很快就用完 |
  | | D2 计费不透明 | 不知道扣了多少 / 扣得不明不白 |
  | | D3 退款难 | 想退款找不到入口 / 退款被拒 |
  | | D4 涨价抱怨 | 太贵了 / 比竞品贵 |
  | **E. 内容与安全** | E1 不当内容 | 输出有歧视 / 偏见 / 不适当内容 |
  | | E2 隐私担忧 | 担心数据泄露 / 担心被训练 |
  | | E3 Prompt 注入 | 用户注入攻击 / 绕过安全限制 |
  | **F. 客服与支持** | F1 响应慢 | 客服半天不回 |
  | | F2 解决率低 | 问题没解决 / 转来转去 |
  | | F3 态度差 | 客服不耐烦 / 机械回复 |
  | **G. 商务与合作（B 端）** | G1 定制需求 | 想要定制功能 |
  | | G2 合同/发票 | 合同流程慢 / 发票问题 |
  | **H. 其他** | H1 其他 | 兜底 |

### 3.4 字段定义（每条反馈记录什么）

- **这一节写什么**：一张大表，把 VOC 表的所有字段列出来——字段名、类型、必填、说明、示例。
- **颗粒度要求**：至少 18 个字段——反馈 ID / 收集日期 / 来源渠道 / 用户 ID / 用户分层 / 原文 / 情感极性 / 情感强度 / 一级主题 / 二级分类 / 三级子标签 / 反馈类型 / 严重度 / 影响用户数 / 是否付费 / 处理 Owner / 处理状态 / 承诺解决日期。
- **填写要点**：
  - **原文字段必须保留用户原话**：不要 PM 自己"翻译"成"用户反馈回答不准确"——要保留"我问它北京有多少人口，它说 3000 万，我查了下明明是 2100 万，这也太离谱了吧"这种带情绪的原话。
  - **用户分层要打标**：新用户/活跃/沉默/流失；免费/付费/头部——不同分层的反馈权重不同。
  - **影响用户数要去重**：同一个问题 10 个人提，算 1 个问题 10 个用户，不是 10 条独立反馈。
- **示例片段**：

  | 字段 | 类型 | 必填 | 说明 | 示例 |
  |---|---|---|---|---|
  | 反馈 ID | 自增 | 是 | 唯一标识 | FB-2026-0001 |
  | 收集日期 | 日期 | 是 | 哪天收到的 | 2026-11-02 |
  | 来源渠道 | 单选 | 是 | 从哪来的 | {App Store / 客服工单 / 应用内 / 小红书 / 访谈} |
  | 用户 ID | 文本 | 否 | 匿名则填"匿名" | {u_12345} |
  | 用户分层 | 单选 | 是 | 新/活跃/沉默/流失；免费/付费/头部 | {活跃 / 付费} |
  | 原文 | 长文本 | 是 | 用户原话，禁止改写 | "我问它北京有多少人口，它说 3000 万……" |
  | 情感极性 | 单选 | 是 | 正面/中性/负面 | {负面} |
  | 情感强度 | 1-5 | 是 | 1 很弱 / 5 极强 | {4} |
  | 一级主题 | 单选 | 是 | 见 3.3 | {A 核心功能效果} |
  | 二级分类 | 单选 | 是 | 见 3.3 | {A2 幻觉编造} |
  | 三级子标签 | 多选 | 否 | 见 3.3 | {事实错误 / 数字算错} |
  | 反馈类型 | 单选 | 是 | Bug/功能建议/抱怨/表扬/咨询 | {抱怨} |
  | 严重度 | 单选 | 是 | P0/P1/P2/P3 | {P1} |
  | 影响用户数 | 数字 | 是 | 同问题去重后人数 | {12} |
  | 是否付费用户 | 布尔 | 是 | 是/否 | {是} |
  | 处理 Owner | 人员 | 是 | 必须具体到个人 | {@张三} |
  | 处理状态 | 单选 | 是 | 待认领/处理中/待验证/已关闭/已拒绝 | {处理中} |
  | 承诺解决日期 | 日期 | 否 | SLA 到期日 | 2026-11-05 |
  | 处理动作 | 长文本 | 否 | 已修复/排期 vX.X/拒绝并回复 FAQ | {排期 v2.4} |
  | 是否回复用户 | 布尔 | 否 | 是/否 | {是} |
  | 用户是否满意闭环 | 1-5 | 否 | N/A 则填 N/A | {4} |
  | 关联需求/Bug 单号 | 文本 | 否 | 飞书项目/Jira 链接 | {链接} |

### 3.5 情感极性与 SLA 分级

- **这一节写什么**：情感极性决定了用户的情绪强度，SLA 决定了处理时效——两者结合才能知道"哪些反馈要马上处理、哪些可以排期"。
- **颗粒度要求**：情感极性 3 档 + 情感强度 5 级 + SLA 4 级表。
- **填写要点**：
  - **情感强度 5 级**：1 很弱（"感觉有点慢"）/ 2 弱（"有点慢"）/ 3 中（"太慢了吧"）/ 4 强（"怎么这么慢！"）/ 5 极强（"这也太慢了我要卸载！"）。
  - **SLA 按严重度定**：P0 阻断 2h 响应 / 24h 解决；P1 严重 8h / 3 天；P2 一般 24h / 2 周；P3 建议 2 天 / 季度。
  - **强烈负面（情感强度 5）即使严重度不高也要升级**：一个要卸载的用户，即使问题是"UI 有点丑"，也要优先处理。
- **示例片段**：

  **情感极性与强度对照**：

  | 情感极性 | 强度 | 特征 | 示例 |
  |---|---|---|---|
  | 正面 | 1-2 | 轻微满意 | "还行吧" |
  | 正面 | 3-5 | 明显满意/表扬 | "这个功能太好用了！" |
  | 中性 | 1-5 | 客观描述/咨询 | "请问怎么导出数据？" |
  | 负面 | 1-2 | 轻微不满 | "感觉有点慢" |
  | 负面 | 3-4 | 明显抱怨 | "太慢了吧，能不能优化下" |
  | 负面 | 5 | 强烈愤怒/威胁流失 | "这也太慢了！我要退款！卸载了！" |

  **SLA 对照表**：

  | 严重度 | 响应时限 | 解决时限 | 升级路径 | 典型场景 |
  |---|---|---|---|---|
  | P0 阻断 | 2h | 24h | 直接抄送产品负责人 | 安全问题/资损/宕机 |
  | P1 严重 | 8h | 3 天 | 周会评审 | 核心功能出错/付费用户投诉 |
  | P2 一般 | 24h | 2 周 | 排期评审 | 体验问题/边缘场景 |
  | P3 建议 | 2 天 | 季度 | 需求池投票 | 功能建议/偶发小问题 |

### 3.6 处理闭环（两层闭环模型）

- **这一节写什么**：VOC 的灵魂是"闭环"——不能只收反馈不处理。参考 Renascence 的两层闭环模型：个体闭环 + 系统闭环。
- **颗粒度要求**：个体闭环（Service Recovery）+ 系统闭环（Systemic Improvement）+ 闭环节奏（每日/每周/每月）。
- **填写要点**：
  - **个体闭环（Service Recovery）**：单个 Detractor（NPS 打 0-6 分的人）/ P0 投诉 → 24h 内人工触达 → 道歉/补偿/解决 → 回访。目标是把 Detractor 拉回 Passive 甚至 Promoter。
  - **系统闭环（Systemic Improvement）**：同类反馈累计到阈值（比如 10 个人提同一个问题）→ 立项修复 → 版本发布 → 通告反馈用户。目标是从根上解决问题，不是只安抚一个人。
  - **闭环节奏**：每日值班 PM 分诊；每周四跨职能评审会；每月发布《VOC 月度报告》。
- **示例片段**：

  **两层闭环模型**：

  | 层级 | 目标 | 触发条件 | 动作 | 考核指标 |
  |---|---|---|---|---|
  | **个体闭环**（Service Recovery） | 挽回单个愤怒用户 | NPS Detractor / P0 投诉 / 付费用户强烈不满 | 24h 内人工触达 → 道歉/补偿/解决 → 回访 | Detractor 转 Promoter 比例 / 用户回访满意度 |
  | **系统闭环**（Systemic Improvement） | 从根上解决共性问题 | 同类反馈累计 ≥10 条 / P1 问题 ≥3 条 | 立项修复 → 版本发布 → 通告反馈用户 | 反馈→需求→上线转化率 |

  **闭环节奏**：
  - **每日**：值班 PM 分诊新增反馈、打标、指派 Owner；超期工单升级。
  - **每周四**：跨职能评审会（产品/研发/客服/运营），看 Top 问题、过超期工单、决定哪些进需求池。
  - **每月**：发布《VOC 月度报告》同步管理层，回流产品路线图；评审 taxonomy 是否需要调整。

### 3.7 BI 看板布局（VOC 数据怎么可视化）

- **这一节写什么**：VOC 表的数据不能只躺在表格里——要做成看板，让所有人一眼看到"这个月用户在抱怨什么、表扬什么、哪些问题在恶化"。
- **颗粒度要求**：至少 5 屏——总览指标卡 / 反馈量趋势 / 分类分布饼图 / AI 专项看板 / 渠道分布。
- **填写要点**：
  - **第一屏必须是核心指标卡**：NPS / CSAT / CES / 待闭环工单数 / 超期工单数——管理层打开第一眼就看这些。
  - **AI 专项看板必须单列**：幻觉率趋势 / 误拒率趋势 / 工具失败率趋势——这些是 AI 产品的独有指标，传统看板没有。
  - **头部付费客户单独视图**：不能让 100 个免费用户的吐槽淹没了 1 个年付 10 万的头部客户的反馈。
- **示例片段**：

  | 屏 | 内容 | 图表类型 | 看什么 |
  |---|---|---|---|
  | **第 1 屏：核心指标卡** | NPS 当月/上月/上季 / CSAT 平均 / CES 平均 / 待闭环工单数 / 超期工单数 | 数字卡片 | 整体满意度趋势、闭环健康度 |
  | **第 2 屏：反馈量趋势** | 近 12 周反馈总量（正面/中性/负面堆叠） | 堆叠面积图 | 反馈量是否在涨、负面占比是否在升高 |
  | **第 3 屏：分类分布** | 一级主题饼图 / 二级分类 Top 10 柱状图 | 饼图 + 柱状图 | 用户主要在抱怨哪类问题 |
  | **第 4 屏：AI 专项看板** | 幻觉率趋势 / 误拒率趋势 / 工具失败率趋势 / 上下文丢失率趋势 | 多线折线图 | AI 核心问题的趋势是好还是坏 |
  | **第 5 屏：渠道分布** | 客服/商店/应用内/社媒/问卷的反馈量占比 | 饼图 | 哪个渠道的反馈最多、哪个渠道没接 |
  | **第 6 屏：闭环漏斗** | 新反馈→已认领→处理中→已解决→用户满意 | 漏斗图 | 闭环哪里卡壳了 |
  | **第 7 屏：头部客户专属** | 头部付费客户反馈单独列表 | 明细表 | 不能被淹没 |

### 3.8 AI 预标 + 人工复核流程（重点）

- **这一节写什么**：VOC 量大了之后，PM 一条一条打标不现实——要用 LLM 自动预标，人工只复核不确定的。
- **颗粒度要求**：LLM 预标字段清单 + 置信度分档处理（≥0.9 自动入库 / 0.5-0.9 人工复核 / <0.5 丢弃）+ 复核结果回灌模型。
- **填写要点**：
  - **LLM 自动提取哪些字段**：情感极性、情感强度、一级主题、二级分类、关键实体（提到了什么功能/什么问题）。
  - **置信度分档**：≥0.9 直接入库；0.5-0.9 进人工复核队列；<0.5 丢弃或转人工判断。
  - **复核结果回灌模型**：人工复核的结果要定期回灌给 LLM，让预标准确率越来越高。
  - **每月测 Cohen's Kappa**：LLM 预标和人工复核的一致性——<0.7 说明预标 Prompt 要优化了。
- **示例片段**：

  **LLM 预标流程**：
  1. 新反馈进入 VOC 表 → 自动调用 LLM
  2. LLM 输出：情感极性 / 情感强度 / 一级主题 / 二级分类 / 关键实体 / 置信度
  3. 按置信度分档处理：
     - **≥0.9**：自动入库，状态为"已预标待抽查"
     - **0.5-0.9**：进人工复核队列，PM 每天抽 20% 校准
     - **<0.5**：标记为"低置信度"，转值班 PM 判断或丢弃
  4. 人工复核结果 → 每周汇总 → 回灌优化预标 Prompt
  5. 每月统计 Cohen's Kappa：≥0.7 合格；<0.7 暂停自动预标，优化 Prompt 后再启用

  **LLM 预标 Prompt 示例**：
  > 请阅读以下用户反馈，输出 JSON：
  > - sentiment: "positive" / "neutral" / "negative"
  > - sentiment_strength: 1-5
  > - primary_topic: 从以下选项选：{A 核心功能效果 / B 性能 / C 易用性 / D 价格 / E 安全 / F 客服 / G 商务 / H 其他}
  > - secondary_category: 从二级分类列表选最匹配的
  > - key_entities: 提到的功能/问题/数字
  > - confidence: 0-1（你对以上判断的置信度）
  >
  > 用户反馈原文："{粘贴原文}"

### 3.9 VOC 如何驱动产品迭代

- **这一节写什么**：VOC 不是收上来就完了——要每周从里面挑出 TOP 问题，带进产品评审会，变成 PRD 需求。
- **颗粒度要求**：每周 TOP 10 问题模板 + 从 VOC 到 PRD 的转化路径 + 转化率考核指标。
- **填写要点**：
  - **每周四跨职能评审会**：过 TOP 10 问题，决定哪些进需求池、哪些排期、哪些拒绝。
  - **转化路径要清晰**：VOC 反馈 → 每周评审 → 进需求池 → 排期 → 开发 → 上线 → 通告用户。
  - **转化率要考核**：反馈→需求→上线的转化率——如果收了 1000 条反馈只上线了 3 个功能，说明 VOC 表只是"垃圾桶"，没有真正驱动产品。
- **示例片段**：

  **每周 TOP 10 问题模板**：

  | 排名 | 问题 | 影响用户数 | 负面占比 | 一级主题 | 严重度 | Owner | 本周决定 |
  |---|---|---|---|---|---|---|---|
  | 1 | 幻觉：编造事实 | 45 | 90% | A2 | P1 | @张三 | 排期 v2.4 |
  | 2 | 首字延迟 >5s | 38 | 85% | B1 | P1 | @李四 | 本周优化 |
  | 3 | 误拒：该答不答 | 32 | 80% | A 误拒 | P1 | @王五 | 下周评审 |
  | … | | | | | | | |

  **转化路径**：
  1. VOC 表每周自动汇总 TOP 10 问题
  2. 周四跨职能评审会：逐个过，决定"排期/拒绝/转 FAQ/继续观察"
  3. 排期的问题 → 进需求池 → 下周 PRD 评审
  4. PRD 通过 → 排期开发 → 上线
  5. 上线后 → 通告提过这个问题的用户（"你提的 XX 问题已经修复了"）

  **考核指标**：
  - 反馈→需求转化率 = 进需求池的反馈数 / 总反馈数（目标 10-20%）
  - 需求→上线转化率 = 已上线的需求数 / 进需求池的需求数（目标 50%+）
  - 用户回访率 = 回复了用户的反馈数 / P0/P1 反馈数（目标 100%）

### 3.10 数据隐私与脱敏

- **这一节写什么**：VOC 表里有大量用户原话、用户 ID、付费信息——必须脱敏，不能把用户隐私直接暴露在表里。
- **颗粒度要求**：脱敏规则 + 权限分级 + 存储周期。
- **填写要点**：
  - **原文要脱敏**：去掉手机号、姓名、订单号、身份证号——保留"我充了 500 块"但不要保留"订单号 20261102123456"。
  - **权限分级**：客服能看到自己渠道的反馈；PM 能看到全量；研发只能看到技术相关的标签，不能看到用户隐私。
  - **存储周期**：原始反馈保留 1 年；脱敏后的统计数据永久保留。
- **示例片段**：

  **脱敏规则**：

  | 字段 | 脱敏前 | 脱敏后 |
  |---|---|---|
  | 手机号 | 13812345678 | 138****5678 |
  | 姓名 | 张三 | 用户 A |
  | 订单号 | 20261102123456 | 订单号已脱敏 |
  | 身份证号 | 110101199001011234 | 已脱敏 |
  | 邮箱 | zhangsan@xxx.com | z***@xxx.com |

  **权限分级**：

  | 角色 | 能看到什么 |
  |---|---|
  | 客服 | 自己渠道的反馈 + 原文（用于回复用户） |
  | PM | 全量反馈 + 标签 + 统计 |
  | 研发 | 技术标签 + 严重度 + 处理动作（不看用户隐私） |
  | 管理层 | 看板汇总数据（不看明细） |

## 四、不同产品类别的差异化要点

### A 类（对话式 AI / Agent 产品）
- **AI 专属标签是核心**：幻觉/上下文丢失/人设偏离/工具调用失败——这些是 A 类产品 VOC 的主要分类。
- **人设相关反馈多**：用户会对 Agent 的人设、语气、性格提反馈——这是传统软件没有的分类。
- **对话体验反馈多**：多轮是否流畅、记忆是否准确、回复是否自然——都是主观体验类反馈。
- **NPS 样本要选对**：A 类产品的 NPS 要在用户完成一次完整对话后触发，不是随便弹个窗。

### B 类（RAG 知识库 / 问答产品）
- **回答准确性是 VOC 核心**：用户对"回答对不对、有没有引用正确来源"最敏感。
- **幻觉/误拒是高频分类**：编造事实、该答不答——这两类在 B 类产品的 VOC 里占比最高。
- **引用溯源问题**：用户会反馈"你说的这个文档根本没有这句话"——这是 RAG 产品的特有 VOC。
- **权限相关反馈**：B 端 RAG 产品会有"我为什么看不到这个文档"的权限类反馈。

### C 类（AIGC 多模态生成产品）
- **VOC 偏主观评价**："生成的图片不好看""风格不对""动作不自然"——都是主观感受类。
- **质量类反馈占比高**：风格偏离、崩坏、指令遵循失败——不是"功能 Bug"，是"质量问题"。
- **参数类反馈**：用户会提"希望加 XX 参数""希望能调 XX"——这是功能建议类。
- **人工评分维度**：C 类产品的 VOC 要配合人工评分（1-5 分），不能只靠情感极性。

### D 类（AI 评测平台 / 内部工具）
- **一般不用 VOC**：这是内部工具，没有 C 端用户声音。
- **如果一定要做**：反馈来自内部用户（算法/PM/QA），主要是"评测题不好用""Judge 不准""平台 bug"。
- **更适合用反馈表/工单系统**，不是 VOC——没有"用户声音"这种分散的、非结构化的输入。

### E 类（B 端 SaaS / 传统产品 AI 化）
- **反馈来自商户/客服**：不是 C 端用户主动在应用内提，而是商户找客服、销售转述。
- **头部客户反馈单独视图**：年付 10 万的客户和免费试用的客户，反馈权重完全不同。
- **商务类反馈多**：价格、合同、发票、定制需求——B 端特有的分类。
- **CSM 访谈是重要来源**：B 端产品的 VOC 很大一部分来自客户成功经理的定期回访。
