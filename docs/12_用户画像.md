# 【用户画像】SKILL

> **适用产品类别**：A / B / C / D / E 全类别。用户画像是所有 AI 产品 0→1 的地基——A 类对话式 Agent 要靠它锁"用户愿不愿意跟 AI 聊、聊几轮"；B 类 RAG 要靠它锁"用户对 AI 回答的信任门槛"；C 类 AIGC 要靠它锁"用户从想法到成品的完整路径"；D 类评测平台要靠它锁"标注员/评委的专业背景与评分偏差"；E 类 B 端 SaaS 要靠它分清"老板拍板、店员使用"的两张脸。任何不写画像就开干的 AI 产品，最后一定是按工程师自己的想象在做产品。
> **文档目的**：把目标用户从"抽象人群"变成"具体的人"——有名字、有背景、有任务、有痛点、有诉求、有使用场景、有决策路径，让研发、设计、运营、销售对着同一个"人"干活，而不是各凭感觉。读者是 PM、设计师、研发、算法、运营、销售、业务 Owner。
> **撰写时机**：立项前后、用户访谈/问卷跑过一轮之后、PRD 撰写之前。画像不是一次写完就永久有效——MVP 上线后要根据真实行为数据回头修订，版本迭代时每季度刷新一次。

---

## 一、撰写前需要收集的资料清单

### 1.1 定性资料
- 至少 8-15 个深度访谈录音/逐字稿（每个角色至少 3 人，宁可少而深，不要多而浅）
- 用户当前的工作流（TA 现在用什么工具、走什么流程、卡在哪一步、花多少时间）
- 用户对"好结果"的定义（什么算满意、什么算不可接受、什么情况下会自己动手改）
- 用户原话金句（痛点原话、期待原话、抱怨原话——这些是画像卡里最有价值的东西）
- 用户的情绪线索（什么时候烦躁、什么时候兴奋、什么时候放弃、什么时候分享给别人）

### 1.2 定量资料
- 后台行为数据（使用频率、单次时长、漏斗转化、留存、功能渗透）
- 客服工单/投诉/应用商店评论的高频关键词
- 已跑过的问卷数据（如果有）：人口学分布、使用行为分布、付费意愿分布
- 竞品用户评论（间接用户声音，用来交叉验证）

### 1.3 业务侧资料
- 业务方对"主要用户"的定义（谁真正付钱、谁真正用、谁真正受益）
- 组织架构图（B 端尤其重要：谁是决策者、谁是审批者、谁是执行者、谁是复核者）
- 现有客户/试点名单（B 端）或已注册用户分层（C 端）
- 业务红线（哪些用户绝对不能触达、哪些场景绝对不能替用户做）

### 1.4 二手资料
- 行业报告中的用户规模与结构（用来估算 TAM/SAM，不是用来写画像）
- 公开的用户调研报告（同类产品的年龄/职业分布）
- 销售/CSM 一线反馈（B 端客户最常提什么需求、最常抱怨什么）

## 二、资料来源渠道

| 来源 | 拿什么 |
|---|---|
| 1V1 深度访谈（30-60 分钟） | 工作流、痛点原话、情绪线索、决策路径——这是画像卡的第一原料 |
| 可用性测试/伴随观察 | 用户真实操作时的卡点、犹豫、放弃动作，比口头说的准 |
| 后台埋点数据 | 真实使用频率、漏斗、留存、功能渗透，用来校验访谈自报告 |
| 客服工单/应用商店评论/社媒声量 | 高频痛点、抱怨原话、期待原话 |
| 问卷定量数据 | 人口学分布、行为分布、付费意愿——用来给画像"加权" |
| 销售/CSM/运营一线 | B 端决策链、客户组织结构、采购预算来源 |
| 业务 Owner/专家访谈 | 业务红线、行业惯例、用户的隐性知识 |
| 竞品用户评论（App Store/小红书/知乎） | 间接用户声音，用来交叉验证 |
| 二手行业报告 | 用户规模与结构的宏观估算，不用于写画像卡本身 |

> **铁律**：画像卡里每一条"痛点/诉求"都要能指回一条访谈原话或一条工单原文；写不出来源的"用户觉得"都是 PM 自己的想象，必须删掉。

## 三、完整框架结构（到三级标题）

> 以下 6 章骨架融合自 8 份真实用户画像。A/B/C/D/E 各类按"差异化要点"章节裁剪；但 **第 0、1、2、3、4 章是任何 AI 产品都不能省的**。

### 3.0 画像方法论说明

- **这一节写什么**：开篇一页纸讲清"这份画像基于什么方法、样本量多大、置信度多高"。这是防止画像被业务方一句话推翻的护盾——"你这画像哪来的？"——答案就在这一页。
- **颗粒度要求**：必须写清 4 件事——①数据来源构成（访谈 N 人 / 问卷 N 份 / 行为数据覆盖 N 用户 / 二手资料 N 份）；②时间窗口（数据截至哪天）；③置信度分级（哪些结论是"高置信"、哪些是"假设待验证"）；④更新机制（多久刷新一次、谁负责）。
- **填写要点**：
  - **不要假装画像 100% 准确**——0→1 阶段画像必然有"假设待验证"的部分，显式标注出来反而更可信。
  - 样本量写具体数字，不要写"我们访谈了一些用户"。
  - 置信度分级建议三档：🟢 高置信（多源数据交叉验证）/ 🟡 中置信（单源访谈或自报告）/ 🔴 待验证（PM 假设，尚未被数据支持）。
- **示例片段**：
  ```
  | 项目 | 说明 |
  |---|---|
  | 画像版本 | v0.9（MVP 上线前基线版）；MVP 上线 4 周后基于真实行为数据刷新为 v1.0 |
  | 数据来源构成 | ①深度访谈 12 人（{角色A}6 人 / {角色B}4 人 / {角色C}2 人），每人 45-60 分钟；
  ②行为数据覆盖近 90 天活跃用户 {N} 人；③客服工单 {N} 条（近 6 个月）；
  ④问卷回收 {N} 份（有效 {N} 份）；⑤二手行业报告 {2} 份 |
  | 数据时间窗口 | {YYYY-MM-DD} 至 {YYYY-MM-DD} |
  | 置信度分级 | 🟢 高置信：核心任务、高频痛点、决策路径（多源交叉验证）；
  🟡 中置信：单次时长、付费意愿区间（单源自报告）；
  🔴 待验证：对 AI 主动触发的接受度、对"不用于训练"的付费意愿 |
  | 更新机制 | 每季度刷新一次；MVP 上线后第 4 周做首次行为数据校验；Owner：{PM 姓名} |
  | 局限性声明 | 本画像基于{一个地域/一个行业/一类客户}样本，跨{地域/行业}推广前需重新验证 |
  ```

### 3.1 画像总图（角色关系图）

- **这一节写什么**：一张 mermaid 关系图，把所有核心角色摆到一张图上——谁是主要用户（天天用产品的人）、谁是间接受益者（不直接用但结果归 TA）、谁是决策者（拍板买不买的人）、谁是复核者（对 AI 结果做最终判断的人）、谁是旁观者（受影响但不参与）。
- **颗粒度要求**：至少标出 3-5 类角色；每类角色用一句话标注"TA 与产品的关系"；用箭头画出"谁的产出流向谁、谁的反馈影响谁"；显式标出"主要用户 vs 决策者是否同一人"——这是 E 类 B 端项目最常见的坑。
- **填写要点**：
  - **不要把所有角色都画成"一样重要"**——用节点大小或颜色区分主要用户（大节点/深色）和旁观者（小节点/浅色）。
  - E 类 B 端必须显式画出"老板拍板、店长使用、店员执行、财务复核"这条链——这四类人的需求经常打架。
  - A 类对话式 Agent 要画出"用户 vs AI 角色"的关系，但 AI 角色不算业务角色，单独标注。
- **示例片段**：
  ```
  flowchart LR
    subgraph 决策链
      Boss["{决策者}<br/>{职位}：拍板采购、批预算<br/>🟡 间接受益"]
      Head["{管理者}<br/>{职位}：分配任务、看数据<br/>🟡 间接受益"]
    end
    subgraph 使用链
      User["{主要用户}<br/>{职位}：每天{核心动作}<br/>🟢 直接使用者"]
      Reviewer["{复核者}<br/>{职位}：抽检 AI 结果、改判<br/>🟢 直接使用者"]
    end
    Boss -->|批预算/定指标| Head
    Head -->|派任务| User
    User -->|产出{材料}| Reviewer
    Reviewer -->|改判/反馈| Head
    Reviewer -->|AI 结果问题| User
    Note["⚠️ 主要用户与决策者不是同一人：
    老板关心{降本/合规}，
    店员关心{别增加我的工作量}"]
  ```

### 3.2 核心角色清单总表

- **这一节写什么**：一张总表把所有角色的"代号、一句话定义、与产品关系、优先级、占比估计"列出来，让读者一眼看完所有角色。
- **颗粒度要求**：每个角色一行，列至少含：{代号} / {一句话定义} / {典型代表} / {与产品关系} / {优先级 P0/P1/P2} / {估计占目标用户比例} / {置信度}。
- **填写要点**：
  - 代号要好记（"小林-新人店员"比"角色3"强 10 倍）。
  - 优先级按"本期产品主要服务谁"定，不是按"谁最大牌"定——老板再大牌，本期不做老板端就标 P2。
  - 占比估计给区间（"约 60-70%"），不要拍一个精确数字。
- **示例片段**：
  ```
  | 代号 | 一句话定义 | 典型代表 | 与产品关系 | 优先级 | 估计占比 | 置信度 |
  |---|---|---|---|---|---|---|
  | 小林 | {入行 0-1 年的新人店员} | 22 岁，职高毕业，刚入职 3 个月 | 每天用产品完成{核心动作}，主要用户 | P0 | 60-70% | 🟢 |
  | 老王 | {入行 5 年的熟练店员} | 30 岁，带过 3 个新人 | 偶尔用产品，更多是"看不惯 AI 做得慢" | P1 | 20-25% | 🟢 |
  | 张店长 | {门店管理者} | 35 岁，管 8 家店 | 不直接用，但看 AI 产出的数据看板 | P0 | 5-10% | 🟡 |
  | 李老板 | {区域运营总监} | 40 岁，拍板采购 | 不直接用，但决定买不买、续不续费 | P0 | <2% | 🟡 |
  | 财务复核 | {总部财务} | 28 岁，对账 | 抽检 AI 生成的{材料}，改判 | P1 | <1% | 🟡 |
  ```

### 3.3 角色画像卡（每个角色一张，7 个模块）

> 每个 P0 角色一张完整卡片。下面以"小林"为例演示 7 个模块怎么写；P1/P2 角色可以只写模块 1/3/4/5。

#### 模块 1：角色定义

- **这一节写什么**：一句话把这个角色钉死——"{职业}的{姓名代号}，{年龄/工龄}，{TA 在组织里的位置}"。
- **颗粒度要求**：一句话版本不超过 30 字；必须有代号（"小林"），不能只写"用户"。
- **填写要点**：
  - 代号要带人设感（"小林-新人"、"老王-老油条"、"张店长-中层"），让研发在群里讨论时能直接说"小林会怎么想"。
  - 不要把多个角色揉进一张卡——一张卡只写一个"人"。
- **示例片段**：
  > **小林**——{入行 0-1 年的新人店员，22 岁，职高毕业，刚入职 3 个月，在{门店类型}做{岗位}。}

#### 模块 2：背景画像

- **这一节写什么**：把 TA 的"硬件参数"列出来——年龄、职业、工龄、常用工具、AI 使用经验、所在组织、收入水平（可选）、设备环境。
- **颗粒度要求**：至少 8 个字段；每个字段要具体到"程度"，不要写"中等"这种废话。
- **填写要点**：
  - **AI 使用经验这一栏最关键**——写清 TA 用过哪些 AI 产品、用了多久、用来干什么、对 AI 的态度（期待/怀疑/恐惧）。
  - 常用工具要列到"手机上装了什么 App、电脑上用什么软件"——这决定了产品的入口和交互。
  - 设备环境要写"主要用手机还是电脑、什么网络、什么场景下用"。
- **示例片段**：
  ```
  | 维度 | 描述 |
  |---|---|
  | 年龄/性别 | 22 岁，女 |
  | 职业/工龄 | {门店店员}，入职 3 个月，之前在{其他行业}做过 1 年 |
  | 学历 | 职高/大专，{专业} |
  | 收入水平 | 月薪 {4-5K}，{对价格敏感} |
  | 常用工具 | 手机：{微信/抖音/美团/点评}；电脑：{门店 ERP 系统，只会填表不会查数} |
  | AI 使用经验 | 用过{豆包/DeepSeek}，主要用来"改文案/想朋友圈/问题目"，平均每周用 2-3 次；
  对 AI 的态度：{觉得好玩但不太信，重要的事还是自己来} |
  | 所在组织 | {连锁门店}，{8-15 人}团队，店长直管 |
  | 设备环境 | 主要用{手机}上班时间用{门店平板}；网络{门店 Wi-Fi}；
  工位{狭小，没地方放电脑} |
  | 典型一天 | 9:00 开门→{接待/理货}→12:00 午休（刷手机）→14:00 继续→20:00 下班
  →{刷抖音/追剧} |
  ```

#### 模块 3：核心任务

- **这一节写什么**：TA 每天/每周/每月要完成的事，按频率排序。这是产品功能设计的"任务源头"——产品要替 TA 做的事，必须从这张表里找。
- **颗粒度要求**：至少 5-8 个任务；每个任务写清"频率（每天几次/每周几次）+ 当前怎么做 + 花多少时间 + 完成标准"。
- **填写要点**：
  - **按频率排序**，不要按重要性排序——高频的事才是产品该切入的事。
  - 每个任务要写"完成标准"——TA 怎么知道这件事做完了？这是验收的源头。
  - 标注哪些任务是"重复性高、规则明确、AI 适合切入"的，哪些是"需要人际判断、AI 不能碰"的。
- **示例片段**：
  ```
  | 任务 | 频率 | 当前怎么做 | 耗时 | 完成标准 | AI 适合切入？ |
  |---|---|---|---|---|---|
  | {接待顾客/回答常见问题} | 每天 20-40 次 | 口头回答，靠记忆和培训手册 | 每次 1-3 分钟 | 顾客不投诉、不买错 | ✅ 高频重复 |
  | {填写门店日报} | 每天 1 次 | 手写表格→拍照发群 | 10-15 分钟 | 店长说"OK" | ✅ 规则明确 |
  | {处理退换货} | 每天 1-3 次 | 查 ERP、填单、找店长签字 | 10-20 分钟 | 顾客拿到退款 | ⚠️ 需人际判断 |
  | {学习新品知识} | 每周 2-3 次 | 看总部发的 PPT/视频 | 每次 20 分钟 | 店长抽问能答上 | ✅ 可 AI 陪练 |
  | {参加例会} | 每周 1 次 | 听店长讲、记笔记 | 60 分钟 | 知道本周指标 | ❌ 人际场景 |
  | {处理客诉} | 每月 2-5 次 | 自己先上，搞不定找店长 | 30-60 分钟 | 顾客不再闹 | ❌ 高情绪场景 |
  ```

#### 模块 4：痛点与障碍

- **这一节写什么**：TA 现在做这些事卡在哪。分三类写——效率痛点（太慢/太重复）、质量痛点（老出错/不知道对错）、情绪痛点（烦/累/没成就感/怕被骂）。
- **颗粒度要求**：每个痛点必须配一句"用户原话金句"；三类痛点至少各 2 条；每条痛点写清"发生场景 + 影响 + 当前怎么绕过去的"。
- **填写要点**：
  - **原话金句是这张卡最值钱的东西**——直接引访谈录音里的话，不要 PM 自己总结。"每天填表填到头大"比"用户对填表有负面情绪"强 100 倍。
  - 情绪痛点经常被忽略，但它是用户是否愿意长期用产品的关键——B 端用户不是"因为好用"才用，是"因为不烦"才用。
  - 标注每条痛点的"AI 能解决吗"——能解决的进 PRD，不能解决的（比如怕被店长骂）写进运营策略。
- **示例片段**：
  ```
  【效率痛点】
  P1｜每天填日报，同样的数据要在 ERP、微信群、纸表里写三遍
     · 原话："我每天下班前要花 20 分钟填表，写完还得拍照发群，店长还要在群里 @我改"
     · 发生场景：每天 19:30-20:00，下班高峰期
     · 当前绕过：能拖就拖，第二天补
     · AI 能解决吗：✅ 自动汇总

  P2｜新品知识记不住，每次顾客问都要翻手册
     · 原话："顾客站在面前问我这个产品和那个有啥区别，我翻手册翻半天，顾客都走了"
     · 发生场景：每天接待时
     · 当前绕过：大概其说，说错了被投诉
     · AI 能解决吗：✅ 实时问答

  【质量痛点】
  P3｜退换货单老填错，被总部退回
     · 原话："这个月已经被退了 3 次单子了，每次都要重新填，店长脸都绿了"
     · 发生场景：每月对账时
     · 当前绕过：填完让店长先看一眼再交
     · AI 能解决吗：✅ 规则校验

  【情绪痛点】
  P4｜学新品的时候没人问，PPT 看不懂只能背
     · 原话："PPT 里全是参数，我也看不懂，只能硬背，背完第二天就忘"
     · 发生场景：每周培训
     · 当前绕过：抄老员工的笔记
     · AI 能解决吗：✅ AI 陪练式提问

  P5｜做错事怕被店长骂，不敢问
     · 原话："我也想问店长这个单子怎么填，但问了她又要说'这个都不会'"
     · 发生场景：遇到拿不准的事
     · 当前绕过：猜着填，错了再改
     · AI 能解决吗：⚠️ 情绪问题，AI 可以做"安全的提问对象"，但不能替代店长辅导
  ```

#### 模块 5：诉求与期待

- **这一节写什么**：TA 希望 AI 帮 TA 做什么，按优先级排序。这是产品功能的"需求池源头"。
- **颗粒度要求**：至少 5-8 条诉求；每条写清"用户原话 + 期望的具体结果 + 期望的边界（TA 不希望 AI 做什么）"。
- **填写要点**：
  - **区分"嘴上说的"和"真正会用的"**——访谈时用户说"我希望 AI 帮我写周报"，但上线后可能根本不用；要交叉看行为数据。
  - 每条诉求要写"边界"——用户不仅要 AI 做什么，还要 AI 不做什么（"不要自动发出去，我要先看一眼"）。
  - 优先级排序要基于"痛点强度 × 频率 × AI 可行性"，不是用户自己说的优先级（用户经常高估自己觉得酷的功能）。
- **示例片段**：
  ```
  | 优先级 | 用户原话诉求 | 期望结果 | 期望边界 |
  |---|---|---|---|
  | P0 | "能不能帮我把日报自动填好，我就签个字" | 每天 19:00 自动生成日报草稿，我确认后提交 | 不要自动提交，我要先看；不要替我决定哪些数据该写 |
  | P0 | "顾客问我的时候，我希望手机上能直接查到答案" | 顾客一问，我 5 秒内能拿出准确回答 | 答案要能溯源到总部手册，不要 AI 自己编 |
  | P1 | "学新品的时候，能不能像同事一样问我问题" | 每天 10 分钟 AI 陪练，问我新品知识 | 不要让我背 PPT，要让我会用自己的话讲 |
  | P1 | "退换货单填的时候能提醒我哪里错了" | 我填的时候实时提示，不要等交完才被退回 | 提醒要具体（"这里日期格式错了"），不要只说"有误" |
  | P2 | "下班了别再来找我" | 非工作时间不推送任务 | 紧急客诉除外，但客诉要走店长而不是找我 |
  ```

#### 模块 6：使用场景

- **这一节写什么**：TA 什么时候、在哪里、用什么设备、在什么心情下使用产品。这是交互设计的源头——同样的功能，在工位上和在地铁上的设计完全不一样。
- **颗粒度要求**：至少 3-5 个典型场景；每个场景写清"时间 + 地点 + 设备 + 心情 + 任务 + 干扰程度"。
- **填写要点**：
  - **心情这一栏最容易被忽略但最重要**——用户在"烦躁/着急/放松/害怕"下对 AI 的期待完全不同。
  - 干扰程度要写清（"旁边有人"/"戴着耳机"/"随时被打断"）——这决定了产品能不能用语音、能不能用长文本。
  - 标注每个场景下"AI 响应必须多快"——着急时 P95 要 2 秒，放松时 10 秒也行。
- **示例片段**：
  ```
  | 场景 | 时间 | 地点 | 设备 | 心情 | 任务 | 干扰 | 期望响应速度 |
  |---|---|---|---|---|---|---|---|
  | 开门前准备 | 9:00-9:15 | 门店 | 平板 | 平静、有点困 | 看今日任务、查新品 | 偶尔有顾客进店 | 5 秒内 |
  | 接待中被问 | 10:00-18:00 | 门店前台 | 手机（单手） | 紧张、怕顾客走 | 实时查答案 | 顾客站在面前 | 2 秒内，最好语音 |
  | 午休刷手机 | 12:00-13:00 | 休息区 | 手机（双手） | 放松、累 | 学新品、玩一下 AI | 没人打扰 | 30 秒都行 |
  | 下班前填表 | 19:30-20:00 | 门店 | 平板 | 烦躁、想走 | 提交日报 | 店长在旁边 | 1 分钟内搞定 |
  | 晚上回家 | 21:00-22:00 | 家 | 手机 | 放松 | 偶尔问 AI 问题 | 床、刷剧 | 不主动推就行 |
  ```

#### 模块 7：决策路径

- **这一节写什么**：TA 怎么决定用不用这个产品——谁推荐的、从什么渠道知道的、试多久才敢用、什么条件下愿意付费、什么情况下会弃用。
- **颗粒度要求**：写清"认知→尝试→采纳→付费→留存/流失"五段；每段标注关键人和关键动作。
- **填写要点**：
  - **E 类 B 端这一栏要拆成"决策者路径"和"执行者路径"两条**——老板怎么批预算、店员怎么被培训用，是两件事。
  - "弃用条件"要写具体——什么情况下 TA 会再也不用？（"AI 编造了一个被顾客拆穿的答案"比"AI 不准"强）。
  - 付费意愿要写"触发点"——不是"TA 愿意付多少钱"，而是"什么情况下 TA 会说'这个值'"。
- **示例片段**：
  ```
  | 阶段 | 关键动作 | 关键人 | 备注 |
  |---|---|---|---|
  | 认知 | 店长在群里发"以后用这个" | 店长/总部 | 不是自己找的，是被安排的 |
  | 尝试 | 入职第 1 天培训 30 分钟，试填 1 次 | 培训师 | 第一次体验决定会不会用 |
  | 采纳 | 第 1 周每天用，第 2 周形成习惯 | 自己 | 如果第 1 周出错 2 次以上就放弃 |
  | 付费 | 小林不付费，公司统一采购 | 李老板 | 小林只对"是不是增加我工作量"敏感 |
  | 留存 | 每月店长表扬"小林日报填得好" | 店长 | 正向反馈比产品功能更重要 |
  | 弃用条件 | ①AI 编造答案被顾客投诉；
  ②连续 3 次填错还要我自己改；
  ③店长说"别用了还是手工填" | — | 任一发生即弃用 |
  ```

### 3.4 画像之间的冲突与权衡

- **这一节写什么**：当主要用户和决策者、执行者和复核者的需求打架时，产品优先满足谁。这是画像文档最有决策价值的一章——不是罗列矛盾，而是给出权衡原则。
- **颗粒度要求**：至少列出 3-5 组冲突；每组写清"冲突点 + 两方诉求 + 权衡结论 + 理由"。
- **填写要点**：
  - **不要假装所有角色需求都能满足**——一定有取舍。PM 的价值就是把取舍写出来并说明理由。
  - 冲突要具体到功能级别（"老板要看数据看板 vs 店员不想被监控"），不要写"大家都希望产品好用"这种废话。
  - 权衡结论要写"本期优先满足谁、为什么"，并标注"这个决策的风险是什么"。
- **示例片段**：
  ```
  | 冲突 | 一方诉求 | 另一方诉求 | 权衡结论 | 理由与风险 |
  |---|---|---|---|---|
  | 数据透明度 | 老板要看到每个店员每天的{动作}明细 | 店员觉得"被监控"，有抵触 | 本期只给店长看汇总数据，不看个人明细；
  3 个月后视接受度开放 | 理由：先用起来比管理精细化重要；
  风险：老板可能觉得"我花了钱为什么看不到" |
  | AI 自动 vs 人工确认 | 老板要"全自动，省人力" | 店员怕"AI 填错了还要我背锅" | 所有 AI 产出必须人工确认后才流转；
  不做自动提交 | 理由：B 端客户对"AI 直接改正式数据"零容忍；
  风险：效率提升打折 |
  | 功能丰富 vs 简单 | 老板要"什么都能做" | 店员要"3 步搞定" | 本期只做 P0 的 2 个功能，
  其他进 Backlog | 理由：新人店员的学习成本是留存的关键；
  风险：老板觉得"功能太少" |
  | 实时 vs 异步 | 店员要"顾客在面前 2 秒答出来" | 算法说"实时准确率不够" | 实时走"高频 FAQ 库"，
  复杂问题异步给答案 | 理由：高频问题召回率够；
  风险：复杂问题顾客已经走了 |
  ```

### 3.5 画像验证计划

- **这一节写什么**：怎么证明这个画像是对的。画像不是写完就结束——必须有验证机制，否则它就只是 PM 的假设。
- **颗粒度要求**：至少列出 3 类验证方式（人物验证 / 行为埋点验证 / A/B 测试验证）；每种方式写清"验证什么假设 + 怎么验 + 成功标准 + 时间"。
- **填写要点**：
  - **人物验证**：找 5-8 个"符合画像的真实用户"看画像卡——问"这写的是你吗？有没有不像的地方？"——这是最快的验证方式。
  - **行为验证**：把画像里的"使用频率/任务耗时"和后台真实数据对比——差 2 倍以上说明画像失真。
  - **A/B 验证**：对画像里的关键诉求（如"希望 AI 先给草稿再人工确认"）做小流量 A/B，看采纳率。
  - 显式标注"哪些画像结论是假设、上线后要立刻验证"。
- **示例片段**：
  ```
  | 验证方式 | 验证什么假设 | 怎么验 | 成功标准 | 时间 |
  |---|---|---|---|---|
  | 人物验证 | 画像卡是否"像"真实用户 | 找 5 个符合小林画像的店员，让 TA 看画像卡并指出不像的地方 | 80% 以上说"这就是我"；
  不像的点 <3 处 | MVP 上线前 1 周 |
  | 行为埋点验证 | 每天填日报 10-15 分钟、每周用 2-3 次 AI 学新品 | 上线后埋点对比 | 实测耗时与画像估计差 ≤30%；
  每周使用频次 ≥2 次 | 上线后第 2 周 |
  | A/B 测试 | "AI 先给草稿再人工确认"比"直接提交"采纳率高 | 小流量 A/B：A 组草稿模式，B 组直接提交 | 草稿模式采纳率 >B 组 20% | 上线后第 4-6 周 |
  | 弃用条件验证 | "AI 编造答案被顾客投诉"是最大弃用因子 | 跟踪弃用用户访谈 | 弃用用户中 ≥50% 提到 AI 出错 | 上线后第 8 周 |
  | 待验证假设（🔴） | 小林愿意为"AI 不用于训练"付费 | MVP 上线后弹窗调研 | 付费意愿 ≥30% 再考虑做付费版 | 上线后第 4 周 |
  ```

## 四、不同产品类别的差异化要点

### A 类（对话式 AI / Agent 产品）
- **模块 6 使用场景加厚**：重点写"角色沉浸感"——用户愿不愿意跟 AI 聊、聊几轮会停、什么话题最投入、什么话题会跳出角色。这些决定了 Agent 的 Prompt 边界和主动触发策略。
- **模块 4 情绪痛点是核心**：用户对 AI 角色的情绪反应（觉得"假"、觉得"被冒犯"、觉得"有意思"）比功能痛点更影响留存。
- **模块 7 决策路径要加"首次对话体验"**：A 类产品的留存几乎完全取决于前 3 轮对话——画像里要写清"用户在什么心情下开启第一次对话"。
- **冲突权衡**：要写"用户希望 AI 像真人 vs 用户希望 AI 别太假"这条矛盾——过度拟人化反而引发反感。

### B 类（RAG 知识库 / 问答产品）
- **模块 5 诉求与期待加厚**：重点写"信任建立"——用户对 AI 回答的信任门槛、什么时候会自己去核实、什么情况下会弃用。这直接决定产品要不要做引用溯源。
- **模块 4 质量痛点是核心**：用户最怕的不是"答得慢"，而是"答错了还一本正经"——幻觉痛点要单独拆出来写。
- **模块 6 使用场景**：要写清用户"在什么场景下会自己去核实答案"（高风险场景：医疗/法律/财务）vs"什么场景下直接采信"（低风险：娱乐/闲聊）。
- **冲突权衡**：要写"AI 给出确定答案 vs AI 说'我不确定'"——用户更烦哪个？B 类产品的拒答边界就靠这个决策。

### C 类（AIGC 多模态生成产品）
- **模块 3 核心任务加厚**：重点写"创作流程"——用户从想法到成品的完整路径（灵感→草稿→生成→修改→定稿），每一步卡在哪。
- **模块 4 质量痛点**：重点写"修改成本"——用户改一次要花多少时间、改几轮才满意、什么情况下放弃直接用原版。
- **模块 5 诉求**：要写"满意的生成条件"——什么样的 prompt 能一次出好图/好文案？用户对"风格一致"的要求有多强？
- **模块 7 决策路径**：C 类产品的付费触发点是"第一次免费生成满意作品"——画像要写清这个"啊哈时刻"长什么样。

### D 类（AI 评测平台 / 内部工具）
- **模块 2 背景画像加厚**：重点写"评测人员画像"——标注员/评委的专业背景、从业年限、对评分标准的理解偏差。这是评测一致性的关键。
- **模块 4 痛点**：评测人员的痛点不是"AI 不准"，而是"评分标准模糊、bad case 重复标、改判没反馈"。
- **模块 5 诉求**：评测人员要的是"评分工具顺手、标准清楚、改判能被听见"——不是"AI 自动打分"。
- **冲突权衡**：要写"评测人员希望少干活 vs 业务方希望评测又多又准"——这是 D 类产品的永恒矛盾。

### E 类（B 端 SaaS / 传统产品 AI 化）
- **模块 7 决策路径必须拆两条**：老板拍板路径（预算/采购/审批）和店员使用路径（培训/上手/留存）完全分开写。
- **模块 1 角色定义至少 4 类**：决策者（老板/总监）、管理者（店长/主管）、执行者（店员/专员）、复核者（财务/质检）——这四类人的需求差异巨大。
- **模块 4 情绪痛点**：B 端执行者最怕的是"AI 让我多干活"和"AI 让我背锅"——这两条是留存生死线。
- **模块 6 使用场景**：B 端用户是"被安排用"而不是"自己想用"——首次体验（培训 30 分钟）决定 80% 的留存。
- **冲突权衡**：老板要"全自动降本"vs 店员要"别增加我工作量"——本期一定优先店员体验，否则老板买了也用不起来。

## 五、完成度 Checklist

- [ ] 开篇写清了画像方法论（数据来源构成/时间窗口/置信度分级/更新机制/局限性声明）
- [ ] 画像总图标出了主要用户/决策者/复核者/间接受益者，并显式标注"主要用户与决策者是否同一人"
- [ ] 核心角色清单总表至少 3-5 个角色，每个有代号、一句话定义、优先级、占比、置信度
- [ ] 每个 P0 角色都有完整画像卡，7 个模块（定义/背景/任务/痛点/诉求/场景/决策路径）齐全
- [ ] 每个痛点都配了用户原话金句，不是 PM 自己总结
- [ ] 核心任务按频率排序，标注了"AI 适合切入"的任务
- [ ] 使用场景至少 3-5 个，每个写清时间/地点/设备/心情/干扰/期望响应速度
- [ ] 决策路径写清了认知→尝试→采纳→付费→留存/流失五段，弃用条件具体到事件
- [ ] 画像冲突与权衡至少 3-5 组，每组给了明确结论和理由
- [ ] 画像验证计划至少 3 类（人物验证/行为验证/A/B 验证），标注了哪些是待验证假设
- [ ] 差异化要点已按 A/B/C/D/E 类别裁剪
- [ ] 所有结论可回溯到访谈原话/工单/数据，没有"用户觉得"这种无源表述
- [ ] 显式标注了 🔴 待验证假设，没有把假设伪装成事实

## 六、AI 生成 Prompt 模板

```
你是一名资深 AI 产品经理。请根据以下项目信息，撰写一份完整的《用户画像》文档。

【项目背景】
{项目名称、业务方向、产品要解决什么问题}

【产品类别】
{A=对话式 Agent / B=RAG 问答 / C=AIGC 生成 / D=评测平台 / E=B 端 SaaS，可多选}

【已知用户角色线索】
{你已初步知道的角色：例如"店长/店员/财务"，以及他们大概的分工}

【访谈素材要点】
{访谈过 N 人，每个人的核心原话金句、痛点、工作流简述}

{示例}
- 小林（新人店员）："每天填表填到头大，同样数据写三遍"
- 老王（老店员）："AI 太慢了，还不如我自己来"
- 张店长："我要看到每天每个店的数据"

【行为数据线索】
{后台看到的使用频率、漏斗、留存数据}

【业务侧约束】
{预算谁出、谁拍板、谁用、业务红线}

要求：
1. 严格按照《用户画像 SKILL》第三章框架撰写（3.0 方法论 → 3.5 验证计划）
2. 每个 P0 角色写一张完整画像卡，7 个模块（定义/背景/任务/痛点/诉求/场景/决策路径）齐全
3. 痛点必须配用户原话金句；使用场景必须写清心情和干扰程度；决策路径必须写清弃用条件
```
