# 【PRD 产品需求文档】SKILL

> **适用产品类别**：A / B / C / D / E 全类别。PRD 是所有 AI 产品 0→1 的中枢文档——A 类对话式 Agent 用它锁角色与 Workflow，B 类 RAG 用它锁知识源与召回契约，C 类 AIGC 用它锁提示词组装与质量门禁，D 类评测平台用它锁 Golden Set 与评分公式，E 类 B 端 SaaS 用它锁功能边界与工单状态。任何一个 AI 功能模块在进入开发前，都必须有一份被评审过的 PRD。
> **文档目的**：把"用户要什么、系统做什么、AI 怎么调用、失败怎么兜底、怎么算做完"这五件事一次性钉死，让产品、算法、前端、后端、测试、业务方对着同一份文档干活，而不是对着群聊记忆干活。读者是研发、算法、测试、业务 Owner 和验收人。
> **撰写时机**：需求/立项报告已通过、用户调研已完成、功能边界已与业务方拉齐之后；进入详细设计与排期之前。MVP 阶段每个版本/每个功能模块至少一份 PRD。

---

## 一、撰写前需要收集的资料清单

### 用户侧
- 核心角色清单（至少 2 类：直接使用者 + 间接受益者/复核者）
- 每个角色的当前工作流（用户现在怎么做这件事、卡在哪、花多久）
- 用户对"好"的定义（什么结果算满意、什么算不可接受）
- 现有替代方案（人工怎么做、竞品怎么做）

### 业务侧
- 业务方给出的硬指标（节省多少工时、提升多少准确率、覆盖多少场景）
- 业务规则/SOP（评分表、审核规则、话术标准、合同条款清单）
- 业务红线（什么绝对不能 AI 做、什么必须人复核）
- 上线边界（本期做哪个班/哪个部门/哪种合同/哪种报告，不做什么）

### 技术侧
- 可用模型清单（LLM/ASR/TTS/Embedding/Rerank 各有哪些候选、单价）
- 现有系统接口（SSO、CRM、ERP、对象存储、消息通知）
- 性能约束（并发量、首字时延、单次成本预算）
- 部署约束（私有化/国产化/数据不出域）

### 数据侧
- 已有知识库/语料（多少份、什么格式、谁审核过）
- 评测集基础（是否已有 Golden Set、谁来标金标）
- 埋点现状（已埋了哪些事件、数据从哪看）
- 合规要求（录音/合同/PII 的留存期、删除方式、可见范围）

## 二、资料来源渠道

| 来源 | 拿什么 |

## 三、完整框架结构（到三级标题）

> 以下 13 章骨架融合自 5 份真实 PRD。A/B/C/D/E 各类按"差异化要点"章节裁剪；但 **第 0、1、2、5、7、9、11、12 章是任何 AI 产品都不能省的**。

### 3.0 文档信息与执行前提

- **这一节写什么**：一页纸钉死"这份 PRD 算不算数"。包括文档状态（草稿/评审稿/开发中/已冻结）、版本号、计划基线、试点规模、所有必须指定的 Owner、上游依据（立项/调研/竞品文档链接）。
- **颗粒度要求**：Owner 必须具名或明确"W1 指定"；试点规模（多少人/多少合同/多少报告）必须给数字；计划基线给起止日期；口径冲突必须显式标注"待冻结"。
- **填写要点**：
  - 写清"本期不承诺"——这是防止范围蔓延的第一道闸门。
  - 所有数字（人数、周期、准确率门槛）标注是"建议值"还是"已冻结"。
  - 列出上游文档链接，让评审人能追溯决策依据。
- **示例片段**：
  ```
  | 文档状态 | 评审稿；W1 完成范围、Owner、基线与预算冻结后转"开发中" |
  | 版本 | v1.0 MVP；影子模式，AI 结果不改变正式认证 |
  | 计划基线 | {起始日} 至 {结束日}，共 {N} 周；审批延期则整体顺延 |
  | 首期用户 | {一个自然班/一个部门/一种合同类型}，约 {15-30} 人 |
  | 必须指定的 Owner | Sponsor、业务 Owner、产品负责人、技术 Owner、AI Owner、知识/评分 Owner、安全 Owner、验收负责人 |
  | 本期不承诺 | 不承诺直接提升{开单率/成单率}；不替代人工正式{认证/审批}；不接入真实客户 |
  ```

### 3.1 产品概述（一句话 + MVP 核心假设）

- **这一节写什么**：用一句话说清"产品是什么、给谁用、解决什么、本期目标、本期不承诺"；再列 3-5 条 MVP 核心假设（哪些前提如果不成立，这个项目就该 pivot）。
- **颗粒度要求**：一句话版本必须能在电梯里讲完；核心假设要可证伪（例如"用户愿意独立完成 3 次练习"而不是"用户会喜欢 AI"）。
- **填写要点**：
  - 区分"产品结果"和"业务结果"——AI 陪练不直接等于开单率提升。
  - 核心假设是后续 Go/Pivot/Stop 决策的依据，不能写虚。
- **示例片段**：
  ```
  一句话版本：为{目标用户}提供"{核心闭环}"的最小产品，验证{核心假设1}，并{核心假设2}。

  MVP 核心假设：
  1. {目标用户}愿意在{任务场景}中独立完成不少于{N}次有效使用。
  2. 动态{商户/问题/生成}比静态题库更能暴露{核心能力}问题。
  3. 若 AI 输出能引用{原话/原文/数据出处}并给出下一步动作，用户会进行针对性复练。
  4. 将低置信度、红线、临界分和申诉转人工后，AI 可承担重复初评，人仍守住最终责任。
  ```

### 3.2 版本范围与建设顺序

- **这一节写什么**：一张"必须做 / 明确不做"对照表；一张分阶段建设顺序表（先验证什么、主要产出、不过闸怎么办）。
- **颗粒度要求**：每个"不做"都要给一句边界说明；每个阶段都要有"不过闸怎么办"的退路（降级为异步/转人工/不进入下一阶段）。
- **填写要点**：
  - 不做清单要具体到能力（"不接 CRM"、"不做排行榜"、"不做自动外呼"），不要写"后续再做"。
  - 建设顺序按"风险从高到低"排——先验证最不确定的 AI 能力，再做页面和管理后台。
  - 这是 Vibe Coding 视角的关键：给 Coding Agent 的唯一事实来源，范围外的功能一律不做。
- **示例片段**：
  ```
  | v1.0 必须完成 | v1.0 明确不做 |
  |---|---|
  | {一个目标部门}；{核心场景1}与{核心场景2} | 一次接入{相邻场景}和全部{业务线} |
  | {固定数量}个{角色/模板}：{类型A/类型B/类型C} | 开放式{剧本/模板}创作平台、复杂个性化推荐 |
  | {离线/异步链路}验证评分/审核，再建设{实时链路} | 真实{录音/通话}智能分析、自动外呼或实时辅助 |
  | 转写/解析、逐考点评分、证据定位、改进建议 | AI 自动{认证/审批}、补考、淘汰或绩效判断 |

  | 阶段 | 先验证什么 | 主要产出 | 不过闸怎么办 |
  |---|---|---|---|
  | A｜W1-W2 | 问题基线和人工标准是否可用 | 统一量表/规则、红线、边界样本、Owner、评测集 | 规则不统一则停止评分/审核开发 |
  | B｜W3-W5 | 异步链路能否成立 | 异步 MVP、报告、复核队列、离线评测报告 | 保留人工工具或重做规则，不进入实时链路 |
  | C｜W6-W8 | 实时链路的真实性/延迟/稳定性 | 实时{对话/生成}、任务、复练、权限、日志 | 降级为异步，不拖延整个项目 |
  | D｜W9-W10 | 真实用户是否使用、是否节省人工 | 影子试点、评测报告、Go/Continue/Pivot/Stop 决策 | 不扩范围，留下停止或转向记录 |
  ```

### 3.3 用户角色与权限

- **这一节写什么**：每个角色"可使用什么功能、数据范围是什么、禁止事项是什么"；并给出权限原则。
- **颗粒度要求**：至少 4-6 类角色（直接用户、复核员/主管、内容 Owner、运营、系统管理员）；每类角色的"数据范围"要写到"只能看本人/只能看本班/不能跨组织"。
- **填写要点**：
  - **权限必须在数据查询和 RAG 检索前生效，不能只在前端隐藏按钮**——这是 AI 产品权限的生死线。
  - 区分"系统能力角色"（如 Agent）和"登录用户角色"——Agent 不是登录角色。
  - 显式列出"禁止把未复核 AI 结果回写正式系统"。
- **示例片段**：
  ```
  | 角色 | 可使用功能 | 数据范围 | 禁止事项 |
  |---|---|---|---|
  | {直接用户} | 查看任务、开始{对练/审核/生成}、查看报告、申请复核 | 仅本人任务、音频/转写、评分/审核结果 | 查看他人记录；修改场景/知识/规则 |
  | {培训师/复核员} | 下发任务、查看负责班组完成情况、抽检和改判 | 仅被分配班组；不能跨组织查看原始材料 | 直接改动已发布知识；删除原始 AI 结果 |
  | {主管/认证官} | 处理红线、临界分、复核争议与最终决策 | 本团队及待复核记录 | 把未复核 AI 分数直接当正式结果 |
  | {知识/规则 Owner} | 维护场景/知识/量表/红线/正反例，提交审批 | 所负责业务线的配置与评测集 | 越权发布其他业务线内容；无回归评测直接上线 |
  | {系统管理员} | 身份、权限、模型接口、日志、存储与告警 | 系统运维数据；业务内容默认不可见 | 越权查看或修改业务报告 |

  权限原则：权限在数据查询与 RAG 检索前生效；所有管理操作留审计日志；录音/合同/PII 按敏感数据处理。
  ```

### 3.4 核心业务场景与原始用户流程图

- **这一节写什么**：把每个关键角色的"触发→任务→当前问题→v1.0 目标结果"列成表；并画出**改造前**的原始用户流程（mermaid flowchart）。
- **颗粒度要求**：每个场景一行，触发条件写清；原始流程图必须画出"排队/等待/人工听/人工查"这些浪费环节——这是 ROI 的来源。
- **填写要点**：
  - 原始流程要诚实（人工怎么做就怎么画，不要美化）。
  - 目标结果要可度量（"5 分钟内得到反馈"而不是"更快得到反馈"）。
- **示例片段**：
  ```
  | 角色与触发 | 要完成的任务 | 当前问题 | v1.0 目标结果 |
  |---|---|---|---|
  | {新人}｜收到培训任务 | 反复练{核心动作} | 需要等{师傅/培训师}有空；静态题难暴露连续追问问题 | 随时开始{动态练习}，5 分钟内得到具体反馈 |
  | {新人}｜收到低分反馈 | 知道哪句话有问题，针对薄弱项重练 | 只有总分不知道怎么改；重练仍需约人 | 点击薄弱项进入专项场景，保留前后可比记录 |
  | {培训师}｜管理一个班 | 安排任务、掌握完成情况、发现需辅导的人 | 逐人陪练/听音/搬结果随人数线性增加 | 只处理未完成、低置信度、红线和共性薄弱项 |

  原始流程（mermaid）：
  flowchart LR
    A["完成课程"] --> B["找师傅/培训师"] --> C["排队等待"] --> D["人工 1V1"]
    D --> E["人工听录音/逐项检查"] --> F["延迟反馈"] --> G["再次排队"]
  ```

### 3.5 核心流程与交互（含正常/异常/人工兜底）

- **这一节写什么**：画出 v1.0 改造后的主流程图（含分支判断）；再用一张表把"正常流程 / 语音或转写异常 / 评分或审核异常 / 安全异常"的系统行为和结束状态写清。
- **颗粒度要求**：主流程必须画出"是否低置信度/红线/临界分/申诉"的分支；异常分支必须写"系统行为 + 用户看到什么 + 结束状态"三件事。
- **填写要点**：
  - **没有兜底的 AI 产品不能上线**——这是合同审核 PRD 的原话。
  - 异常不是失败，是被设计过的路径；每条异常都要有明确结束状态，不要只写"报错"。
  - 用 mermaid sequenceDiagram 画系统时序（用户→编排器→Agent→规则引擎→人工复核）。
- **示例片段**：
  ```
  flowchart TD
    A["培训师发布任务"] --> B["用户登录+设备/权限检测"]
    B --> C["开始{对练/上传/生成}"]
    C --> D["转写/解析/会话记录"]
    D --> E["逐考点评分/逐项审查"]
    E --> F{"是否低置信/红线/临界分/申诉"}
    F -->|否| G["展示反馈并针对性复练"]
    F -->|是| H["进入人工复核队列"]
    H --> I["确认或改判并记录原因"]
    I --> G

  | 流程 | 系统行为 | 结束状态 |
  |---|---|---|
  | 正常流程 | 任务→检测→{对练/生成}→转写/解析→评分/审查→反馈→复练 | 完成任务并保存可追溯记录 |
  | {语音/文件}异常 | 要求重说/重传；连续失败则保存已完成轮次并切异步 | 标记"无效/已降级"，不进入效果样本 |
  | 评分/审查异常 | 证据不足、规则冲突或低置信时不输出确定结论 | 显示"待复核"，进入人工队列 |
  | 安全异常 | 发现越权/敏感信息/P0 红线时中止输出并告警 | 冻结记录；安全/业务 Owner 处理 |
  ```

### 3.6 产品功能需求（F01-Fn，交互级颗粒度）

- **这一节写什么**：这是 PRD 最厚的一章。每个 P0 功能一行七列：**ID/优先级、功能、使用前提、用户操作与系统响应、业务规则、异常与兜底、验收标准**。
- **颗粒度要求**：写到"用户点什么按钮→系统调什么服务→失败时看到什么提示"的交互节点级。**不能只写"用户可以对话"**。每个功能必须有可量化的验收标准（成功率≥95%、P95≤2秒、绑定率100%）。
- **填写要点**：
  - 功能编号 F01/F02...；优先级 P0/P1/P2；本期只做 P0。
  - "使用前提"写清什么条件下这个功能才能用（任务已发布、量表已冻结、麦克风已授权）。
  - "用户操作与系统响应"要分步骤写，不要一句话糊过去。
  - "业务规则"写版本绑定、状态锁定、权限约束。
  - "异常与兜底"写失败路径，不要只写 Happy Path。
  - "验收标准"必须可测，数字来自技术评审冻结值。
- **示例片段**：
  ```
  | ID/优先级 | 功能 | 使用前提 | 用户操作与系统响应 | 业务规则 | 异常与兜底 | 验收标准 |
  |---|---|---|---|---|---|---|
  | F01<br/>P0 | 登录、身份与告知 | 用户在试点名单内；已配置组织和角色 | 用户通过 SSO 进入；首次使用确认录音/材料用途、可见范围和删除方式；系统加载最小权限 | 未同意不得创建{语音/上传}会话；权限同时约束页面、接口、数据和检索 | SSO 失败/字段缺失/撤回同意时禁止使用，提示联系运营并记审计日志 | 白名单登录成功率≥99%；全部越权测试被拦截；每条{录音/合同}有告知版本与确认时间 |
  | F03<br/>P0 | {场景选择/设备检测} | 用户有有效任务；浏览器已授权麦克风 | 用户查看目标与时长，选择已分配的{商户/模板}；系统检测麦克风/网络/音量并创建 session_id | 首期只开放{固定画像}；不展示隐藏规则、通关条件和评分答案 | 设备不通过可重试；文字仅作故障兜底且不计入效果样本 | 已发布场景启动成功率≥95%；每次使用可追溯到场景、知识、规则、Prompt 和模型版本 |
  | F06<br/>P0 | 证据化报告 | 会话有效结束；规则和知识版本可用 | 系统展示分项表现、做得好的地方、问题、改进动作、{用户原话/原文位置}与时间戳，并标注置信度 | 最终量表 W2 冻结；无原话/原文证据不得给确定结论；总分/门槛/红线由规则引擎计算 | 证据不足/规则冲突/临界分或低置信显示"待复核"；转写不完整时报告标记无效 | 100% 确定反馈绑定证据；证据正确率≥95%；有效报告 P90≤5 分钟 |
  ```

### 3.7 AI 能力需求（Agent 架构 / Workflow / Prompt / RAG / 评测门槛）

> 这一章是 AI PRD 区别于传统 PRD 的核心。A/B/C/D 类必须写全；E 类若 AI 只是嵌入小功能可裁剪，但 Agent 六要素和兜底不能省。

#### 3.7.1 架构选型与系统边界

- **这一节写什么**：明确"单 Agent / 固定多 Agent / Workflow 编排 + Agent 混合"哪种方案，以及为什么。画系统架构图。
- **颗粒度要求**：每个组件的职责写清（会话编排器、Agent、RAG、规则引擎、证据校验、人工复核队列）；明确"哪些是确定性代码做、哪些是 LLM 做"。
- **填写要点**：
  - **LLM 不应该算数、不应该自己算总分、不应该自己决定通过/不通过**——分数、门槛、红线、权重由确定性规则引擎算。
  - 角色扮演和评分/审查必须分离——同一个模型不能既"演"又"判"，会穿帮。
  - 审核类产品公式：**可信度 = 准确率 × 可解释性 × 人类可控性**。
- **示例片段**：
  ```
  架构结论：v1.0 采用"固定编排的{N} Agent ＋ 确定性规则引擎"。
  {角色 Agent} 只负责{对练/生成}；{评分/审查 Agent} 只负责会后评价；
  会话状态、权限、版本、总分、门槛、红线和人工复核触发均由普通服务控制。

  | 组件 | 必须承担的职责 |
  |---|---|
  | 会话编排器/状态机 | 创建 session/turn，锁定版本快照，驱动固定调用顺序，管理阶段、轮次、超时、重试、打断和结束；本身不是 Agent |
  | {角色} Agent | 根据{人设/任务状态/用户最新表达}生成{回应/内容}；不教学、不评分、不读通过线 |
  | {评分/审查} Agent | 会话结束后读取完整{转写/合同}，逐考点做判断、定位证据、生成建议；不计算正式总分 |
  | 知识/RAG 与证据校验 | 按权限和版本检索已审批内容；校验证据、turn_id、时间戳、规则引用是否相互支持 |
  | 确定性规则引擎 | 执行分值映射、权重、舍入、总分、门槛、红线、复核触发；规则缺失时禁止用默认值 |
  ```

#### 3.7.2 Agent 六要素（Role / Inputs / Action Path / Tool Rules / Output / Constraints）

- **这一节写什么**：每个 Agent 按六要素写清楚。这是可研 PRD V2.0 和合同审核 PRD 沉淀下来的标准结构。
- **颗粒度要求**：六要素每个都要写实，不能只写"你是一个专业助手"。Output 必须给 JSON Schema 示例；Constraints 必须列红线。
- **填写要点**：
  - **Role**：身份 + 经验年限 + 必须基于什么工作 + 严禁什么。
  - **Inputs**：列具体字段（会话快照、规则版本、检索结果、全局事实）。
  - **Action Path**：分步骤 1/2/3，每步调什么工具、做什么判断。
  - **Tool Rules**：每个工具的名字、入参、调用时机、禁止越权。
  - **Output**：JSON Schema 示例，字段一一对应业务方要看的东西。
  - **Constraints**：这是区分初级和资深 PM 的章节——禁止编造、禁止超范围、证据不足时怎么处理。
- **示例片段**（角色 Agent）：
  ```
  ## {角色} Agent

  | 目标 | 像当前{商户/模板}一样回应；过程中不扮演老师/审查员 |
  |---|---|
  | 输入 | session/turn 标识、场景快照、{人设/任务}、允许事实、禁止承诺、会话阶段、已触发异议、最近轮次、用户最新表达与 ASR 置信度、经权限过滤的检索片段 |
  | 工具 | 只读 get_scene_snapshot、retrieve_approved_facts；生产环境由编排器预取后传入，Agent 不自主调用外部系统，更无写权限 |
  | 不可见数据 | 评分维度、权重、通过线、标准答案、学员历史成绩、正式认证结果、其他用户数据 |
  | 失败处理 | ASR 低置信先要求重说；检索为空时不得补写事实；模型超时或 Schema 非法重试 1 次；仍失败使用经审批的中性回复或转异步 |

  Output JSON：
  {
    "schema_version": "1.0", "trace_id": "...", "session_id": "...", "turn_id": "...",
    "reply_text": "...",
    "response_action": "QUESTION|OBJECT|CLARIFY|ACCEPT_PARTIALLY|REJECT",
    "stage_after": "...", "objection_id": null, "suggest_end": false,
    "risk_flags": [], "confidence": 0.0, "source_ids": []
  }
  ```
- **示例片段**（评分/审查 Agent）：
  ```
  | 目标 | 基于完整{转写/合同}逐考点抽取行为、定位用户原话/原文、引用规则并给出建议；只评价用户表达 |
  |---|---|
  | 输入 | 冻结后的完整 transcript（speaker、turn_id、时间戳、ASR 置信度）、场景快照、规则快照、红线规则、经审批知识与正反例 |
  | 工具 | 只读 retrieve_rubric_context、retrieve_approved_knowledge；不得写报告、改分或改任务状态 |
  | 不可见数据 | 角色 Agent 隐藏提示、正式通过线、人员处置规则、其他用户数据 |
  | 判断规则 | 无证据不得给确定结论；未获得展示机会记 not_observed，转写无效记 invalid_input，不得按 0 分；只引用用户原话/原文，不加工 |
  | 失败处理 | 规则缺失/冲突、完整输入不可用、证据无法匹配、低置信时输出 UNSCORABLE/PENDING_REVIEW |

  Output JSON：
  {
    "schema_version": "1.0", "session_id": "...", "rubric_version": "...",
    "status": "SCORED|UNSCORABLE|PENDING_REVIEW",
    "checkpoint_results": [{
      "criterion_id": "...",
      "observation_status": "observed|not_observed|invalid_input",
      "proposed_level": "NOT_MENTIONED|PARTIAL|SUPPORTED|COMPLETE|EXCEPTIONAL",
      "evidence": [{"turn_id": "...", "start_ms": 0, "end_ms": 0, "exact_quote": "..."}],
      "rule_refs": [{"source_id": "...", "version": "...", "section": "..."}],
      "feedback": "...", "confidence": 0.0, "reason_codes": []
    }],
    "risk_flags": []
  }
  ```

#### 3.7.3 知识库 / RAG 设计

- **这一节写什么**：列出有哪几个逻辑库、每个库存什么、怎么检索、怎么隔离、怎么发布回滚。
- **颗粒度要求**：每个库必须写清"谁能读、谁不能读"；召回流程要写到"先过滤权限→BM25+向量→Rerank→阈值"；版本状态机要写全（draft/in_review/approved/shadow/retired）。
- **填写要点**：
  - **规则库 vs 知识库要分开**：规则库定义"查什么/怎么判"，知识库提供"依据/事实"。
  - 场景、规则、Prompt、量表必须按 ID/版本**精确读取**，不能靠向量相似度选。
  - 数据回流（用户改判、纠错）**禁止自动回写生产 RAG**，必须走脱敏→标注→审批→回归评测→新版本流程。
- **示例片段**：
  ```
  | 逻辑库 | 内容 | 存储/检索 | 调用与隔离 |
  |---|---|---|---|
  | SCENE_CATALOG 场景与角色库 | 人设、事实、状态机、触发/结束条件、禁止泄露内容 | 版本化 JSON，按 scene_id 精确读取 | 编排器、角色 Agent；不得含规则、通过线、标准答案 |
  | KB_PRODUCT_COMPLIANCE 事实与合规库 | 产品能力、价格/折扣边界、可表达事实、禁止承诺 | 文档库+元数据+BM25/向量混合索引 | 两个 Agent 按权限只读；禁止用模型常识补写公司事实 |
  | RUBRIC_REGISTRY 规则与红线库 | 维度、观察点、正反例、分值映射、权重、门槛、红线 | 版本化结构化规则，按 rubric_id 精确读取 | 评分/审查 Agent、规则引擎、复核台；角色 Agent 不可见 |
  | EVAL_DATASET 离线评测集 | 人工标注对话、金标证据、边界/无答案/红线/注入样本 | 独立数据集仓库，不建生产索引 | 只供离线评测；两个生产 Agent 均不可访问 |

  召回流程：原始查询 → 查询改写 → pgvector 语义 Top12 → 全文检索 Top12 → RRF 合并去重
            → scope/状态/有效期/权限/任务标签过滤 → 返回 Top 3-5 → 低于阈值返回 no_match
  ```

#### 3.7.4 AI 评测门槛与发布门禁

- **这一节写什么**：上线前必须达到的硬指标表。包括 AI-人工一致率、证据引用正确率、角色遵循率、红线召回率、幻觉率、首字时延、结构化输出合法率。
- **颗粒度要求**：每个指标给"v1.0 门槛 + 口径"；评测集规模给数字（至少 20 段多轮对话、100 个检查点、30 个红线/注入样本）；每题跑三次全过才算过。
- **填写要点**：
  - **严重幻觉/违规指导/权限泄露 = 0 容忍**，任一发生即失败。
  - 指标口径必须写清（只统计双方均 observed 的维度、排除 not_observed 和中断会话）。
  - 模型/Prompt/知识任一改动，评测集全部重跑。
- **示例片段**：
  ```
  | 指标 | v1.0 门槛 | 口径 |
  |---|---|---|
  | AI-人工分项判断一致率 | ≥85% | 与双人共识比较；只统计双方均 observed 的维度 |
  | 反馈证据引用正确率 | ≥95% | 引用确为用户原话/原文，位置有效，能支持结论 |
  | 角色遵循率 | ≥90% | 不跳出角色、不泄露答案、不无条件配合、不虚构事实 |
  | 红线召回率 | 整体≥95%；P0 漏报 0 | 在冻结红线与对抗样本上逐条计算 |
  | 依据不足识别召回率 | ≥90% | 覆盖无答案、规则冲突、输入无效、证据不足样本 |
  | 生产知识 Recall@5 | ≥90% | 黄金问题集命中可支持答案的有效知识，权限过滤后计算 |
  | 结构化输出合法率 | ≥99.5% | 含一次修复重试后的 Schema 合法响应 |
  | 严重幻觉/违规/权限泄露 | 0 | 任一发生即失败 |
  | 首字响应时间 | P95≤2 秒 | 用户结束发言到系统开始播放有效回复 |
  ```

### 3.8 数据与系统对接

- **这一节写什么**：外部系统对接清单（SSO、组织、知识、ASR/TTS/模型网关、对象存储、宿主业务系统、正式认证/HR 系统的读写边界）；核心数据对象字段。
- **颗粒度要求**：每个对接系统写"读写方式与频率、关键字段、失败处理"；显式列出"v1.0 禁止读写"的系统（正式认证、HR、真实通话）。
- **填写要点**：
  - 禁止把 AI 影子结果回写正式系统——这是边界。
  - 核心数据对象（User/Task/Session/Score/Review）字段要列到能建表。
- **示例片段**：
  ```
  | 系统/数据 | 读写方式与频率 | 关键字段 | 失败处理 |
  |---|---|---|---|
  | SSO/组织身份 | 登录时实时读取 | user_id、org_id、role、status | 读取失败禁止登录；不允许默认高权限 |
  | 试点名单 | MVP 受控导入；每日校验 | cohort_id、user_id、阶段、负责培训师 | 导入校验失败逐行返回；未匹配用户不创建任务 |
  | ASR/TTS/模型网关 | 会话中实时；评分异步 | model_id、prompt_version、transcript、confidence、latency、cost | 超时重试一次；仍失败转异步/人工，记录供应商错误 |
  | 正式认证/HR/真实通话 | v1.0 禁止读写 | 无 | 任何误调用视为 P0 事故并停止试点 |
  ```

### 3.9 数据埋点需求

- **这一节写什么**：用户行为漏斗埋点表——创建→生成/对练→交互修改→产出/导出→反馈。
- **颗粒度要求**：每个事件给"事件名、触发时机、补充字段"；所有事件统一携带 user_id、session_id、release_id、event_time、status。
- **填写要点**：
  - 失败事件必须带 error_stage、error_code、retry_result。
  - 漏斗关键节点（创建→首次生成→导出→复练）一个不能少。
- **示例片段**：
  ```
  所有事件统一携带 user_id、{task_id}、scene_id、session_id、event_time、status；失败事件增加 error_stage、error_code、retry_result。

  | 事件 | 触发时机 | 补充字段 |
  |---|---|---|
  | task_list_view | 进入任务列表 | task_type、task_count |
  | practice_start_click | 点击开始 | mic_auth_result |
  | practice_started | 成功创建会话并开始采音/上传 | scene_version、release_id |
  | practice_ended | 主动结束或异常中断 | duration、turn_count、end_type |
  | record_saved | 记录保存完成 | audio_status、transcript_status |
  | score_finished | 评分成功或失败 | score_status、rubric_version |
  | practice_error | 语音/模型/保存/评分异常 | error_stage、error_code、retry_result |
  | export_success | 导出报告/合同 | export_format、time_from_creation |
  | feedback_submit | 用户点赞/点踩/采纳/忽略 | target_content、feedback_score、reason |
  ```

### 3.10 非功能需求与整体成功指标

- **这一节写什么**：性能、稳定性、安全、隐私、数据生命周期、兼容性、可观测性、可替换性；以及 W10 整体成功指标（业务/产品/AI/运营/安全）。
- **颗粒度要求**：性能指标给 P95/P90 数字；可用性给百分比；成功指标分四层（北极星/商业/业务/技术），不要一上来就说准确率。
- **填写要点**：
  - 北极星指标衡量"用户价值"（采纳率、愿不愿意用），不是模型准确率。
  - 收入/开单率这类业务结果只做长期观察，不作为本期硬验收。
  - 模型、ASR/TTS、知识版本必须通过接口配置，不写死在业务流程里。
- **示例片段**：
  ```
  | 类别 | v1.0 要求 |
  |---|---|
  | 性能 | 页面加载 P95≤3 秒；首音 P95≤2 秒；有效报告 P90≤5 分钟 |
  | 稳定性 | 试点时段可用性≥99.5%；至少{N}路并发压测；中断最多丢失当前未完成轮次 |
  | 安全 | SSO、RBAC、传输/存储加密、检索前权限过滤、导出控制、管理操作审计；越权泄露为 0 |
  | 隐私 | 明示录音/材料用途、可见范围、留存期与删除方式；未经审批不得用真实数据训练 |
  | 可替换性 | 模型、ASR/TTS、知识版本通过接口配置，不写死 |

  成功指标四层：
  - 北极星：采纳率 = 用户未做实质性修改即导出的报告数/总导出数 ≥ {52%}
  - 商业：{业务线}营收同比提升≥{15%}
  - 业务：单份{报告/合同}初稿完成工时≤{2.0}天
  - 技术：随机抽检{20%}，事实性错误率≤{18%}
  ```

### 3.11 项目计划、责任分工与验收时间

- **这一节写什么**：分阶段排期表（W1-Wn）、每阶段完成产出与验收闸门（G0/G1/G2...）、责任分工 RACI。
- **颗粒度要求**：每个闸门（Gate）给"不过则不进入下一阶段"的明确条件；RACI 表每个事项写清最终负责 A、执行 R、会签 C。
- **填写要点**：
  - 排期按"先验证风险最高的 AI 能力"排，不是按"先做页面"排。
  - 闸门 G1（规则冻结）、G2（离线评测过闸）、G3（安全评审）、G4（Go/Continue/Pivot/Stop）必须显式。
- **示例片段**：
  ```
  | 阶段 | 主要责任 | 完成产出 | 验收时间与条件 |
  |---|---|---|---|
  | W1 | 项目负责人+各 Owner | 范围、试点名单、人工基线、接口、数据分级、Owner、预算 | G0：Owner、基线、预算、停止条件未确认则不开发 |
  | W2 | 知识/规则 Owner+双业务评委+AI 评测 | 唯一规则、通过线、红线、边界样本、评测集 | G1：核心规则无冲突，样本完成双人标注 |
  | W3-W4 | 产品+前后端+AI+QA | F01-F04、F06、F08、F10 异步闭环 | 内部验收：主流程、无答案、冲突、越权、人工复核可跑通 |
  | W5 | AI 评测+双业务评委 | 离线评测报告、是否进入实时链路决定 | G2：一致率、证据、红线、严重幻觉达到试点线 |
  | W6-W7 | 前后端+AI/语音+产品 | F05、F07、F09 实时链路 | 联调验收：正常、降级、中断恢复、并发压测通过 |
  | W8 | QA+安全/法务+业务验收 | 端到端测试、安全评审、告知与删除方案 | G3：无 P0 问题、复核人员到位，才可进入真实用户 |
  | W9 | 业务运营+产品 | 影子试点、问卷/访谈、使用与人工投入数据 | 试点收口：指标分母完整，异常与申诉全部闭环 |
  | W10 | Sponsor+各 Owner | 业务/产品/AI/安全验收报告与版本决策 | G4：Go / Continue / Pivot / Stop |
  ```

### 3.12 验收、上线与停止记录（Go/Continue/Pivot/Stop）

- **这一节写什么**：明确四种决策的触发条件，以及"完成的定义"。
- **颗粒度要求**：每种决策给触发条件；v1.0 完成的定义必须具体到"一个真实用户在影子模式下跑完了任务→对练/生成→反馈→复练→人工复核，并形成可审计记录"，不是"页面开发完成"。
- **填写要点**：
  - Stop 条件要写早（采用率持续低、评分明显低于人工、规则无法统一、两轮迭代无价值信号、不可接受安全风险）。
  - W10 必须新增《评测报告》和《上线或停止记录》文档，不能只在群聊口头决定。
- **示例片段**：
  ```
  | 决定 | 触发条件 |
  |---|---|
  | 允许试点 | 核心流程、权限、安全、降级方案通过；AI 达到 W5 试点线；人工复核人员到位 |
  | Go | 业务/产品/AI/运营/安全硬门槛均达成且无 P0 事件；可扩量 |
  | Continue | 用户价值和人工节省成立，但一项非安全指标轻微未达；限定 2-4 周修复后复评 |
  | Pivot | 问题成立、用户愿意用，但实时链路或自动评分不可控；转为异步/证据回放/人工辅助 |
  | Stop | 采用率持续低、评分明显低于人工基线、核心规则无法统一、两轮迭代无价值信号，或不可接受安全风险 |

  v1.0 完成的定义：不是"页面开发完成"，而是一个真实用户在影子模式下完成任务、{对练/生成}、反馈、复练和人工复核，且在截止日前形成可审计的验收与版本决策记录。
  ```

### 3.13 依赖与待确认项

- **这一节写什么**：所有"还没定但不定就没法开发"的事项，以及未确认的影响和最晚确认时间。
- **颗粒度要求**：每条写清"待确认 / 未确认的影响 / 最晚时间"。
- **填写要点**：
  - 评分口径冲突、模型供应商、录音留存期、入口集成这些高频坑必须列。
- **示例片段**：
  ```
  | 待确认 | 未确认的影响 | 最晚时间 |
  |---|---|---|
  | Sponsor、各 Owner 姓名 | 无法决策、审批和验收 | W1 结束前 |
  | 准确试点名单、日程、人工基线 | 无法计算等待、工时和完成率 | W1 结束前 |
  | 唯一评分/审核规则、通过线、红线、抽检比例 | 无法开发或评测自动评分 | W2 结束前 |
  | 模型/ASR/TTS 供应商、部署、并发、SLA、单价、预算 | 影响成本、延迟、安全和实时链路 | W1 方案；W5 放量 |
  | 录音/材料告知、留存期、删除 SLA、可见范围 | 无法通过安全验收 | W2 方案；W8 验收 |
  ```

## 四、不同产品类别的差异化要点

### A 类（对话式 AI / Agent 产品）
- **3.7 章是核心**：必须写清双 Agent（角色扮演 + 评分/决策）分离、状态机、打断规则、角色 Agent 不可见数据清单。
- **3.7.2 六要素**：角色 Prompt 必须给完整模板（含触发规则和边界规则），不能只写"扮演一个{类型}客户"。
- **3.7.4 评测**：红线召回率、角色遵循率、Prompt 注入抗性三项必须硬门槛。
- **兜底**：ASR 低置信、用户打断、网络中断、角色跳出、Prompt 注入都要有路径。

### B 类（RAG 知识库 / 问答产品）
- **3.7.3 RAG 章加厚**：知识源准入、清洗切片、召回重排、引用溯源、更新回滚、日志闭环七件套。
- **3.7.2 Agent**：必须写"无结果时返回 no_match，不得用模型常识补写"；输出必须带 source_id 和原文位置。
- **验收**：Recall@5、引用正确率、依据不足识别率是硬指标；不能用未审批资料。
- **边界**：检索前必须做权限过滤；不同业务线/不同 org 的知识物理或逻辑隔离。

### C 类（AIGC 多模态生成产品）
- **3.7.2**：提示词组装模板（Role + Global Context + Current Task + Constraints），多模型 fallback 策略。
- **3.7.3**：Truth Base 概念——全局事实数据（投资总额、技术参数）必须锁死，生成时一字不改。
- **3.10**：采纳率是北极星；事实性错误率是技术硬指标；单次生成成本要算。
- **兜底**：RAG 召回低于阈值时降级到关键词搜索或明确提示"未找到匹配文档"，不要硬生成。

### D 类（AI 评测平台 / 内部工具）
- **3.7.4 是核心**：评测集规模、标注流程、双盲评分、GSB 判定、bad case 五段式归因（现象→轨迹→归因→修复→复测）。
- **3.6 功能**：必须有评测任务管理、评分界面、bad case 闭环、版本对比功能。
- **3.7.3**：评测集与生产 RAG 物理隔离，评测数据不进入生产索引。
- **非功能**：可按模型/Prompt/知识版本切片看指标波动。

### E 类（B 端 SaaS / 传统产品 AI 化）
- **3.2 范围**：必须显式列"不接 CRM、不做自动外呼、不回写正式审批系统"——B 端项目范围蔓延是头号风险。
- **3.3 权限**：SSO/RBAC/数据可见范围必须写清；B 端客户对越权泄露零容忍。
- **3.6 功能**：交互级颗粒度最重要——B 端用户是来干活的，不能容忍"点了没反应"。
- **3.11 排期**：B 端大项目周期 6 个月-1 年，单次迭代 1 个月；试点客户验收标准要书面化。
- **审核类特有**：规则可配置（法务/业务能自助加条款）、风险必须附法规依据、Human-in-the-Loop 采纳/忽略反馈回流。

## 五、完成度 Checklist

- [ ] 文档信息页已写清版本状态、Owner、试点规模、计划基线、本期不承诺
- [ ] 一句话版本 + 3-5 条可证伪的 MVP 核心假设
- [ ] "必须做 / 明确不做"对照表，且不做项给了边界说明
- [ ] 4-6 类角色的权限矩阵，含"禁止事项"和权限原则（检索前生效）
- [ ] 原始用户流程图（改造前）和 v1.0 主流程图（含分支）
- [ ] 每个 P0 功能写到了七列交互级颗粒度（ID/前提/操作响应/业务规则/异常兜底/验收标准）
- [ ] AI 架构选型结论明确，组件职责写清，LLM 不做分数计算
- [ ] 每个 Agent 按六要素（Role/Inputs/Action Path/Tool Rules/Output/Constraints）写全，Output 给 JSON Schema
- [ ] RAG 库设计含 scope 隔离、版本状态机、数据回流不自动回写生产
- [ ] AI 评测门槛表含一致率/证据率/红线召回率/幻觉率/时延，且每题跑三次全过
- [ ] 埋点事件表覆盖创建→生成→交互→产出→反馈漏斗，统一携带版本号
- [ ] 非功能需求含性能数字、安全、隐私、可替换性
- [ ] 成功指标分四层（北极星/商业/业务/技术），不只讲准确率
- [ ] 排期含 G0-G4 闸门，RACI 责任分工明确
- [ ] Go/Continue/Pivot/Stop 四种决策触发条件写清，v1.0 完成的定义具体
- [ ] 依赖与待确认项清单含最晚确认时间
- [ ] 兜底策略覆盖：ASR/转写/解析失败、RAG 空结果/冲突、模型超时、Schema 非法、Prompt 注入、越权、录音/材料保存失败、评分失败

```
你是一名资深 AI 产品经理。请根据以下项目信息，撰写一份完整的 PRD（产品需求文档）。

【项目背景】

【目标用户】
{核心用户角色、间接受益者/复核者、他们现在怎么干、卡在哪}

【核心功能】
{本期要做的 3-8 个 P0 功能一句话描述、本期明确不做什么}

【产品类别】
{A=对话式 Agent / B=RAG 问答 / C=AIGC 生成 / D=评测平台 / E=B 端 SaaS，可多选}

【技术约束】
{可用模型、部署方式、并发量、成本预算、数据合规要求}

【业务规则/SOP】
{评分表、审核规则、话术标准、红线、已有的业务知识}

【已有资料】
{知识库/语料规模、是否已有评测集、上游系统接口清单}

要求：
1. 严格按照《PRD SKILL》第三章 13 章框架撰写（0 文档信息 → 13 依赖待确认）

6. 去具体化：不要使用任何真实产品名、公司名、行业名，全部用 {占位符}（如 {产品名}、{目标行业}、{关键指标}）
7. 示例片段用 mermaid 流程图和表格，不要写大段散文
8. 最后输出一份完成度 Checklist 供自查
```
